**Why trailing-slash stripping is isolated:** I initially added it directly to `normalizeCrawlUrl`. Running the existing test suite immediately surfaced that this function's return value is also fed straight into `crawler.run(…)` (`:129`, `:170`) and into `enqueueLinks` via `normalizeDiscoveredUrl` (`:585`) — i.e. it's the literal URL Crawlee requests over the wire, not just an identity string. Several tests failed with documents whose content was literally `"Not found"`, because the test server (like many real servers — static hosts, S3, Next.js, etc.) serves different content for `/docs` than `/docs/`. Stripping the slash before the fetch silently requested the wrong resource. I moved trailing-slash removal into a separate `stripTrailingSlash` step applied only where a URL is fixed as a document's *identity* (`sourceUrl`/`id`/`metadata.url`), never before a request is made. The code comment at `:624-628` records this constraint so it isn't "simplified" back in later.

### Residual risk

**Duplicate documents on next sync, not lost documents.** `buildDocument` hashes the canonical URL into `ConnectorDocument.id`, which `connector-sync.ts` uses as `sourceId` to find-or-create a `kb_document` row (`connector-sync.ts:419-422`). For a page whose canonical form changes under the new rules (had a trailing slash, tracking params, or mixed-case host), the next sync computes a new hash, so `findBySourceId` misses and a **new** `kb_document` is created (`connector-sync.ts:502-512`) alongside the old one — nowhere in that file prunes documents by a missing `sourceId` (confirmed via repo-wide grep for stale/prune/delete-by-sourceId logic), so the old row is never deleted or corrupted. It stays fully indexed and servable exactly as before; it just stops receiving updates and a sibling document now covers the same page. This satisfies "must continue to be served correctly" literally, but means already-crawled sites will see a one-time bump in duplicate documents on their next sync — a natural follow-up would be a backfill/merge migration, which is out of scope here (implementation-only, single file).
