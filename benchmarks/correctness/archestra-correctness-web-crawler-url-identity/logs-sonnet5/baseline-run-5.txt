## Summary

**File changed:** `platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts` (only file touched, as instructed).

**What changed**, both inside `normalizeCrawlUrl` (web-crawler-connector.ts:609-621):
- **Host lowercasing** (line 612): explicit `url.hostname.toLowerCase()`.
- **Tracking-param stripping** (line 619, helper at 623-636): deletes `utm_source/medium/campaign/term/content`, `gclid`, `fbclid` via a new `TRACKING_QUERY_PARAMS` set (line 52-60). Guarded by a presence check first — `URLSearchParams` mutation re-serializes the *entire* query string (verified: `[expr]`→`[expr]`, and a valueless `[expr]` gains a spurious `[expr]`), so touching it unconditionally would silently perturb the canonical URL, and thus the `id`, of every already-indexed page that has *any* query string, not just tracking ones. The guard makes this a no-op for URLs with no tracking params — i.e. it doesn't fire on the vast majority of already-indexed documents.
- **Default-port stripping**: kept verbatim.

**What I deliberately left out: trailing-slash removal.** I initially implemented it and traced its actual effect through the file rather than assume it was safe, which surfaced three concrete, independent breakages:
1. `normalizeCrawlUrl`'s output is the literal fetch/enqueue target (web-crawler-connector.ts:132,173, and the `enqueueLinks` call at :427) — unlike host case or the query string, trailing-slash presence isn't universally content-neutral across real servers, so rewriting it risks requesting a different resource than the one actually indexed.
2. `buildAllowedPathPrefixes` (web-crawler-connector.ts:472-483) uses trailing-slash presence on the normalized start URL to decide whether the default crawl scope is "this directory" or "this file's parent directory" (line 481). Stripping the slash first collapses a `/docs/`-scoped crawl to prefix `[expr]` — the entire origin — a silent scope-widening regression, independent of any test.
3. `web-crawler-connector.test.ts` pins the opposite behavior: a page reached at `/docs/` keeps `[expr]` (lines 163-166), and a page with an explicit `[expr]` tag keeps that trailing slash verbatim in both `sourceUrl` and the `id` hash (lines 178-180) — i.e. even the site's own stated canonical form isn't second-guessed. Since I was told not to modify tests, and every trailing-slash fixture in the suite pins "preserved," there was no code path left where stripping it wouldn't either break these assertions or hit #1/#2.

Given `[expr]` is the durable upsert key (`connector-sync.ts:419`, `findBySourceId`), a naive full implementation would have shifted identity for a large share of already-indexed pages — precisely what the task said must not happen. Scoping tracking-param stripping to only fire when present, and skipping trailing-slash rewriting entirely, keeps `id`/`sourceUrl` byte-identical for any already-indexed page that doesn't literally contain one of the seven named tracking parameters.

**Residual risk:** for pages that *do* have a tracking parameter baked into their fallback canonical URL (no `[expr]` tag, discovered via a tracking-tagged link), the next sync computes a new `id`, so `findBySourceId` won't match the old row — that old row isn't deleted or corrupted, it just stops being updated (documents are served by their own DB UUID, not this hash, per `routes/knowledge-base.ts:701-728`, so nothing 404s), while a fresh row is created alongside it. This is bounded (most site-authored canonical tags already omit tracking params) and has an existing operator remedy: `POST /api/connectors/:id/force-resync` (`routes/knowledge-base.ts:1039-1092`) wipes and re-crawls the connector cleanly.
