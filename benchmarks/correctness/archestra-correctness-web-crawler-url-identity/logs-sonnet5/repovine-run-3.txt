## Why two normalizer functions, not one

The obvious reading — strengthen `normalizeCrawlUrl` in place — breaks the connector. That function's output isn't just an identity key: it's also the literal URL Crawlee fetches (`crawler.run(…)`) and enqueues (`normalizeDiscoveredUrl`), and it feeds the crawl-scope containment check (`buildAllowedPathPrefixes`'s directory-vs-file heuristic). Running the connector's own test suite after that first attempt caught it immediately: 17 tests failed because stripping a trailing slash before fetching turns `GET /docs/` into `GET /docs`, which the test server (and plenty of real servers) treats as a different resource — wrong content, missing linked pages, and a start URL like `/docs/` silently widening scope to the whole site.

Fix: `normalizeCrawlUrl` stays exactly as it was (fragment + default-port strip only) for every fetch/enqueue/scope use. A new `normalizeDocumentUrl` wraps it and applies the four stronger rules, wired in only at `normalizeCanonicalUrl` — the point that computes `buildDocument.id`/`sourceUrl`, i.e. only after the real page is already fetched. This mirrors how `[expr]` already overrides identity in this file without touching what gets crawled.

| Rule | Where |
|---|---|
| Strip tracking params (utm_*, gclid, fbclid) | `normalizeDocumentUrl`, gated to only touch `searchParams` when a tracking param is present |
| Strip trailing slash on non-root paths | `normalizeDocumentUrl` |
| Lowercase host | `normalizeDocumentUrl` (empirically a no-op today — `[expr]` already lowercases host — added explicitly per spec rather than relying on that implicit behavior) |
| Default-port strip | Unchanged, still in `normalizeCrawlUrl` |

The tracking-param gate exists because `URLSearchParams` mutation re-serializes the *whole* query string via `application/x-www-form-urlencoded` rules (verified: `[expr]`→`[expr]`, bare flags gain `[expr]`), even for params you didn't touch. Gating it means URLs with no tracking params are byte-identical before/after — smaller diff surface, and it's what makes the migration below tractable.

## The persisted-identity problem, and the migration

`buildDocument.id` (sha256 of the canonical URL) becomes `kb_documents.source_id` — written once at ingest, never re-derived, no prune step. Without a backfill, the first sync after deploying this change would fail to match every already-indexed page whose URL had a tracking param, trailing slash, or mixed-case host, inserting a duplicate row per page while the old row goes stale forever (search returns both). This is exactly what the task's "must continue to be served correctly" requirement is guarding against.

Added `0313_recanonicalize_web_crawler_source_ids.sql` (generated via `drizzle-kit generate --custom`, `drizzle-kit check` clean, `check:migrations` reports 0 errors/0 warnings on the new file). Scope, deliberately conservative:

- **Always safe:** trailing-slash-only changes; queries untouched (no tracking param) or fully emptied (every param was a tracking param).
- **Left unmigrated by design:** rows whose query mixes tracking and non-tracking params — SQL can't guarantee byte-exact replication of `URLSearchParams`'s re-serialization without reimplementing form-urlencoded encoding, and a wrong hash is worse than no migration (churn, still won't match next sync).
- **Collision-safe:** strengthening normalization can make two previously-distinct rows (e.g. `/docs` and `/docs/`) resolve to the same new identity. The unique index on `[expr]` forbids writing both, so only one is re-keyed (preferring a row already at the target identity, else the most recently updated); the other keeps its old identity — still valid, still served, just not re-matched by the next crawl.

I verified this logic — not just reasoned about it — against a throwaway in-memory PGlite instance (the same ephemeral mechanism the test suite uses) seeded with synthetic fixtures covering all of the above, including three distinct collision scenarios. All resolved correctly with no constraint violations, and every migrated hash matched what the live TypeScript `normalizeDocumentUrl` computes for the same input.
