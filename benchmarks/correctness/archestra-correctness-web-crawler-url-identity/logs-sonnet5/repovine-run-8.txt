### What changed, and why it's split into two functions

`normalizeCrawlUrl` was doing double duty: it normalized the URL used both to **fetch/enqueue** pages and to compute the document's **stored identity** (`id`/`sourceUrl`/`metadata.url`, via `normalizeCanonicalUrl`). Applying the new rules there broke real crawl behavior — proven by this repo's own test suite: `web-crawler-connector.test.ts`'s mock server (`createTestSite`, lines 722-739) does exact-path routing with no trailing-slash tolerance, so once trailing slashes were stripped from the *request* URL, `/docs` no longer matched the registered `/docs/` route and came back as a literal 404 body. That produced cascading failures (wrong titles, missing content, missing discovered links, wrong batch counts) — genuine regressions, not just stale assertions.

Fix: kept `normalizeCrawlUrl` (web-crawler-connector.ts:624) exactly as it was (hash-strip + default-port-strip), and added a new `canonicalizeDocumentUrl` (web-crawler-connector.ts:595) that layers the four new rules on top of it, used only inside `normalizeCanonicalUrl` (web-crawler-connector.ts:607), which is the single function that feeds `buildDocument`'s `id`/`sourceUrl`/`metadata.url`. New rules: lowercase host, strip `utm_source/utm_medium/utm_campaign/utm_term/utm_content/gclid/fbclid`, strip a trailing slash on non-root paths — plus the pre-existing default-port stripping (still via `normalizeCrawlUrl`).

### Deliberately left unchanged (with proof)

- **Fetch/enqueue/scope-validation call sites** — `crawler.run(…)` (lines 129, 170), `createCrawler`'s `startUrl` (line 191), `validateParsedConfig`'s scope self-check (line 352), `normalizeDiscoveredUrl` (line 583). Left on the unchanged `normalizeCrawlUrl`. Proof it must stay separate: the test-suite regression above, reproduced and fixed during this change.
- **Scope-matching (`buildAllowedPathPrefixes`, `pathMatchesPrefix`)** — untouched. `pathMatchesPrefix` (line 563) already strips *its own* prefix's trailing slash before comparing (`[expr]`), so it's already tolerant of either form; no change needed, confirmed by `"normalizes include path prefixes..."` and `"scopes the crawl to the start URL's directory..."` passing.
- **`metadata.fetchedUrl`** (line 462) — still the raw, un-canonicalized request URL, as before. It records what was actually fetched (audit/debug), not identity; only `extracted.canonicalUrl` (which I did change) feeds `id`/`sourceUrl`/`metadata.url`.
- **`connector-sync.ts`'s `findBySourceId` matching/no-prune contract** — untouched. That contract is what makes the migration necessary in the first place (per the repovine annotation on this module); the correct fix is re-keying stored `source_id`s to it, not changing the lookup.

### The migration

`kb_documents.source_id` is `sha256(…)`, written once at ingest and never re-derived; sync has no prune step (confirmed via `connector-sync.ts`'s `ingestDocument`/`KbDocumentModel.findBySourceId`, and the module's repovine annotation, which cites migration `0131_fix_agent_tool_trailing_underscores` as the precedent for this exact class of fix). Left alone, the first sync after this change would insert a duplicate for every URL whose canonical form changed, leaving the old row orphaned — directly violating "every document already indexed must continue to be served correctly."

`0313_fix_web_crawler_source_id_normalization.sql` recomputes `source_id`/`source_url`/`metadata.url` from each `web_crawler` document's already-normalized `source_url`, and merges rows that collide onto the same recomputed URL (keeping the most recently updated one, cascading its chunks via the existing `kb_chunks.document_id` FK's `ON DELETE CASCADE`) — since those collisions are exactly the same-page duplicates this task is about. Rows for other connector types, or whose `source_url` doesn't match the expected shape, are left untouched.

Verified by: `pnpm exec drizzle-kit check` (passes), the repo's `check:migrations` linter (0 errors), and a throwaway PGlite scenario script (seeded pre-existing "legacy" rows including a 3-way trailing-slash/case/utm collision, a non-tracking-param URL that must *not* merge, a root path, a different connector type, and a malformed URL) — all assertions passed, then the script was deleted; nothing was run against a real database, per this repo's rule against unapproved data-modifying SQL. **`pnpm db:migrate` still needs to be run explicitly by you** (or your deploy pipeline) to apply it.
