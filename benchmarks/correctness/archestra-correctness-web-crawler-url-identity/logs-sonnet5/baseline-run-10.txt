## Implementation complete

**File changed:** `platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts` (only file touched, no tests modified).

### What changed and why

The old `normalizeCrawlUrl` is shared by two different consumers: the literal URL Crawlee fetches (seed URL, discovered links) and the canonical URL used for `id`/`sourceUrl`/`metadata.url`. I split the four rules across two mechanisms based on which consumers they're safe for:

| Rule | Where applied | Why there |
|---|---|---|
| Strip `utm_source/medium/campaign/term/content`, `gclid`, `fbclid` | `normalizeCrawlUrl` (:628-642) — every caller | Query params outside routing are conventionally ignored by servers; can't change what's served |
| Lowercase host | `normalizeCrawlUrl` (:628-642) — every caller | Hostnames are case-insensitive per RFC 3986/7230; can't change what's served |
| Strip default port | `normalizeCrawlUrl` (:628-642) — every caller | Unchanged, pre-existing behavior |
| Strip trailing slash on non-root paths | New `dedupeTrailingSlashVariants`/`trailingSlashDedupeKey` (:432-449), used only inside `enqueueAllowedLinks` (:409) | Trailing-slash equivalence is server-dependent, not spec-guaranteed |

### Code paths deliberately left unchanged (and the proof)

1. **The literal fetch/request URL** — the crawl seed (`:129`, `:170`, `:191`) and discovered-link enqueue targets (`normalizeDiscoveredUrl`, `:592-608`) do *not* get trailing-slash stripping.
   Proof it's load-bearing: the `beforeRedirect` hook (`:237-265`) already re-validates scope/SSRF on every redirect hop specifically so the crawler never silently substitutes a different resource than the one it was asked to fetch. Stripping a trailing slash pre-fetch risks requesting a path the origin server doesn't treat as equivalent (404, different content) — unlike tracking params/host case, this isn't guaranteed safe by any spec.

2. **`id`/`sourceUrl`/`metadata.url`** — `normalizeCanonicalUrl` (`:610-627`) and `buildDocument` (`:468-486`) get tracking-param/host-case stripping (safe, via the shared function) but *not* trailing-slash stripping.
   Proof it's load-bearing: `buildDocument`'s `id` (`:474-476`) is `sha256(…)`. I traced how that flows downstream — it's stored as `sourceId` and matched against existing rows via a `[expr]` unique index in `kb-document.ts`, deciding update-vs-insert on every sync in `connector-sync.ts`. There is **no stale-document cleanup** anywhere in the sync pipeline — the only bulk-deletion path is the manual, whole-connector `force-resync` endpoint. If trailing-slash stripping touched `id`, every already-indexed directory-style page (the majority of section/index pages a crawler indexes — e.g. anything ending in `/`) would get a new `id` on its next sync, creating a duplicate row and permanently orphaning the old one — reintroducing the exact bug this task fixes, at the database layer. `[expr]` (`:483`) is pre-existing evidence the codebase already treats "the literal fetched URL" and "the canonical identity URL" as distinct concepts; I extended that separation rather than inventing it.

3. **`excludePathPatterns` matching** (`isPathInScope`, `:565-582`) — matches against the already tracking-stripped URL, since stripping happens inside the shared `normalizeCrawlUrl` upstream of scope checks. Untouched; no existing config depends on tracking params surviving into exclusion regexes.

### Summary and residual risk

Trailing-slash, tracking-param, and host-case variants of the same page now enqueue as one fetch going forward (trailing slash: per-page, at discovery time; the other two: everywhere, including identity). All four rules were checked by hand against every URL in the existing test fixtures — none use tracking params, mixed-case hosts, or same-page trailing-slash-variant links, so no pinned assertion should be affected, though I could not run the suite here (this benchmark worktree has no `node_modules`; builds/tests/type-checks are intentionally blocked, confirmed via the `tsc`/`vitest` shims instructing static-only verification). I did do a full mechanical bracket-balance check and a manual trace of every edited expression.

Residual risk: tracking-param/host-case stripping **does** touch `id`, so an already-indexed page whose *current* stored canonical URL happens to carry one of the seven tracking params or a mixed-case host will get a new `id` on its next sync, orphaning the old row (rare in practice — those usually decorate inbound links, not a site's own canonical tags — but possible). Recommend running "force resync" per connector after deploying to fully rebuild and clear any such transients in one pass rather than letting them trickle in. Separately, the trailing-slash dedup is intentionally narrow (per-page, discovery-time only) — it reduces duplicate fetches but doesn't retroactively merge documents already duplicated under the old normalization.
