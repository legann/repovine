## Summary

**Core change** — `platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts`

`normalizeCrawlUrl` (line 606) now does, in addition to its existing hash-stripping and default-port-stripping:

| Rule | Implementation |
|---|---|
| Lowercase host | `[expr]` |
| Strip tracking params | new `TRACKING_QUERY_PARAMS` set (`utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`, `gclid`, `fbclid`) deleted via `url.searchParams.delete()` |
| Drop trailing slash | `url.pathname` sliced by one char when it's not `"/"` and ends in `/` |

`normalizeDiscoveredUrl` (line 571) and `normalizeCanonicalUrl` (line 589) already funnel every URL through `normalizeCrawlUrl`, so they inherit the fix with no changes of their own.

**Data migration** — new `platform/backend/src/database/migrations/0313_rekey_web_crawler_source_ids.sql`

`kb_documents.source_id` is `sha256(…)`, written once at ingest (`connector-sync.ts` `ingestDocument`) and never re-derived; sync has no prune step (confirmed by reading `connector-sync.ts` and `models/kb-document.ts`, not just the repovine annotation that flagged it). Without a migration, the very next sync would miss every existing page by `source_id` and insert a duplicate row that's never cleaned up — directly violating "every document already indexed must continue to be served correctly." The migration:
- re-derives `source_url`/`source_id` for `web_crawler`-type `kb_documents` rows only, using the same three new rules,
- dedupes any collisions the re-key creates (e.g. `/page` and `/page/` previously indexed as two documents now target one `source_id`), keeping the newest row — same rule the precedent `0169_hot_flatman.sql` used when this unique index was first introduced.

I initially wrote this as drop-index → update → recreate-index, but an ephemeral PGlite test caught a real bug: Postgres enforces the non-deferrable unique index per-row, not per-statement, so update-then-dedup fails on the first collision. Redesigned around a temp table so the index is never dropped — this also satisfies the repo's own migration linter, which hard-errors on `DROP INDEX`/`CREATE UNIQUE INDEX` as unsafe for rolling deploys.

**Verification performed:** `tsgo --noEmit` clean; `pnpm knip` (dev+production) clean; `drizzle-kit check` → "Everything's fine"; `check:migrations` → 0 errors/0 new warnings; a disposable PGlite run exercising mixed-case host, tracking params, a real trailing-slash collision pair, an already-canonical row, root path, and a non-web_crawler connector — all assertions passed, including exact-match against independently-computed `sha256(…)`. I did **not** run `pnpm db:migrate` against any real database, per the "no DB modifications without approval" rule — the migration file exists but is unapplied until you (or CI) run it.

I also updated the module's repovine annotation (it was flagged content-stale) so the risk section reflects that this instance is now fixed, while keeping the durable warning that any *future* `normalizeCrawlUrl` change needs the same re-key treatment.

**Deliberately left unchanged, with proof:**
- Other connectors' identity derivation (jira/confluence/sharepoint/etc., see `registry.ts:34` for the full map) — the migration's `[expr]` scopes it strictly to this connector.
- SSRF/scope checks — `assertPublicCrawlUrl` (`web-crawler-connector.ts:637`), `isAllowedUrl` (`:524`), `isPathInScope` (`:544`) — operate on parsed protocol/origin/pathname, orthogonal to the identity-string normalization asked for.
- Not in scope per the task's exact four bullets: full query-string stripping/sorting, path case-folding, `www.` collapsing, index-filename stripping, http→https canonicalization.

**Residual risk:** the SQL migration strips tracking params via a plain `[expr]`-split/name-filter, while the TS code uses `URLSearchParams.delete()` (which re-serializes *all* surviving params through its own percent-encoding). Both agree for ordinary ASCII query strings (verified), but a page with unusual percent-encoding in a *non-tracking* param could compute a different hash in the migration than the next live crawl computes, re-creating one duplicate row for that narrow case — the same "best-effort, not byte-perfect" tradeoff the precedent `0131` migration made.
