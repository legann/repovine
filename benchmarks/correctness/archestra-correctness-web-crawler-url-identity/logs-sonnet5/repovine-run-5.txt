### Why the migration, not just the function

`normalizeCrawlUrl`'s output is persisted once as `kb_documents.source_id` and never re-derived (`connector-sync.ts:419` `findBySourceId` / `:502` `create`), and there's no prune step. Changing the normalizer alone means the next sync recomputes a different `source_id` for every page whose old URL had a tracking param or trailing slash, fails to match the existing row, and inserts a duplicate — the stale row stays forever and `query.ts:265` surfaces both. That's what the task's "must continue to be served correctly" line rules out, so I re-keyed existing rows in the same change, following this repo's precedent for this exact class of fix (`migrations/0131_fix_agent_tool_trailing_underscores.sql`).

I verified the SQL against the real TS logic empirically (PGlite, 16 cases + a deliberate pre-existing-collision case) rather than trusting hand-derived regex — first pass caught real bugs (see residual risk below), second pass passed all cases. `drizzle-kit check`, the repo's `check:migrations` linter, `tsgo --noEmit`, and Biome all pass clean.

### Residual risk

- **Host lowercasing is a no-op in practice.** Verified empirically: `[expr]` already lowercases ASCII/IDNA/IPv6 hosts, so no pre-existing row could have had mixed case. Kept per the literal spec (harmless, self-documenting), but it doesn't fix anything real.
- **Pre-existing near-duplicates aren't merged.** If two rows were already indexed under URLs that both canonicalize to the same new form (e.g. a page crawled once clean and once via a tracking link), the migration's collision guard leaves both rows untouched rather than merging them (verified in the PGlite test) — it prevents *new* duplication, it doesn't retroactively fix pre-existing dupes of this kind.
- **Query-string re-encoding on the rare row that both has a tracking param and unusual characters in a sibling param.** Removing one key via `URLSearchParams` reserializes the rest of the query using form-urlencoded rules (e.g. space → `[expr]`), so a sibling param with atypical characters could shift encoding. Guarded to only fire when a tracking param is actually present, so untouched query strings are provably byte-identical.
- **Assumed Postgres ≥ 11** for the built-in `sha256()` used in the migration (no `pgcrypto` needed). Only version reference found in-repo is `postgres:16-alpine` (n8n's compose file); didn't locate the main app's engine version pin to double-confirm.
- Did not run `pnpm db:migrate` (per repo rule against DB-modifying commands without approval) — the migration file is ready but not applied; only `drizzle-kit check`/`check:migrations` (static) were run.
