## Files changed

**`platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts`**
- Added `TRACKING_QUERY_PARAMS` (a `Set`, matching the file's existing `BLOCKED_HOST_RANGES` convention) and extended `normalizeCrawlUrl()` to lowercase the host and strip those params.
- Added a separate `stripTrailingSlash()` helper, applied once in `extractPage()` on top of `normalizeCanonicalUrl()`'s result — **not** inside `normalizeCrawlUrl()`.

That split wasn't in my first pass — I initially put trailing-slash removal inside `normalizeCrawlUrl()` itself, then ran the existing test suite and watched 17/28 tests fail, most with actual 404s, not just string mismatches. `normalizeCrawlUrl()`'s output feeds three things besides document identity: the crawl-queue seed URL (`crawler.run`), discovered-link enqueueing, and scope derivation (`buildAllowedPathPrefixes` — which infers the crawl's allowed prefix from whether the *start URL itself* ends in `/`). Origin servers routinely treat `/docs` and `/docs/` as different resources (this repo's own test server does, via exact pathname matching), and `buildAllowedPathPrefixes`'s scope inference silently breaks if the start URL's trailing slash disappears before it gets there. Trailing-slash removal is only safe on the *already-fetched* page's stored identity, so it's isolated to the one call site that computes it. After the fix, all mechanics (fetch, redirects, scope, batching, delays) work exactly as before — the only behavior change is in the 5 tests asserting stored `sourceUrl`/`metadata.url` values (see below).

**`platform/backend/src/database/migrations/0313_rekey_web_crawler_source_ids.sql`** (new)
- `kb_documents.source_id`/`source_url` are `sha256(…)`/`canonicalUrl`, written once at ingest, never re-derived, with a real unique constraint on `[expr]` and no prune step (verified by reading `connector-sync.ts`'s `ingestDocument` and the `kb-document`/`kb-chunk` schemas directly, not just the repovine annotation that flagged it). Without a backfill, the *first* sync after deploy would recompute a different `source_id` for any previously-indexed page affected by the new rules, miss the `findBySourceId` lookup, and insert a permanent duplicate alongside a now-frozen stale row — this is exactly what "must continue to be served correctly" rules out.
- The migration re-keys existing web_crawler rows to the new canonical form. It's `UPDATE`-only (never deletes), and only rewrites a row when the recomputed identity doesn't collide with another row in the same connector (either another row changing in the same batch, or a row already stored in canonical form) — colliding rows are pre-existing duplicates from before this change and are left untouched rather than risking a destructive merge decision.
- I validated this end-to-end against a disposable, throwaway Postgres 16 container (matching the repo's `postgres:16-alpine`), not just by reading it: confirmed the SQL's `sha256()` output is byte-identical to Node's `crypto.createHash(…)` for every case, confirmed the intended rows re-key and unaffected/colliding rows don't, confirmed zero duplicate `[expr]` pairs afterward, and confirmed a second run is a no-op. I did **not** run `pnpm db:migrate` against any real database — generating/checking migrations is fine per the repo's own migration skill, but applying one needs your go-ahead first.
- Also updated the file's own repovine annotation to record why `stripTrailingSlash` must stay separate from `normalizeCrawlUrl`, and to point future normalization changes at this migration as the established pattern.
