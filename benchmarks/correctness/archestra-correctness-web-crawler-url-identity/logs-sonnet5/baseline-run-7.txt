**Why trailing-slash stripping is scoped to `normalizeCanonicalUrl` only, not `normalizeCrawlUrl` itself:** `normalizeCrawlUrl` also produces the URL that's actually requested (`crawler.run(…)` seed, and `enqueueLinks` targets via `normalizeDiscoveredUrl`). A server can legitimately serve a directory path differently with vs. without its trailing slash (a 404 instead of a redirect is common on static hosts). I confirmed this isn't hypothetical: this repo's own test harness (`createTestSite` in the test file) routes by exact `pathname` string match, so a first draft that stripped the slash pre-fetch turned every directory-style seed/discovered-link request into a 404 — breaking crawl mechanics far beyond the canonicalization itself (`testConnection`, batching, redirect-following, retries all regressed). Splitting the rule to only affect the stored canonical identity avoids that while still fully fixing the duplicate-document problem: two pages fetched as `/docs/install/` and `/docs/install` (no canonical tag) still resolve to the same canonical string and thus the same `id`, so the sync layer's own content-hash-match logic collapses them into one row — at the cost of one extra (but harmless) page-visit against the crawl budget if both forms are ever actually linked.

I verified the final logic empirically (plain-Node simulation, since this worktree has no `node_modules` to run the real TS suite) against the exact URL literals used in the test fixtures — confirmed fetch URLs are byte-identical to before, and four "trivially different" variants (mixed-case host, default port, tracking params, trailing slash) of the same page all canonicalize to one identical string.

### "Must continue to be served correctly" — how this is satisfied

`buildDocument` hashes the canonical URL into `id` (`createHash(…)`), and `connector-sync.ts` uses that `id` as `source_id`, upserted via a `UNIQUE(…)` index — the sole key deciding "update this row" vs. "insert a new one." This code makes no DB changes, so every already-indexed row stays exactly as-is: still returned by `GET .../documents/:docId`, still rendered in citations and the documents table (both consume `sourceUrl` verbatim, never re-validating it), still surfaced by vector/full-text search. Nothing here can corrupt or hide existing rows.

**Residual risk:** for a page whose canonical form is unchanged by the new rules (the common case — no tracking params, no non-root trailing slash, already-lowercase host), the id is identical to before and the next sync updates the existing row exactly as today. For a page whose canonical form *does* change (e.g. it was indexed via a URL carrying `[expr]`, or a directory URL with a trailing slash, or a mixed-case host), the next sync computes a new id, finds no matching row, and inserts a fresh one — the old row is not deleted (there's no reconciliation/pruning step in `connector-sync.ts` today; `deleteByConnectorAndSourceId` exists but isn't wired into the sync loop), so it becomes a stale duplicate until a manual `force-resync` (wipes and re-crawls the whole connector) or a manual per-document delete. This is a pre-existing architectural gap, not something introduced by this change, and building reconciliation is out of scope for a normalization fix.

**Test impact:** per the constraint not to modify tests, I did not touch `web-crawler-connector.test.ts`. Five of its tests pin the pre-fix trailing-slash behavior on directory-style canonical URLs (`sourceUrl`/`id`/`metadata.url` expected to retain a trailing slash for paths like `/docs/` and `/docs/install/`) and will now fail — this is the direct, unavoidable, and correct consequence of fixing the described bug, since those assertions encode exactly the behavior being intentionally changed. All other tests (scope enforcement, redirect handling, retries, batching, `testConnection`, content extraction, title fallback, SSRF/DNS checks) are unaffected, since the fetch/enqueue path is untouched.
