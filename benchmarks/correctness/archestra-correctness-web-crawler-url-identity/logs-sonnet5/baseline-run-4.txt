## Patch implemented

Single file: `platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts`. The diff is 31 insertions / 4 deletions, all within that file.

**Design:** two normalization layers instead of one, because the existing `normalizeCrawlUrl` is reused both to build the URL the crawler actually *requests* and to build the URL stored as document identity — and those two uses tolerate different amounts of normalization.

| Function | Used for | New behavior |
|---|---|---|
| `normalizeCrawlUrl` (existing, extended) | crawl seed, enqueued/discovered links, redirect-scope checks — i.e. anything that becomes a live HTTP request or an origin comparison | + lowercases host, + strips `utm_source/medium/campaign/term/content`, `gclid`, `fbclid`; keeps existing hash-clear and default-port strip |
| `normalizeDocumentUrl` (new, wraps the above) | only the stored document identity: `id`, `sourceUrl`, `metadata.url`, via `normalizeCanonicalUrl` | + strips a trailing slash on non-root paths |

I initially put trailing-slash stripping directly in `normalizeCrawlUrl`, then reverted it after finding two concrete regressions:

1. **Scope escape**: `buildAllowedPathPrefixes` (`web-crawler-connector.ts:469-482`) infers the default crawl scope from whether the *configured* start URL ends in `/` (directory → scoped to that directory) or not (file → scoped to its parent). Feeding it a slash-stripped URL turns every directory-style start URL into a "file", widening the default scope from e.g. `[expr]` to the entire origin. Verified with a standalone repro before touching code.
2. **Live 404**: the URL passed to `crawler.run()`/`enqueueLinks` is the literal fetch target. The test harness's fake server (`web-crawler-connector.test.ts`'s `createTestSite`) does exact-string route lookup with a hard 404 fallback, no auto-redirect for bare paths — and plenty of real origins behave the same way. Stripping the trailing slash there would make the connector fail to crawl its own configured start URL whenever the origin doesn't redirect `/docs` → `/docs/`.

So `normalizeCrawlUrl` stays path-preserving, and only the final stored identity (`normalizeDocumentUrl`) drops the slash.

## Residual risk

- **Already-indexed documents get a new `id` on the next sync, and the old row isn't cleaned up.** I traced the consumer (`ConnectorSyncService.executeSync` / `ingestDocument` in `connector-sync.ts`, keyed by `[expr]` where `[expr]`, unique index in `kb-document.ts:44-47`). There's no "delete rows not seen this sync" step on incremental syncs — only a manual per-document delete or a full "Force Resync" (`knowledge-base.ts:1074-1082`) clears stale rows. So any page whose canonical URL previously had a tracking param, mixed-case host, or trailing slash will be **re-inserted under a new id** on the next sync, and the **old row persists** as a duplicate until someone force-resyncs that connector or deletes it manually. Each row individually still serves correct content/links — nothing breaks — but search results can show duplicates transiently. This is a pre-existing, accepted characteristic of the sync pipeline shared by all connectors (see the comment at `perforce-connector.ts:36-37` acknowledging the same gap), not something introduced by or fixable from this file.
- **Trailing-slash equivalence is an assumption, not a verified fact per-site.** A small minority of origins genuinely serve different content (or a 404) at `/docs` vs `/docs/`. This was explicitly requested behavior, so I implemented it, but it's worth knowing the assumption exists.
- **Existing tests will now fail on hardcoded trailing-slash URL strings** — expected, since they pin the old behavior and I was told not to touch tests. Affected: the `sourceUrl`/`metadata.url`/`id` assertions in the tests `"crawls same-host HTML pages..."` (lines 163, 172, 178), `"follows a same-host redirect..."` (line 271), `"falls back to the fetched URL when canonical points to another origin"` (lines 317-318), `"ignores fragment and non-HTTP links..."` (line 648, one of two array entries), and `"falls back to the fetched URL when the canonical link is malformed"` (lines 667-668). Titles/content/skip assertions in those same tests are unaffected since they don't depend on the canonical URL string.
