## Summary

**File changed:** `platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts` (only file touched).

### What changed

| Rule | Where | Applies to |
|---|---|---|
| Strip `utm_source/medium/campaign/term/content`, `gclid`, `fbclid` | `normalizeCrawlUrl` | every URL the crawler requests *and* document identity |
| Lowercase host | `normalizeCrawlUrl` | same |
| Default-port stripping | `normalizeCrawlUrl` (unchanged) | same |
| Strip trailing slash on non-root paths | new `normalizeDocumentUrl` (wraps `normalizeCrawlUrl`) | **only** `id`/`sourceUrl`/`metadata.url` — never the fetch |

I split normalization into two layers instead of one:
- `normalizeCrawlUrl` — used for every URL actually requested over HTTP (crawl seed, discovered `[expr]` links). It only gets transformations guaranteed equivalent at the HTTP layer.
- `normalizeDocumentUrl` — used only inside `normalizeCanonicalUrl` to label the resulting document (`id`, `sourceUrl`, `metadata.url`). It adds trailing-slash collapsing on top.

Trailing-slash equivalence isn't guaranteed the way query-param/host-case/port equivalence is — some servers serve different content, redirect, or 404 one form of `/foo` vs `/foo/`. Folding it into the fetch path risks requesting the wrong resource; keeping it identity-only means the crawl always fetches exactly what was linked/configured, and only the final label converges.

### Code paths deliberately left unchanged (with proof)

1. **`buildAllowedPathPrefixes`** (`web-crawler-connector.ts:469-482`) — untouched. Its directory-vs-file heuristic at line 478 (`path.endsWith(…)`) reads the pathname from a `startUrl` that both call sites (line 191, line 352) build via `normalizeCrawlUrl(…)`, not `normalizeDocumentUrl(…)`. Since `normalizeCrawlUrl` never touches trailing slashes, this heuristic sees the exact same pathname shape as before. (This was the main trap: if trailing-slash stripping had landed in `normalizeCrawlUrl` itself, a directory-scoped crawl like `startUrl: ".../blog/"` would silently widen to the whole origin, because stripping the slash flips which branch of this function fires.)
2. **`isAllowedUrl` / `isPathInScope` / `pathMatchesPrefix`** (`web-crawler-connector.ts:529-568`) — untouched. Both sides of every comparison already go through `normalizeCrawlUrl`, so origin/host comparisons stay consistent; `pathMatchesPrefix` already treats a prefix's own trailing slash as insignificant (line 565).
3. **`connector-sync.ts` ingestion path** (`ingestDocument`, `connector-sync.ts:393-532`, lookup at `connector-sync.ts:419-422`) — out of scope, shared by every connector type. See residual risk below.

### Residual risk

- **Document-identity churn on re-sync.** `ConnectorDocument.id` is `sha256(…)`, and ingestion (`connector-sync.ts:419-422`) upserts by that id with no fallback. After this change, the first re-crawl of a previously-indexed page whose URL had a trailing slash, tracking params, or mixed-case host computes a *different* id, so `findBySourceId` misses and a new `kb_documents` row is created. The old row is never deleted — `deleteByConnectorAndSourceId` (`kb-document.ts:332`) has zero callers repo-wide (verified via grep) — so it lingers, frozen at its last content, until the connector itself is deleted. Nothing 404s or serves wrong content (both stored `sourceUrl`s remain valid, resolvable URLs), but the KB will carry a duplicate per affected page. Fixing this needs shared ingestion/model changes well outside `web-crawler-connector.ts`, so I left it as-is.
- **Existing unit tests will fail.** This environment blocks running tests (no `node_modules`), so I traced the suite statically. `web-crawler-connector.test.ts` hardcodes directory-style URLs (e.g. `[expr]`, `.../docs/install/`) as expected `sourceUrl`/`id`/`metadata.url` values in 5 tests: *"crawls same-host HTML pages…"*, *"follows a same-host redirect and indexes the destination"*, *"falls back to the fetched URL when canonical points to another origin"*, *"falls back to the fetched URL when the canonical link is malformed"*, *"ignores fragment and non-HTTP links when discovering pages"*. Those assertions expect the trailing slash preserved; the new `normalizeDocumentUrl` strips it, so these will now fail. This is the direct, unavoidable effect of implementing "remove a trailing slash on non-root paths" — I couldn't find a placement that satisfies both that requirement and those hardcoded strings, and the task's constraint is not to touch tests. Flagging rather than silently sidestepping the requirement.
- Fetch-path behavior (what actually gets requested, redirect/SSRF checks, crawl scoping) is unaffected by any of this — verified by keeping `normalizeCrawlUrl` path-shape-preserving.
