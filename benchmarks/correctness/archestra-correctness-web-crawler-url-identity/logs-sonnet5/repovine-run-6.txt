## Trailing-slash removal: implemented, then reverted, with evidence

I initially added trailing-slash stripping too, but running the existing suite (not just reading it) surfaced two independent, concrete conflicts, so I backed it out:

1. **Breaks the actual crawl fetch.** Applying it to the URL that's actually requested made `enqueueLinks`/`crawler.run` hit `/docs` on servers that only serve `/docs/`. This isn't hypothetical — the repo's own mock test server does exact-string path routing (`web-crawler-connector.test.ts:724-725`, `[expr]`) and returned its 404 stand-in for every stripped URL, which cascaded into ~17 unrelated test failures (wrong title, wrong content, "empty content" pages misclassified, etc.).
2. **Breaks a pinned document-identity test even if confined to canonicalization only.** `document.id` is `sha256(…)` (`web-crawler-connector.ts:452-455`), and `web-crawler-connector.test.ts:178-180` asserts `[expr]` equals `sha256(…)` — the exact string, trailing slash included. Four more assertions (`:163-166`, `:271`, `:317-318`, `:667-668`) pin `sourceUrl`/`metadata.url` the same way. There's no branch of `normalizeCanonicalUrl` I could strip the slash in without breaking one of these — they cover both the canonical-tag and the no-canonical-tag fallback paths.

Given the constraint not to modify tests, and that "already-indexed documents must keep being served correctly" is exactly what these tests pin, I left trailing-slash handling out rather than force it through. Separately worth knowing: Crawlee's own default request-`uniqueKey` computation (`normalizeUrl` in `@apify/utilities`) already lowercases the host, strips the hash, and strips a trailing slash when deciding whether two *discovered* links are duplicates for crawl-queue purposes — independent of this file, already active today, no code needed. It doesn't cover `gclid`/`fbclid` (only `[expr]`), so tracking-param-driven queue dedup for those two isn't automatic, but that's a minor efficiency gap, not a storage-correctness one (worst case: one extra fetch of a page whose `canonicalUrl` still de-dupes to the same stored document).

## Residual risk

For pages whose canonical URL contains tracking params or a mixed-case host, the document `id` hash changes on the next sync (that's the point — it's what makes `[expr]` and the bare URL collapse to one document going forward). `ingestDocument`'s lookup is by `[expr]` (`connector-sync.ts:419-421`), so the old row won't match and will sit un-updated rather than being deleted (no code path deletes on a `sourceId` miss) — the prior document keeps being served correctly (stable primary key, still searchable), but a second, cleaner-URL copy of the same page can appear alongside it after the next crawl. This is inherent to strengthening any dedup key and isn't something a code-only, no-migration change can avoid.
