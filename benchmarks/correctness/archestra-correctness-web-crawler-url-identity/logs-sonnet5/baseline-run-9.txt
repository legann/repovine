## Summary

**File changed:** `platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts` (only file touched).

### What changed

1. **`normalizeCrawlUrl`** (used everywhere a URL is actually fetched or enqueued — the start URL, discovered links, and scope/origin derivation) now also:
   - Lowercases the host explicitly (`url.hostname.toLowerCase()`).
   - Strips the 7 tracking params (`utm_source/medium/campaign/term/content`, `gclid`, `fbclid`) via a new `TRACKING_QUERY_PARAMS` set, matching the existing `BLOCKED_HOST_RANGES` style.
   - Keeps the existing hash-stripping and default-port-stripping unchanged.

2. **New `normalizeDocumentUrl`** wraps `normalizeCrawlUrl` and additionally strips a trailing slash on non-root paths. It's used only inside `normalizeCanonicalUrl`, i.e. only when computing the document's stored identity (`id`, `sourceUrl`, `metadata.url`) — never for the URL that's actually requested over HTTP.

### Why the split, not one function

Trailing-slash removal is unsafe to apply to a URL *before* it's fetched: many servers 404 on the slash-less form with no redirect (the repo's own test fixture server does exactly this — exact-path routing, no fallback). Two concrete things would break if trailing-slash stripping were applied at fetch/enqueue time instead of only at the identity layer:

- `buildAllowedPathPrefixes` (`web-crawler-connector.ts:469`: `[expr]`) derives the crawl scope from whether the start URL's path ends in `/`. Stripping the slash before this check flips a directory-style start URL (e.g. `/docs/`) into the "file" branch, widening the scope from `[expr]` to `/` — silently crawling the whole host instead of the configured section.
- Every test that starts a crawl at a directory path like `/docs/` would 404 immediately against the fixture server, since it does exact string matching with no redirect for the slash-less form.

Tracking-param stripping and host-lowercasing, by contrast, are safe to apply at fetch time too (query strings don't affect routing/existence of a resource, and HTTP hosts are case-insensitive), so those live in the shared `normalizeCrawlUrl` and also reduce redundant re-crawls of the same page under differently-tagged marketing links.

### Left unchanged, with proof it's out of scope

- **Host lowercasing was already guaranteed** by the WHATWG URL parser before this change — `[expr]` (line 607) already lowercases the host for `http:`/`https:` (verified for both ASCII and IPv6-literal hosts). The explicit `[expr]` I added is defensive/self-documenting, not a behavior fix.
- **`pathMatchesPrefix`** (`web-crawler-connector.ts:556-560`) already tolerates a trailing-slash mismatch when matching scope prefixes, so no change was needed there.
- **`metadata.fetchedUrl`** (built from `[expr]`, `web-crawler-connector.ts:277`) is untouched — it's meant to record the literal URL that was fetched, distinct from the normalized canonical identity.

### Residual risk

Per research into the ingestion pipeline (`connector-sync.ts`, `models/kb-document.ts`), documents upsert on `[expr]` and there is **no stale-document reconciliation** (`KbDocumentModel.deleteByConnectorAndSourceId` has zero call sites — dead code; a prior duplicate incident was cleaned up manually in migration `0169_hot_flatman.sql`). Any already-indexed page whose canonical form changes shape under the new rules (had tracking params, a trailing slash, or an uppercase host) will get a new hash on its next sync, landing as a **new row alongside the old, orphaned one** rather than updating it in place — this is a pre-existing architectural gap, not something introduced by this change, and fixing it would mean touching the sync/reconciliation layer, which is out of scope here. It's safe in the sense that `sourceUrl` is confirmed to be a pure display string with no exact-match lookups anywhere downstream, so old rows keep serving valid, clickable links — they just may appear as duplicates until a future sync/cleanup pass addresses that gap.
