## Summary

Implemented and validated. Here's the full picture.

### Files changed

| File | Change | Why |
|---|---|---|
| `platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts` | Split URL normalization into two functions; added tracking-param + trailing-slash rules | The literal ask |
| `platform/backend/src/database/migrations/0313_rekey_web_crawler_source_ids.sql` (+ journal/snapshot) | New data-only migration | Re-key already-indexed rows so they aren't orphaned by the normalization change |

**The connector change isn't a single edited function — it's a split**, driven by something the graph annotation flagged and the test suite then proved: `normalizeCrawlUrl` wasn't only a display/identity helper. It fed the *actual HTTP requests* (crawl seed, every enqueued link) and the *crawl-scope computation*. Adding trailing-slash/tracking-param stripping there broke 12 of 28 existing tests with real 404s — e.g. a start URL of `/docs/` normalized to `/docs`, so `buildAllowedPathPrefixes` (web-crawler-connector.ts:471) computed scope `/` instead of `/docs/` (crawl-scope broadened to the whole site), and the seed request 404'd against a server that only serves the slash form. So:

- `normalizeCrawlUrl` (web-crawler-connector.ts:613-624) stays conservative — hash-strip, default-port-strip, host-lowercase (this last one is a no-op today since `[expr]` already lowercases host for http/https by spec; kept explicit for clarity). Still used everywhere a URL gets *requested* or *scope-matched*: seed URLs (:131, :172), `createCrawler`'s `startUrl`/`allowedPathPrefixes` (:193-197), `validateParsedConfig` (:354-359), and `normalizeDiscoveredUrl` for every enqueued link (:573-585).
- New `normalizeDocumentUrl` (:631-638) wraps it and adds tracking-param stripping (via new `stripTrackingParams`, :644-654, using raw string splitting rather than `URLSearchParams` so untouched params keep their exact original encoding) and non-root trailing-slash removal. Used **only** by `normalizeCanonicalUrl` (:591-606), which is the sole source of `extractPage`'s `canonicalUrl` → `buildDocument`'s `id`/`sourceUrl`/`metadata.url` (:449-467). It never builds a URL that gets fetched.

**The migration** exists because `buildDocument`'s `id` (sha256 of `canonicalUrl`) is persisted as `kb_documents.source_id`, the key `connector-sync.ts:419` (`KbDocumentModel.findBySourceId`) uses to match existing rows on incremental sync — and that sync has no prune step. Without re-keying, the first sync after deploy would treat every affected page as new, insert a duplicate row, and search would return the page twice — that's a "not served correctly" outcome. This mirrors a precedent already in the repo (`0131_fix_agent_tool_trailing_underscores`, a SQL/TS slugify mismatch of the same shape). The migration only re-keys `source_id`/`source_url` for rows whose recomputed URL is unique within their connector (verified via `drizzle-kit check` and `check:migrations`, both clean); it does not execute against any database, per this repo's "no DB modifications without approval" policy — that's for the user to run via the normal `pnpm db:migrate` flow.

### Deliberately left unchanged (with proof)

- **`metadata.url` and `content_hash`** — not touched by the migration. Proof: nothing reads `metadata.url` (confirmed by search across backend and frontend); `connector-sync.ts:405-416` computes `content_hash` over `[expr]` together, so editing `metadata.url` here would desync it from `content_hash` exactly as a real re-crawl will do anyway on its own.
- **Pre-existing duplicate pairs** (pages already indexed twice under two old identities, e.g. with/without trailing slash) — left un-merged. Proof: `kb-document.ts:44-47`'s unique index on `[expr]` means collapsing them requires picking a surviving row and deleting the loser's chunks — a data-loss-capable decision needing human judgment, not something for an unattended migration.
- **`web-crawler-connector.test.ts`** — not modified, per explicit constraint. 5 assertions now fail as a direct, intended consequence of the trailing-slash rule: lines 163-166, 271, 317-318, 648, 667-668 all assert the old slash-preserving `sourceUrl`/`metadata.url` form. All other 23 tests pass; the 12 that were failing from the fetch/scope bug now pass after the function split.
- **Other connectors** (Confluence, Jira, etc.) — task scoped this to the web-crawler connector by name; confirmed no other connector shares this URL-normalization code path.

### Residual risk

- Migration is hand-verified (Node.js reference semantics for the TS side, careful SQL derivation, passing linter) but not executed end-to-end against a live/seeded database — recommend running it in staging first.
- The 5 test assertions above need updating for a fully green suite; left as-is per constraints.
- Pre-existing duplicate content isn't auto-collapsed; needs manual follow-up if desired.
- One-time extra re-chunk/re-embed for migrated pages on their next real crawl (since `content_hash` is deliberately left untouched) — self-resolving, not a correctness issue.
- SQL `sha256(…)` assumes UTF8 server encoding, matching Node's default — not independently verified against the deployed DB's encoding.
