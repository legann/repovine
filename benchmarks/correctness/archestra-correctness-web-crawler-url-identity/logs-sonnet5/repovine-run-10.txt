### The connector change, and why it's split in two

I initially put all four normalizations into `normalizeCrawlUrl`. That broke the existing test suite: `normalizeCrawlUrl` isn't only used for document identity — it also builds the actual HTTP request URLs (crawl seed: lines 129, 170, 191, 352; discovered links via `normalizeDiscoveredUrl`, line 585). Stripping a trailing slash before the fetch changed what got requested: origin servers can route `/docs` and `/docs/` to different resources, so pages 404'd, and `buildAllowedPathPrefixes` (lines 471–483) infers crawl scope from whether the start path ends in `/` — feeding it a stripped path flipped a directory-scoped crawl (`[expr]`) into "file's parent directory," i.e. scope widened to the whole host.

So the final shape:
- `normalizeCrawlUrl` (line 608): unchanged hash-strip + default-port-strip, plus an explicit `url.hostname.toLowerCase()` (line 611). Still used for every request-target URL. Host-lowercasing is technically redundant — I confirmed `[expr]` already lowercases per WHATWG parsing — but harmless everywhere and it's what the task asked for, so I kept it explicit.
- `canonicalizeForIdentity` (line 625, new): strips the 7 tracking params and one trailing slash on non-root paths. Wired in *only* at line 382, wrapping `normalizeCanonicalUrl(…)` inside `extractPage` — i.e. only the value that becomes `buildDocument`'s `id`/`sourceUrl`/`metadata.url` (line 449–455), never a fetch target.

### The migration, and why it exists

`buildDocument` hashes the canonical URL into `id`; `connector-sync.ts` persists that hash once as `kb_documents.source_id` and matches on it every sync via `findBySourceId`, with no prune step. Changing the hash's derivation means any already-indexed page with a tracking param or trailing slash would hash differently on its next crawl — the old row goes stale forever, a duplicate gets inserted, search returns both. That's exactly what "every document already indexed... must continue to be served correctly" rules out.

The migration recomputes `source_id`/`source_url`/`metadata.url` for existing `web_crawler` documents using the same two transforms, skipping host-case/port since those were already applied when the rows were first written. It's guarded against two collision cases (two existing rows converging on the same new identity; a new identity colliding with another untouched row) — affected rows are left as-is rather than the migration erroring out.

On using `sha256()` in SQL: a same-shape precedent (`0276_squash_skill_sandbox_and_versioning.sql:110-114`) explicitly calls hash-reproduction in SQL "impractical... across pg/PGlite" and falls back to a sentinel instead. I checked rather than assumed — spun up a disposable Postgres 16 container and confirmed core `sha256(…)` (no `pgcrypto`) byte-matches Node's `crypto.createHash(…)`, and validated the full path/query transform logic against 11 cases matching a Node reference implementation exactly, plus the collision guards, in the same disposable container. It's also now exercised for real: PGlite replays every migration file before each backend test run, and 741 tests across `knowledge-base/` + `kb-document.test.ts` passed with zero migration errors.
