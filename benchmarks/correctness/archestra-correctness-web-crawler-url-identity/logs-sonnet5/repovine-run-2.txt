### Why the trailing-slash rule was dropped

I implemented it initially, then ran the connector's existing test suite (`web-crawler-connector.test.ts`, which I did not modify, per the constraint) and it broke **17 of 28 tests**. Bisecting confirmed trailing-slash stripping was the sole cause (removing just that one block: 28/28 pass). Root cause, proven two ways:

1. **It changes what's actually fetched.** `normalizeCrawlUrl` seeds the crawl (`crawler.run(…)`) and builds discovered links (`normalizeDiscoveredUrl`). The test's mock HTTP server does exact-path lookup with no directory-redirect emulation (`web-crawler-connector.test.ts:724-731`: `[expr]`, 404 otherwise) — stripping `/docs/` to `/docs` 404s. Real servers that don't auto-redirect bare directory paths would fail the same way.
2. **It changes stored document identity, which 4 independent tests pin to the un-stripped form**, across all three branches of `normalizeCanonicalUrl`:
   - explicit valid canonical tag: `web-crawler-connector.test.ts:163-180` (asserts `sourceUrl`, `metadata.url`, and `doc.id`'s sha256 all equal the `.../docs/install/` form, slash intact)
   - cross-origin canonical → fallback: `:297-319`
   - malformed canonical → fallback: `:651-669`
   - no canonical tag → fallback: `:629-649`

   There's no branch of the identity computation left to apply the rule to without breaking one of these. This isn't a test-suite artifact — the same mechanism (servers that don't redirect bare directory paths) is a real production risk, not a hypothetical.

Given "do not modify tests" is an explicit constraint, I could not resolve this by updating the four assertions. I flagged rather than silently dropped it: **if you want this rule, those 4 assertions need to change to expect the stripped form** — happy to do that as a follow-up once you confirm tests may be touched.

### Backward compatibility for already-indexed documents

`kb_documents.source_id` is `sha256(…)`, written once at ingest and never re-derived (confirmed via the module's repovine annotation and `connector-sync.ts:393-422`'s `findBySourceId` match-by-`[expr]` logic, backed by a unique index on exactly those two columns). Since I only shipped tracking-param-stripping and host-lowercasing:
- **Host lowercasing is a no-op against existing data** — verified empirically that `[expr]` already lowercases the ASCII host at parse time, so old `source_id`s already reflect it.
- **Tracking-param stripping is the only real delta.** A previously-indexed page whose canonical URL carried a `[expr]`/`gclid`/`fbclid` param will get a new `source_id` on its next crawl, and since `connector-sync` has no prune step, that inserts a new row alongside the old one (duplicate search hit; old row goes stale) rather than updating in place.

I deliberately did not author a data migration to re-key affected `source_id`s in this change. This repo pairs backfills of comparable complexity with a dedicated migration test (e.g. `0290_backfill_artifact_files.sql` + `.test.ts`, `0299_backfill_orphaned_schedule_projects.sql` + `.test.ts`), which the task's constraints forbid me from adding; the migration would also need to enable `pgcrypto` (no precedent in this repo's ~312 migrations) for SQL-side SHA-256 hashing. Given a wrong migration is worse than none (could permanently misalign a `source_id`), I'm surfacing this rather than shipping something untested. **Nothing about already-indexed documents breaks today** — existing rows and their chunks are untouched and fully searchable; the only effect is on the *next* crawl of a page whose URL has tracking params.
