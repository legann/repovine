## Files changed

**`platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts`** — the only file touched, as scoped.

- Added a `TRACKING_QUERY_PARAMS` constant (`utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`, `gclid`, `fbclid`).
- `normalizeCrawlUrl` now also lowercases the host and strips those tracking params, in addition to the existing hash-strip and default-port-strip.
- Added `normalizeDocumentUrl`, which wraps `normalizeCrawlUrl` and additionally removes a trailing slash on non-root paths.
- `normalizeCanonicalUrl` (which produces `doc.id`/`sourceUrl`/`metadata.url`) now calls `normalizeDocumentUrl` instead of `normalizeCrawlUrl` at its three return points.

### Why two functions instead of one

I traced every call site of `normalizeCrawlUrl` before touching it. Two are the actual HTTP fetch targets: the crawl seed URL (`[expr]`) and discovered links passed to `context.enqueueLinks` (`:583`, via `normalizeDiscoveredUrl`). The test fixtures (`web-crawler-connector.test.ts`) back this with a mock server that does exact-string pathname routing and no redirects (`createTestSite`, test.ts:722-725: `[expr]`, 404 on miss). Stripping a trailing slash from those URLs would turn `GET /docs/` into `GET /docs`, which 404s in that harness and would equally 404 against any real origin that doesn't redirect a bare path to its directory form — i.e., pages the connector successfully indexes today would stop being crawled at all. That's a strictly worse outcome than a cosmetic identity-string change, so trailing-slash stripping is isolated to `normalizeDocumentUrl`, used only for the stored identity (`doc.id`/`sourceUrl`/`metadata.url`), never for a URL Crawlee will request. Host-lowercasing and tracking-param-stripping don't have this problem (routing never depends on them), so those stay in the shared `normalizeCrawlUrl` and benefit both fetch-target dedup and identity.

## Related code paths deliberately left unchanged, with proof

- **`buildAllowedPathPrefixes` (`:469-482`)** — derives the implicit crawl-scope prefix from whether the start URL's path ends in `/` (a trailing slash means "restrict to this directory"; no slash means "restrict to the parent directory"). My first draft fed the trailing-slash-stripped URL into this function and it silently widened scope — e.g. a crawl configured for `https://example.com/docs/` would expand to the whole origin, since `/docs` (stripped) has no directory component left to anchor on. I confirmed this is exactly what test `"scopes the crawl to the start URL's directory when it is a file"` (test.ts:570-592) guards against. Because `normalizeCrawlUrl` (which still feeds this function at `:191` and `:352`) no longer touches trailing slashes, this path needed no code change — but it's the reason the two-function split exists rather than one shared normalizer.
- **`isPathInScope` / `pathMatchesPrefix` (`:544-569`)** — matches a candidate path against a prefix by stripping *the prefix's own* trailing slash before comparing (`:565`). This already tolerates either form on the candidate side, so it's unaffected by anything here and needed no change.

## Behavior change

`doc.id`/`sourceUrl` now canonicalize trailing slash, tracking params, and host case; every URL Crawlee actually requests is unchanged except for tracking-param/host-case normalization (both routing-inert). Only this one file changed.

**Residual risk (the main one):** `doc.id` is `sha256(…)`, used as the upsert key (`connectorId`, `sourceId`) in `connector-sync.ts`. For a page already indexed whose stored canonical form had a trailing slash, tracking params, or mixed-case host, the *next* sync computes a different `id` for the same logical page. `findBySourceId` will miss, so `ingestDocument` inserts a new row instead of updating the old one (create branch at connector-sync.ts:501-512). There's no stale-document pruning anywhere in the sync path (confirmed by reading all of `connector-sync.ts`), so the old row isn't deleted — it stays fully valid and servable (still searchable, still a working citation link), just duplicated alongside the new one until someone deletes it manually or runs `force-resync` (`deleteByConnector`, routes/knowledge-base.ts:1073-1082). So already-indexed documents keep being served correctly (nothing breaks or disappears), but expect one-time duplicate KB entries for affected pages on their first post-upgrade resync. Fixing that fully would require either a backfill migration or dedup-by-`sourceUrl` logic in the shared sync engine — both outside this task's file scope.

**Minor risk:** an `excludePathPatterns` regex anchored on a tracking param or trailing slash would stop matching once those are stripped before the check (`isPathInScope`, `:544-561`). Low-probability, and a direct consequence of the requested canonicalization rather than a bug.

**Test impact:** I couldn't run the suite (this worktree is intentionally not bootstrapped — installs/builds/tests are blocked), so I traced all 28 tests in `web-crawler-connector.test.ts` by hand against the new logic. 23 pass unaffected (scope enforcement, SSRF/redirect checks, batching, config validation, content extraction, skip/failure handling all use raw request URLs or paths untouched by this change). 5 tests assert an exact `sourceUrl`/`metadata.url`/`doc.id` value for a directory-style page (e.g. `[expr]`) and will now fail because they hardcode the pre-change (trailing-slash-preserved) canonical form — the direct, intended consequence of the requested normalization. Per the task constraint I left the test file untouched.
