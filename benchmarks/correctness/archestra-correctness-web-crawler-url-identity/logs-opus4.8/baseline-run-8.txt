## What changed

The crawler now treats trivially-different URLs as one page. I added a canonical form — tracking params stripped, trailing slash removed on non-root paths, host lowercased, default port dropped — and used it as the **request dedupe key**, so `[expr]`, `[expr]`, and `https://example.com/docs` all resolve to a single fetch and a single document.

I deliberately did **not** rewrite the URL the crawler requests and stores. That distinction is what keeps already-indexed documents working, and it's the main thing worth reviewing.

## Files changed

Only `platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts`:

- **`TRACKING_QUERY_PARAMS`** (new constant) — the six utm params plus `gclid`/`fbclid`.
- **`canonicalizeCrawlUrl()`** (new) — builds on `normalizeCrawlUrl` and applies all four rules. Host-lowercasing and default-port dropping already fall out of WHATWG `[expr]` parsing, so the existing port branch is retained and the host needs no extra code; I noted that in a comment rather than writing a no-op `toLowerCase()`.
- **`buildCrawlRequest()`** (new) + the two `crawler.run(…)` seeds — the start URL is fetched exactly as configured, but keyed canonically.
- **`enqueueAllowedLinks()`** — passes `transformRequestFunction` so each discovered link gets its canonical `uniqueKey`.

I verified the pure normalization standalone with `node` (this worktree has no `node_modules`; `pnpm`/`tsc` are stubs that exit 127, so builds, typechecks, and tests cannot run here). Variant groups collapse to one key, the root `/` keeps its slash, non-tracking params like `[expr]` survive, and the function is idempotent.

## Why the stored URL is untouched

`buildDocument` derives the document id from the canonical URL — `[expr]` at `web-crawler-connector.ts:461`, and `sourceUrl: [expr]` at `:466`. That id **is the upsert key**: `connector-sync.ts:419-421` looks up the existing row by `[expr]`, against a unique index on that pair (`database/schemas/kb-document.ts:44`).

Nothing prunes a document that stops appearing in a crawl. `executeSync` has no delete path, and the only `KbDocumentModel.deleteByConnector` call is connector deletion (`routes/knowledge-base.ts:1074`). So if the canonical URL changes, every page re-keys, a fresh row is inserted, and the old row survives forever — still chunked, still embedded, still returned by `queryService.query`. Since a trailing slash is the common case (`/docs/`), a literal rewrite would have orphaned most of the existing index as stale duplicates. Keying the *request* instead of the *document* gets the dedupe with zero re-keying.

This is also what the pinned tests encode: `web-crawler-connector.test.ts:163-166` expects `sourceUrl` of `/docs/` and `/docs/install/`, and `:178-180` expects `[expr]`. Independently, the test server matches `pathname` exactly (`:724-731`), so requesting `/docs` for a start URL of `/docs/` would 404 — which mirrors the real-world hazard that `/docs` and `/docs/` are distinct HTTP resources and only *some* servers redirect between them.

## Residual risk

**`transformRequestFunction` and `uniqueKey` are unverified against the installed types.** Both are long-standing public Crawlee APIs and `@crawlee/cheerio` is pinned at `3.14.1`, but I could not typecheck. This is the one thing to confirm on a bootstrapped checkout.

**Dedupe strands the loser.** If a site links both `/a` and `[expr]`, that page previously produced two documents; now it produces one. The surviving document keeps its id, but the other row is never pruned and will serve stale content. That's inherent to any dedupe here, not to this implementation.

**The stored URL is the first-reached variant.** If a page is *only* ever linked with a tracking parameter, the citation URL retains it. Canonicalizing stored URLs is a reasonable follow-up, but it re-keys documents and therefore needs a backfill migration over `kb_documents.source_url` → `source_id` (with collision collapsing) — a data change well outside a normalization patch, and one I couldn't pair with a migration test under the no-tests constraint.

**Crawlee may already normalize `uniqueKey` by default.** Setting it explicitly makes the connector's dedupe independent of that, and is idempotent if the defaults happen to agree.

**`maxRequestsPerCrawl` now counts fewer requests**, so a crawl that previously hit the page cap on duplicates may now reach deeper pages. Intended, but it is a visible change in what gets indexed.
