## Summary

I strengthened the web crawler's URL normalization and — critically — reconciled the identities already persisted from the old normalization, so no already-indexed document is duplicated or lost.

The repovine annotation on `web-crawler-connector` was the key: `normalizeCrawlUrl` is the identity chokepoint, `kb_documents.source_id` is its persisted form (written once, never re-derived), and connector-sync has **no prune** — so changing normalization alone would insert a second row per page on the next sync and return both from search. The re-key had to reuse the live normalizer (not reimplement it in SQL) to avoid the exact SQL/TS drift that migration `0131` existed to fix.

## 1. Files changed

**`backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts`**
- Added `TRACKING_QUERY_PARAMS` (utm_source/medium/campaign/term/content, gclid, fbclid).
- `normalizeCrawlUrl` (`:614`) now also lowercases the host and strips tracking params, keeping the existing default-port stripping. It does **not** strip trailing slashes — this function drives what gets **fetched** (start URL `:131/:172/:193`, discovered links `:585`) and the crawl scope, so it must request the exact path a server publishes (a page served only at `/x/` must not be fetched as `/x`).
- New exported `canonicalizeDocumentUrl` (`:643`) = `normalizeCrawlUrl` + trailing-slash removal on non-root paths. This is the **document identity**: `normalizeCanonicalUrl` (`:591`) now routes through it, so `buildDocument`'s id/`sourceUrl`/`metadata.url` collapse `/x` and `/x/` (and tracking-param variants) to one document.

**`backend/src/database/seed.ts`**
- Added `renormalizeWebCrawlerDocumentIdentities()` (`:778`), invoked from `seedRequiredStartingData()` (`:1002`, run at boot after migrations). It re-keys `source_id`/`source_url` for `[expr]` rows using the same `canonicalizeDocumentUrl`, and collapses rows that now share a canonical URL (keeping the already-canonical row, else the oldest; losers deleted, chunks cascade). Idempotent.
- This is a **code** backfill, not SQL, because `[expr]` and `pgcrypto`/`digest()` is unavailable in the PGlite test DB (I verified empirically) — the repo itself documents sha256-in-SQL as impractical (`[expr]`). It follows the established `migrateSecretsToEncrypted` precedent (`seed.ts:739`): an idempotent startup transform of stored rows using JS crypto.

## 3. Behavior change & residual risk

**Behavior:** trivially-different URLs (tracking params, host case, default port, trailing slash) now canonicalize to one document identity; crawl fetching and scope are unchanged. On the next sync after deploy, the startup re-key has already aligned every stored `source_id` with the new normalizer and merged pre-existing duplicates, so each page maps to exactly one row.

**Verification:** I could not run the repo's `tsc`/test suite (this worktree has no installed `node_modules`); I verified by inspection and an isolated Node harness (17/17 checks) covering the four rules, root/port edge cases, `/x`≡`/x/` and utm-variant collapse, idempotency, and the re-key⇔next-sync-output equivalence that guarantees in-place updates.

**Residual risk:**
- **Pinned test assertions change.** `web-crawler-connector.test.ts` asserts the *old* identity with trailing slashes (`:163-166`, `:172-180`, `:271`, `:317-318`, `:648`, `:667-668`). The new canonicalization legitimately changes those `sourceUrl`/`id`/`metadata.url` outputs; per the "do not modify tests" constraint I left them untouched, so those assertions need the test owner to update to the slash-stripped URLs. Crawl-behavior assertions (titles, counts, scope, skips) are unaffected because fetching is unchanged.
- A page linked as both `/x` and `/x/` may be fetched twice in one crawl (deduped at storage) — harmless extra request.
- The backfill scans all web-crawler `kb_documents` in one transaction each boot (no-op once canonical), matching `migrateSecretsToEncrypted`'s whole-table pattern; very large deployments would see a large one-time transaction.
