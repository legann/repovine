## What changed

**One file:** `platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts`

I added `buildRequestDedupeKey()` — strips the seven tracking params, sorts the query, removes a trailing slash on non-root paths, and relies on the URL parser for lowercase host + default-port stripping — and wired it in as crawlee's `uniqueKey` on **every** request: the seed (`buildSeedRequest`, used by both `sync` and `testConnection`) and discovered links (`transformRequestFunction` in `enqueueAllowedLinks`).

The important design decision: **the strengthened normalization is applied to the key the crawler compares by, not to the URL it fetches or stores.** That is forced by the constraint you gave, and I want to be explicit that it means I did *not* rewrite `normalizeCrawlUrl`'s output.

## Why not just strengthen `normalizeCrawlUrl`

Its return value is simultaneously (a) the URL that gets fetched and (b) the document's identity. Three independent things break if you canonicalize it:

1. **Every already-indexed document is orphaned.** `[expr]` (`web-crawler-connector.ts:463`) is the `sourceId` that `connector-sync.ts:419-421` looks up via `findBySourceId`. Change the string, and the next sync misses every existing row and inserts a duplicate. Nothing cleans up: `KbDocumentModel.deleteByConnectorAndSourceId` (`models/kb-document.ts:332`) has **zero callers**, and rows are only ever removed wholesale by `deleteByConnector` (`models/kb-document.ts:324`, called from `routes/knowledge-base.ts:1074` on connector deletion). The old row keeps its chunks and keeps being served (`[expr]` join straight onto `kb_documents`), so you'd get each page twice — once stale, forever. The unique index on `[expr]` (`database/schemas/kb-document.ts:44-47`) confirms `source_id` *is* the identity.
2. **The crawl scope silently widens.** `buildAllowedPathPrefixes` reads the start URL's trailing slash (`web-crawler-connector.ts:487-491`): `/docs/` yields prefix `/docs/`, but `/docs` falls through to `path.slice(…)` → `/`. Stripping the slash from the start URL turns a docs-scoped crawl into a whole-origin crawl, pulling out-of-scope pages into an ACL'd knowledge base.
3. **`/a` and `/a/` are different resources.** Per RFC 3986 they are distinct targets; the equivalence is a site convention. Rewriting a URL you are about to `GET` risks a 404 on hosts that don't redirect, and costs an extra 301 on those that do.

A dedupe key has none of these properties — it is never requested and never persisted — so it can canonicalize freely.

## Behavior change and residual risk

Verified against real `URL`: `[expr]` and `https://ex.com/docs/guide` now collapse to one queue entry, so the page is fetched and indexed once. Previously crawlee's built-in key (`@apify/utilities.normalizeUrl` — it strips `[expr]` but *not* `gclid`/`fbclid`) left three entries. I also checked the key is a strict superset of crawlee's merging, so nothing that used to dedupe now splits. Every URL the existing tests pin (`/docs/`, `/docs/install/`, `/docs/dest/`) keeps a byte-identical `sourceUrl` and `doc.id`.

Two residual risks worth naming:

- **`sourceUrl` is not itself canonicalized.** If a tracking-tagged link is discovered before the clean one, the document is still stored under `[expr]`. Whichever variant wins is now stable within a sync, but the winner can differ *across* syncs depending on link order — which re-keys the document and orphans the old row. That flapping predates this change and this change doesn't fix it. Fixing it properly means canonicalizing `sourceUrl` **plus** a data migration that recomputes `source_id` from `source_url` for `web_crawler` documents and resolves the collisions the unique index would otherwise reject. That's a separate, migration-bearing change; I did not fold it in.
- **I did not run the test suite.** This worktree has no `node_modules` and installs are blocked. I verified the normalization logic by executing it directly on Node's `URL`, and verified the crawlee wiring by reading the installed `@crawlee/core@3.14.1` sources (`request.js:213` honors an explicit `uniqueKey`; `enqueue_links/shared.js:140-150` preserves it through `createRequests`; `RequestTransform` is a single-signature interface, so `ReadonlyDeep` passes it through unchanged). The type-level claims are read, not compiled.
