**Design decision — canonicalization is identity-only, not applied to fetched URLs.** `normalizeCrawlUrl` feeds the crawl **seed** (`:132`, `:173`), scope derivation (`:194`, `:355`), and discovered links (`:586`). Stripping a trailing slash there would change what gets *fetched* — a directory seed `/docs/` requested as `/docs` 404s on many origins — and would widen crawl scope, since `buildAllowedPathPrefixes` derives scope from the seed's trailing slash (`:481`, `[expr]`). So trailing-slash/tracking stripping lives in `canonicalizeDocumentUrl`, which runs *after* fetch on the canonical/loaded URL that becomes the stored identity. Host-lowercasing is safe everywhere (case-insensitive), so it sits in the base `normalizeCrawlUrl`.

**Migration correctness.** It re-derives `source_url` with the *same* transforms and recomputes `[expr]` (core `sha256()`, so it works under PGlite where the test suite applies migrations — `pgcrypto`'s `digest()` is unavailable there). It uses the repo's survivor/loser dedup idiom (migration 0285) for URLs that now collapse together; losers' `kb_chunks` cascade (`kb-chunk.ts:44`). I verified in Node that `canonicalizeDocumentUrl(…)` equals `sqlTransform(…)` **byte-for-byte** (and sha256-hex-equal) across 14 cases incl. `[expr]`-encoded values, uppercase host, `UTM_SOURCE`, root paths, and default ports — this parity is what prevents new duplicates.
