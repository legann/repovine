## 1. The patch

The strengthened normalization lives in `platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts`, applied to the **crawl-frontier de-duplication key**, not to the stored-identity normalizer. Concretely:

- `TRACKING_QUERY_PARAMS` set — the 7 params from the task (`utm_source/medium/campaign/term/content`, `gclid`, `fbclid`) — `web-crawler-connector.ts:52-60`.
- `canonicalizeCrawlKey(…)` — `:645-656`. On top of `normalizeCrawlUrl`'s fragment + default-port stripping it: lowercases host, deletes tracking params, sorts remaining params (folds query order), and strips a trailing slash on non-root paths (`[expr]`).
- Wired as the Crawlee request `uniqueKey` at all three frontier entry points: `testConnection` start (`:132-137`), `sync` start (`:178-183`), and discovered links via `transformRequestFunction` in `enqueueAllowedLinks` (`:437-447`).

**Why this shape and not editing `normalizeCrawlUrl` directly** — the connector's normalized URL is a *persisted identity*, and the task's hard constraint ("every already-indexed document must continue to be served correctly") makes the naive edit incorrect:

- `buildDocument` derives `[expr]` and `[expr]` (`:473-478`); `canonicalUrl` comes from `normalizeCanonicalUrl` → `normalizeCrawlUrl` (`:609-624`).
- `connector-sync.ts` persists that as `kb_documents.source_id` (`sourceId: doc.id`, `connector-sync.ts:504`) and matches existing rows only by `[expr]` via `findBySourceId` (`connector-sync.ts:419-421`).
- There is **no prune**: the only delete is `KbChunkModel.deleteByDocument` on the content-changed update path (`connector-sync.ts:479`); stale rows are never removed.

So changing `normalizeCrawlUrl` would re-key `source_id` for every already-indexed page → on the next sync each page is inserted as a new row while the old row stays → kb search (`search_vector @@ tsquery` over all rows) returns the page twice. Strengthening only the `uniqueKey` collapses trivially-different links to one crawl target while leaving the stored identity byte-identical, so existing `source_id`s still match.

## 3. Summary, behavior change, residual risk

**Behavior:** Within a crawl, links to the same page differing only by tracking params, query-param order, a non-root trailing slash, or host case now collapse to a single fetch/target (previously each variant was fetched and could be stored as a separate document). Stored document identities (`kb_documents.source_id`) are unchanged, so every previously-indexed page is still found and served on the next sync — no duplicates, no migration.

**Files touched (high level):** one connector module (`web-crawler-connector.ts`); no schema, no migration, no tests, no other modules.

**Residual risk:**
- The strengthened folding is **dedup-only**. Stored `source_id`s are deliberately not re-canonicalized, so a page can still acquire a second row if, *across* syncs, a different trivially-variant URL becomes the first-fetched one **and** the page has no `[expr]` (which `normalizeCanonicalUrl` would otherwise pin). Eliminating that fully would require re-keying existing `source_id`s via a data migration (the `0131_fix_agent_tool_trailing_underscores` pattern) — heavier, mutates stored data, and risks unique-key collisions; the constraint here steers away from it.
- `canonicalizeCrawlKey` assumes the listed tracking params are non-content (standard); a site that served different content keyed on, e.g., `utm_content` would have variants deduped to one fetch. This is the intended trade-off of frontier dedup.
- Test note: the suite needs `ARCHESTRA_DATABASE_URL` present at import time (`config.ts:993`); this fresh worktree has no `.env`, so I set a dummy value to let the PGlite-backed setup run — a local env detail, not a code change.
