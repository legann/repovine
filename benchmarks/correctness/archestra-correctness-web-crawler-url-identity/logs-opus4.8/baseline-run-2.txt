## Outcome

All four normalization rules are implemented in one file, and no already-indexed document changes identity. The interesting part of this task turned out to be that the obvious implementation of two of the four rules silently re-keys the entire existing index.

**File changed:** `platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts` (only file).

## Why the naive patch is unsafe

A crawled document's id is `sha256(…)` (`web-crawler-connector.ts:464`), and that id lands in `kb_documents.source_id`, which is how sync matches a page to its existing row (`connector-sync.ts:419`) under a unique index on `[expr]` (`database/schemas/kb-document.ts:44`). When a lookup misses, sync inserts a new row (`connector-sync.ts:502`). Nothing ever prunes a row that stops appearing — the only deletion path is the manual force-resync endpoint (`routes/knowledge-base.ts:1074`). So **any change to the normalized canonical string leaves the old row behind forever, with stale content, still retrievable alongside the new one.** That is what "must continue to be served correctly" rules out.

Two concrete traps followed from that, both of which I confirmed by running the real URL semantics under Node:

**`searchParams.delete()` rewrites queries it doesn't match.** Calling it unconditionally re-serializes the whole query string even when no tracking parameter is present: `[expr]` becomes `[expr]`, `[expr]` becomes `[expr]`, and a bare `[expr]` is dropped. That would re-key every already-indexed URL carrying any query string at all. The patch guards each delete behind `has()`, so an untracked URL is never touched.

**Stripping the trailing slash inside `normalizeCrawlUrl` would widen the crawl scope to the whole host.** `normalizeCrawlUrl` feeds the start URL into `buildAllowedPathPrefixes`, which branches on `path.endsWith(…)` (`web-crawler-connector.ts:489`). Given `/guide` instead of `/guide/` it returns `[expr]`, and `pathMatchesPrefix` accepts everything when the prefix is `/` (`web-crawler-connector.ts:575`). A connector scoped to `https://site/guide/` would begin crawling the entire origin. The same rule would also re-key every directory-style document and change the URL actually fetched, which an origin is free to 404.

So trailing-slash equivalence is implemented where it belongs: as a **scheduling key** (`pageDedupKey`) that collapses `/docs` and `/docs/` to one visit, while the URL that gets fetched, scoped, and stored keeps its original path. Tracking-parameter stripping and host lowercasing are safe on the fetch path and live in `normalizeCrawlUrl`. Host lowercasing is already guaranteed by WHATWG `[expr]`; the explicit assignment makes the invariant local to the function and is a no-op, so it causes no id churn.

## Residual risk

A page whose *only* inbound link carried a tracking parameter was previously indexed under that dirty URL. It will now be indexed under the clean URL, and the old row will linger as a stale duplicate. This affects only URLs that already contained `[expr]`, `gclid`, or `fbclid`; clean URLs are bit-for-bit unchanged. `POST /api/connectors/:id/force-resync` (`routes/knowledge-base.ts:1039`) is the remediation if an operator wants those swept.

Second, `excludePathPatterns` are matched against `[expr]` (`web-crawler-connector.ts:570`). A pattern written to exclude URLs *by* a tracking parameter will no longer match, since the parameter is gone by then. This seems like the intended direction, but it is a behavior change.

Third, `/docs` and `/docs/` are now assumed to be the same page. That is what was asked for, and it is true of essentially every real site, but an origin that serves genuinely different content at the two paths would now have only one of them indexed.
