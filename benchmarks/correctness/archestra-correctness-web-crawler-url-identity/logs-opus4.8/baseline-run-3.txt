## What I changed and why

**`platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts`** (only file touched)

The key insight is that `normalizeCrawlUrl` had **two jobs**, and the four requested rules don't all belong to both:

- It produces the URL the crawler **dereferences** (`crawler.run`, enqueued links).
- It produces the URL that becomes the document's `sourceUrl`, `metadata.url`, and — via hash function at `web-crawler-connector.ts` — the document `id`, stored as `kb_documents.sourceId`.

So I split the concerns:

- **`normalizeCrawlUrl`** (fetched + stored + hashed form) now also strips the tracking parameters. It keeps trailing slashes, because `/a` and `/a/` can be different resources and this URL is always dereferenced. Host lowercasing and default-port stripping are already done by `new URL` for http(s) — I documented that rather than writing a no-op `[expr]`.
- **`pageIdentityKey`** (new) folds the trailing slash on non-root paths and is used solely as Crawlee's request-queue `uniqueKey`, wired in at the start request and via `enqueueLinks`'s `transformRequestFunction`. It's never dereferenced, so folding a slash there is safe.

## Why existing documents keep working

Document identity is `sha256(…)`, looked up by `[expr]` (`connector-sync.ts:419`). There is **no stale-document reconciliation** — deletion only happens for a whole connector (`routes/knowledge-base.ts:1074`) or one document by hand (`:758`). Any change to the hashed URL therefore orphans the old row permanently rather than updating it. That drove two decisions:

1. Trailing-slash removal is kept out of the hashed URL. The existing tests independently pin this — `web-crawler-connector.test.ts:178` asserts `[expr]`, slash included, and `:163` pins the `sourceUrl`s.
2. `stripTrackingQueryParams` rewrites the query **only when a tracking param is actually present**. Two traps I found and verified by execution: `URLSearchParams.delete()` re-encodes the *whole* query even for an absent key (`[expr]` → `[expr]`), and a naive empty-pair filter rewrites `[expr]`. Either would have silently re-keyed clean, already-indexed documents.

## Deliberately left unchanged

- **`metadata.fetchedUrl`** (`web-crawler-connector.ts:453`) still records the raw fetched URL. It's provenance, not identity, and `web-crawler-connector.test.ts:176` pins it to the un-normalized `/docs/install.html`.
- **`normalizeCanonicalUrl`'s cross-origin fallback** (`:588`) and the `beforeRedirect` scope checks (`:233`, `:239`) compare `origin` / raw `search`. Origins are already lowercased by `new URL`, and those checks are security boundaries, not dedup.
- **Other connectors** — `registry.ts:34` is the only construction site for `WebCrawlerConnector`; these helpers are module-private and unexported, so nothing else can observe them.

## Residual risk

- A page whose **only** inbound link carried a tracking param was indexed under a dirty URL; it now re-keys to the clean URL, creating a new row and orphaning the old one. This is inherent to the requested dedup — you can't both strip tracking params from document URLs and preserve IDs of documents that had them. Documents without tracking params are byte-identical, which is the case I protected.
- `TRACKING_QUERY_PARAMS` matches param names case-sensitively, so `[expr]` is not stripped. Real-world usage is lowercase; broadening it would widen the re-keying blast radius.
- An `excludePathPatterns` regex written to match a tracking param (patterns test `[expr]`, `:550`) will no longer match, since the param is stripped before the scope check.
- `pageIdentityKey` now owns page-identity semantics that Crawlee's `Request.computeUniqueKey` previously supplied. That's deliberate — it was an `@internal` API — but it means a future Crawlee upgrade won't fix or change this behavior for us either way.

I used a sibling worktree's `node_modules` to run the tests (this worktree had none) and removed the symlinks afterward; both worktrees are clean apart from the intended file.
