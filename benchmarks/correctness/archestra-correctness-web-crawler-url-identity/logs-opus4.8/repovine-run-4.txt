## 1. What changed and why

Two files. The URL normalizer is one contract with the identities it has already persisted (`kb_documents.source_id`, unique per connector, written once, never re-derived; connector-sync has no prune). Strengthening the normalizer alone is incomplete: the first sync afterward would insert a duplicate row for every URL whose normalization changed, and kb search would return both the stale and the new row. So the change is normalizer + a reconciliation of existing rows.

**`platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts`**
- `normalizeCrawlUrl` (the fetch/scope/enqueue/identity base) now **lowercases the host** and **strips tracking params** (`utm_source/medium/campaign/term/content`, `gclid`, `fbclid`), on top of the existing hash-clear and **default-port stripping** (kept).
- The **trailing-slash removal** lives in a new `normalizeDocumentIdentityUrl`, applied only to the stored **document identity** (via the exported `deriveWebCrawlerDocumentIdentity`, which `buildDocument` now uses). It is deliberately *not* in `normalizeCrawlUrl`: fetched/enqueued/scoped URLs must keep their trailing slash — the test harness exact-matches routes (`web-crawler-connector.test.ts:725`, `[expr]`), so stripping the entry URL's slash would 404 the crawl, and `buildAllowedPathPrefixes` derives the scope prefix from `[expr]` (connector `.ts:468`). Identity-level stripping still collapses `/p` and `/p/` to one document, which is the task's goal.

**`platform/backend/src/database/seed.ts`**
- New `migrateWebCrawlerDocumentSourceIds()`, wired into `seedRequiredStartingData` next to the existing data migrations. It re-derives each web-crawler document's identity from its stored `source_url` with the connector's own normalizer, de-duplicates rows that now collapse to one identity (keep freshest, delete the rest — `kb_chunks` cascade on delete, `schemas/kb-chunk.ts:44`), and re-keys survivors. In a transaction, idempotent, count-logged — mirroring `migrateSecretsToEncrypted` (`seed.ts:739`).

Why a startup backfill and **not** a SQL migration: `[expr]` is computed in app code. The PGlite test harness loads only the `vector` extension (`test/global-setup.ts:33`, `test/setup.ts:88`), and it replays every migration to build the shared snapshot — a `pgcrypto`/`digest()` migration would fail there and break the whole backend suite. `0276_squash_skill_sandbox_and_versioning.sql:111` records that app-code hashing is "impractical" in SQL. `seed.ts` is the established in-repo path for reconciliations SQL can't express (`migrateSecretsToEncrypted` re-writes stored values with app-code crypto); it runs only at server boot (`server.ts:955`), never in tests.
