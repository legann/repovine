## What changed

`platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts` — the only file touched.

The important discovery is that `normalizeCrawlUrl` was doing two different jobs at once. It produced **the URL the crawler fetches and scopes against** (seed at `:129`/`:170`, scope base at `:191`/`:352`, discovered links at `:583`) *and* **the URL that becomes a document's identity** (via `normalizeCanonicalUrl` → `sha256` at `:453`, `sourceUrl` at `:458`, `metadata.url` at `:461`). Applying all four rules to that one function would have introduced two real regressions, so I split it in two:

| Rule | Request/scope URL | Document canonical URL |
|---|---|---|
| strip fragment | yes (existing) | yes |
| strip default port | yes (existing) | yes |
| lowercase host | yes | yes |
| strip tracking params | yes | yes |
| drop trailing slash | **no** | **yes** |

Trailing-slash removal is confined to the document URL because `/a` and `/a/` are distinct HTTP resources. Stripping it from the request URL would (a) make the crawler fetch a path the site never published, and (b) silently widen the crawl scope — `buildAllowedPathPrefixes` branches on exactly that trailing slash at `web-crawler-connector.ts:477-478`, so a seed of `https://ex.com/docs/` would have collapsed from the prefix `/docs/` to `/`, crawling the whole origin. The two URL forms are still fetched separately and converge on one document at ingest, which is what the task asks for.

One detail is doing real work: I guard the tracking-param deletion with `searchParams.has()`. Mutating `searchParams` re-serializes the entire query string (`[expr]` becomes `[expr]`, `[expr]` becomes `[expr]`), so an unguarded delete would have changed the hash of **every** already-indexed document that has a query string. With the guard, URLs carrying no tracking parameter keep their query byte-for-byte.

## Left unchanged, with the source that puts it out of scope

- **`buildAllowedPathPrefixes` (`web-crawler-connector.ts:469-481`)** — it reads `[expr]` and branches on `path.endsWith(…)` at `:477-478`. Because the request-level normalizer preserves the path, this function receives the same input as before and needs no change.
- **`buildDocument` (`web-crawler-connector.ts:453-462`)** — it already separates `url: [expr]` from `fetchedUrl: [expr]`. That existing split is precisely the layering the fix needs, so the change lands entirely in `normalizeCanonicalUrl`.
- **`pathMatchesPrefix` (`web-crawler-connector.ts:563`)** — already treats `/docs` and `/docs/` prefixes as equivalent, so scope matching tolerates either form.
- **`connector-sync.ts:419-421` and `:502-504`** — document identity is `sourceId: [expr]`. This is the connector's contract with the sync layer; changing it would re-key every connector, not just the crawler.
- **`query.ts:267`** — the read path only *projects* `sourceId`, never filters on it. This is why documents indexed before the change keep serving correctly: nothing at serve time recomputes a URL hash, so existing rows retain their content, `sourceUrl`, and chunks.
- **`models/kb-document.ts:332` (`deleteByConnectorAndSourceId`)** — has no callers; the only bulk delete is `routes/knowledge-base.ts:1074`, on connector deletion. I did not wire up pruning.

## Residual risk

**An existing test now contradicts the requested behavior, and I could not touch it.** `web-crawler-connector.test.ts` pins the old trailing-slash canonicalization in three assertions: `sourceUrl` at lines 163-166, `metadata.url` at line 175, and the `sha256` id at lines 178-180 all expect `[expr]` and `[expr]`. Under the new canonicalization these become `/docs` and `/docs/install`, so **those three assertions will fail**. This is unavoidable for any implementation of "remove a trailing slash on non-root paths" — that rule *is* a change to the canonical URL. `fetchedUrl` (line 176) still passes, since request URLs are untouched. The test needs updating to the new expectations; the constraints forbade me from doing it.

**Re-keying on the next sync.** Only two of the four rules can change a document's id: trailing-slash removal and tracking-param stripping. Host-lowercasing and default-port stripping cannot, because WHATWG `URL` already lowercases the host for http/https and the old code already stripped default ports — I confirmed both in Node. For a page whose stored canonical URL ends in a non-root slash or carries a `[expr]`/`gclid`/`fbclid` parameter, the next sync's `findBySourceId` (`connector-sync.ts:419`) misses and `create` (`:502`) inserts a fresh row. The old row is never deleted, so that page is served **twice** — once stale, once fresh — until it is cleaned up. Fully closing this needs a one-time backfill that recomputes `kb_documents.source_id`/`source_url` for `web_crawler` connectors, and that backfill has to merge collisions (`/docs` and `/docs/` may both exist today, and `kb_documents_source_idx` is unique on `[expr]`). I did not write it: it deletes and rewrites user rows, which is outside the stated scope and, per `platform/CLAUDE.md` rule 8, needs your explicit approval. I'm happy to write it if you want.

One minor, benign effect: on URLs that *did* carry a tracking parameter, the surviving query string is re-serialized (`[expr]` → `[expr]`). These are equivalent under standard query parsing, and those URLs were being re-keyed anyway.
