## What changed

One file: `platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts`.

- Added `TRACKING_QUERY_PARAMS` (the seven listed params) alongside the other module constants.
- `normalizeCrawlUrl` now lowercases the host, strips those tracking params, and keeps the existing fragment- and default-port-stripping.

I deliberately did **not** strip the trailing slash inside `normalizeCrawlUrl`. That is the load-bearing decision, and it has three independent justifications.

## Why the trailing slash stays

**It is already done, where it actually matters.** Crawlee derives each request's `uniqueKey` via `Request.computeUniqueKey` → `@apify/utilities`'s `normalizeUrl`, which strips the trailing slash, strips any `[expr]`-prefixed param, sorts query params, lowercases the host, and drops the fragment. So `/a` and `/a/` are *already* fetched once and yield one document. I first implemented a custom `uniqueKey` to do this myself, then measured it against the default and found it was a regression — my seven-param list misses the `[expr]` wildcard (`utm_id`, `utm_reader`) and doesn't sort params:

| variant vs. canonical | Crawlee default | my custom `uniqueKey` |
|---|---|---|
| `[expr]` | deduped | **not deduped** |
| `[expr]` vs `[expr]` | deduped | **not deduped** |
| trailing slash | deduped | deduped |
| `[expr]` | **not deduped** | deduped |

I reverted that half of the patch. The only real gap was `gclid`/`fbclid`, which `normalizeUrl` doesn't touch (it only matches the `utm_` prefix) — and stripping them in `normalizeCrawlUrl` closes it, because the cleaned URL is what gets enqueued.

**Applying it to the URL itself would corrupt two things.** `buildAllowedPathPrefixes` (`web-crawler-connector.ts:469-481`) reads the start URL's trailing slash to scope the crawl: `/docs/` yields `[expr]`, but `/docs` yields `[expr]` — the whole origin. Stripping the slash first would silently widen a subtree crawl to the entire site. And `buildDocument` (`web-crawler-connector.ts:453`) sets `[expr]` with `sourceUrl` from the same value (`:458`), which brings us to the constraint you flagged.

## Why already-indexed documents keep working

`connector-sync.ts:419-421` looks a document up by `[expr]`; on a miss it inserts a fresh row (`:502-504`). Nothing prunes documents absent from a crawl — `deleteByConnectorAndSourceId` exists at `models/kb-document.ts:332` but has no caller outside its own test, and `kb_documents_source_idx` (`database/schemas/kb-document.ts:44`) is only a uniqueness constraint. So any change to the canonical URL re-keys a page, orphaning the old row as a stale duplicate that still gets served.

The patch preserves identity because a `searchParams.delete()` of a key that isn't present leaves `href` byte-identical — Node only re-serializes the query when it actually changes. I verified every URL the frozen test suite pins (`/docs/`, `/docs/install/`, `/docs/dest/`, `/`, …) passes through unchanged, including that `sha256(…)` still equals the hash asserted at `web-crawler-connector.test.ts:178`.

## Left unchanged, with proof

- **`beforeRedirect`'s scope check** (`web-crawler-connector.ts:250`) matches `excludePathPatterns` against the raw `target.search`. It's a fail-closed security check on the URL as the origin sent it; normalizing there would let a redirect slip past an exclude pattern. Out of scope.
- **`buildAllowedPathPrefixes`** (`:469`) reads only `pathname`, which neither tracking-param stripping nor host-lowercasing can affect. No change needed.
- **No data migration.** Only documents whose stored URL actually contained one of the seven params get re-keyed; everything else is bit-identical, as shown above.
- The existing default-port block is now redundant — `[expr]` already yields `http://e.com/`. You asked me to keep it, so I did.

## Residual risk

The real one: a page previously indexed under a URL carrying one of the seven tracking params **will** be re-keyed on the next sync, and since nothing prunes, the old row lingers as a stale duplicate alongside the new clean-URL row. That re-key is intrinsic to the request — collapsing those URLs into one document is the point — but the leftover row needs a one-off cleanup that I did not write, since it would want a test and tests are out of scope here. Two smaller ones: when a tracking param *is* removed, the remaining query is re-encoded (`[expr]` becomes `[expr]`), affecting only URLs already being re-keyed; and an `excludePathPatterns` regex that deliberately matched `utm_` in a query string will no longer fire.
