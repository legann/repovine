## What I changed

**One file:** `platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts` (+57/−1).

All four rules are implemented in a new `buildUrlDedupKey` (`:636`), composed on top of the existing `normalizeCrawlUrl` so default-port stripping stays the single source of truth. It is applied as a **comparison key** for the crawl frontier (`:204`, `:431`), not as a rewrite of the URL that gets fetched or stored.

That split is forced by the "already indexed documents must keep working" constraint. Document identity is `sha256(…)` (`web-crawler-connector.ts:462`), looked up as `[expr]` (`connector-sync.ts:419-421`), and **nothing in the sync path prunes rows that a later crawl no longer emits** — I searched for prune/stale/orphan logic and there is none. So rewriting the stored URL would change the hash for every page whose URL ends in `/` or carries a `[expr]` param, creating a duplicate row on the next sync while the old row lingers forever, frozen at its last-synced content and still being served. Applying the rules to the fetched URL is separately unsafe: `/a` and `/a/` are distinct resources per HTTP, so a rewritten request can 404.

The repo already has this exact pattern — `normalizeBaseUrl` (`connection-setup.routes.ts:783`) builds a "normalized comparable form" for comparison only, lowercasing host and stripping trailing slashes.

The pinned tests independently confirm this reading: they fix `sourceUrl`/`metadata.url` (`test:163-166`, `:317-318`, `:667-668`), the ID hash (`:178-180`), the fetched URL via `itemId` (`:203`, `:522`), and the title fallback (`:548`) to trailing-slash forms like `/docs/` and `/docs/install/`. A naive rewrite breaks all of those, and I was told not to modify tests.

## Behavior change

Discovered links are claimed once per crawl by comparable form, so URLs differing only by tracking params (`utm_source`/`utm_medium`/`utm_campaign`/`utm_term`/`utm_content`/`gclid`/`fbclid`, case-insensitive), a trailing slash on a non-root path, host casing, a default port, or a fragment are fetched and indexed once instead of N times. Non-tracking query params, paths, ports, schemes, and hosts still distinguish pages. Every already-indexed document keeps its exact `sourceId`, `sourceUrl`, and `metadata.url`, so nothing is orphaned and no backfill is needed.

Host lowercasing is explicit in the helper for the stated contract, though `new URL` already lowercases http/https hosts — it is intent, not a behavior change.

**Residual risk.** A site that serves genuinely different content at `/a` and `/a/`, or that uses a tracking-param name as a real router key, will now have one of the two variants skipped; its previously-indexed row survives and is still served, but goes stale. For a page with no `[expr]`, the stored URL is whichever variant is discovered first — deterministic for fixed markup, but if the site reorders its links so the other variant is seen first, that page's canonical URL and therefore its ID changes, creating a new row and orphaning the old one. Narrow, and unreachable for pages that declare `[expr]`. Per repo convention #5 a behavior change like this would normally get a test pinning it; the task explicitly forbade adding tests, so I'm flagging the gap rather than silently skipping it.
