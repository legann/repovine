## 2. Deliberately unchanged

**Document identity — `normalizeCanonicalUrl` (`:592-607`) and `buildDocument` (`:456-465`).** `[expr]` is persisted verbatim as `kb_documents.source_id`: written at `connector-sync.ts:504`, and it is the only key the next sync matches on (`connector-sync.ts:419-422`), under a unique index (`database/schemas/kb-document.ts:44`). Nothing prunes rows whose source disappears — `ingestDocument` only inserts or updates, and `KbDocumentModel.deleteByConnectorAndSourceId` (`models/kb-document.ts:332`) has no non-test caller. A canonicalized id would therefore insert a **second** row for every already-indexed page while the original kept being served. It is also pinned by tests I must not touch: `web-crawler-connector.test.ts:163-166` (`sourceUrl`), `:175` (`metadata.url`), `:178-180` (`id` hash), `:271`, `:317`, `:667` all assert trailing slashes survive.

## 3. Behavior, and residual risk

Net effect: a page reachable through several trivially-different URLs is fetched and indexed once per crawl. Crawlee's default `uniqueKey` already normalized part of this (`@apify/utilities` `normalizeUrl` strips `[expr]`, sorts params, lowercases the host, drops one trailing slash), so the **net new** collapsing is `gclid`/`fbclid` and repeated trailing separators — plus the rule now lives in our code instead of a transitive dependency's default.

Risks:
- **Retired duplicates linger.** Where two variants were previously indexed as two rows, only one is refreshed now; the other stays in `kb_documents` (no prune path) and keeps serving stale content. Remedy is operator-triggered: `POST /api/connectors/:id/force-resync` (`routes/knowledge-base.ts:1039`, deletes documents at `:1074`).
- **Stored URLs are not canonical.** A page linked only as `[expr]` is still stored under that URL, and which variant wins is discovery-order dependent — a pre-existing wrinkle, not introduced here. Canonicalizing stored URLs needs a `source_id` backfill (or a legacy-id fallback in `ingestDocument`); deliberately out of scope given the constraint above.
- **Verification is static.** This worktree is intentionally not bootstrapped (`pnpm` shim blocks install/type-check/test), so I could not run vitest or Biome. I instead read the pinned `[expr]` sources to confirm `transformRequestFunction` runs on `urls`-built options before `createRequests` and that `[expr]` and `Request` preserve a supplied `uniqueKey` (memory storage keys entries by `uniqueKeyToRequestId(…)`), checked `RequestOptions`/`RequestTransform`/`RequestsLike` typings, executed the key logic standalone in Node, confirmed no key collisions among every URL the test suite serves, and kept added lines ≤80 columns.
