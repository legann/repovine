## The one design decision worth your attention

The strengthened form is the **key used to decide "same page"**, not a rewrite of the URL that gets requested and stored. Three specific things break if `normalizeCrawlUrl` itself strips trailing slashes:

1. **Already-indexed documents get re-keyed.** `id` is `sha256(…)` (`:471`) and lands as `sourceId` under a unique index on `[expr]` (`database/schemas/kb-document.ts:44`), which is the sole lookup key for refreshing a document (`connector-sync.ts:419`). Every page whose URL had a trailing slash or tracking param would insert a *new* row, and the old row is never pruned — `deleteByConnectorAndSourceId` (`models/kb-document.ts:332`) has zero callers. The connector has no DB access, so it cannot detect what was already indexed; any change to its id derivation is unconditionally breaking. This is your stated hard constraint.
2. **The crawl scope silently widens.** `buildAllowedPathPrefixes` reads the start URL's trailing slash (`:495-499`): `/docs/` yields prefix `[expr]`, but `/docs` falls to `[expr]` → **`/`, the whole origin**. That prefix is the boundary the redirect guard enforces (`:246`).
3. **Requests can 404.** An origin serving `/docs/` is free to 404 rather than redirect `/docs` — the repo's own test server does exactly this (`web-crawler-connector.test.ts:727`).

So `sourceUrl`, `metadata.url`, and `id` stay byte-identical for every page already indexed; the dedup happens before a request is made.

If you want the stored URLs themselves rewritten, that is a separate change needing a `sourceId` backfill migration plus test updates — say so and I'll do it.

## Residual risk

- **First-form-wins is order-dependent.** A page linked under several variants is indexed under whichever the site lists first. If that order changes between syncs, the id flips → one orphaned row. A deterministic rule (always prefer the clean form) would be stable but would re-key already-indexed pages once, which your constraint forbids.
- **Pre-existing duplicate rows go stale.** A page double-indexed under two variants now refreshes only the surviving one; the other keeps being served, never updated. Removing it needs the unused pruning path above.
- **New pages can carry a tracking param in the citation URL** if that's the only form linked.
- **Redirect targets aren't deduped** — two URLs redirecting to one page still yield two documents. Pre-existing; untouched.
