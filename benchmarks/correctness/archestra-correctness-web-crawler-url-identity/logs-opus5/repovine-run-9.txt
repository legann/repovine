## Files changed

**1. `platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts`** (+47/−4)

- `normalizeCrawlUrl` now strips the seven tracking parameters, lowercases the host, and keeps the existing default-port stripping.
- New `canonicalizeDocumentUrl` adds trailing-slash removal on non-root paths; `normalizeCanonicalUrl` (the document-identity path) routes through it.
- `stripTrackingQueryParams` filters raw `[expr]` segments rather than mutating `url.searchParams`. This is not stylistic: `searchParams.delete()` re-serializes the whole query, so it rewrites `[expr]` to `[expr]` — I verified this, and it would have silently moved the identity of URLs carrying *no* tracking parameter.

**2. `0313_renormalize_web_crawler_source_ids.sql` + `meta/_journal.json`** (new, 215 lines)

This is what makes already-indexed documents keep working. `kb_documents.source_id` is the persisted form of this normalization: the connector stores `sha256(…)` (`web-crawler-connector.ts:449`), `connector-sync.ts` matches existing documents by `[expr]` via `findBySourceId`, `kb_documents` has a unique index on that pair (`kb-document.ts:44-47`), and `ingestDocument` has **no prune step**. Changing the normalizer without re-keying means the first sync inserts a second row per affected page and kb search returns both the fresh and the stale one — immediately, not at some later maintenance point.

`source_url` stores the same canonical URL the `source_id` was hashed from, so the new identity is re-derivable in SQL. The migration replays only the delta (tracking params + one trailing slash); host-lowercasing and default-port stripping were already applied by the URL parser when the value was written. It merges rows that now collapse together (chunks follow via the FK cascade), rewrites `source_url` and `metadata.url`, and skips any row where `[expr]` rather than re-keying on an assumption that doesn't hold. Data-only migration with a descriptive name and no snapshot, matching `0131_fix_agent_tool_trailing_underscores` — the repo's own precedent for a SQL/TS normalization mismatch of this shape.

## One design decision worth flagging

My first pass put trailing-slash removal in `normalizeCrawlUrl` itself, as literally specified. That is a functional regression: `normalizeCrawlUrl`'s output is also the URL the crawler *fetches*, and `/a` and `/a/` are different HTTP resources. The repo's own test server resolves paths exactly (`[expr]`, test file line 725), so it 404s on the trimmed path — and real sites that only serve the directory form behave the same, silently losing content. Splitting identity from fetching delivers the requested canonicalization (`/page/` and `/page` become one document) with no change to which URLs are requested.

## Deliberately left unchanged

- **`buildAllowedPathPrefixes`** — with the fetch URL keeping its slash, `[expr]` still yields `/guide/` and the directory scope is preserved (`web-crawler-connector.ts:469-473`). Under the trailing-slash-in-fetch variant this would have widened a docs-subtree crawl to the whole origin via `pathMatchesPrefix`'s `[expr]` (line 555).
- **`connector-sync.ts`** — connector-agnostic; it stores `sourceId: doc.id` verbatim (`ingestDocument`). Making the lookup tolerate legacy ids would push crawler-specific logic into shared infra and would not fix rows already duplicated.
- **`content_hash`** — recomputing it would mean replicating `hashInput`'s content-plus-sorted-key-JSON in SQL. Left alone deliberately: the next sync sees a change and re-chunks the affected documents, which is correct, just extra work.
- **Other `web_crawler` references** — `[expr]` only test whether credentials are required; `registry.ts:34` constructs the connector; frontend only lists the type. None derive document identity.
