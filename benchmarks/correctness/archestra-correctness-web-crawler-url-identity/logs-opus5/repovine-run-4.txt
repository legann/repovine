## What I changed

**1. `platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts`**

The normalization is now split along the line that matters — what the crawler *fetches* vs. what identifies a *document*:

| Function | Applies | Used by |
|---|---|---|
| `normalizeCrawlUrl` | fragment, default port, host lowercase, tracking params | seed fetch, discovered-link enqueue, scope checks (`:131`, `:172`, `:193`, `:354`, `:587`) |
| `canonicalizeDocumentUrl` | the above **+ trailing-slash removal** | `normalizeCanonicalUrl` → `buildDocument` identity (`:597`–`:606`) |

Tracking params are filtered as *text*, not via `URLSearchParams`: re-serializing rewrites retained values (`[expr]`→`[expr]`), which would have changed the identity of pages carrying no tracking param at all. Trailing slashes collapse fully (`/a//` → `/a`) so the function is idempotent — it's applied repeatedly, including to already-normalized values.

**2. `.../migrations/0313_normalize_web_crawler_source_ids.sql`** (+ `meta/0313_snapshot.json`, `meta/_journal.json`)

This is what makes already-indexed documents keep working. `kb_documents.source_id` is the sha256 of the canonical URL, written once and **never re-derived**, and `connector-sync` has **no prune step** (`connector-sync.ts:421`, `:504`). Without a backfill, the first sync after this change inserts a second row per affected page while the old row stays — kb search reads both and returns the page twice, and the stale copy is never updated again.

The backfill works because `source_url` stores the *same string* that was hashed, and the new canonicalization is a superset of the old one, so re-canonicalizing the stored URL yields exactly what a fresh crawl now produces. It expresses the normalization **once** as a SQL function used by both passes — deliberately, because migration `0131_fix_agent_tool_trailing_underscores` exists precisely because a SQL and a TS normalization drifted apart. It de-duplicates collapsing rows before re-keying (unique index on `[expr]`), and only touches rows where `[expr]` actually holds.

## Deliberately left unchanged

- **`connector-sync.ts` ingest/lookup** — `sourceId: doc.id` (`:421`, `:504`) consumes whatever identity a connector produces; it's shared by every connector. Re-keying belongs in a migration, not in this path.
- **Fetched/enqueued URLs keep their path** — `buildAllowedPathPrefixes` treats a trailing slash as "scope to this directory" vs. "the parent directory" (`web-crawler-connector.ts:481-482`), and rewriting a user's configured `/docs/` to `/docs` 404s on any origin that doesn't redirect. Canonicalizing identity delivers "such URLs canonicalize to one" without that hazard.
- **Other connectors** — identities derive independently (`gitlab-connector.ts:666`, `linear-connector.ts:1134`); the migration filters `[expr]` (`:80`, `:103`).
- **`kb_chunks`** — no explicit cleanup: `kb-chunk.ts:44` is `onDelete: "cascade"`.
- **`metadata.url` / `fetchedUrl`** — `fetchedUrl` depends on redirect behavior SQL can't predict; the existing content-changed path refreshes metadata (`connector-sync.ts:468-475`). The migration does refresh `source_url`, since that's the citation link retrieval returns (`models/kb-chunk.ts:117`, `:174`).
