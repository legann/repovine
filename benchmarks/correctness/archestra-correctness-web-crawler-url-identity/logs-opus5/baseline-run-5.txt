## What I changed

One file: `platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts`.

The strengthened normalization is applied as the crawl's **request dedup key**, not as a rewrite of the URL that gets fetched and stored:

| Addition | Line | Role |
|---|---|---|
| `TRACKING_QUERY_PARAMS` | `:35` | utm_source/medium/campaign/term/content, gclid, fbclid |
| `buildCrawlUrlKey()` | `:638` | strips tracking params, drops a trailing slash on non-root paths, lowercases host, keeps default-port + fragment stripping (via `normalizeCrawlUrl`) |
| `buildCrawlRequest()` | `:658` | `[expr]` for `crawler.run()` (`:126`, `:167`) |
| `transformRequestFunction` on `enqueueLinks` | `:429` | assigns the canonical key to every discovered link |

Crawlee's request queue deduplicates on `uniqueKey`, so `/docs/page`, `/docs/page/`, `[expr]`, `//EXAMPLE.com/docs/page/`, and `:443` variants now collapse to a single fetch — and therefore a single document — whether they appear on one page or across the crawl.

**Why a key and not a URL rewrite.** `[expr]` (`:463`) is persisted as `kb_documents.source_id` and is the *only* lookup key at ingest (`connector-sync.ts:419-422`). Nothing reconciles a document whose id changes: `deleteByConnector` runs only when the connector itself is deleted (`routes/knowledge-base.ts:1074`), and `[expr]` is a unique index (`database/schemas/kb-document.ts:44`). Rehashing every already-indexed page would leave the old row serving stale content forever beside a fresh duplicate. Keeping the fetched URL as-is also avoids requesting a resource the server may not have — `/docs` and `/docs/` are distinct HTTP resources.

Proof it must stay: `:463` feeds the persisted `source_id` via `connector-sync.ts:419-422`, with no cleanup path (`routes/knowledge-base.ts:1074`) and a unique index (`database/schemas/kb-document.ts:44`).

## Residual risk

- `transformRequestFunction` / `RequestOptions.uniqueKey` are stable crawlee 3.x APIs (locked at 3.14.1), but I could not type-check them here — worth one `pnpm type-check` + the connector's test file before merge.
- Where a site genuinely links two variants and *both* were indexed by an earlier sync, the crawl now visits one; the other row stays in `kb_documents` as an unrefreshed duplicate. That collapse is the intent of the change, and the surviving document keeps its original id.
- The stored URL is the variant the crawl discovers first, so a document whose only inbound link carries `[expr]` keeps that URL in its `sourceUrl` — unchanged from today's behavior, and the condition for existing ids remaining valid.
- Two pages declaring `[expr]` that differ only by a trailing slash still produce two documents; document identity is out of scope for the reason above.
