## Why 4 files and not 1

`normalizeCrawlUrl`'s output *is* the persisted document identity: `sha256(…)` → `doc.id` → `kb_documents.source_id`, written once at `connector-sync.ts:504`, unique per `[expr]` (`schemas/kb-document.ts:44-47`), never re-derived, and sync has no prune. Trailing slashes are common, so changing the normalizer alone would insert a second row for every re-keyed page on the *first* sync and leave the stale row in search permanently.

A SQL migration can't do this: `source_id` is a sha256, needing pgcrypto `digest()` — no migration among the 312 uses it — and re-implementing the normalization in SQL is the exact SQL/TS divergence that `0131_fix_agent_tool_trailing_underscores` existed to repair. In TS the real normalizer is reused.

The re-key is exact because stored `source_url` is the same string that was hashed, and the old normalization (hash + default port) is a subset of the new one, so `newNorm(…)`. Verified against the old normalizer: the re-key lands on the new ingest id in 9/9 cases. Collisions (both `/docs` and `/docs/` already indexed) skip instead of violating the unique index; chunks are preserved, so nothing is re-embedded. Idempotent — zero writes once aligned. I used a dedicated `updateSourceId` rather than widening `UpdateKbDocumentSchema`, which deliberately omits `sourceId` (`types/kb-document.ts:64-73`).

## Regression I found and fixed

`buildAllowedPathPrefixes` inferred crawl scope from the *normalized* start URL's trailing slash. With slashes stripped, `https://h/docs/` → `/docs` read as a page, widening prefixes from `[expr]` to `[expr]` — the whole site. It now reads `config.startUrl`. Simulated: `/blog` out, `/private` excluded, external out, `/docs/guide/` still in.
