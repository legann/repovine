**`normalizeCrawlUrl`** now lowercases the host, strips `utm_source/medium/campaign/term/content`, `gclid`, `fbclid`, and removes trailing slashes on non-root paths (default-port stripping kept).

Two non-obvious decisions, both driven by test results rather than assumption:

- **Query rewriting bypasses `URLSearchParams`.** I verified `searchParams.delete()` re-serializes *surviving* params as form-urlencoded (`[expr]`→`[expr]`) even when the deleted key is absent — that would have silently changed the identity of pages carrying no tracking param at all. Operating on the raw query string round-trips those URLs byte-identically.
- **Every trailing slash is removed, not just the last.** Stripping one leaves the function non-idempotent (`/a//`→`/a/`→`/a`), which breaks the "already canonical" reasoning the migration depends on and makes the re-key order-sensitive. Removing all makes `normalize(…)`.

## The part that isn't the normalizer

`normalizeCrawlUrl`'s output is a *persisted identity*: `buildDocument` hashes it into `doc.id`, and `connector-sync.ts:504` stores that as `kb_documents.source_id`, which is written once and never re-derived, under a unique index on `[expr]` with no prune step. Changing the normalizer without a backfill means the first sync fails to match every existing page, inserts a second row, and kb search returns both copies forever. Hence the migration — it replays the two new rules in SQL over `source_url`, deletes rows that collapse onto one identity (chunks cascade via `kb-chunk.ts:44`), and re-keys the survivor, preferring an already-canonical row so its embeddings are untouched.

I couldn't run Postgres here, so I verified the SQL two ways: a faithful replay of its semantics matched the real JS normalizer on **31/31** stored-URL shapes (including `[expr]`/`[expr]` encoding, bare `[expr]`, `//`, non-default ports), and a simulation of the dedupe confirmed the unique index holds with no page served twice.

I also found and fixed a bug the change would otherwise have introduced: `buildAllowedPathPrefixes` read the *normalized* start URL, so stripping the trailing slash turned a crawl scoped to `/docs/` into one scoped to `/` — the whole origin. It now reads `config.startUrl`, which is provably equivalent to the old behavior (normalization never altered `pathname`).
