## What changed

**`platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts`**
- `TRACKING_QUERY_PARAMS` (:37) — utm_source/medium/campaign/term/content, gclid, fbclid.
- `canonicalizePageUrl()` (:650) — new canonicalizer layered on `normalizeCrawlUrl`: lowercases the host, drops tracking params, drops a trailing slash on non-root paths, keeps the existing hash/default-port stripping.
- `buildDocument()` (:463) — the document id is now `sha256(…)`, so `/docs/`, `/docs`, and `[expr]` are one document.
- Per-crawl dedup by document id (:202, :287-307) — when two requests canonicalize to one page, the first is indexed and the rest are reported as skipped (`"duplicate of an already-crawled page"`), instead of the page being chunked and re-written once per URL spelling.

**Continuity for already-indexed documents.** The document id *is* the dedup key (`kb_documents.source_id`, unique per connector — `database/schemas/kb-document.ts:44`), and nothing prunes rows a sync stops emitting (deletes exist only at `routes/knowledge-base.ts:1074` and `:758`). Re-keying alone would therefore leave every already-indexed `/dir/` page behind as a second copy that is served from search forever and never updated again. So:
- `[expr]` (`types/knowledge-connector.ts:553`) — ids an item was stored under before a connector changed its id derivation. The crawler sets it to the pre-canonicalization hash, which is byte-identical to what the old code produced (it hashed `extracted.canonicalUrl` verbatim).
- `ConnectorSyncService.resolveExistingDocument()` (`knowledge-base/connector-sync.ts:547`) — falls back to `previousIds`, re-keys the existing row to the new id, and deletes any further rows that collapsed into the same document (chunks cascade via `kb_chunks.document_id`).
- `KbDocumentModel.rekeySourceId()` (`models/kb-document.ts:232`).

Because `content` and `metadata` are untouched, an adopted row's `contentHash` still matches, so it takes the "unchanged, skipping" path: no re-chunk, no re-embed, no gap in search coverage. Connectors that don't set `previousIds` get exactly the old single lookup.

## Behavior summary and residual risk

Trivially-different URLs for one page now produce one `kb_documents` row; already-indexed pages are adopted in place on the next sync (logged as `"Re-keyed existing document to the connector's new source id"`), keeping their chunks and embeddings.

- **One existing test assertion is invalidated by design and I left it as-is per the constraint:** `web-crawler-connector.test.ts:178-180` asserts `[expr]`; the canonical id is now `sha256(…)`. The other assertions in that file (including every `sourceUrl`/`metadata` expectation and `[expr]`) still hold. Repo rule 5 would have this change come with tests for the canonicalizer and the re-key path — that's the deferred follow-up.
- Two URLs a site treats as genuinely different pages but that differ only by a trailing slash or tracking param now collapse into one document; the loser's content is dropped. Inherent to the requested rule.
- Documents indexed under a tracking-param URL whose site also links the clean form collapse to one row; the surviving copy is the most recently synced one.
- `previousIds` stays on every non-canonical page URL indefinitely, costing one extra indexed lookup per such document per sync.
- Concurrent syncs of one connector could race the re-key into a unique-index violation; it surfaces as a per-document `itemErrors` entry (`connector-sync.ts:177-186`), not a failed sync.
- Query-param order is not canonicalized (`[expr]` vs `[expr]` remain distinct) — not requested, and sorting params changes URLs that some servers treat as significant.
- **Not verified by running anything:** this worktree has no `node_modules` and the `pnpm` shim blocks installs, type-checks, and tests, so the patch was validated by reading only.
