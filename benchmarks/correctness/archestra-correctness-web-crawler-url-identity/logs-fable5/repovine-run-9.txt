## What changed and why

The crawler now has **two normalization tiers** in `web-crawler-connector.ts`, because "which page is this" and "which URL do I fetch/show" have different safety requirements:

- **Crawl form** — `normalizeCrawlUrl` (line 619): existing fragment + default-port stripping, plus explicit host lowercasing and tracking-param removal (`utm_source/medium/campaign/term/content`, `gclid`, `fbclid`). Tracking params are filtered as raw `[expr]`-segments (`stripTrackingQueryParams`, line 648) instead of via `URLSearchParams`, so surviving params keep their exact original serialization and hashes stay stable. Applies to start URLs, discovered links, and the stored `sourceUrl`.
- **Canonical identity** — new `normalizeDocumentUrl` (line 640): crawl form plus trailing-slash removal on non-root paths. Used in exactly two places: the document id (`buildDocument`, line 457, `sha256(…)`) and crawlee request-dedup keys (`transformRequestFunction` at line 433, `buildStartRequest` at line 665), so slash variants of a queued page aren't fetched twice.

Trailing-slash removal deliberately does **not** apply to fetched URLs or `sourceUrl`: `/path` and `/path/` can be served differently (the connector's own test server 404s the slashless form), and `sourceUrl` is the clickable link users follow. Result: URLs differing only by tracking params, trailing slash, or host case collapse into **one document**, while every URL the crawler requests or displays is one that actually resolves.

**Serving already-indexed documents correctly** required more than the connector edit. The module's graph annotation flags the load-bearing contract: `kb_documents.source_id` is the persisted output of this normalization, written once at ingest (`connector-sync.ts:504`), matched by `[expr]` (`connector-sync.ts:419-422`), never re-derived — and connector-sync has no prune. Changing the id derivation alone would make the first post-deploy sync re-ingest every affected page under a new `source_id` and serve the stale row alongside the new one forever. So I added data migration **`0313_rekey_web_crawler_document_source_ids.sql`** (following the in-repo precedent `0131_fix_agent_tool_trailing_underscores`): it mirrors `normalizeDocumentUrl` in SQL, re-keys `[expr]` from the stored `source_url` (which itself stays untouched — it remains the resolvable link), and pre-deduplicates rows that now collapse to one page (freshest row kept, losers deleted with their chunks via the existing `ON DELETE CASCADE`, `kb-chunk.ts:44`). Delete-then-update as separate statements avoids transient unique-index violations on `kb_documents_source_idx` (`kb-document.ts:44-47`).

A second serving-continuity subtlety: `metadata` feeds the sync `contentHash` (`connector-sync.ts:404-416`). Keeping `metadata.url`/`sourceUrl` in crawl form means unchanged pages hash identically after deploy — no mass re-chunk/re-embed of the whole corpus.
