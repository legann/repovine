## What was done

The crawler now has **two URL forms** instead of one: the form it **dials** stays exactly as today, while a strengthened **canonical form** becomes the page identity — and a data migration re-keys every already-indexed document to that new identity so existing documents keep being matched, updated in place, and served without duplicates.

The one-function approach (making the single `normalizeCrawlUrl` do everything) was rejected deliberately: its output is also the URL the crawler dials, and stripping trailing slashes from *dialed* URLs turns working crawls into 404s/redirects (the entire test suite demonstrates this — every test server exact-matches `/docs/`). Instead, canonicalization applies where identity is decided, and frontier dedupe uses crawlee's explicit `uniqueKey`, so trailing-slash and tracking-param variants of a page are fetched once and indexed once while the server still receives the URL that was discovered.

## Files changed and why

**`platform/backend/src/knowledge-base/connectors/web-crawler/web-crawler-connector.ts`**
- `normalizeCrawlUrl` (canonical identity) now: lowercases the host, strips `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`, `gclid`, `fbclid`, removes trailing slashes on non-root paths, and keeps the existing fragment/default-port stripping. Query filtering is textual (not `URLSearchParams`) so surviving parameters keep their exact serialization — re-encoding would silently shift identities of pages with no tracking params at all.
- New `normalizeRequestUrl` preserves today's dialed form (fragment + default port only). `createCrawler`, `validateParsedConfig`, and `normalizeDiscoveredUrl` use it, so dialing, SSRF checks, scope checks, and exclude-pattern semantics are byte-identical to before.
- Seeds and discovered links are enqueued with `[expr]` (`buildStartRequest`, `transformRequestFunction` in `enqueueAllowedLinks`), deduplicating the frontier on canonical identity — this also stops URL variants from burning `maxPages` budget.

**`platform/backend/src/database/migrations/0313_rekey_web_crawler_source_ids.sql`** (+ journal entry)
`kb_documents.source_id` is sha256 of the canonical URL, written once at ingest and never re-derived, and connector-sync has no prune — so without re-keying, the first sync after this change would insert a duplicate row next to every stale one. The migration re-normalizes each stored web-crawler `source_url` in SQL (mirroring the TypeScript byte-for-byte for the stored input domain), recomputes the sha256, collapses rows that now canonicalize to the same page keeping the most recently updated one (chunks cascade), and updates `source_id`/`source_url`. This follows the repo's own precedent, migration `0131_fix_agent_tool_trailing_underscores`, which fixed exactly this class of SQL/TS normalization mismatch.

**`docs/pages/platform-knowledge-connectors.md`** — one sentence in the Web Crawler "Indexed:" paragraph documenting the canonicalization (per the platform rule to audit docs on behavior changes).

**`repovine.annots.json`** (via `write_annotation`) — the module annotation's recorded risk ("stored source_ids diverge from the normalizer") is resolved; it now records the two-form design and the standing TS↔SQL parity contract. `.gitignore` gained `.repovine/` as a repovine-tooling side effect.

Residual risk, stated plainly:
1. **5 of 28 crawler tests now fail** — `[expr]` — every failure is an assertion pinning the *old* identity (`sourceUrl`/`metadata.url`/`id` with a trailing slash, e.g. `expect(…)`). They contradict the mandated normalization and the constraints forbid modifying tests; no behavioral test fails (all fetches, redirects, scoping, batching pass).
2. Frontier dedupe keys on canonical identity, so if a site serves `/a/` but 404s `/a` **and** a broken `/a` link is discovered first, that page is skipped for the sync — the task's premise treats slash variants as the same page, but a rare strict server can violate it.

4. A sync racing the deploy window before 0313 applies could still insert one pre-rekey duplicate; migrations run before app start in this repo's flow, so exposure is a deploy-ordering edge, and re-running the (idempotent) migration would heal it.
