## What changed and why

**Behavior.** The web crawler now normalizes URLs in two tiers, both in `web-crawler-connector.ts`:

- `normalizeCrawlUrl` — the **canonical identity** of a page (what `buildDocument` hashes into the document id and stores as `sourceUrl`/`metadata.url`). It now strips the seven tracking parameters (`utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`, `gclid`, `fbclid`), removes trailing slashes on non-root paths, explicitly lowercases the host, and keeps the pre-existing fragment and default-port stripping. Tracking params are filtered as raw `[expr]`-separated pairs rather than through a `URLSearchParams` round-trip, so untouched parameters keep their original serialization and stored identities stay stable.
- `normalizeFetchUrl` — everything above **except** the trailing-slash removal, applied to URLs the crawler actually dials (seed, discovered links, scope validation). Fetches keep the slash because servers that route paths exactly return 404 for the stripped variant — the repo's own test HTTP server demonstrates this, and applying the strip to fetches would have broken every crawl. This also keeps crawl-scope derivation (`buildAllowedPathPrefixes`) byte-identical to today, avoiding a scope explosion where a start URL of `/guide/` would have widened to `/`.

Request dedup is keyed by the canonical form (a `uniqueKey` on the seed via `buildStartRequest`, and a `transformRequestFunction` in `enqueueAllowedLinks`), so `/page`, `/page/`, and `[expr]` are fetched once per crawl and always produce one document.

**Serving guarantee.** `kb_documents.source_id` is the persisted sha256 of the canonical URL, written once at ingest, matched by `[expr]` at `connector-sync.ts:419`, with no prune step — so changing the normalizer without re-keying stored rows would have made the first post-deploy sync insert a duplicate row for every affected page and leave the old row serving stale content forever. I added data migration **`0313_rekey_web_crawler_source_ids.sql`** (the same mechanism as the precedent `0131_fix_agent_tool_trailing_underscores.sql`): it re-keys existing web-crawler rows to the new canonical form (recomputing `source_id`, rewriting `source_url` and `metadata.url`), and where several stored rows collapse onto one identity it keeps the most recently updated row and deletes the rest (chunks cascade). Stored URLs were provably produced by the unchanged-since-inception old normalizer (`[expr]`, so hosts already lowercase, ports/fragments already stripped), which lets the SQL mirror the TS transformation exactly; both are idempotent, which rules out re-key collisions.

## Residual risk

- Re-keyed rows keep their old `content_hash`, so the first sync after deploy re-chunks and re-embeds exactly those documents once (deliberate: recomputing the hash in SQL would require replicating `JSON.stringify` semantics).
- Tracking-param matching is exact-case on raw names (mirrored in SQL); an exotic percent-encoded or uppercase `UTM_SOURCE` passes through — TS and SQL agree, so identities never diverge.
- If the migration runs while a `batch_embedding` task for a dedupe-deleted document is in flight, that task references a missing row; deploys that quiesce syncs (the normal case) are unaffected.
- Users now see slash-less/tracking-less `sourceUrl` links; real servers resolve these (typically via redirect), and the crawler itself still fetches the slash-preserving form.
