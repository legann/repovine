## What changed and why

**Design: normalization is two-layered.** The task's rules can't all be applied to the URLs the crawler *fetches*: a server without redirects serves exactly one slash form (`/docs/` but not `/docs`), so rewriting request paths would 404 real sites (and the entire existing test suite, whose test servers don't redirect). So:

- `normalizeCrawlUrl` (request form, applied to everything fetched/enqueued/scope-checked): existing fragment + default-port stripping, now plus **explicit host lowercasing** and **tracking-param stripping** (`utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`, `gclid`, `fbclid`) — both safe on the wire.
- `canonicalizeCrawlUrl` (document identity, new): request form plus **trailing-slash removal on non-root paths**. It feeds `normalizeCanonicalUrl` → `buildDocument`, so document `id` (sha256) and `sourceUrl` collapse `/docs`, `/docs/`, and `[expr]` into one identity — and it also sets crawlee request `uniqueKey`s (start request and `enqueueLinks`), so slash variants of an already-queued page are fetched once instead of producing churn.

Param stripping filters raw `[expr]`-pairs rather than mutating `URLSearchParams`, because the latter re-serializes the whole query (`[expr]`→`[expr]`), which would silently re-key URLs that carry no tracking params at all and would be irreproducible in migration SQL.

**Backward compatibility.** `kb_documents.source_id` is the persisted sha256 of this normalization — written once at ingest, never re-derived, with a unique `[expr]` index (`schemas/kb-document.ts:44-47`) and no prune step in sync. Without intervention, the first crawl after this change would insert a duplicate row next to every affected stale row, and search would return both. Migration `0313_rekey_web_crawler_source_ids` therefore re-keys stored rows by applying the two new rules to `source_url` in SQL and rehashing; where several rows now collapse to one identity it keeps the most recently updated row first (chunks cascade), so the later re-key statement can never trip the unique index. This follows the repo's own precedent (`0131_fix_agent_tool_trailing_underscores`), including its lesson: I verified TS↔SQL **byte parity** by running the actual migration file on PGlite against a corpus of hostile URLs (`[expr]`-encoded values, bare `[expr]`, `[expr]`, case-sensitive `UTM_SOURCE`, `utm` in paths, non-default ports, collision groups) — all checks passed, and non-crawler / NULL-URL rows are untouched.
