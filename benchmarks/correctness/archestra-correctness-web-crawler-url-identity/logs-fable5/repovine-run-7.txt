## Report

### What changed

**URL normalization is now two-tier, and every previously indexed document is re-keyed to stay resolvable.** The connector distinguishes what is safe to normalize on a URL it *fetches* from what defines the *identity* a page is indexed under — the naive approach of putting all four rules into the single fetch-path normalizer broke crawling itself (servers legitimately serve `/docs` and `/docs/` differently; 17 of 28 existing tests failed on real fetch behavior, not on identity assertions), so the rules are split:

- `normalizeCrawlUrl` (applied to the start URL and every discovered/queued URL): strips the fragment, **lowercases the host**, keeps the existing **default-port stripping**, and **strips the tracking params** `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`, `gclid`, `fbclid` (case-insensitive keys). None of these can change which resource a URL addresses, so utm-variant links no longer cause duplicate fetches or duplicate documents.
- `canonicalizeDocumentUrl` (the identity a page is indexed under — document id = sha256 of it, plus `sourceUrl`/`metadata.url`): composes `normalizeCrawlUrl` and additionally **removes trailing slashes on non-root paths**. Stripping all trailing slashes (not one) keeps the function idempotent, which matters because normalization runs at queue time and again at canonicalization time.
- Since distinct fetched URLs can now canonicalize to one page, `createCrawler` dedupes emissions per crawl (`seenCanonicalUrls`); a second variant is reported as skipped with reason `[expr]` instead of yielding a same-id document twice per sync.
- `buildAllowedPathPrefixes` now derives the default crawl scope from `config.startUrl` as configured rather than a normalized URL, so a `/docs/` start URL can never have its scope widened to the whole host by slash stripping.

**Backward compatibility** is handled by a data-only migration, `0313_web_crawler_url_normalization.sql`, following the repo's precedent for TS/SQL normalization drift (migration `0131_fix_agent_tool_trailing_underscores`). `kb_documents.source_id` is the persisted sha256 of the normalized URL, written once at ingest with no prune step — without re-keying, the first sync after this change would insert every affected page as a new row and search would return stale duplicates. The migration, scoped to `web_crawler` connectors: (1) collapses rows whose URLs normalize to the same value, keeping the most recently updated (chunks cascade via the `kb_chunks` FK); (2) rewrites `source_id`/`source_url` to the new canonical form, mirroring the TypeScript string transformation byte-for-byte (which is why the TS side filters the raw query string instead of using `URLSearchParams` — re-serialization would be irreproducible in SQL). Already-canonical rows are untouched (no `updated_at` churn).

### Residual risk

- **5 existing tests fail**, all on assertions that pin the pre-change canonical forms — sha256/`sourceUrl`/`metadata.url` of trailing-slash URLs (`web-crawler-connector.test.ts:163-180`, `271`, `317-318`, `648`, `667-668`). Any faithful implementation of the required trailing-slash rule changes those expected values; per the "do not modify tests" constraint I left them, and they need a maintainer update (expected values drop the trailing slash).
- The migration recomputes identity from `source_url`; a web-crawler row with a NULL or non-http(s) `source_url` would be left untouched. The connector has always populated `sourceUrl` (`buildDocument`), so this is a defensive guard, not an expected case.
- Query strings are compared against the tracking set literally (case-insensitive names); percent-encoded parameter names (e.g. `[expr]`) are not recognized — identical behavior in TS and SQL, so identity stays consistent either way.
