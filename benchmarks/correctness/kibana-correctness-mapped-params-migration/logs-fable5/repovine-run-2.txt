## What changed

On upgrade, each rule whose `params.severity` is a string containing uppercase letters (e.g. `High`, `MEDIUM`) has it lowercased. Two things made this more than a one-line transform:

1. **`mapped_params` sync.** `params.severity` is projected at write time into a top-level `mapped_params.severity` sort value (`high` → `[value]` via `SEVERITY_MAP`), and the find/sort/filter path reads that projection instead of `params`. Non-canonical casing projects to `''`, and no write path runs during migration to fix it. The transform therefore recomputes `mapped_params.severity` with the same `getModifiedValue` util the writers use, so a normalized rule sorts and filters exactly like a natively-lowercase one.
2. **AAD re-encryption.** `params` and `mapped_params` are both in the rule's `attributesToIncludeInAAD` (saved_objects/index.ts:58-77). Changing their values without re-encrypting would make every touched rule's API key undecryptable, so version 14 goes through `encryptedSavedObjects.createModelVersion` (decrypt with old AAD → transform → re-encrypt with new AAD), with `shouldTransformIfDecryptionFails: [value]` matching the plugin's long-standing migrate-anyway policy (migrations/utils.ts:31).

Rules with lowercase or absent `severity` pass through with byte-identical attributes (the transform returns the document untouched), and no storage shape changes: v14's schema re-exports v13's, and the change is `unsafe_transform` because core's contract reserves `data_backfill` for newly introduced fields (transformations.ts:78-80).

## Deliberately left unchanged

- **Write paths and find rewrites** (`rules_client/common/mapped_params_utils.ts`, rule create/update): already lowercase-consistent for canonical input; the migration reuses `getModifiedValue` rather than duplicating the mapping.
- **alerting_v2 plugin**: its rule saved-object schemas contain no `params` and no `severity` at all (grep across `alerting_v2/server/saved_objects/schemas/` returns zero hits) — nothing to normalize.
- **Rule templates** (`alerting_rule_template`): they share the rule `params` schema (raw_rule_template/v1.ts:19) but are not rules, have no `mapped_params` projection, and rules created from a template go through the normal create path, which validates params and computes `mapped_params` fresh.
- **`ad_hoc_run_params`**: stores a point-in-time rule snapshot including `params` (raw_ad_hoc_run_params/v1.ts:28); these are transient backfill-run documents, not rules.
- **Legacy 7.x–8.8 migrations**: frozen; they run before model versions, and the 8.2 `addMappedParams` migration is what guarantees `mapped_params` exists on any rule with a `severity` param by the time v14 runs.
- **`mapped_params.risk_score`**: never recomputed — only the severity member is touched, keeping already-lowercase rules at zero value changes.

## Residual risk

- Every rule document is decrypted and re-encrypted once during the v14 migration (inherent to ESO model versions; same as the shipped `connector_token` v2). Attribute values are unchanged for already-canonical rules; only API-key ciphertext bytes refresh.
- A rule whose API key can't be decrypted migrates with encrypted attributes stripped and a logged warning instead of failing the upgrade — the same degradation every prior alerting ESO migration chose.
- Non-canonical labels like `INFO` become `info` and still project to `''` — identical behavior to before, by design.
- This worktree intentionally blocks bootstrap/type-check/lint/tests (the yarn shim exits with "finalize from static reading"), so verification was static: every import, export, and type in the new code was cross-checked against its defining source (`SavedObjectModelUnsafeTransformFn` at core index.ts:153, `getModifiedValue` in the rules_client barrel, `createModelVersion` on the ESO setup contract, the `typeSafeGuard` idiom as used by fleet/entity_manager).
