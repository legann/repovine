## Summary

**What changed:** Rule saved objects (`alert` type) gain model version **14**, which lowercases `params.severity` (e.g. `High`, `MEDIUM`, `Critical` → `high`, `medium`, `critical`) during upgrade. Rules with lowercase severity or no severity param pass through with values untouched. Nothing else about the stored shape changes.

**The key design constraint:** `params` is in the rule type's `attributesToIncludeInAAD` (`saved_objects/index.ts:58-77`), so editing it in a plain model version would break decryption of every migrated rule's encrypted API key. The migration is therefore wrapped in `encryptedSavedObjects.createModelVersion` (decrypt → transform → re-encrypt), the same pattern as the actions plugin's `connectorTokenModelVersions`. It sets `shouldTransformIfDecryptionFails: true`, matching alerting's long-standing legacy behavior (`migrations/utils.ts:31`), so rules whose key was already undecryptable still migrate (with the dead key stripped) instead of failing the upgrade. The transform is an `unsafe_transform` rather than `data_backfill` because core documents backfill as for newly-introduced fields only.

**Files changed** (all under `x-pack/platform/plugins/shared/alerting/server/saved_objects/`):
- `model_versions/rule_model_versions.ts` — converted the static map to a `getRuleModelVersions(…)` factory (versions 1–13 unchanged, only re-indented); added the `normalizeSeverityParam` transform and ESO-wrapped version `'14'` with the type's registration frozen as of v14.
- `schemas/raw_rule/v14.ts` (new) + `schemas/raw_rule/index.ts` — v14 schema re-exports v13 (no shape change), following the existing v13 pattern.
- `model_versions/index.ts`, `index.ts` — re-export rename and `[expr]` at the registration site.

**Deliberately left unchanged:**
- `mapped_params.severity` (the derived sortable form, e.g. `[value]`): miscased rules already store `''` there because `SEVERITY_MAP` is lowercase-keyed (`rules_client/common/mapped_params_utils.ts:19-24`), and it's recomputed from params on every rule create/update/bulk-edit (`transform_rule_domain_to_rule_attributes.ts:30`, `update_rule.ts:365`, `update_rule_in_memory.ts:289`) — it self-heals, and rewriting it would exceed the "nothing beyond case normalization" constraint.
- Legacy `migrations/` pipeline — frozen 7.x/8.x history; model versions are the active mechanism (used by MVs 1–13).
- `alerting_rule_template` and `ad_hoc_run_params` SO types — separate types; the task targets existing rules (`raw_rule_template/v1.ts:19` shares the params schema but templates aren't rules; ad-hoc runs are backfill execution snapshots).
- Snooze conditions' `severity_equals` values — schema-enforced lowercase literals at write time (`raw_rule/v12.ts:27-36`), not the severity param.
- Write-path APIs — no create/update-time normalization was requested.
- Core snapshot tests need nothing: `type_registrations.test.ts` tracks only type names, and no test asserts on the alert type's model version map or virtual version.

**Residual risk:** type check/lint/Jest could not be executed here (environment intentionally not bootstrapped — the bootstrap attempt returned an explicit "do not run installs/tests" notice), so correctness rests on static verification against the cited precedents. The migration re-encrypts every rule doc once (new ciphertext bytes, identical plaintext) — inherent to the ESO wrapper and identical to how connector tokens handled it. Normalization is strictly case-folding: values like `'Critical '` (trailing space) or non-canonical labels are lowercased but not trimmed or remapped, per the constraint.
