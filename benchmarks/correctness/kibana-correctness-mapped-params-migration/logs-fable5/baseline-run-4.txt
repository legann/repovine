## Summary

**What changed:** Rule saved objects (`alert` type) now have model version **14**, which lowercases the `severity` rule param (`params.severity`) during upgrade. Rules with an already-lowercase severity or no severity param pass through byte-identical at the attribute level; nothing else about the stored shape changes.

**Where the migration is localized:** `x-pack/platform/plugins/shared/alerting/server/saved_objects/model_versions/rule_model_versions.ts` — the active migration mechanism for the rule SO type (the legacy `migrations/` map is frozen at 8.8.0).

**The load-bearing design decision:** `params` is in the rule type's `attributesToIncludeInAAD` (`saved_objects/index.ts:58-77`), meaning the encrypted `apiKey`/`uiamApiKey` attributes are cryptographically bound to `params`. A plain model version that rewrote `params.severity` would leave every affected rule's API key permanently undecryptable — rules would load but fail to run. Version 14 is therefore wrapped in `encryptedSavedObjects.createModelVersion`, which decrypts with the pre-transform attributes, applies the normalization, and re-encrypts against the updated AAD. `shouldTransformIfDecryptionFails: true` matches the plugin's existing precedent (`createEsoMigration`'s `shouldMigrateIfDecryptionFails: true`) so already-corrupt documents don't block the upgrade. The change uses `unsafe_transform`, since core documents `data_backfill` as only for newly-introduced fields (`model_change.ts:107-109`).

**Files touched:**
- `alerting/server/saved_objects/model_versions/rule_model_versions.ts` — `ruleModelVersions` const became `getRuleModelVersions(…)` (same pattern as the actions plugin's `connectorTokenModelVersions`); added the transform and version `'14'`.
- `alerting/server/saved_objects/index.ts` — extracted the rule ESO registration into a shared `ruleTypeRegistration` const, used for both `encryptedSavedObjects.registerType` and the model version's input/output types (single source of truth, no import cycle).
- `alerting/server/saved_objects/model_versions/index.ts` — export rename.
- `alerting/server/saved_objects/schemas/raw_rule/v14.ts` (new) + `raw_rule/index.ts` — v14 schema re-exports v13 (no shape change), following the exact v13 precedent.

**Deliberately unchanged, with proof of out-of-scope:**
- **`mapped_params.severity`** (derived sort/filter field): every write path and the 8.2 backfill compute it via `getMappedParams` → `[expr]` (`[expr]`; `saved_objects/migrations/8.2/index.ts:14-34`). `SEVERITY_MAP` has only lowercase keys, so rules with mis-cased severity already persist `''` there — leaving it preserves exact pre-upgrade filter/sort behavior, and rewriting it would alter stored values beyond the case normalization. It self-corrects on the next params update.
- **Legacy migrations (7.10–8.8)**: immutable historical map; the task explicitly asks for a model version.
- **Rule templates** (`alerting_rule_template`): separate, unencrypted SO type at model version 1 (`rule_template_model_versions.ts`); the task scopes to rules.
- **`alerting_v2` plugin**: its rule SO schema (`rule_saved_object_attributes`, model version 1) has no `severity` param; that plugin's severity references are alert-event dispatcher code.
- **Write-path normalization** (create/update APIs): the task asks for migration of existing data only.

**Residual risk:** The environment blocks bootstrap, so type check/lint/jest could not be run — all imports, exported symbols, and API signatures were verified statically against source. The ESO wrapper re-encrypts every rule doc during migration (plaintext and AAD unchanged for untouched rules; ciphertext bytes re-roll — inherent to `createModelVersion` and identical to the actions plugin precedent). Rules whose API key was already undecryptable pre-upgrade get their encrypted attributes stripped with a logged warning instead of failing the migration — those rules were already non-functional, and this mirrors long-standing plugin behavior. Serverless zero-downtime is safe: the ESO registration itself is unchanged (input == output), and the doc shape is unchanged, so the previous version reads v14 docs through its v13 `forwardCompatibility` schema and decrypts them normally.
