## Summary

Added **model version `14`** to the alerting rule saved object (`alert` type), which lowercases each rule's `params.severity` value during upgrade. Rules whose severity is already lowercase, is absent, or is not a string pass through untouched. No mappings or shape changes.

The one non-obvious requirement: `params` is part of the AAD that the rule's encrypted attributes (`apiKey`, `uiamApiKey`) are cryptographically bound to (`RuleAttributesIncludedInAAD`, `saved_objects/index.ts:58`). Rewriting `params` without re-encrypting would make every migrated rule's API key undecryptable — rules would stop running. The migration is therefore wrapped in `encryptedSavedObjects.createModelVersion(…)`, which decrypts each rule, applies the transform, and re-encrypts with the updated AAD. `shouldTransformIfDecryptionFails: true` matches the policy of every prior alerting rule migration (`migrations/utils.ts:31`), so rules that were already undecryptable don't block the upgrade.

## Related paths deliberately left unchanged

- **`mapped_params.severity`** (derived sort/filter copy): `getMappedParams` maps only exact lowercase values and stores `''` otherwise (`[expr]`), so miscased rules already have `''` there — the migration doesn't regress them, and the value is recomputed on the next rule update. Backfilling it would exceed the task's scope ("normalizes each existing rule's `severity` param").
- **Write-path normalization** (create/update/bulk-edit APIs): the task asks for a migration only; param casing at write time is owned by each rule type's param validator (e.g. security solution's `Severity` io-ts type, which already enforces the lowercase enum).
- **Legacy migrations** (`saved_objects/migrations/`, 7.10–8.8): frozen historical migration functions; model versions are the current mechanism for this type (`modelVersions` on the registration, versions 1–13 already present).
- **`alerting_v2` plugin**: separate `alerting_rule` SO type (`alerting_v2/common/saved_object_types.ts:8`) with its own schema (`metadata.name`, ES|QL rules) — no `severity` rule param and no `mapped_params` machinery.
- **`severity_equals` snooze-condition literals** in `raw_rule/v12.ts`: those constrain snooze conditions, not the rule param; already lowercase-only.

## Residual risk

- This worktree is intentionally not bootstrapped (bootstrap is blocked), so **type check, eslint, and jest could not be executed**; correctness was verified statically against the exact same patterns used by fleet, actions, and the ESO example plugin. Formatting was hand-applied to prettier conventions.
- The migration decrypts and re-encrypts **every** rule document once (inherent to any AAD-affecting change; same as actions' connector-token v2). Attributes of already-lowercase rules are byte-identical; only ciphertext/nonce changes, which has no observable effect.
- Lowercasing is unconditional for any string `severity` param: a hypothetical rule type storing a non-canonical, case-sensitive severity label would also be lowercased — consistent with the task's definition of the param, and with the platform's own case-sensitive severity handling.
- Any CI snapshot of registered SO type hashes would need a bump; the historical `check_registered_types` test is absent from this tree, and the mappings snapshot (`current_mappings.json`) is unaffected since version 14 adds no mappings.
