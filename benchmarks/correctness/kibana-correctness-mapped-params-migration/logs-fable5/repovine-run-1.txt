## Summary

Existing alerting rules (`alert` saved objects) now get their `severity` param normalized to lowercase on upgrade via a new saved-object **model version 14**. Rules with no `severity` param, a non-string `severity`, or an already-lowercase value pass through untouched. Because `params` is part of the rule's encryption AAD, the transform is wrapped with `encryptedSavedObjects.createModelVersion`, which decrypts each rule's API keys before the change and re-encrypts them against the updated attributes — this is what keeps every rule loadable and runnable after the upgrade (a plain transform would have made `apiKey` undecryptable and broken rule execution).

When the case actually changes, the migration also updates `mapped_params.severity` (e.g. `''` → `[value]`), only if `mapped_params` already exists on the document. That field is the stored projection of `params.severity` that `find`/sort/KQL filters read instead of `params` (`find_rules.ts:87-106` rewrites those queries via `mapped_params_utils.ts`), every writer keeps it equal to `getMappedParams(…)` (`transform_rule_domain_to_rule_attributes.ts:30`), and no write path runs during migration — without this, a rule normalized to `high` would still be invisible to severity filters. No attribute is ever added or removed, so the storage shape is unchanged.

- **Rule write paths / rules client**: the task covers *existing* stored rules; writers already keep `mapped_params` consistent on every create/update (`transform_rule_domain_to_rule_attributes.ts:30`).
- **Legacy migrations** (`saved_objects/migrations/`): frozen per-release transforms for ≤8.x docs; new behavior belongs in an appended model version (the registry is an append-only boundary).
- **Rule templates** (`alerting_rule_template`): a distinct SO type; it stores `params` (`schemas/raw_rule_template/v1.ts:19`) but has no `mapped_params` projection and isn't a rule — the task scopes to "each existing rule".
- **Ad-hoc backfill runs** (`ad_hoc_run_params`): embed a rule-params snapshot (`schemas/raw_ad_hoc_run_params/v1.ts:28`) but are transient execution state deleted after the backfill completes (`task_runner/ad_hoc_task_runner.ts:676-688`), not rules.
- **`alerting_v2` plugin**: its saved objects contain no `severity` anywhere (`[expr]` → zero matches).
- **`latest.ts` raw-rule types**: v14's schema object is v13's, so `RawRule` is unchanged.

### Residual risk

- The ESO wrapper re-encrypts API keys for **every** rule doc during the one-time migration, including untouched ones — same plaintext and AAD, fresh ciphertext; this is inherent to ESO model versions and matches the actions plugin's `connector_token` v2 precedent. Rules whose keys already can't decrypt (rotated encryption key) get those attributes stripped with a logged warning — identical to every prior alerting ESO migration.
- Non-canonical values that aren't just miscased (e.g. `Unknown` → `unknown`) are lowercased but still project to `''`, unchanged from today's behavior for such values.
- I could not run lint/type-check/tests: this worktree is intentionally not bootstrapped (installs and checks are blocked). Every imported symbol, type signature, and the wrapper's decrypt→transform→re-encrypt path was verified by reading the corresponding sources (`create_model_version.ts`, `build_transform_fn.ts`, type exports). In a real PR, the SO CI checks would also flag the new model version for review; per the constraints I added no test or snapshot updates.
