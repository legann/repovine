## What changed

Upgrading Kibana now runs a new model version (**14**) on the `alert` saved-object type that lowercases each rule's `params.severity` when it is a string whose lowercase form differs (`High` → `high`, `MEDIUM` → `medium`). In the same transform, if the rule's existing `mapped_params.severity` projection is present, it is rewritten to the sortable projection of the normalized value (`[value]` etc., or `''` for values outside the canonical set — exactly what the write paths would persist). Rules with lowercase or absent severity, and non-string severity values, pass through untouched. No fields are ever added or removed.

Because `params` and `mapped_params` are in the rule's encrypted-saved-object AAD list, the transform runs inside `encryptedSavedObjects.createModelVersion` (decrypt → transform → re-encrypt), with `shouldTransformIfDecryptionFails: [value]` matching alerting's legacy `shouldMigrateIfDecryptionFails` convention — a naive model version here would have changed AAD without re-encrypting and made every migrated rule's API key undecryptable, breaking rule execution.

- **Rule write paths** (`application/rule/transforms/transform_rule_domain_to_rule_attributes.ts:30`, `update_rule.ts:365`, `bulk_edit/update_rule_in_memory.ts:289`): they already recompute `mapped_params` via `getMappedParams` on every save; the migration reproduces their output for stored docs, so no change is needed.
- **Find/filter/sort rewrite** (`rules_client/common/mapped_params_utils.ts`): read-only consumer of the projection. Its query-time lookup `[expr]` (line 106) is still case-sensitive for **user-supplied filter input** — that's query handling, not stored data, and outside "normalize each existing rule's severity param".
- **Legacy migrations** (`saved_objects/migrations/8.2/index.ts`): frozen pre-8.8 pipeline; post-8.8 changes go through model versions (the 8.2 `addMappedParams` migration is the precedent for computing the projection during migration).
- **`ad_hoc_run_params` SO**: embeds rule `params`, but `data/ad_hoc_run/types/ad_hoc_run.ts:23-26` documents it as a deliberate point-in-time snapshot ("run the rule as it was configured when the backfill job was scheduled"); it is not a rule.
- **`alerting_v2` plugin**: `grep -rn severity server/saved_objects` returns nothing; its severity usages are alert-episode fields in `server/lib/dispatcher/`, not rule params.
- **Rule templates / security-solution code**: templates aren't rules; detection rules are stored as `alert` SOs and are therefore covered by this migration — their strict validator `[expr]` (`security_solution/common/api/detection_engine/model/rule_schema/common_attributes.gen.ts:202`) is the consumer that starts accepting previously miscased rules.
