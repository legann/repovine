## Summary

Existing alerting rules (`alert` saved objects) get a new **model version `14`** that lowercases `params.severity` when it is a string with uppercase characters. Rules whose severity is already lowercase, is absent, or is not a string are passed through byte-identical. Because `params` is part of the rule's AAD (`RuleAttributesIncludedInAAD`, `saved_objects/index.ts:58-77`), the transform is wrapped in the ESO plugin's `createModelVersion`, which decrypts `apiKey`/`uiamApiKey` before the rewrite and re-encrypts after — without this, every normalized rule's API key would become undecryptable and the rule would stop executing after upgrade. `shouldTransformIfDecryptionFails: true` matches the behavior of every legacy alerting migration (`saved_objects/migrations/utils.ts:31`), so an already-undecryptable rule still upgrades (with encrypted attributes stripped and a logged warning) instead of failing the migration.

## Where the migration lives / files changed

- `x-pack/platform/plugins/shared/alerting/server/saved_objects/model_versions/rule_model_versions.ts` — the migration itself. `ruleModelVersions` became a function of `EncryptedSavedObjectsPluginSetup` (same pattern as `connectorTokenModelVersions` in the actions plugin). Version `14` is an `unsafe_transform` (the documented change type for mutating existing data; `data_backfill` is for newly introduced fields) wrapped in `encryptedSavedObjects.createModelVersion`, with a frozen inline copy of the rule ESO registration as both `inputType` and `outputType` — verified programmatically to match the live registration (2 encrypted attrs, 18 AAD attrs, type `alert`). It is frozen inline because model-version transforms must keep using the registration as of this version even if the live one evolves, and because importing from `../index` would form a require cycle in which the constants are `undefined` at module-eval time.
