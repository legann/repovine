## Summary

Alerting rules (`alert` saved-object type) get a new **model version 14** that lowercases `params.severity` (`High` → `high`, `MEDIUM` → `medium`, …). Rules whose severity is already lowercase, non-string, or absent pass through untouched. Two properties of this type made a naive transform unsafe, and both are handled:

- **`severity` is a mapped param.** The find/sort/filter path reads the stored `mapped_params.severity` projection instead of `params.severity` (`mapped_params_utils.ts`), and only rule create/update write paths recompute it — so the transform recomputes `mapped_params` via the same shared `getMappedParams()` the write paths use. A rule stored as `High` previously projected to `''` (invisible to severity filters); after migration it projects to `[value]` and behaves exactly like a rule that had been saved as `high`.
- **`params` and `mapped_params` are AAD attributes of an encrypted type** (`RuleAttributesIncludedInAAD`), so mutating them would break `apiKey` decryption. Version 14 is wrapped in `encryptedSavedObjects.createModelVersion` (decrypt → transform → re-encrypt), with `shouldTransformIfDecryptionFails: [value]` matching the plugin's existing convention (`migrations/utils.ts:31`) so already-undecryptable rules still migrate (stripped, logged) instead of failing the upgrade.

## Deliberately unchanged, with proof

- **Rule write/read paths and `mapped_params_utils.ts`** — already produce canonical state for lowercase severities; migration reuses `getMappedParams` rather than altering the contract (precedent: `migrations/8.2/index.ts:21-29` does the same in a migration).
- **Legacy migrations dir and model versions 1–13** — frozen released surfaces; new behavior is appended as a new version (repovine boundary annotation on `rule_model_versions.ts`).
- **`schemas/raw_rule/latest.ts`** — still resolves to the v12 schema because v13/v14 change no shape (constraint: no storage-shape change).
- **Rule templates (`alerting_rule_template`)** — persist `params` (`raw_rule_template/v1.ts:19`) but are not rules, have no `mapped_params` in their schema, and are not ESO-registered (`saved_objects/index.ts:306-329`); task scope is "each existing rule".
- **`alerting_v2` plugin** — `grep -rn severity alerting_v2/server/saved_objects/` returns nothing; its severity code is alerts-as-data dispatch, not rule params.
- **Security-solution severity UI / `@kbn/rule-data-utils` alert severity fields** — alert documents, not rule saved objects. Detection rules themselves live in the same `alert` type and are covered by this migration automatically.
