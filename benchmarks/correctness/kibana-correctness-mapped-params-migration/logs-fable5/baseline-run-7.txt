## Summary

**Changed behavior**: On upgrade, the `alert` saved-object type migrates to model version `14`, which lowercases `params.severity` on every rule where it is a string with non-lowercase characters (`High` → `high`, `MEDIUM` → `medium`). Rules with lowercase severity or no severity param pass through the transform unchanged. Because `params` is part of the encryption AAD for rule API keys (`RuleAttributesIncludedInAAD`, `saved_objects/index.ts:67`), the version is wrapped in `encryptedSavedObjects.createModelVersion`, which decrypts `apiKey`/`uiamApiKey` against the old attributes and re-encrypts against the transformed ones — without this, every case-normalized rule's API key would become undecryptable and the rule would stop running.

**Migration localized in**: `x-pack/platform/plugins/shared/alerting/server/saved_objects/model_versions/rule_model_versions.ts` — model version `'14'`, an `unsafe_transform` (core's docs forbid `data_backfill` for mutating existing fields, `model_change.ts:107-109`). The ESO registration snapshot (`inputType`/`outputType`, identical since the registration itself doesn't change) is pinned in-file, following the actions plugin's `connector_token_model_versions.ts`. `shouldTransformIfDecryptionFails: true` matches the plugin's legacy stance (`migrations/utils.ts:31`) so a rule with an undecryptable key still migrates (key stripped, as before) instead of aborting the upgrade.

**Files changed**:
- `.../saved_objects/model_versions/rule_model_versions.ts` — map converted to a function of the ESO setup contract; transform + pinned ESO registration + version `'14'` added.
- `.../saved_objects/schemas/raw_rule/v14.ts` (new) — re-exports v13's schema; no data-shape change, same convention as `v13.ts`.
- `.../saved_objects/schemas/raw_rule/index.ts` — exports `rawRuleSchemaV14`.
- `.../saved_objects/index.ts` — registration now passes the ESO setup: `[expr]`.

**Deliberately left unchanged**:
- **`mapped_params.severity`** (derived search field): for mixed-case severities it already stored `''` (`mapped_params_utils.ts:106`, `[expr]`), so the migration doesn't make it newer-wrong, and it holds transformed values (`[value]`), not the label — rewriting it would exceed "case normalization only". It self-heals on the next rule update (`getMappedParams`, `mapped_params_utils.ts:31-44`).
- **Write path**: new rules can still be created with mixed-case severity; params are opaque to the framework (`raw_rule/v1.ts:277`, `recordOf(…)`) and the task scopes the change to migrating existing rules.
- **`alerting_v2` plugin**: separate SO type at model version 1; its severity lives in alert-event data streams (`alerting_v2/server/resources/datastreams/alert_events.ts`), not rule params.
- **Legacy `saved_objects/migrations/`**: frozen version-based history ending at `8.8.0`; model versions are the active mechanism.
- **`latest.ts`**: unchanged, consistent with v13 (it points at v12, where the schema shape was last defined).

**Residual risk**: the migration decrypts/re-encrypts every rule's API key once (inherent to `params` ∈ AAD; same mechanism the actions plugin shipped for connector tokens). Non-canonical string labels (e.g. `Sev1`) are also lowercased, per the task's unconditional normalization. One known CI fallout I could not address within constraints: the ESO CI check `encrypted_saved_objects/integration_tests/ci_checks/check_registered_types.test.ts` inline-snapshots the model-version list and will need `[expr]` added (its `alert` registration hash is unaffected since the live ESO registration is untouched). I also couldn't run `type_check`/`eslint` because this benchmark worktree blocks bootstrapping; line widths, import style, and types were verified manually against the declarations.
