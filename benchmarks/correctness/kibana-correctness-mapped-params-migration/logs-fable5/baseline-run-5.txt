## Summary

Implemented model version **14** of the alerting rule saved object (`alert` type) that lowercases `params.severity` on existing rules during upgrade. Rules whose `severity` is already lowercase, is absent, or is not a string pass through untouched. Because `params` is part of the rule's encrypted-saved-object AAD (`RuleAttributesIncludedInAAD` in `saved_objects/index.ts:58`), the version is wrapped with the ESO plugin's `createModelVersion`, which decrypts each document with the pre-transform attributes and re-encrypts with the post-transform attributes — without this, changing `params` would make `apiKey` permanently undecryptable. `shouldTransformIfDecryptionFails: true` matches the tolerance policy of every prior alerting ESO migration (`saved_objects/migrations/utils.ts:31`), so an already-undecryptable rule is migrated with a warning instead of failing the upgrade.

## Where the migration lives, and files changed

The migration is localized in the alerting plugin's model-versions layer, `x-pack/platform/plugins/shared/alerting/server/saved_objects/`:

| File | Change |
|---|---|
| `model_versions/rule_model_versions.ts` | The migration itself: `transformSeverityParamToLowercase` (an `unsafe_transform`, since core docs restrict `data_backfill` to newly introduced fields), a frozen snapshot of the rule ESO registration as of v14, and new version `'14'` wrapped in `encryptedSavedObjects.createModelVersion`. `ruleModelVersions` became the factory `getRuleModelVersions(…)` — the same conversion the actions plugin made for `connectorTokenModelVersions`. |
| `schemas/raw_rule/v14.ts` (new) | Re-exports the v13 schema; no shape change (same pattern v13 used for its mapping-only change). |
| `schemas/raw_rule/index.ts` | Exports `rawRuleSchemaV14`. |
| `model_versions/index.ts` | Re-exports `getRuleModelVersions`. |
| `saved_objects/index.ts` | Registers `[expr]` for the `alert` type. |

The ESO registration snapshot is duplicated inline (type `'alert'`, encrypt `apiKey`/`uiamApiKey`, the 18 AAD attributes) rather than imported from `../index.ts`: importing would create a module cycle (`index.ts` → `model_versions` → back), and the snapshot must stay frozen at its v14-era values even if the live registration later changes — same reasoning as the per-version registrations in `actions/server/saved_objects/model_versions/connector_token_model_versions.ts`.

## Related code paths deliberately left unchanged

- **`mapped_params.severity` is not recomputed.** It is derived from params only at rules-client write time (`getMappedParams`, `server/rules_client/common/mapped_params_utils.ts:31`), and `[expr]` (line 106) means a rule stored with `High` already persisted `''` there before the upgrade. It is only consumed to rewrite find/filter/sort fields (same file), so leaving it byte-identical preserves exact pre-upgrade behavior; rewriting it would be a value backfill beyond case normalization. It self-corrects on the rule's next update.
- **Write paths.** Param validation belongs to each rule type (`validate.params` via `rule_type_registry.ts`), not the framework; normalizing new writes is a behavior change outside "migrate existing rules".
- **Legacy migrations dir (`saved_objects/migrations/`).** Frozen pre-8.8 mechanism; all data changes since (MV 1–13) go through model versions, and legacy migrations don't run under serverless ZDT.
- **`alerting_v2` plugin.** Its `alerting_rule` SO has no `params`/`severity` attribute (nothing in `server/saved_objects/schemas/rule_saved_object_attributes/`); severity there is an alert-event field extracted from ES|QL rows at runtime (`server/lib/rule_executor/build_alert_events.ts`, `resources/datastreams/alert_events.ts:43`).
- **Rule templates and ad-hoc runs.** `alerting_rule_template` persists `params` (`schemas/raw_rule_template/v1.ts:19`) and `ad_hoc_run_params` embeds a rule snapshot with `params` (`schemas/raw_ad_hoc_run_params/v1.ts:28`), but neither is a rule: templates don't execute, ad-hoc runs are transient backfill records. The task scopes normalization to "each existing rule".
- **`schemas/raw_rule/latest.ts`.** Still aliases the v12 schema object — v13 and v14 are pure re-exports of it, so the `RawRule` type is already current; the repo made the same call when v13 was added (`v13.ts:8`).
- **Snooze severity literals in `raw_rule/v12.ts:27`.** Those are alert-severity values inside snooze conditions, already schema-enforced lowercase, unrelated to `params.severity`.

## Residual risk

- This worktree is intentionally not bootstrapped, so `type_check`, eslint, and jest could not be run; verification is static, though the code mirrors compiled in-repo precedents (actions' `createModelVersion` usage, fleet's `SavedObjectModelUnsafeTransformFn` transforms) line-for-line in structure.
- Every rule is decrypted and re-encrypted once during the v13→v14 migration (inherent to ESO model versions). For unchanged rules only the `apiKey` ciphertext bytes rotate — plaintext, AAD, and all attributes are identical. Rules whose key material can't be decrypted are migrated with encrypted attributes stripped and a logged warning; such rules were already unable to execute.
- Rules that had non-lowercase severity keep their pre-existing empty `mapped_params.severity` until their next save — an intentional no-regression, not a fix.
- In the upstream repo, the registered-types migration-hash CI snapshot (not present in this worktree) would need its routine update for the `alert` type in a real PR.
