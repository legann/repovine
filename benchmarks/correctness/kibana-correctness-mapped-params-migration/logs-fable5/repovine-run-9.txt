## Summary

**What changed:** the `alert` saved-object type (the storage for all Kibana alerting rules) gains **model version 14**, which lowercases `params.severity` on existing rule documents during upgrade. Rules with no `severity` param, a non-string `severity`, or an already-lowercase value pass through with attributes untouched. Because a rule's `severity` also feeds the persisted `mapped_params` projection that `find`/sort/filter reads in place of `params` (`SEVERITY_MAP`: `[expr]` → `[expr]`, non-canonical case → `''`), the transform recomputes `mapped_params` with the same `getMappedParams` util every write path uses — so a rule stored as `High` becomes findable as `high` after upgrade, restoring the plugin's invariant `[expr]`.

**Why the ESO wrapper:** `params` and `mapped_params` are in the `alert` type's AAD set (`saved_objects/index.ts:58-77`). Rewriting them in a plain model version would leave every migrated rule's encrypted `apiKey` undecryptable. Version 14 is therefore wrapped in `encryptedSavedObjects.createModelVersion` (decrypt → transform → re-encrypt), with a frozen inline snapshot of the current registration as both `inputType` and `outputType`, and `shouldTransformIfDecryptionFails: [value]` so rules with already-broken keys don't abort the upgrade — the established pattern from `connector_token_model_versions.ts` and the ESO example plugin. The change type is `unsafe_transform`, since core docs explicitly forbid `data_backfill` for mutating existing fields (`model_change.ts:107-109`).

**Deliberately unchanged, with the source proving each out of scope:**
- **`mapped_params` write/read paths** (`mapped_params_utils.ts`, `transform_rule_domain_to_rule_attributes.ts:30-42`, find-path rewriting): writers already persist `[expr]`; the migration now produces the identical result, so no consumer change is needed.
- **Live ESO registration** (`saved_objects/index.ts:51-77`): the migration changes attribute values, not the registration; version 14 freezes its own snapshot per the `connector_token_model_versions.ts:20-44` precedent.
- **Legacy 7.x/8.x migrations** (`saved_objects/migrations/`): frozen mechanism; the task specifies a model version. The 8.2 migration (`migrations/8.2/index.ts:14-34`) served only as precedent for recomputing `mapped_params` in a migration.
- **`raw_rule` schemas v1–v13 and `latest.ts`**: released model versions are frozen (repovine boundary annotation); v14 has the same shape as v13/v12, so the `RawRule` type in `latest.ts` is already correct.
- **`alerting_v2` plugin**: its rule saved-object schemas contain no `severity` attribute (grep over `alerting_v2/server/saved_objects/` returns zero matches).
- **Write-time validation of severity case**: `params` is `schema.recordOf(…)` (`raw_rule/v1.ts:277`) — the framework doesn't validate severity, and adding enforcement would change behavior beyond the case normalization (constraint 1).
- **ESO CI tripwire snapshot** (`encrypted_saved_objects/integration_tests/ci_checks/check_registered_types.test.ts:96-115`): designed to fail whenever an ESO type gains a model version, forcing security-team review; updating its inline snapshot (adding `[expr]`) is a test-file change, prohibited by constraint 3. The registration-hash snapshot in the same file is unaffected since the live registration is unchanged.

**Residual risk:** this worktree intentionally blocks bootstrap/type-check/tests, so the change is verified statically only — though every type-level construct is copied from code that compiles today (`connectorTokenModelVersions`, `transformRuleDomainToRuleAttributes`, core's documented `typeSafeGuard` pattern). In CI, the ESO model-version snapshot test will fail until regenerated with `[expr]` — its intended purpose. During the one-time migration every rule document is decrypted and re-encrypted (inherent to AAD-touching transforms); for already-lowercase rules the stored attributes are unchanged and only the `apiKey` ciphertext is re-encrypted to an equivalent value.
