## Where the migration lives

`x-pack/platform/plugins/shared/alerting` owns alerting rules as the `alert` saved-object type, versioned through `ruleModelVersions` (registered in `server/saved_objects/index.ts`). Two properties of that type shaped the implementation:

1. **`alert` is an encrypted saved object** with `params` and `mapped_params` in its AAD list (`saved_objects/index.ts:58-77`). A plain transform that edits `params.severity` would change the AAD and make every migrated rule's `apiKey` undecryptable — the rule would load but never run again. The new version is therefore created via `encryptedSavedObjects.createModelVersion(…)` (decrypt → transform → re-encrypt), following the in-tree precedent `actions/server/saved_objects/model_versions/connector_token_model_versions.ts`. `shouldTransformIfDecryptionFails: [value]` matches the policy alerting already uses for all its legacy ESO migrations (`saved_objects/migrations/utils.ts:31`), so rules whose encryption was already broken don't fail the whole upgrade.
2. **`severity` is doubly persisted.** Write paths project it into a stored `mapped_params.severity` sort key via `SEVERITY_MAP` (`rules_client/common/mapped_params_utils.ts`); find/sort/filter read that projection instead of `params`, and non-canonical casing projects to `''`. Since write paths don't run during migration, the transform recomputes `mapped_params.severity` (reusing the production `getModifiedValue`) whenever it lowercases `params.severity` — no shape change, just keeping the existing invariant `[expr]`.

The transform itself: if `params.severity` is not a string (ML anomaly rules store a numeric severity — `x-pack/platform/packages/shared/ml/common-types/alerts.ts:138`) or is already lowercase, the document is returned untouched; otherwise `severity` is lowercased and the `mapped_params` projection (only if already present on the doc) is updated to match.
