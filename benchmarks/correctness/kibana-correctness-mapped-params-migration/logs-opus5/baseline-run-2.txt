## Where I localized it

Model version **14** on the `alert` saved object, in the alerting plugin's rule model-version map. The `alert` SO is an Encrypted Saved Object and **`params` is part of its AAD** (`saved_objects/index.ts:58-77`), so the migration is wrapped in `encryptedSavedObjects.createModelVersion`. Mutating `params.severity` without that wrapper changes the AAD out from under the stored ciphertext and permanently breaks decryption of every migrated rule's `apiKey` — the wrapper decrypts with the old values and re-encrypts with the new ones.

## Deliberately left unchanged

- **Numeric `severity` params.** `anomaly_detection/v1.ts:18` (`schema.number(…)`) and `uptime_duration_anomaly/v1.ts:15` (`schema.number()`) store an anomaly score under the same key. The `[expr]` guard skips them. APM uses `anomalySeverityType` (`apm_anomaly/v1.ts:42`), a different key.
- **`mapped_params.severity`.** `SEVERITY_MAP` is keyed on lowercase and falls back to `''` (`[expr]`), so mixed-case rules *already* store `''` there — unchanged before and after, no regression. Recomputing it would alter a second persisted attribute, which "beyond the case normalization" excludes. It self-heals on the next rule write (`transform_rule_domain_to_rule_attributes.ts:30`, `update_rule.ts:365`, `update_rule_in_memory.ts:289`). Cheap follow-up if you want it fixed now.
- **`alerting_rule_template` SO.** Reuses the rule params schema (`raw_rule_template/v1.ts:19`, `v2.ts:19`) so templates can carry severity, but templates are not rules and the type has no `encryptedSavedObjects.registerType` (`saved_objects/index.ts:250-272`).
- **`ad_hoc_run_params` SO.** Embeds a rule snapshot with free-form params (`raw_ad_hoc_run_params/v1.ts:28`) and `rule` is in AAD (`saved_objects/index.ts:104`), but the object is deleted when the backfill run finishes (`ad_hoc_task_runner.ts:675-688`).
- **`alerting_v2`.** No severity in any of its saved objects; its severity references are alert-event fields in the dispatcher (`lib/dispatcher/types.ts:26`).

## Residual risk

- Every rule in the deployment is decrypted and re-encrypted on upgrade, including ones needing no change. Cost scales with rule count. This is inherent to ESO model versions — there's no per-document opt-out of the wrapper.
- `shouldTransformIfDecryptionFails: true` means a rule whose `apiKey`/`uiamApiKey` can't be decrypted with the primary *or* secondary keys has those attributes stripped and logs a warning rather than blocking the upgrade. Such rules were already non-functional; they need a re-save to mint a new API key. This matches the policy of every existing alerting ESO migration (`migrations/utils.ts:31`).
- A deployment with no decryption keys throws a plain `Error` (not `EncryptionError`) and fails the migration — identical to the legacy path (`create_migration.ts:137` vs `create_model_version.ts:114`), so no new exposure.
- Serverless/ZDT is single-release safe: no attribute is added to or removed from AAD, and the previous Kibana version rebuilds AAD from the migrated document's current values, which match what MV14 encrypted with.
