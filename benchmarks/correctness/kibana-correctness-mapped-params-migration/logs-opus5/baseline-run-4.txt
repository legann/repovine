## Where I localized it

Model version **14** on the `alert` saved object (the alerting plugin's rule SO) — the single type that persists `params.severity`.

The controlling fact: `params` is listed in `RuleAttributesIncludedInAAD` (`saved_objects/index.ts:58-77`), so it feeds the decryption AAD for the encrypted `apiKey`/`uiamApiKey`. A plain model version that rewrote `params.severity` would invalidate the ciphertext for exactly the rules it migrated — those rules would stop running. So the change is wrapped in `encryptedSavedObjects.createModelVersion`, which decrypts → transforms → re-encrypts in one pass. Same pattern as `actions/server/saved_objects/model_versions/connector_token_model_versions.ts:56` and alerting's own legacy `createEsoMigration` (`migrations/utils.ts:23-33`).

I used `unsafe_transform` rather than `data_backfill` because core documents backfill as "only ... to backfill newly introduced fields. ... using such transformations to mutate existing data of the document can lead to data corruption" (`model_change.ts:107-109`).

## Deliberately left unchanged

- **`mapped_params.severity`** — derived, index-only field. `SEVERITY_MAP` (`mapped_params_utils.ts:19-24`) is keyed on lowercase, so a rule stored as `'High'` already has `[expr]` today; leaving it stale preserves pre-migration behavior exactly, and `getMappedParams` recomputes it on the next create/update (`transform_rule_domain_to_rule_attributes.ts:30`, `update_rule.ts:365`, `update_rule_in_memory.ts:289`). Touching it would be a value change beyond case normalization.
- **`alerting_v2`** — separate SO type `alerting_rule` (`alerting_v2/common/saved_object_types.ts:9`) with its own `ruleModelVersions`; grep for `severity` across its `server/saved_objects/` and `common/` returns nothing, and its rule type isn't ESO-registered.
- **Legacy `migrations/` map** — frozen at `8.8.0` (`migrations/index.ts:85`); new work belongs in model versions.
- **Read-side validation** (e.g. `[expr]`, `common_attributes.gen.ts:202`) — normalizing at rest makes stored values conform; no read coercion added.
- **`raw_rule/latest.ts`** — `RawRule` is unchanged since v14 → v13 → v12.

## Residual risk

1. **A CI tripwire will fail and needs security sign-off.** `encrypted_saved_objects/integration_tests/ci_checks/check_registered_types.test.ts` pins the `alert` hash (line 70) and an inline snapshot of ESO model versions needing `[expr]` (lines 124-132). It exists specifically to force review of new ESO model versions against zero-downtime rules. I left it per the "do not modify tests" constraint — it must be updated before merge.
2. **Whole-corpus re-encryption.** `createModelVersion` has no per-document predicate, so every `alert` doc is decrypted and re-encrypted at MV14, including already-lowercase rules. Plaintext and AAD are identical for those; only the ciphertext/IV differs. Same blast radius as the existing 8.2 migration, which used `[expr]`.
3. **`shouldTransformIfDecryptionFails: true`** means a rule with an unreadable API key gets its encrypted attributes stripped (with a logged warning) and needs re-authentication, rather than failing the entire upgrade. This matches alerting's existing migration behavior (`migrations/utils.ts:31`). Rules with `apiKey: null` are unaffected — the decrypt iterator skips null attributes (`encrypted_saved_objects_service.ts:560`).
4. **Non-canonical values** like `'Sev1'` are lowercased to `'sev1'` rather than mapped into the canonical set, following the literal "normalize to lowercase" requirement.
5. **No build verification.** This worktree isn't bootstrapped, so `type_check`, `eslint`, and Jest were unavailable. I verified statically: all imported symbols exist and are exported from the stated packages, transform/result types match, bracket balance, all 14 version keys present, and — scripted — that the pinned `attributesToEncrypt`/`attributesToIncludeInAAD` sets are byte-identical to the live registration, since a typo there would break decryption for every rule.

Serverless ZDT is safe in one release: the AAD attribute *set* is unchanged (input and output registrations are the same object), so the previous Kibana version reconstructs identical AAD from the migrated document and decrypts normally — and it handles lowercase severity better than mixed case.
