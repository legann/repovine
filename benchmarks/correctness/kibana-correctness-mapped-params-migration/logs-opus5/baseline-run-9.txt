## Where the migration is localized

`alert` saved-object type, **model version 14**, in the alerting plugin — the single storage location for rule params. Security Solution detection rules, ES|QL rules, etc. all persist `params.severity` in this same SO type, so one model version covers them.

**Files changed:**

| File | Change |
|---|---|
| `server/saved_objects/model_versions/rule_model_versions.ts` | `ruleModelVersions` becomes a factory taking the ESO setup contract; adds MV 14 (frozen ESO registration snapshot + `normalizeSeverityCasing` transform) |
| `server/saved_objects/schemas/raw_rule/v14.ts` (new) | Re-exports the v13 schema — no data-shape change |
| `server/saved_objects/schemas/raw_rule/index.ts` | Exports `rawRuleSchemaV14` |
| `server/saved_objects/index.ts` | Calls `ruleModelVersions(…)` |

**The load-bearing detail:** `params` is in the rule's AAD (`saved_objects/index.ts:58-77`), so rewriting `params.severity` changes the AAD of every document the transform touches. A plain model version would leave those rules unable to decrypt their `apiKey` — they'd load but stop executing. The version is therefore wrapped in `encryptedSavedObjects.createModelVersion` (`create_model_version.ts:118-133`: decrypt with pre-transform AAD → transform → re-encrypt with post-transform AAD), with `[expr]` since the registration itself is unchanged. `shouldTransformIfDecryptionFails: true` matches the plugin's own precedent for rule migrations (`migrations/utils.ts:31`), so one already-broken key can't abort the whole index migration.

## Residual risk

- **`mapped_params.severity` goes stale.** A rule stored as `'High'` currently maps to `''` (`mapped_params_utils.ts:106` lookup miss). After the migration `params.severity` is `'high'` but `mapped_params.severity` stays `''` until the rule's next write. Sorting/filtering by severity for those rules is no worse than today, but the two fields now disagree. Say the word and I'll extend the transform to recompute it.
- **Every rule is re-encrypted**, including already-lowercase ones — unavoidable with `createModelVersion`, which decrypts/re-encrypts around the transform. Plaintext and AAD are identical, so behavior is unchanged; only the ciphertext bytes differ.
- **Undecryptable API keys are stripped** rather than failing the migration. Those rules were already non-functional; they now log a warning and need their key re-created.
- **One CI snapshot needs regenerating:** `encrypted_saved_objects/integration_tests/ci_checks/check_registered_types.test.ts` needs `[expr]` in its model-version inline snapshot (`jest_integration ... -u`). I left it alone per "do not modify tests." The registration `hashMap` in the same file is unaffected — I didn't change the ESO registration.
- Serverless ZDT is satisfied: no AAD attribute added, removed, or re-encrypted-status changed, so a previous Kibana version reconstructs AAD from the migrated document and decrypts it — single-stage release per the ESO change matrix.
