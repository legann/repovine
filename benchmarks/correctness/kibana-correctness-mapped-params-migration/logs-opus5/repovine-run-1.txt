## Where I localized the migration

The `severity` param lives on the **`alert` saved object** (`RULE_SAVED_OBJECT_TYPE`), inside the free-form `params` record (`raw_rule/v3.ts:295`). The decisive constraint is at `saved_objects/index.ts:58-77`: `params` is in `RuleAttributesIncludedInAAD`, and the type is registered as an ESO with `apiKey`/`uiamApiKey` encrypted (`index.ts:306-315`). Rewriting `params` therefore changes the decryption AAD — a plain `data_backfill` would leave every touched rule's API key undecryptable, i.e. loaded but non-functional. So the migration is wrapped in `encryptedSavedObjects.createModelVersion`, which decrypts with the old AAD and re-encrypts against the new one (`encrypted_saved_objects/server/create_model_version.ts:93-139`).

Two choices worth flagging: `unsafe_transform` rather than `data_backfill`, because core documents `data_backfill` as add-only ("using such transformations to mutate existing data of the document can lead to data corruption", `model_change.ts:107-109`); and `shouldTransformIfDecryptionFails: true`, matching `createEsoMigration` (`migrations/utils.ts:31`) so an undecryptable rule doesn't fail the whole upgrade. The ESO registration snapshot is pinned inline (same pattern as `actions/.../connector_token_model_versions.ts:20-44`) — importing it from `../index` would be an import cycle that hits TDZ at module evaluation.

## Deliberately left unchanged

**`mapped_params.severity`** — the one that matters. `getMappedParams` denormalizes `params.severity` into a sortable projection that `find`/sort/filter read *instead of* `params` (`mapped_params_utils.ts:31-44`, `131-185`). A rule stored as `High` has `[expr]`, because `SEVERITY_MAP` has no `High` key. I left it stale. Source: those values are `20-low`/`40-medium`/`60-high`/`80-critical` (`mapped_params_utils.ts:19-24`, `104-109`) — a different encoding, not a case variant, so writing them is by definition "beyond the case normalization" the constraint permits. Repovine carries a boundary annotation on this exact coupling; I'm reporting rather than acting on it.

**`alerting_v2`'s `ruleModelVersions`** — different module, different SO type (`alerting_rule`, `alerting_v2/common/saved_object_types.ts:8`), and `severity` appears nowhere in its schemas or mappings.

**`security-rule` prebuilt rule assets** — stores a top-level `severity` (`[expr]`), but these are Elastic-shipped rule *content* from the Fleet package, not a user's alerting rule with a `severity` param.

## Residual risk

- **Stale projection.** For migrated rules, `params.severity` now reads `high` while `mapped_params.severity` stays `''`. Filtering by severity behaves exactly as before the migration (that path never reads `params`), so nothing regresses at upgrade — but the next edit through any write path recomputes the projection to `60-high`, and the rule silently starts matching `severity: high` filters. Deferred, not avoided.
- **Snapshot test will fail.** `encrypted_saved_objects/integration_tests/ci_checks/check_registered_types.test.ts:132` pins the model-version list and needs `[expr]`. Its own comment says to regenerate with `jest_integration -u`; the "no test changes" constraint blocked me from doing so. The type-hash snapshot at line 70 is unaffected — the ESO registration is unchanged.
- **Full re-encryption.** `createModelVersion` decrypts and re-encrypts *every* rule, not just mixed-case ones — inherent to the wrapper, and the reason the connector-token precedent uses a no-op backfill. Rules whose API key already can't be decrypted get their encrypted attributes stripped rather than blocking the upgrade.
- **Unverified statically.** This worktree has no `node_modules`, so type-check, lint, and tests could not run. I verified types by reading the contracts (`SavedObjectModelUnsafeTransformFn` is exported at `core-saved-objects-server/index.ts:153`; `[expr]` resolves to `[expr]`, never overridden in v4–v12) and confirmed `@kbn/encrypted-saved-objects-plugin` is already in the alerting `tsconfig.json`, so no new dependency is introduced.
