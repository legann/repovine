## Where I localized it

The rule saved object is `alert`, registered in `x-pack/platform/plugins/shared/alerting/server/saved_objects/index.ts:147`. Its model versions ran 1–13, so the migration is **model version 14**.

Two non-obvious couplings drove the design — both verified in source, not assumed:

**1. `params` is in the decryption AAD.** `RuleAttributesIncludedInAAD` (`saved_objects/index.ts:58-77`) contains both `params` and `mapped_params`, and the type encrypts `apiKey` (`index.ts:313`). The file's own comment warns these "must remain in this array to prevent decryption failures during migration." A plain model version rewriting `params.severity` would leave `apiKey` encrypted under stale AAD — **every migrated rule would permanently fail to decrypt its API key and could not run**. So v14 is wrapped in `encryptedSavedObjects.createModelVersion(…)`, which decrypts with the pre-transform AAD and re-encrypts with the post-transform AAD. This forced `ruleModelVersions` to become a factory taking the ESO setup contract.

**2. `severity` has a second stored copy.** `mapped_params.severity` is a sortable projection (`'60-high'`) that the find path reads *in place of* `params` for every sort field, search field, and KQL filter. `SEVERITY_MAP` is lowercase-only and `getModifiedValue` returns `''` for anything else (`[expr]`), and only the rule write paths recompute it — they don't run during migration. Normalizing `params` alone would leave these rules stuck at `''`, still unsortable/unfilterable by severity. The transform refreshes the projection through the same `getModifiedValue` helper, and only when the document already carries it, so no attribute is invented.

I used `unsafe_transform` rather than `data_backfill`: core documents backfill as new-fields-only, where mutating existing data "can lead to data corruption or inconsistency" (`transformations.ts:78-80`).

## Residual risk

1. **Tests not updated** (per your constraint) **and they will fail**: `encrypted_saved_objects/integration_tests/ci_checks/check_registered_types.test.ts` pins the `alert` migration hash at line 70 and enumerates `[expr]` around line 124. Both need regenerating for `[expr]`.
2. **All rules are re-encrypted, not just normalized ones** — inherent to `createModelVersion`. With `shouldTransformIfDecryptionFails: true`, a rule whose `apiKey` cannot be decrypted has its encrypted attributes stripped and must be re-saved; that becomes unrecoverable. I chose this because the alternative fails the entire Kibana upgrade, and it matches the plugin's own convention (`migrations/utils.ts:31` uses `shouldMigrateIfDecryptionFails: true`). Rules that decrypt normally are unaffected.
3. **Templates reintroduce drift** — a template with `severity: 'High'` will still create new mixed-case rules. Worth a follow-up decision; I did not expand scope to it.
4. Values that lowercase to something non-canonical (`'Foo'` → `'foo'`) still project to `''`, exactly as today.
5. Serverless ZDT is single-stage: AAD *membership* is unchanged, only values, so the prior Kibana version constructs the same AAD and decrypts fine.
