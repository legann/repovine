## Summary

**Behavior change:** New model version `14` on the `alert` (rule) saved object lowercases `params.severity` in place. Rules with an already-lowercase severity, a non-string severity, or no severity param are returned untouched (identity return, no document rewrite).

**Where I localized it:** the alerting plugin's rule saved-object model versions — `x-pack/platform/plugins/shared/alerting/server/saved_objects/`.

| File | Change |
|---|---|
| `schemas/raw_rule/v14.ts` | **New.** Re-exports v13's schema — no shape change |
| `schemas/raw_rule/index.ts` | Export `rawRuleSchemaV14` |
| `model_versions/rule_model_versions.ts` | `normalizeSeverityParam` transform + model version `'14'`; const → `getRuleModelVersions(…)` factory |
| `model_versions/index.ts` | Export the factory |
| `saved_objects/index.ts` | Hoist the rule ESO registration into one shared const, used by both `encryptedSavedObjects.registerType` and the factory |

**The load-bearing detail:** `params` is in `RuleAttributesIncludedInAAD` (`saved_objects/index.ts:58-77`), and `collectAttributesForAAD` binds attribute **values**, not just names (`encrypted_saved_object_type_definition.ts:95-105`). A plain `data_backfill` rewriting `params.severity` would invalidate the AAD of every migrated rule and permanently break `apiKey`/`uiamApiKey` decryption. So version 14 is wrapped in `encryptedSavedObjects.createModelVersion` with the same registration as `inputType`/`outputType`, which decrypts with the pre-transform AAD and re-encrypts with the post-transform one. Passing the *same object* for both is deliberate — `create_model_version.ts:70` reference-compares them to reuse one service.

## Deliberately left unchanged

1. **`mapped_params.severity`** — the denormalized projection that find/sort/filter read *instead of* `params.severity`. Proof it's not regressed: `getModifiedValue` returns `[expr]` and `SEVERITY_MAP` is keyed only by the four lowercase values (`[expr]`), so any rule with mis-cased severity already stored `''` there. Refreshing it would be a data change beyond the case normalization the task scopes. ⚠️ **Consequence:** those rules stay unfindable by severity filter until the rule is next updated and `getMappedParams` re-runs. This is exactly the coupling the repovine boundary annotation on this module flags.
2. **`alerting_rule_template`** — can carry a severity param (`raw_rule_template/v1.ts:19`, `v2.ts:19` reuse `[expr]`). A template is not a rule, and it has no ESO registration.
3. **`ad_hoc_run_params`** — stores a params record in a rule snapshot (`raw_ad_hoc_run_params/v1.ts:28`). Transient backfill-job state regenerated from the rule.
4. **`alerting_v2` rule SO** — its attribute schemas define no `severity` (no hits under `alerting_v2/server/saved_objects/schemas/`), and it is not an ESO (`alerting_v2/server/saved_objects/index.ts` registers only ACTION_POLICY and API_KEY_PENDING_INVALIDATION).
5. **Alerts-as-data severity** (`kbn-rule-data-utils/src/alerts_as_data_severity.ts`) — the `kibana.alert.severity` document field, with a deliberately wider vocabulary (`warning`/`minor`/`major`, comment at lines 16-17). Different surface; alert docs aren't saved objects.
6. **`latest.ts`** — still resolves `RawRule` from v12, unchanged because v14 adds no shape change (same reason v13 didn't touch it).

No tests added or modified.

## Residual risk

- **I could not run `type_check`, `eslint`, or `jest`** — this worktree is intentionally not bootstrapped and the commands are blocked. Everything above is verified by reading the type definitions (`SavedObjectModelUnsafeTransformFn`, `SavedObjectsModelUnsafeTransformChange`, `CreateEsoModelVersionFnOpts`), not by executing the toolchain.
- **No encryption key configured:** re-encryption throws for rules with a non-null `apiKey`. Identical exposure to the existing `createMigration`-based rule migrations already wired at `saved_objects/index.ts:139`; `attributesToEncryptIterator` skips null attributes, so disabled/keyless rules are unaffected.
- **`shouldTransformIfDecryptionFails: true`** — a rule whose key can't be decrypted gets its encrypted attributes stripped with a warning rather than failing the upgrade, matching this plugin's own policy (`migrations/utils.ts:31`). Such a rule needs its API key regenerated, but it was already unusable.
- **Vocabulary breadth:** the transform lowercases *any* string severity, not only the four canonical values. I found no rule type storing a case-sensitive `severity` with different semantics, and the framework already treats `params.severity` as the shared mapped param across all rule types — but a rule type doing so would be affected.
