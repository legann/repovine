## Three findings that shaped it

**1. `params` is in the decryption AAD.** `RuleAttributesIncludedInAAD` (`saved_objects/index.ts:58-77`) lists both `params` and `mapped_params`. A plain model-version transform would change the AAD and leave every migrated rule's `apiKey` permanently undecryptable. So version 14 goes through `encryptedSavedObjects.createModelVersion` with matching input/output registrations (decrypt → transform → re-encrypt). The AAD *attribute set* is unchanged, so this is a single-stage Serverless change.

**2. `params.severity` is not always a string.** `response-ops/rule_params/anomaly_detection/v1.ts:18` declares `schema.number(…)` and `uptime_duration_anomaly/v1.ts:15` declares `schema.number()`; `ml/.../alerting_service.ts:885` consumes it as `anomalyScoreThreshold`. An unguarded `[expr]` would throw and fail the whole upgrade. Guarded with `[expr]`.

**3. `mapped_params.severity` is the value find/sort/filter actually read.** `[expr]` rewrites every sort field, search field, and KQL filter on `params.severity` to `[expr]`. `SEVERITY_MAP` (`mapped_params_utils.ts:19-24`) is lowercase-keyed, so a `High` rule stores `''` there today, and only write paths recompute it. Normalizing `params` alone would produce a document state no writer can create — and the rule would still be missing from severity filters. The transform recomputes that one key via `getModifiedValue`, only when `mapped_params` already exists, so the stored shape is unchanged.

I used `unsafe_transform` rather than `data_backfill`: core's `model_change.ts:107-109` states `data_backfill` "should only be used to backfill newly introduced fields" and that mutating existing data with it "can lead to data corruption or inconsistency". `shouldTransformIfDecryptionFails: true` matches the plugin's existing rule-migration policy (`saved_objects/migrations/utils.ts:31`) and the in-repo model-version precedent (`actions/.../connector_token_model_versions.ts:72`).

## Residual risk

- `createModelVersion` decrypts and re-encrypts **every** rule, including ones the transform returns unchanged — extra upgrade CPU proportional to rule count. Same shape as the existing 8.2 ESO migration. Decrypted content and AAD are identical for those rules, so behavior is unchanged.
- `shouldTransformIfDecryptionFails: true` strips encrypted attributes from a rule whose key already fails to decrypt, rather than aborting startup for all rules.
- One-time normalization only; no write-path validation was added, so a rule type could still persist mixed case later.
- A severity outside `SEVERITY_MAP` after lowercasing (e.g. `Sev1` → `sev1`) still projects to `''` — unchanged from today.
- **Verification was static.** This worktree has no `node_modules`, so `scripts/type_check`, `scripts/eslint`, and Jest could not be run.
