## Where I localized it

The `severity` param lives on the **`alert` saved object** (`params` is a free-form record — `schemas/raw_rule/v1.ts:277`), so the migration belongs in that type's model-version map: **new model version 14**.

The decisive constraint is that `alert` is an **Encrypted Saved Object** and `params` is in its AAD (`saved_objects/index.ts:67`, inside `RuleAttributesIncludedInAAD`). AAD is built from the full stored values of those attributes (`encrypted_saved_objects_service.ts:642-661`), so rewriting `params.severity` invalidates the AAD that `apiKey`/`uiamApiKey` were bound to. A plain `data_backfill` model version would persist the lowercased value next to ciphertext bound to the old AAD — every migrated rule would become permanently undecryptable. So version 14 is wrapped in `encryptedSavedObjects.createModelVersion`, which decrypts → transforms → re-encrypts (`create_model_version.ts:93-139`).

Two follow-on choices:
- **`unsafe_transform`, not `data_backfill`** — core documents backfill as only for fields introduced by the same version, warning that mutating existing data "can lead to data corruption or inconsistency" (`model_change.ts:107-109`); it also deep-merges (`build_transform_fn.ts:61`).
- **`shouldTransformIfDecryptionFails: true`** — matches alerting's own convention for every legacy rule migration (`migrations/utils.ts:31`). Without it a single undecryptable rule aborts the whole upgrade and Kibana won't start.

The transform is a no-op unless `severity` is a string that differs from its lowercase form, so missing, already-lowercase, and non-string values pass through untouched (a throwing migration would block startup).

## Deliberately left unchanged

- **`mapped_params.severity`** — `SEVERITY_MAP` (`mapped_params_utils.ts:19-24`) is keyed on lowercase, so `getModifiedValue` already resolved `'High'` to `''` (`:104-109`) when the rule was written. The stored value is unchanged by this migration, so there's no regression; rewriting it would be recomputing a derived value (`[expr]`), not case normalization, which the constraint excludes.
- **`alerting_rule_template` SO** — reuses the rule `params` schema (`schemas/raw_rule_template/v1.ts:19`) so it can carry `severity`, but it is a separate SO type and not a rule.
- **`ad_hoc_run_params` SO** — embeds a rule snapshot with `params` (`schemas/raw_ad_hoc_run_params/v1.ts:28`); separate SO type, transient backfill records.
- **`alerting_v2`'s own `ruleModelVersions`** — registers type `'alerting_rule'` (`alerting_v2/common/saved_object_types.ts:8`), a different data model with no `severity` in its schemas.
- **Legacy `migrations/` map** — frozen at 8.x behind `switchToModelVersionAt`; new migrations go in model versions.
- **No tests added or modified**, per the constraint. No existing test references `ruleModelVersions`, and `setupSavedObjects` is called only from `plugin.ts:419` with an unchanged signature.

## Summary

Rules with `params.severity` stored as `High`/`MEDIUM`/`Critical` are rewritten to lowercase on upgrade; rules already lowercase, without `severity`, or with a non-string `severity` are functionally untouched. Storage shape is unchanged.

Residual risk:
- `createModelVersion` has no `isMigrationNeededPredicate` (unlike the legacy `createMigration`), so **every** rule is decrypted and re-encrypted on upgrade to MV14, even ones needing no change. Their plaintext and behavior are identical, but the ciphertext bytes change, and upgrade time scales with rule count.
- With `shouldTransformIfDecryptionFails: true`, a rule whose API key can't be decrypted has its encrypted attributes stripped and logged rather than aborting the upgrade — the same tradeoff alerting already makes for all legacy migrations, and such a key was already unusable.
- `mapped_params.severity` stays stale (as it was pre-migration) until the rule is next updated.
- The `alert` type hash changes, so the `check_saved_objects` CI check will flag the new model version for review — expected for any MV addition, with no checked-in baseline to regenerate.
- I could not execute type-check, lint, or tests here; verification was static reading plus a script diffing the pinned AAD snapshot against the live registration.
