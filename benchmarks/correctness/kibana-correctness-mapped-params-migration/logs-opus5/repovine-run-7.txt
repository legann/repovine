## What changed

Added **model version 14** to the alerting `alert` saved object, normalizing `params.severity` to lowercase. Rules with an already-lowercase severity, a non-string severity, or no severity are returned untouched (identity), so nothing else is rewritten.

The load-bearing detail: **`params` is part of the rule's decryption AAD** (`saved_objects/index.ts:58-77`). A plain model version rewriting it would leave every migrated rule's `apiKey` permanently undecryptable. So version 14 is wrapped in `encryptedSavedObjects.createModelVersion`, which decrypts each doc with the AAD built from its pre-transform attributes and re-encrypts with the post-transform attributes (`encrypted_saved_objects/server/create_model_version.ts:106-138`). Input and output registrations are identical — only an AAD *value* changes, not the attribute set — which also keeps Serverless ZDT constraints satisfied.

`shouldTransformIfDecryptionFails: true` mirrors the policy alerting already applies to its own ESO migrations (`saved_objects/migrations/utils.ts:31`).

## Deliberately left unchanged

- **`mapped_params.severity`** — the denormalized projection that find/sort/filter actually read. `getModifiedValue` maps any non-canonical casing to `''` (`mapped_params_utils.ts:104-109`, `SEVERITY_MAP` at 19-24), so every rule this migration touches already stores `''` there (written by the 8.2 backfill, `migrations/8.2/index.ts:21-31`). Query values are rewritten through that *same* function (`modifyFilterKueryNode:171`, `getModifiedSearch:125`, sort field via `getModifiedField:62-74`), so leaving the stored value alone makes find/sort/filter results byte-identical before and after. Recomputing it would change which queries match those rules — beyond "case normalization".
- **`alerting_v2`'s `ruleModelVersions`** — different SO type, at MV1 with no `severity` attribute; its severity is a runtime alert-event field from ES|QL results (`build_alert_events.ts:23-33`) landing in the `alert_events` data stream (`resources/datastreams/alert_events.ts:43`), and its rule SO isn't ESO-registered at all (only the action policy is — `alerting_v2/server/saved_objects/index.ts:85-90`).
- **Legacy pre-8.x migrations** — `7.11/index.ts:77-101` is a ServiceNow *connector action* param named `severity`; `7.13/index.ts:44` is `severityMapping`, a different field.
- **`getMappedParams` write paths** (`update_rule.ts:365`, `update_rule_in_memory.ts:289`, `transform_rule_domain_to_rule_attributes.ts:30`) — already correct given a lowercase severity, and they self-heal a migrated rule's projection on its next update.
