## Where I localized it

`x-pack/platform/plugins/shared/alerting/server/saved_objects/model_versions/rule_model_versions.ts` — the model-version registry for the `alert` saved object (the alerting rule SO). Added **model version `14`**. This is the right layer: security detection rules and every other rule type store `severity` as a param on this same SO, so one migration covers all of them.

Two non-obvious constraints drove the shape of the patch:

**1. Rules are encrypted saved objects, and `params` is in the decryption AAD.** `RuleAttributesIncludedInAAD` (`saved_objects/index.ts:58`) contains both `params` and `mapped_params`. A plain `data_backfill`/`unsafe_transform` rewriting `params` would leave every migrated rule's `apiKey` undecryptable, so rules would stop executing — violating "must continue to function". Version 14 is therefore wrapped in `encryptedSavedObjects.createModelVersion`, which decrypts → transforms → re-encrypts (`create_model_version.ts:93-139`). The AAD attribute *set* is unchanged (only values change), so `inputType`/`outputType` are the same registration — which is also what keeps this ZDT/serverless-safe, since the prior Kibana version rebuilds AAD from the document's current values.

**2. `severity` is a mapped param with a stored derived projection.** `SEVERITY_MAP` is case-sensitive (`mapped_params_utils.ts:19-24`), so a rule stored as `High` currently projects to `[expr]`. `find_rules.ts` rewrites every sort field, search field, and KQL filter on `params.severity` to `mapped_params.severity`, and that projection is recomputed only by the rule write paths, which don't run during migration. The transform therefore realigns `mapped_params.severity` through the existing `getModifiedValue` helper — otherwise the normalization would be invisible to precisely the code that consumes severity.

Its `severity` hits are alert-event/episode fields read from an ES|QL column at runtime (`lib/rule_executor/build_alert_events.ts`, `[expr]`), not SO params. Nothing to migrate.
- **Legacy migrations `.../saved_objects/migrations/` (7.10–8.8)** — released and frozen. Their `severity` hits are ServiceNow *connector action* params (`7.11/index.ts:77-101`, inside `action.params`) and `severityMapping` (`7.13/index.ts:44`), not the rule `severity` param.
- **`SEVERITY_MAP`/`getModifiedValue`** — not made case-insensitive; that would change behavior for already-lowercase rules. The migration reuses the helper rather than duplicating the map.
- **`cases` SO severity** (`cases/.../schemas/v1.ts:58`) — a different saved-object type, not `alert`.

## Residual risk

- **Every rule document is rewritten**, not just miscased ones: the decrypt/re-encrypt pass runs on all rules (same as the `connector_token` v2 precedent). Upgrade cost scales with rule count.
- **`shouldTransformIfDecryptionFails: true`** — a rule whose `apiKey` can't be decrypted has its encrypted attributes stripped and logged rather than aborting the whole upgrade. Such rules were already non-functional, and this matches the flag the plugin's own legacy rule migrations already use (`migrations/utils.ts:31`). The alternative would fail Kibana startup.
- **Uniform lowercasing** — a rule type treating `params.severity` case-sensitively with a non-canonical vocabulary would be affected. I grepped rule-type param schemas and found no such in-repo type (all `alert` severity params use `[expr]`), but custom/third-party rule types can't be ruled out. Non-canonical *words* are safe either way: `Informational` → `informational` still projects to `''`, exactly as before.
