## What I changed

**Localization:** the `alert` saved object in `x-pack/platform/plugins/shared/alerting` — new **model version 14**. That is the only SO type that persists a rule `severity` param.

| File | Change |
|---|---|
| `server/saved_objects/model_versions/rule_model_versions.ts` | Adds MV 14; `ruleModelVersions` becomes a factory taking `EncryptedSavedObjectsPluginSetup` |
| `server/saved_objects/schemas/raw_rule/v14.ts` *(new)* | Re-exports v13 — no shape change |
| `server/saved_objects/schemas/raw_rule/index.ts` | Exports `rawRuleSchemaV14` |
| `server/saved_objects/constants.ts` *(new)* | Leaf module holding SO type names + encryption/AAD lists |
| `server/saved_objects/index.ts` | Passes `encryptedSavedObjects` to the factory; constants moved to the leaf module and re-exported |

Two findings drove the design:

**The rule SO is encrypted and `params` is in its AAD** (`saved_objects/constants.ts`, formerly `index.ts:67`). A plain `data_backfill` that rewrites `params.severity` would re-index the doc with a changed AAD but an unchanged `apiKey` ciphertext, making every migrated rule's API key permanently undecryptable — the rule would load but never execute. MV 14 therefore goes through `encryptedSavedObjects.createModelVersion`, which decrypts with the pre-transform AAD and re-encrypts with the post-transform one. `connector_token_model_versions.ts:56` is the in-repo precedent. Encrypted attributes and AAD *membership* are unchanged, so one registration serves as both `inputType` and `outputType`.

**Importing the AAD list from `..` would have created a runtime cycle** (`index.ts` → `model_versions` → `index.ts`), yielding `[expr]` — an empty AAD — at module-eval time. I extracted the constants to a leaf `constants.ts` and re-export them from `index.ts`, so all existing import paths still work.

Transform detail: `toLowerCase()` (not `toLocaleLowerCase`, which turns `HIGH` into `hıgh` under a Turkish locale); non-string, already-lowercase, and non-canonical values return `[expr]`.

## Deliberately left unchanged

- **`mapped_params.severity`** — a separate persisted keyword (`[expr]`) that find/sort/filter reads *instead of* `params.severity` (`mapped_params_utils.ts:53`). `getModifiedValue` returns `[expr]` (`[expr]`), so a rule storing `High` already has `mapped_params.severity: ''`. Leaving it keeps filter behavior byte-identical to pre-upgrade; rewriting it to `60-high` would change which rules match existing severity filters — beyond "the case normalization".
- **`alerting_v2` rule SO** — its persisted schema (`saved_objects/schemas/rule_saved_object_attributes/v1.ts`) has no `params` object at all, so there is no severity param.
- **Legacy migrations `7.11/index.ts:77` and `7.13/index.ts:44`** — those touch `action.params.severity` (a ServiceNow connector param) and `params.severityMapping`, not the rule's own `params.severity`.
- **`[expr]`** — `actionGroup.severity.level` is a numeric registry-time concept for alert-improvement detection.
- **`ALERT_SEVERITY` / `ALERT_SEVERITY_IMPROVING`** (`[expr]`) — alert-document fields written to alert indices at execution time, not rule SO params.
- **`latest.ts`** — still derives `RawRule` from v12, since v14 adds no shape change (v13 set that precedent).

## Residual risk

- Rules that had mis-cased severity keep a stale `mapped_params.severity: ''` until next written, so they stay unfindable by severity filter. Pre-existing; this patch neither fixes nor worsens it. This is the one item I'd flag for an explicit follow-up decision.
- MV 14 decrypts and re-encrypts **every** rule, so `apiKey` ciphertext changes even for untouched rules. Plaintext and AAD are unchanged; this is inherent to `createModelVersion`.
- `shouldTransformIfDecryptionFails: true` — a rule whose key can't be decrypted is logged and has encrypted attrs stripped rather than failing the whole upgrade.
- Non-canonical values (e.g. `'P1'`) are intentionally preserved, since `params` is free-form per rule type and lowercasing an unrelated rule type's label could break its own validation.
