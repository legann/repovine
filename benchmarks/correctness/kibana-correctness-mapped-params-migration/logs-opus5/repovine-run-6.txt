## Three things that shaped the implementation

**1. The rule SO is encrypted and `params` is in its AAD.** `RuleAttributesIncludedInAAD` lists `params` and `mapped_params` (`saved_objects/index.ts:58-77`), and AAD is built from the *values* of those attributes (`encrypted_saved_objects_service.ts:644-662`). A plain `data_backfill` would re-save each rule under an AAD its `apiKey`/`uiamApiKey` ciphertext was never sealed with, so the rule would stop decrypting. Version 14 goes through `encryptedSavedObjects.createModelVersion`, which decrypts with the pre-transform attributes and re-encrypts with the post-transform ones (`create_model_version.ts:93-139`). The attribute *sets* don't change, so `inputType`/`outputType` share one registration and no multi-stage serverless release is needed.

**2. `severity` is a mapped param.** find/sort/filter rewrite `params.severity` to `mapped_params.severity` (`[expr]`), and that projection is rebuilt only by the create/update write paths (`transform_rule_domain_to_rule_attributes.ts:30`), which do not run during migration. A rule stored as `High` projects to `''` (`[expr]`). Normalizing params alone would leave params saying `high` while the value the query path actually reads stays `''`. The transform re-derives it through the plugin's own `getModifiedValue`, restoring `[expr]`.

**3. `params.severity` is not always a label.** `@kbn/response-ops-rule-params` declares it as `schema.number` for `anomaly_detection` (`anomaly_detection/v1.ts:18`) and `uptime_duration_anomaly` (`uptime_duration_anomaly/v1.ts:15`). A bare `[expr]` would throw on every such rule and fail the upgrade — guarded with `[expr]`.

`shouldTransformIfDecryptionFails: true` matches the plugin's existing rule-migration convention (`migrations/utils.ts:31`).

## Residual risk

- **No toolchain run.** Checked by hand: braces balance, versions 1..14 consecutive, all imported symbols confirmed exported (`SavedObjectModelUnsafeTransformFn` at `src/core/packages/saved-objects/server/index.ts:153`, `getModifiedValue` from the `rules_client/common` barrel). A `type_check` + `eslint` pass is the cheapest confirmation.
- **New import cycle** `[expr]`. Same shape as the existing `partially_update_rule.ts` and `migrations/8.2` cycles, and the values are read inside the factory (called from `setup()`), not at module evaluation — safe under both CJS and ESM, but it is the part most worth a lint/type run.
- **Undecryptable rules** are stripped and migrated with a warning rather than aborting the upgrade. Such a rule needs its API key regenerated — it was already broken, and the alternative is failing the whole migration.
- **Every rule doc is rewritten** at upgrade: `createModelVersion` decrypts and re-encrypts unconditionally, so ciphertext bytes change even for rules the transform returns unchanged. Plaintext, AAD, and stored shape are identical; the cost is upgrade I/O proportional to rule count.
- **The `alert` type's migration hash changes.** No test in this checkout asserts it, but a full Kibana checkout has a registered-types snapshot whose `alert` entry would need updating — not touched, per the no-tests constraint.
