## Summary

**Where I localized the migration:** `x-pack/platform/plugins/shared/alerting` — the core Alerting plugin's `alert` saved-object type (`[expr]`). This is the only place with real casing drift: it has 13 accumulated model versions, and its `params` bag is genuinely free-form per rule type. I ruled out the sibling `alerting_v2` plugin (`x-pack/platform/plugins/shared/alerting_v2`) — its `rule_model_versions.ts` only defines model version `'1'`, so no pre-existing data could have the casing bug.

**The non-obvious wrinkle:** the `alert` SO type is Encrypted-Saved-Object-registered, and `params`/`mapped_params` are both in its AAD attribute list (`saved_objects/index.ts:67-68`). A plain migration mutating `params.severity` would silently break decryption of every rule's `apiKey`, since AAD is recomputed from current attribute values at decrypt time. This required wrapping the transform in `encryptedSavedObjects.createModelVersion(…)` (decrypt → transform → re-encrypt), following the exact pattern already used for `x-pack/platform/plugins/shared/actions/server/saved_objects/model_versions/connector_token_model_versions.ts`.

**Files changed:**
- `.../alerting/server/saved_objects/schemas/raw_rule/v14.ts` (new) — re-exports v13's schema unchanged (no shape change).
- `.../alerting/server/saved_objects/schemas/raw_rule/index.ts` — registers `rawRuleSchemaV14`.
- `.../alerting/server/saved_objects/model_versions/rule_model_versions.ts` — converted `ruleModelVersions` from a static map to a factory `[expr]`; added version `'14'` via `createModelVersion`, with an `unsafe_transform` (`normalizeRuleSeverityCase`) that lower-cases `params.severity` and, in the same step, refreshes `mapped_params.severity` using the existing `getModifiedValue`/`SEVERITY_MAP` lookup so the sort/filter projection stays consistent with the corrected value.
- `.../alerting/server/saved_objects/index.ts` — call site now passes `ruleModelVersions(…)`.

**Deliberately left unchanged (with proof):**
- Model versions 1–13: repovine's own annotation on this file states released versions are frozen; new behavior is appended, matching v13's own precedent comment ("No data-shape change in model version 13").
- `mapped_params_utils.ts` (`SEVERITY_MAP`, `getMappedParams`): only imported/reused (`getModifiedValue`), not modified — the write path (`transform_rule_domain_to_rule_attributes.ts:29`) already computes `mapped_params` correctly for every future create/update.
- Legacy classic migrations (`saved_objects/migrations/7.x`–`8.8`): none touch `severity`; the task asked specifically for a model version, which is the additive mechanism layered alongside classic migrations in `saved_objects/index.ts:121` + `:147`.
- Security Solution / Cases / ML severity code (`severity_mapping`, `AlertSeverity`, `CaseSeverity`, etc.): different packages and SO types entirely, unrelated to the generic Alerting `alert` SO's `params.severity`.

**Flagged, not fixed (test file, per constraints):** `x-pack/platform/plugins/shared/encrypted_saved_objects/integration_tests/ci_checks/check_registered_types.test.ts` has an inline snapshot enumerating every ESO type's model versions (currently `[expr]` ... `[expr]`).
