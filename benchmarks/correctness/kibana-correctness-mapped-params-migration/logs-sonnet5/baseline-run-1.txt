## Summary

**Where it's localized:** `x-pack/platform/plugins/shared/alerting` — the plugin that registers the `alert` saved-object type backing today's rules. I added model version **14** to the existing `ruleModelVersions` map (versions 1–13 already lived there).

**Files changed:**

|---|---|
| `server/saved_objects/model_versions/rule_model_versions.ts` | Added `lowercaseSeverityParam` transform + model version `'14'`. **Why `createModelVersion` instead of a plain `data_backfill`:** research turned up that `params` is listed in `RuleAttributesIncludedInAAD` (`saved_objects/index.ts`), i.e. it's part of the Additional Authenticated Data used to encrypt each rule's `apiKey`/`uiamApiKey`. Changing `params.severity`'s value — even without adding/removing keys — changes the serialized AAD, which would break decryption of the API key on any rule touched by a plain migration. `encryptedSavedObjects.createModelVersion` (confirmed via the `encrypted-saved-objects` skill and the `EsoModelVersionExample` reference plugin) wraps the change in decrypt→transform→re-encrypt so the key keeps decrypting after the value change. `shouldTransformIfDecryptionFails: true` (matching the reference plugin) keeps one rule's already-corrupted key from blocking migration of every other rule — directly serving "every existing rule must continue to load and function normally."

I also used `unsafe_transform` rather than `data_backfill` for the change itself: `data_backfill`'s own doc-comment in `model_change.ts` says it "should only be used to backfill newly introduced fields... using such transformations to mutate existing data... can lead to data corruption," and this migration mutates an existing field's existing value, which is exactly what `unsafe_transform` is for.

**Deliberately left unchanged, with evidence:**
- `mapped_params.severity` (the derived sort/filter sidecar) — computed by `getModifiedValue`/`getMappedParams` in `rules_client/common/mapped_params_utils.ts`, recomputed by the rules_client on the next rule write, not by a SO migration. Touching it would exceed "case normalization... beyond" scope.
- Rule-type-agnostic scope, no `alertTypeId` gating — `params` is `[expr]` at the alerting-core layer, and `mapped_params_utils.ts` already treats `severity` generically across rule types, so I matched that.
- Legacy versioned migrations (`[expr]`) — frozen history; no new folder has been added there since Model Versions were introduced (highest is `8.8`), confirming Model Versions is the current mechanism.
- Rule-type `severity` enum/schema definitions (Security Solution's Zod `Severity`, legacy io-ts `Severity`, Observability's unrelated `anomalySeverityType`) — these validate new writes, not existing persisted data; out of scope for a migration.
- `alerting_v2` plugin's own parallel `ruleModelVersions` — confirmed it registers a distinct SO type (`alerting_rule`, not `alert`); a separate, newer system, not where the described legacy-casing rules live.
