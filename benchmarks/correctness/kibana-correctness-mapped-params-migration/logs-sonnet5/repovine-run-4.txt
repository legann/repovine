## Summary

**Where the migration lives:** `x-pack/platform/plugins/shared/alerting/server/saved_objects/model_versions/rule_model_versions.ts` — the only file changed. Added model version `'14'` to `ruleModelVersions` (the `alert` saved-object type, owned by `@elastic/response-ops`) with a single `data_backfill` change, `backfillRuleSeverityCase`. No mapping or schema change was needed (severity lives in the free-form `params`/`mapped_params` blobs, whose declared types don't change), so version 14 has no `schemas` block — mirroring the established "pure data_backfill" pattern already used by `fleet`'s `package_policy` model versions 4–8/10 and this same plugin's own `ad_hoc_run_params` v3.

**The non-obvious part:** the `alerting` plugin also persists a derived `mapped_params.severity` projection (e.g. `high` → [value], via `SEVERITY_MAP` in `mapped_params_utils.ts`), which `find`/`sort`/`filter` reads instead of `params.severity`. That lookup is case-sensitive, so any rule with bad-case severity already has `[expr]`. Fixing only `params.severity` would leave that stale, so rules with corrected severity would remain invisible to severity-based sort/filter/search. The backfill recomputes `mapped_params.severity` with the same `getModifiedValue` helper the normal write path (`transformRuleDomainToRuleAttributes`) uses, only when `mapped_params` already exists on the document (it does for effectively every real rule, since a prior legacy migration, `saved_objects/migrations/8.2/index.ts`, backfilled it repo-wide). Both fields are updated via a `[expr]` partial, relying on the framework's deep-merge (`lodash.merge`, confirmed in `build_transform_fn.ts`) to leave every other key (`risk_score`, other rule-type params, etc.) untouched.

**Left unchanged, deliberately:**
- Rules with lowercase or absent `severity` — both early-returns produce `[expr]`, a no-op merge (verified against the exact `dataBackfillChangeToTransformFn` merge logic).
- ES mappings for `mapped_params.severity` (`common/saved_objects/rules/mappings.ts:100`) — already `keyword`, no addition needed since only values change, not types.
- The `alerting_v2` plugin (`alertingVTwo`) — it's a separate, newer plugin (different owning team, `@elastic/rna-project-team`) with only one model version so far, so it can't have accumulated case-drift; out of scope per the task's "existing rules... over time" framing.
- No tests added or modified, per constraint.

**Verification:** this worktree is intentionally not bootstrapped for this benchmark (no `node_modules`), so `type_check`/`jest` couldn't be run. I verified types and merge semantics by reading the actual source of `SavedObjectModelDataBackfillFn`/`SavedObjectModelDataBackfillResult`, `RawRule`'s derived config-schema types, and `dataBackfillChangeToTransformFn`, and cross-checked the pattern against existing compiling code in the same plugin and in `fleet`.

**Residual risk:** the rare case of a rule with non-canonical-case `severity` but no `mapped_params` object at all (possible only for documents that bypassed every write path since the 8.2.0 backfill, e.g. certain raw SO imports) — `params.severity` still gets corrected; `mapped_params` is left absent rather than fabricated, consistent with "don't change shape beyond case normalization."
