## Summary

**Where the migration lives:** `x-pack/platform/plugins/shared/alerting` is the single generic Alerting Framework plugin — all rule types across all solutions are stored as one `alert` saved-object type (`[expr]`), migrated through one `rule_model_versions.ts` model-version chain. The sibling `alerting_v2` plugin (owned by a different, newer team) has only one ever-released model version and no `severity` field in its schema at all — no historical data drift to fix there, confirmed via direct inspection.

**The hidden constraint that shaped the implementation:** `params` (which holds `severity`) is listed in `RuleAttributesIncludedInAAD` — it's Additional Authenticated Data for the encrypted `apiKey`/`uiamApiKey` attributes. A plain `data_backfill` that lowercases `params.severity` would change the AAD computed at decryption time versus what was used at encryption time, breaking every affected rule's ability to decrypt its API key (i.e., breaking execution) after the upgrade. This is exactly the failure mode the task's "every existing rule must continue to load and function normally" constraint guards against.

### Files changed
- **`saved_objects/model_versions/rule_model_versions.ts`** — converted `ruleModelVersions` from a plain object to a factory `[expr]`; added model version `'14'`, wrapped in `encryptedSavedObjects.createModelVersion(…)` (same `inputType`/`outputType` registration, since the AAD attribute set itself doesn't change) with a `data_backfill` change (`normalizeRuleSeverityCasing`) that lowercases `params.severity` only when it's a string and not already lowercase. Versions 1–13 are untouched.
- **`saved_objects/rule_encryption_attributes.ts`** (new) — `RULE_SAVED_OBJECT_TYPE`, `RuleAttributesToEncrypt`, `RuleAttributesIncludedInAAD` moved here verbatim from `saved_objects/index.ts`, so the model-versions file can build the same ESO registration used at runtime without a circular import back through the barrel. Re-exported from `index.ts` unchanged, so all existing importers (`partially_update_rule.ts`, the public `server/index.ts` surface) are unaffected.
- **`saved_objects/index.ts`** — imports/re-exports the moved constants; `[expr]` → `[expr]`.
- **`schemas/raw_rule/v14.ts`** (new) + **`schemas/raw_rule/index.ts`** — a schema alias re-exporting v13's schema unchanged (mirrors the existing v13-has-no-shape-change precedent), since this migration changes a value, not the shape.

### Deliberately left unchanged (with proof)
- **`mapped_params.severity`** (`rules_client/common/mapped_params_utils.ts`): `getMappedParams`/`getModifiedValue` project `params.severity` into a sortable `mapped_params.severity` via a case-sensitive `SEVERITY_MAP` (`low`/`medium`/`high`/`critical` keys only). For a rule with e.g. `severity: 'High'`, `mapped_params.severity` is *already* `''` before my change (map miss) — a pre-existing condition. My migration doesn't recompute this derived field: doing so would mean re-deriving a value via unrelated business logic, beyond "case normalization" and beyond "do not change the persisted storage shape." It self-heals the next time the rule is created/updated (`update_rule_in_memory.ts` calls `getMappedParams` on every write), and it only affects rule-list sort/filter-by-severity for that narrow, already-degraded subset — rule loading and execution read `params` directly, never `mapped_params`, so this doesn't violate "every rule must continue to load and function normally." I flagged this explicitly in a repovine boundary annotation on this exact file for future readers.
- **Versions 1–13**: untouched, per the "released versions are frozen" convention already established in this file (and mirrored elsewhere, e.g. the synthetics monitor migration).

### Residual risk
The only non-trivial risk is the AAD-safety mechanism itself: if `createModelVersion`'s decrypt→transform→re-encrypt behaved differently than in its one existing production precedent (`actions` plugin's `connector_token_model_versions.ts`, which I followed pattern-for-pattern including `shouldTransformIfDecryptionFails: true`), rules with already-corrupted encryption state could fail during migration — mitigated the same way that precedent does, by proceeding (with a logged warning) instead of aborting. I could not run `type_check`/`jest` here since this worktree is intentionally not bootstrapped for benchmarking; verification was done by static cross-referencing against the actual type definitions (`SavedObjectModelDataBackfillFn`, `EncryptedSavedObjectTypeRegistration`, `CreateEsoModelVersionFnOpts`) and existing working call sites.
