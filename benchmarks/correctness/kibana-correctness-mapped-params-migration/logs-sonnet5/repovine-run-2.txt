## Summary

Implemented as a new saved-object model version (`14`) on the `alert` type in the `alerting` plugin.

### Where it's localized

The `alerting` plugin (`x-pack/platform/plugins/shared/alerting`, owner `@elastic/response-ops`) is the framework used by all rule types (security, o11y, stack rules). I ruled out `alerting_v2` (a separate WIP plugin, owner `@elastic/rna-project-team`) — `grep -ril severity` on its tree returns only action-policy/episode-dispatch matches, no `severity` rule-param or `mapped_params` concept.

### Files changed

| File | Change |
|---|---|
| `saved_objects/schemas/raw_rule/v14.ts` (new) | Re-exports v13's schema unchanged — no shape change, same pattern v13 used for v12 |
| `saved_objects/schemas/raw_rule/index.ts` | Export `rawRuleSchemaV14` |
| `saved_objects/model_versions/rule_model_versions.ts` | The migration itself: `normalizeRuleSeverityCase` transform + new version `'14'`, appended after frozen versions 1–13 |
| `saved_objects/model_versions/index.ts` | Barrel export for the new version |
| `saved_objects/index.ts` | Wraps version 14 through `encryptedSavedObjects.createModelVersion(…)` at registration; extracted the ESO type-registration object into one shared const to avoid it drifting from the migration's `inputType`/`outputType` |

**The transform**: no-ops when `params.severity` is missing, non-string, or already lowercase. Otherwise lowercases `params.severity` and, if `mapped_params` exists, fixes `mapped_params.severity` via the existing `getModifiedValue(…)` helper — the same function every normal write path already uses to keep the two in sync.

**Why the ESO wrapping matters**: `params`/`mapped_params` are listed in `RuleAttributesIncludedInAAD` — they're Additional Authenticated Data for the rule's encrypted `apiKey`. Changing an AAD field's value without re-encrypting breaks decryption of the API key, which would break rule execution for every migrated rule. Every legacy alert migration touching `RawRule` goes through this same decrypt/re-encrypt discipline (`createEsoMigration`, used in all of `migrations/7.10`–`8.8`); `encryptedSavedObjects.createModelVersion` is its model-version equivalent. `[expr]` mirrors the existing `shouldMigrateIfDecryptionFails` convention so one corrupted rule can't block migration of the whole type.

### Deliberately left unchanged

- **Versions 1–13** of `ruleModelVersions` — repovine's own annotation on this file flags them as frozen; new behavior is appended, not spliced in.
- **`raw_rule/latest.ts`** — still points at v12's types, matching the precedent v13 already set for a no-schema-change version.
- **Rule create/update write paths** — untouched; they already compute `mapped_params` correctly via the same helper I reused, and the task scope is fixing already-persisted data.
- **`risk_score`** — never recomputed; the transform touches only the `severity` sub-key.
- **Snoozed-instance `severity_equals` conditions** (`raw_rule/v12.ts`) — these are `schema.literal()`-enforced enums, already lowercase-only by construction, so no casing bug can exist there.

### Residual risk

- This worktree has no `node_modules` and is intentionally not bootstrapped (confirmed by the bootstrap script's own guard), so I verified types by reading the actual declarations rather than compiling — a real `type_check`/`jest` run is still warranted before merging.
- Per your constraint I added no tests; worth a follow-up test covering the mixed-case→lowercase transform, the `mapped_params.severity` fix, and the already-lowercase/absent no-op cases.
- I lowercase `severity` unconditionally (not just when it matches low/medium/high/critical case-insensitively), since the task said "normalizes ... to lowercase" without restricting to those four. If intent was narrower, that's a one-line gate to add.
