## Summary

I added model version **14** to the `alert` saved-object type (the Kibana alerting rule SO), which lowercases `params.severity` in place.

### Where I localized the migration and why

The rule's `severity` param lives at `attributes.params.severity` on the `alert` saved object (`x-pack/platform/plugins/shared/alerting/server/saved_objects/`). `params` is a generic, rule-type-agnostic bag (`schema.recordOf(…)` since model version 1), so the fix belongs at the SO layer rather than in any one rule type (e.g. `kbn-securitysolution-io-ts-alerting-types`'s `Severity` enum is one producer of this field, but the SO itself doesn't know which rule type wrote it).

The critical constraint driving the implementation: `params` is listed in `RuleAttributesIncludedInAAD` (`saved_objects/index.ts`), i.e. it's part of the Additional Authenticated Data used to encrypt `apiKey`/`uiamApiKey`. Changing `params.severity`'s casing changes the AAD, so a plain data transform would silently break decryption of every rule's API key post-migration. I confirmed this by reading `EncryptedSavedObjectsService.getAAD`/`collectAttributesForAAD`. The correct, established fix (already used by `actions`' `connector_token_model_versions.ts`) is to wrap the change in `encryptedSavedObjects.createModelVersion(…)`, which decrypts with the pre-change AAD and re-encrypts with the post-change AAD.

### Files changed

- **`saved_objects/model_versions/rule_model_versions.ts`** — added `normalizeRuleParamsSeverityCasing` (an `unsafe_transform`: lowercases `params.severity` only when it's a string and differs from its lowercase form; otherwise returns the same doc reference untouched). Converted `ruleModelVersions` from a static map into a factory `[expr]` so it can call `encryptedSavedObjects.createModelVersion(…)` for version `14`, using `RULE_SAVED_OBJECT_TYPE`/`RuleAttributesToEncrypt`/`RuleAttributesIncludedInAAD` (imported, not duplicated, to avoid drifting from the security-sensitive AAD list) as both `inputType` and `outputType` since the encrypted/AAD attribute *sets* don't change, only one value. Set `shouldTransformIfDecryptionFails: true`, matching the `connector_token` precedent, so a rule with an already-undecryptable key doesn't block the whole migration.
- **`saved_objects/schemas/raw_rule/v14.ts`** (new) — re-exports v13's schema; no shape change since `params` was already untyped.
- **`saved_objects/schemas/raw_rule/index.ts`** — exports `rawRuleSchemaV14`.
- **`saved_objects/index.ts`** — call site updated to `ruleModelVersions(…)`.

### Deliberately left unchanged (with source)

- **`mapped_params.severity`** (`[expr]`) — a *derived* indexing field ([value] etc.), not "the severity param" itself. Its `SEVERITY_MAP` lookup is already case-sensitive and pre-existing; recomputing it is a separate bug from casing normalization and would go beyond "case normalization only."
- **`[expr]`** (`schemas/raw_rule/v12.ts:27-36`, `severity_equals`) — a different field (snooze condition), already constrained to lowercase literals by its own `schema.oneOf(…)`, so it can't carry this casing bug.
- **`alerting_v2` plugin's `rule_model_versions.ts`** — separate, newer plugin with a single model version and no `severity` concept; no legacy data to normalize.
