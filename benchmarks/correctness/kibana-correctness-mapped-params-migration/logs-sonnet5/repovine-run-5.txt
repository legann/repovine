## Summary

**Migration location:** `x-pack/platform/plugins/shared/alerting/server/saved_objects/model_versions/rule_model_versions.ts` — added model version `'14'` for the `alert` (rule) saved-object type.

**Files changed:**

| File | Change |
|---|---|
| `saved_objects/model_versions/rule_model_versions.ts` | New `normalizeRuleParamsSeverityCasing` transform + model version `'14'`; `ruleModelVersions` became a factory `[expr]` |
| `saved_objects/schemas/raw_rule/v14.ts` (new) | Re-exports v13's schema — no shape change |
| `saved_objects/schemas/raw_rule/index.ts` | Exports `rawRuleSchemaV14` |
| `saved_objects/index.ts` | Call site: `[expr]` |

**Behavior:** the transform lowercases `params.severity` only when it's a string that isn't already lowercase (no-op otherwise, returning the same doc). It also recomputes `mapped_params.severity` via the existing `getModifiedValue` helper, since that field is a derived projection of `params.severity` used by find/sort/filter and is normally only kept in sync on rule write paths, not during migration — repovine's boundary annotation on this file flagged that gap directly, so I fixed both in the same transform rather than leaving the projection stale.

**A non-obvious constraint drove the implementation shape:** `params`/`mapped_params` are part of this saved-object type's Encrypted-Saved-Objects AAD (`RuleAttributesIncludedInAAD` in `saved_objects/index.ts`). A plain `unsafe_transform` would change AAD content without re-encrypting, breaking every touched rule's `apiKey` decryption post-migration. I wrapped it with `encryptedSavedObjects.createModelVersion(…)`, mirroring the one real precedent in the codebase for this exact scenario (`actions/server/saved_objects/model_versions/connector_token_model_versions.ts` v2).

**Deliberately left unchanged:**
- `alerting_v2` plugin — its rule schema (`rule_saved_object_attributes/v1.ts`) has no `params`/`severity` field at all; unrelated rule model.
- Security Solution's `Severity` enum (`common_attributes.gen.ts`) — the real domain owner of `low/medium/high/critical`, but it's solution-layer code the platform-level Alerting plugin can't import, so the migration lowercases unconditionally rather than validating against that enum.
- ES mappings — untouched; `params` is already `flattened` and `mapped_params.severity` already `keyword`, both accept the normalized values with no mapping change.
- Legacy (pre-model-version) migrations — out of scope per the task's explicit ask for a model-version migration.

**Residual risk:** this worktree has no `node_modules` and bootstrap/type-check/tests are explicitly blocked in this environment, so I verified correctness by static reading against real shipped precedents (`connector_token_model_versions.ts`, `entity_manager`/`synthetics` `unsafe_transform` examples, the existing `8.2` legacy migration) rather than compiling. I confirmed via repovine dependency analysis that `saved_objects/index.ts` is the only consumer of `ruleModelVersions`, so the const→factory signature change has no other call sites to break. Once bootstrap is available, run `node scripts/type_check --project x-pack/platform/plugins/shared/alerting/tsconfig.json` to confirm.
