## Summary

**Where I localized the migration:** `x-pack/platform/plugins/shared/alerting` — the core Alerting framework plugin, which persists every alerting rule (including Security Solution detection rules, which set `params.severity`) as the `alert` saved object type.

**Files changed:**

| File | Change |
|---|---|
| `server/saved_objects/model_versions/rule_model_versions.ts` | Added `normalizeRuleSeverityParamCase` transform + new model version `'14'` using `unsafe_transform` |
| `server/saved_objects/schemas/raw_rule/v14.ts` (new) | Re-exports v13's schema unchanged — no shape change, same pattern v13 used for v12 |
| `server/saved_objects/schemas/raw_rule/index.ts` | Added `rawRuleSchemaV14` export |

The transform reads `doc.attributes.params.severity`; if it's not a string, or already equals its own lowercased form, it returns the document untouched (no new object allocated). Otherwise it returns a copy with only `params.severity` lowercased — everything else (including `latest.ts`'s derived TS types, which correctly still point at v12 since neither v13 nor v14 change the shape) is left alone. Model versions 1–13 are untouched; the fix is purely additive, per the file's own "frozen, append-only" convention.

**Related code paths deliberately left unchanged, with evidence:**

1. **`mapped_params.severity`** (`[expr]`) — a separate sortable projection ([value], etc.) computed only by the create/update write paths via `getMappedParams`/`SEVERITY_MAP`, never during migration. `SEVERITY_MAP` does a case-sensitive lookup, so a mis-cased severity (e.g. `'High'`) already projects to `[expr]` today — that's a pre-existing, independent bug, not something this migration introduces or worsens. Recomputing it would mutate a second field beyond case normalization, which the task explicitly rules out; historical precedent (`saved_objects/migrations/8.2/index.ts`) treats mapped_params backfill as its own separate migration, confirming this is a distinct concern.
2. **`[expr]`** for the `severity_equals` condition (`schemas/raw_rule/v12.ts:27-36`) — already schema-validated as a lowercase-only literal (`schema.literal(…)`), so it cannot be stored mis-cased and needs no migration.
3. **The `alerting_v2` plugin** (`x-pack/platform/plugins/shared/alerting_v2`) — a separate, newer plugin (`kibana.jsonc` id `alertingVTwo`) with its own `RULE_SAVED_OBJECT_TYPE`, currently at model version `'1'` with no `severity` field at all in its schema (`schemas/rule_saved_object_attributes/v1.ts`). No existing data to migrate, out of scope.

**Verification note:** this worktree has no `node_modules` installed (intentionally, per the environment) and I was blocked from running bootstrap/type-check/lint. I verified type correctness by hand — tracing `RawRule`/`SavedObjectModelTransformationFn`/`SavedObjectUnsanitizedDoc` type definitions and confirming `[expr]` makes `params.severity` an `any`-typed access — and matched formatting/patterns against the closest real precedent in the codebase (`synthetics` plugin's `transformGeoProperty` unsafe_transform). No tests were added or modified, per the task constraints.

**Residual risk:** low. The change is additive-only (new version 14, existing 1–13 untouched), touches no ES mappings, and the transform is a no-op for the overwhelming majority of rules (anything already lowercase or with no severity). The main residual risk is exactly the one flagged above and deliberately left alone: `mapped_params.severity` stays stale/empty for previously mis-cased rules until they're next saved through the normal write path — behavior that already exists today and is unchanged by this migration.
