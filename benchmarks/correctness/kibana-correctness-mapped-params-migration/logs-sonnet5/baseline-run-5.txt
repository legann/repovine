## Where the migration lives

The rule (`alert`) saved-object type is registered in `x-pack/platform/plugins/shared/alerting/server/saved_objects/index.ts`, with its model versions defined in `.../saved_objects/model_versions/rule_model_versions.ts`. I added model version **14** there.

**Files changed:**
| File | Change |
|---|---|
| `server/saved_objects/schemas/raw_rule/v14.ts` (new) | Re-exports v13's schema unchanged — no shape change, same convention v13 used for v12 |
| `server/saved_objects/schemas/raw_rule/index.ts` | Exports `rawRuleSchemaV14` |
| `server/saved_objects/model_versions/rule_model_versions.ts` | Adds `normalizeRuleSeverityParam` transform + model version `'14'`; converts `ruleModelVersions` from a static object to a factory `[expr]` |
| `server/saved_objects/index.ts` | Calls `ruleModelVersions(…)` instead of passing the static map |

**Why the factory-function refactor was necessary:** `params` is listed in `RuleAttributesIncludedInAAD` (used as AAD — additional authenticated data — for the encrypted `apiKey`/`uiamApiKey` fields). Mutating an AAD-covered field without going through `encryptedSavedObjects.createModelVersion(…)` would leave the stored ciphertext's AAD stale, breaking `apiKey` decryption the next time each rule runs. I wrapped the transform accordingly, mirroring the existing precedent for this in `x-pack/platform/plugins/shared/actions/server/saved_objects/model_versions/connector_token_model_versions.ts` and the documented example plugin `examples/eso_model_version_example/server/plugin.ts`. The transform itself only touches the plaintext `params.severity` value; the wrapper handles decrypt-before/re-encrypt-after so `apiKey`/`uiamApiKey` stay valid.

The transform (`normalizeRuleSeverityParam`) lowercases `params.severity` only when it's a string and not already lowercase; everything else returns the document untouched.

## Deliberately left unchanged, with evidence

- **`mapped_params.severity`** (`saved_objects/schemas/raw_rule/v1.ts:271-276`): a separately-derived sort/filter field computed by `getMappedParams`/`getModifiedValue` in `rules_client/common/mapped_params_utils.ts`. Touching it would go beyond case normalization (it maps to strings like [value], not a case variant), which the task's constraint against changing storage shape rules out. It also self-heals: it's recomputed on every rule create/update (`application/rule/transforms/transform_rule_domain_to_rule_attributes.ts`), so it isn't permanently stale.
- **Numeric `severity` params** (e.g. anomaly-detection rule types, `response-ops/rule_params/anomaly_detection/v1.ts:18`: `schema.number(…)`): the transform's `[expr]` guard leaves these alone by construction — confirmed this type exists so the generic, alertTypeId-agnostic approach doesn't misfire.
- **ES mapping for `params`** (`common/saved_objects/rules/mappings.ts:91-94`, type `flattened`): flattened fields have no fixed sub-mappings, so a value's case change needs no `mappings_addition`.
- **`alerting_v2` plugin** (`x-pack/platform/plugins/shared/alerting_v2/common/saved_object_types.ts:8`): uses a distinct SO type `'alerting_rule'`, not `'alert'` — a separate, newer system, out of scope for "Kibana alerting rules."

## Residual risk

Low. The schema shape is byte-identical to v13 (no validation risk), the transform is a pure no-op for already-lowercase/absent/non-string severities, and the ESO-wrapped re-encryption keeps `apiKey`/`uiamApiKey` decryptable using the same AAD field list already in production. The one caveat: I could not run `type_check`/`jest` — this worktree has no `node_modules` and is intentionally not bootstrapped for this benchmark — so correctness rests on careful static review (types, import paths, and the ESO wrapping pattern were all cross-checked against existing working precedents in the repo) rather than a compiler/test run.
