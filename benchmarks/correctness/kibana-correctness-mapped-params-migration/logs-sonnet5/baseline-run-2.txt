### Where it's localized and why

`RawRule.params` is `schema.recordOf(…)` (`server/saved_objects/schemas/raw_rule/v1.ts:277`) — an opaque, rule-type-specific bag that alerting-core never validates the contents of. So the fix belongs in `ruleModelVersions`, operating generically on whatever raw string sits at `attributes.params.severity`, rather than in any single rule type's plugin.

The transform (`rule_model_versions.ts:34-54`):
- reads `[expr]`
- no-ops (`[expr]`) if it's not a string, or already equals its lowercased form
- otherwise returns a new doc with only `params.severity` replaced by its lowercase form, everything else spread through unchanged

Used `unsafe_transform`, not `data_backfill` — the model-change doc comment (`src/core/packages/saved-objects/server/src/model_version/model_change.ts:107-109`) is explicit that `data_backfill` is for newly-introduced fields and "mutat[ing] existing data ... can lead to data corruption"; `unsafe_transform` is the documented mechanism for mutating existing values, and is what `synthetics/.../private_locations/model_version_1.ts` and `fleet/.../synthetics_disable_browser_input.ts` both use for structurally identical nested-value fixes.

No mapping change needed: `params` is `type: 'flattened'` (`common/saved_objects/rules/mappings.ts:91-94`), so ES indexes any leaf value under it without a declared field mapping.

This is the concrete real-world instance of the field the task describes, and it lives at `attributes.params.severity` — exactly what the migration touches.
