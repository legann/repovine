## Where the migration lives

The rule saved-object type (`alert`) uses Kibana's model-version system. I added model version `'14'`:

| File | Change |
|---|---|
| `x-pack/platform/plugins/shared/alerting/server/saved_objects/model_versions/rule_model_versions.ts` | New `normalizeRuleParamsSeverity` transform (`unsafe_transform`) + new `ruleModelVersion14` const, added as `'14'` in `ruleModelVersions` |
| `x-pack/platform/plugins/shared/alerting/server/saved_objects/schemas/raw_rule/v14.ts` (new) | Re-exports v13's schema unchanged (no shape change — mirrors how v13 re-exports v12 for its mapping-only change) |
| `x-pack/platform/plugins/shared/alerting/server/saved_objects/schemas/raw_rule/index.ts` | Exports `rawRuleSchemaV14` |
| `x-pack/platform/plugins/shared/alerting/server/saved_objects/model_versions/index.ts` | Re-exports `ruleModelVersion14` alongside `ruleModelVersions` |
| `x-pack/platform/plugins/shared/alerting/server/saved_objects/index.ts` | Wraps version `'14'` with `encryptedSavedObjects.createModelVersion(…)` before passing the map to `registerType` |

The transform itself: if `params.severity` is a string and isn't already lowercase, it's replaced with its lowercased form; otherwise the document is returned untouched (same object reference for the no-op case).

**The important part isn't the lowercasing — it's the encryption interaction.** `saved_objects/index.ts` lists `params` in `RuleAttributesIncludedInAAD` (the Additional Authenticated Data bound to the encrypted `apiKey`/`uiamApiKey` fields). A plain `unsafe_transform` on `params` would rewrite the AAD-relevant content without re-encrypting, so the old ciphertext would fail its AES-GCM auth-tag check on next decrypt — exactly the mis-cased rules would lose their `apiKey` and stop executing, the opposite of "every existing rule must continue to function." I found the sibling `actions` plugin already solved this for its `connector_token` type using `encryptedSavedObjects.createModelVersion(…)` (`x-pack/platform/plugins/shared/actions/server/saved_objects/model_versions/connector_token_model_versions.ts`), so I applied the same wrapper here, reusing the plugin's existing `RuleAttributesToEncrypt`/`RuleAttributesIncludedInAAD` constants.

## Residual risk

This benchmark worktree has no `node_modules` and is intentionally unbootstrapped (bootstrap explicitly refused and told me to verify via static reading only), so I couldn't run typecheck, lint, or the SO migration integration tests. I cross-checked every type against its actual source (`SavedObjectModelUnsafeTransformFn`, `SavedObjectsModelVersionMap`'s optional-key typing — which is why I export `ruleModelVersion14` as a standalone const rather than indexing the map, `EncryptedSavedObjectTypeRegistration`, `RecordOfType`'s `TypeOf`) and modeled the code on working precedent, but recommend running `node scripts/type_check --project x-pack/platform/plugins/shared/alerting/tsconfig.json` and the plugin's existing alerting SO migration integration tests before merging.

One side effect worth flagging: because `createModelVersion` uniformly decrypts-then-re-encrypts, *every* rule's `apiKey`/`uiamApiKey` ciphertext gets rewritten during this upgrade (new bytes, identical decrypted value), not just the mis-cased ones — this is unavoidable and standard for this pattern (same as the `connector_token` v2 precedent), and has no functional effect.
