## Summary

**Files changed:**

1. `x-pack/platform/plugins/shared/alerting/server/saved_objects/model_versions/rule_model_versions.ts` — added model version `14` (a severity-casing-normalization transform) and converted the `ruleModelVersions` export from a static object into a factory function.
2. `x-pack/platform/plugins/shared/alerting/server/saved_objects/index.ts` — one-line call-site update: `[expr]` → `[expr]`.

**The non-obvious part of this task:** `params` and `mapped_params` on the rule saved-object type (`alert`) are both listed in `RuleAttributesIncludedInAAD` (`saved_objects/index.ts:58-77`) — they're baked into the Additional Authenticated Data for the encrypted `apiKey`/`uiamApiKey` attributes. A plain `unsafe_transform` editing `params.severity` would silently desync that AAD, and every migrated rule would fail to decrypt its API key afterward (i.e. fail to run) — a direct violation of "every existing rule must continue to load and function normally." I wrapped the transform in `encryptedSavedObjects.createModelVersion(…)`, which decrypts with the old attributes, runs the transform, and re-encrypts with the new ones, exactly matching the one real precedent for this in the repo (`x-pack/platform/plugins/shared/actions/server/saved_objects/model_versions/connector_token_model_versions.ts`).

The transform itself (`normalizeRuleSeverityCasing`) also keeps `mapped_params.severity` — the sortable/filterable projection that find/sort/filter reads *in place of* `params.severity` — consistent with the newly-lowercased value, using the same `SEVERITY_MAP` formula (`low`→[value], etc.) the live write path already applies. Without this, rules with previously-mis-cased severity would have their `params.severity` fixed but remain invisible to severity sort/filter (stuck at `''`).

**Residual risk:**
- This benchmark worktree has no `node_modules` and an explicit environment guard forbids `bootstrap`/`type_check`/`eslint`/`jest`. I verified the code by direct static cross-reference against the actual `@kbn/core-saved-objects-server` and `@kbn/encrypted-saved-objects-plugin` type source files and against the one real in-repo usage of the identical `createModelVersion` pattern, but nothing here has been compiled or executed.
- Bumping to model version 14 causes a full reindex/re-encryption of every rule document (standard Kibana SO migration behavior for any version bump, not something new here) — rules with already-lowercase severity get fresh ciphertext but identical decrypted values and behavior.
- `[expr]` (matching the actions-plugin precedent) means a rule whose `apiKey` was already undecryptable *before* this migration, for unrelated reasons, has its key stripped with a logged warning rather than aborting migration for every other rule — a deliberate choice to avoid one bad document blocking the whole fleet.
