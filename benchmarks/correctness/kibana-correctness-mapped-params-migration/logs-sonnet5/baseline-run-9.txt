## Summary

**Where I localized the migration:** the "alert" saved-object type in `x-pack/platform/plugins/shared/alerting/server/saved_objects/`, as model version 14. Rules are stored there generically — `params` is a rule-type-specific `[expr]` (flattened in ES), so the transform reaches into `attributes.params.severity` without depending on any specific rule type.

**Files changed:**

| File | Change |
|---|---|
| `server/saved_objects/model_versions/rule_model_versions.ts` | Converted `ruleModelVersions` from a static object to a factory `[expr]`; added `lowercaseRuleParamsSeverity` transform and model version `'14'` |
| `server/saved_objects/schemas/raw_rule/v14.ts` (new) | Re-exports v13 schema — no shape change, matching the v12→v13 precedent |
| `server/saved_objects/schemas/raw_rule/index.ts` | Exports `rawRuleSchemaV14` |
| `server/saved_objects/index.ts` | Call site now invokes `ruleModelVersions(…)` |

**Key mechanics:** `params` is one of the attributes included in the encrypted-saved-object AAD (`RuleAttributesIncludedInAAD` in `saved_objects/index.ts`) that authenticates the encrypted `apiKey`/`uiamApiKey`. A plain `data_backfill`/`unsafe_transform` mutating `params` would silently break API-key decryption for every rule, since the AAD computed after migration would no longer match what was used to encrypt. So version 14 is wrapped in `encryptedSavedObjects.createModelVersion(…)` (same pattern as `actions`' `connector_token_model_versions.ts`), which decrypts using the old attribute values, applies the transform, then re-encrypts using the new ones — keeping `apiKey` valid under the mutated `params`. `shouldTransformIfDecryptionFails: true` matches that same precedent so one already-corrupt document can't block the whole migration.

The transform itself: reads `params.severity`, leaves the document untouched unless it's a string whose lowercased form differs, otherwise returns a shallow-copied doc with only `params.severity` replaced. No ES mapping change was needed since `params` is already `flattened`.

**Deliberately left unchanged (with proof):**
- `mapped_params.severity` (`schemas/raw_rule/v1.ts:271-276`, ES mapping `common/saved_objects/rules/mappings.ts:95-104`) — a separately-typed, derived sort-key field (e.g. [value] via `SEVERITY_MAP` in `rules_client/common/mapped_params_utils.ts`), not the plain-enum "param" the task describes.
- `alerting_v2`'s rule saved-object type (`'alerting_rule'`, `server/saved_objects/schemas/rule_saved_object_attributes/v1.ts`) — has no `params` or `severity` field at all; its "severity" is a runtime-computed alert-event attribute, unrelated to stored rule config.
- Snooze-condition `severity_equals` literals (`schemas/raw_rule/v12.ts:25-36`) — a distinct enum for snooze rules, already lowercase by schema (`literal(…)` etc.), not user-supplied data subject to casing drift.
- Write-time normalization for newly created/updated rules — out of scope; the task asks only for a migration fixing existing data, not new-write validation.
