    ## Important gotcha for touching `params`: AAD/encryption

## Summary

**Where the migration is localized:** the `alert` saved-object type (Kibana's rule SO, `x-pack/platform/plugins/shared/alerting/server/saved_objects/`), as model version `14`.

**Files changed:**

| File | Change |
|---|---|
| `saved_objects/schemas/raw_rule/v14.ts` (new) | Re-exports v13's schema — no shape change, matching the precedent set by `v13.ts` re-exporting `v12`. |
| `saved_objects/schemas/raw_rule/index.ts` | Adds `rawRuleSchemaV14` export. |
| `saved_objects/model_versions/rule_model_versions.ts` | Adds `lowercaseSeverityParam` transform and a `'14'` model version entry; converts `ruleModelVersions` from a plain object into a factory `[expr]`. |
| `saved_objects/index.ts` | Call site update: `modelVersions: ruleModelVersions` → `[expr]`. |

**Why the factory-function/encryption plumbing was necessary:** `params` is one of the fields in `RuleAttributesIncludedInAAD` (`saved_objects/index.ts:58-77`) — it's part of the AAD used to encrypt the rule's `apiKey`. A plain data transform on `params.severity` would change the AAD's computed value without updating the ciphertext, breaking `apiKey` decryption for every rule that has one (confirmed by reading `getAAD` in `encrypted_saved_objects_service.ts:642-661`, which serializes AAD attribute *values*, not just names). So v14 is wrapped in `encryptedSavedObjects.createModelVersion(…)`, which decrypts with the pre-transform AAD, applies the lowercasing, then re-encrypts with the post-transform AAD — the same pattern already used by `connectorTokenModelVersions` v2 in the sibling `actions` plugin.

**The transform itself** (`lowercaseSeverityParam`) reads `params.severity`, and leaves the document byte-for-byte unchanged unless `severity` is a string and not already lowercase. This guard also protects against a real landmine found during research: ML anomaly-detection rules store `severity` as a **number** (0–100), so an unguarded `[expr]` would throw and could halt migration for all rules.

**Deliberately left unchanged, with proof:**
- `mapped_params.severity` (derived via `getMappedParams`/`SEVERITY_MAP` in `[expr]`) — task scope is the `severity` **param**, and the constraint says not to change storage shape beyond case normalization; touching a second field would exceed that.
- Rule templates (`alerting_rule_template` SO type, `rule_template_model_versions.ts`) — same underlying `params` schema, but the task speaks of "existing rules" that must "load and function," which describes executable rule instances, not template scaffolding.
- The experimental `alerting_v2` plugin's `alerting_rule` SO type — confirmed via its README ("ES|QL-first... alerting plugin") it's a separate, parallel system; its rule schema has no `severity` field at all today.
- ES mapping for `params` (`flattened`, unchanged) — flattened fields need no mapping update for a value-only change.

**Residual risk:** this environment is intentionally unbootstrapped for the benchmark (no `node_modules`), so I verified correctness by reading the core saved-objects and encrypted-saved-objects source directly rather than running `type_check`/`eslint`/Jest. I traced the exact type signatures and the decrypt→transform→re-encrypt flow to confirm they line up, but the usual toolchain verification hasn't run. Every rule with an `apiKey` gets its ciphertext re-encrypted (new bytes, identical decrypted content) as an unavoidable side effect of the AAD-safe approach — functionally invisible but worth flagging.
