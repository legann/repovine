## Where the migration is localized

**Plugin:** `x-pack/platform/plugins/shared/alerting` (`@kbn/alerting-plugin`, SO type `alert`) — confirmed this is the correct target because it owns `params.severity`/`SEVERITY_MAP` and has 13 existing model versions of live production data. A second plugin, `alerting_v2` (`@kbn/alerting-v2-plugin`), also exists but its rule saved-object schema (`alerting_v2/server/saved_objects/schemas/rule_saved_object_attributes/v1.ts`) has no `params`/`severity` field at all — a different data model — so it's out of scope by construction.

**Files changed:**

| File | Change |
|---|---|
| `saved_objects/model_versions/rule_model_versions.ts` | Converted `ruleModelVersions` from a static map to a factory taking `EncryptedSavedObjectsPluginSetup`; added model version `'14'` with the severity-lowercasing transform |
| `saved_objects/schemas/raw_rule/v14.ts` (new) | Re-exports v13's schema unchanged — no shape change, only a value rewrite |
| `saved_objects/schemas/raw_rule/index.ts` | Added `rawRuleSchemaV14` export |
| `saved_objects/index.ts` | Call site: `[expr]` |

**Why the extra machinery:** `RuleAttributesIncludedInAAD` (`saved_objects/index.ts:58-77`) includes `params`, and `apiKey`/`uiamApiKey` are encrypted. A migration that rewrites `params` directly would recompute a different AAD at next-decrypt time than the one used when the API key was encrypted, breaking rule execution for every touched rule. So version 14 is wrapped in `encryptedSavedObjects.createModelVersion(…)` (decrypt with old AAD → transform → re-encrypt with new AAD), mirroring the one existing precedent for this in the codebase, `actions/server/saved_objects/model_versions/connector_token_model_versions.ts`. `[expr]` matches that same precedent, so one rule with an already-broken key can't halt migration for the whole deployment.

The transform itself (`normalizeRuleSeverityCasing`) is a `data_backfill`-shaped no-op unless `params.severity` is a string whose lowercase form differs, in which case it rewrites only that leaf, spreading the rest of `params` untouched. I used `unsafe_transform` rather than `data_backfill` because core's own doc comment on `data_backfill` (`@kbn/core-saved-objects-server/src/model_version/transformations.ts`) says it's for backfilling new fields, not mutating existing values.

## Deliberately left unchanged

| Path | Evidence it's out of scope |
|---|---|
| `mapped_params.severity` (sortable projection, e.g. [value]) | `[expr]`: `SEVERITY_MAP` lookup is case-sensitive, so mis-cased rules already project to `''` today — pre-existing, not something this migration worsens. It's recomputed only by the create/update write path (`getMappedParams`), never by migrations, so touching it here would exceed a pure case fix and isn't required for rules to load/run. |
| `alerting_v2` plugin | `alerting_v2/.../rule_saved_object_attributes/v1.ts` has no `params`/`severity` field. |
| `alerting_rule_template` SO type | `raw_rule_template/v1.ts:19` reuses the same `params` schema, so templates *could* carry the same mis-casing, but templates aren't ESO-registered (no `apiKey`) and aren't scheduled/executing — the task's "load and function" concern doesn't apply to them. |
| Rule-type `paramsSchema` casing conflicts | Checked the actual canonical definition (`kbn-securitysolution-io-ts-alerting-types/src/severity/index.ts:11`: `t.keyof(…)`) — confirms lowercase is universal, so no rule type's own validator expects different casing. |
| `rawRuleSnoozeConditionSchema`'s `severity_equals.value` (`raw_rule/v12.ts:27-35`) | A strict `schema.literal(…)` enum — mis-cased values were never storable there, so nothing to normalize. |

## Residual risk

Every existing rule of this type gets re-encrypted (new ciphertext, same plaintext) as a side effect of the model version bump, even when severity was already lowercase — inherent to routing all docs through decrypt→transform→encrypt, not something scoped down further without losing AAD correctness for the rules that do change. Cannot type-check in this worktree (intentionally not bootstrapped per its own bootstrap-log guard), so the change is verified by static reading against the real interfaces (`EncryptedSavedObjectTypeRegistration`, `SavedObjectModelUnsafeTransformFn`, `RawRule`) and the one existing same-pattern precedent in `actions`, rather than a compiler run.
