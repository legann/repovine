## Summary

Added saved-object **model version 14** to the alerting plugin's `alert` rule type that lowercases a rule's `params.severity`. Because `params` is part of the rule's encryption AAD, the transform is wrapped in `encryptedSavedObjects.createModelVersion` so every rule is decrypted and re-encrypted — otherwise migrated rules' `apiKey` would become undecryptable.

### Where I localized it

`x-pack/platform/plugins/shared/alerting/server/saved_objects/` — the `alert` SO type (`[expr]`, registered at `index.ts:115`), whose model versions live in `model_versions/rule_model_versions.ts` (append-only registry, currently v1–v13). This is the plugin that owns the `severity` param, its `mapped_params` sort projection, and the ESO registration.

### Files changed

| File | Change |
|---|---|
| `model_versions/rule_model_versions.ts` | `ruleModelVersions` const → `getRuleModelVersions(…)` factory; added the `unsafe_transform` severity-lowercasing fn and ESO-wrapped v14 |
| `schemas/raw_rule/v14.ts` *(new)* | Re-exports v13 schema (no data-shape change), mirroring the v13 precedent |
| `schemas/raw_rule/index.ts` | Exports `rawRuleSchemaV14` |
| `model_versions/index.ts` | Barrel: `ruleModelVersions` → `getRuleModelVersions` |
| `saved_objects/index.ts` | Builds one `ruleTypeRegistration` (from the shared `RuleAttributesToEncrypt`/`RuleAttributesIncludedInAAD` constants) and passes it to the factory |

The transform lowercases only when severity is a string that isn't already lowercase; rules with a lowercase or absent `severity` return `[expr]` unchanged. Change type is `unsafe_transform` (core docs mark `data_backfill` as additive-only — "using such transformations to mutate existing data can lead to data corruption"). `shouldTransformIfDecryptionFails: true` matches the alerting migration convention at `saved_objects/migrations/utils.ts:31`.

### Deliberately left unchanged (with source proof)

| Path | Why out of scope |
|---|---|
| `mapped_params` projection & write paths (`rules_client/common/mapped_params_utils.ts`) | Constraint: "no storage change beyond the case normalization." `SEVERITY_MAP` (lines 19–24) has only lowercase keys, so `getModifiedValue` (104–109) already projects any non-canonical severity to `''`. Migrated rules keep `[expr]` — the same value find/sort/filter read before, so no regression. Recomputing it is a write-path job (`getMappedParams`), not the migration's. |
| Released model versions v1–v13 | Append-only registry (repovine `boundary` annotation); new behavior appends as v14. |
| `alerting_v2` plugin (`plugins/shared/alerting_v2`) | Separate plugin/SO type (`alertingVTwo`, `@elastic/rna-project-team`); its `ruleModelVersions` has only v1 `[expr]`, and grep found **no** `severity`/`mapped_params`/rule-AAD — the mechanism the task describes doesn't exist there. |
| Legacy `getMigrations` (SemVer migrations, `saved_objects/migrations/`) | Task specified a model version; the legacy chain is frozen and untouched. |
| `encryptedSavedObjects.registerType` AAD/encrypt sets (`index.ts:306`) | Registration is unchanged; `[expr]`. Re-encryption is driven by the AAD *value* change, not a registration change. |

### Residual risk

- **`mapped_params` staleness (non-regressing):** a rule migrated from e.g. `High`→`high` keeps `[expr]`, so find/sort/filter by the now-correct `high` won't match it until the rule's next write (which recomputes `mapped_params`). It didn't match before the migration either — no behavior regression, and rule execution (which reads `params.severity` directly) is correct immediately.
- **Full re-encryption:** `createModelVersion` decrypts/re-encrypts *every* rule, so `apiKey` ciphertext rotates even for already-lowercase rules. Decrypted content and behavior are identical (opaque bytes only). An undecryptable rule proceeds with its encrypted attributes stripped (per `shouldTransformIfDecryptionFails: true`), consistent with the existing alerting convention.
- **Verification gap:** this worktree has no `node_modules`, so `scripts/type_check` and `scripts/eslint` can't run (bootstrap is heavy/out of scope). I validated types against the core model-version definitions, the `createModelVersion` implementation, and the `actions` `connectorTokenModelVersions` + ESO example precedents, and confirmed import style against `kbn-eslint-config` (`consistent-type-imports: separate-type-imports`).
