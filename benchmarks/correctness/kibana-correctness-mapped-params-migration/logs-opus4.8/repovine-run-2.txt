## Summary

I added **`alert` saved-object model version 14** to the classic alerting plugin, normalizing each existing rule's `params.severity` to lowercase.

### Where I localized it

The migration belongs in the classic alerting plugin's append-only model-version registry — repovine pointed straight at `rule_model_versions.ts`, whose annotation flagged the critical coupling: `severity` is a `MAPPED_PARAMS_PROPERTIES` value that's also persisted in a sortable `mapped_params.severity` projection (`SEVERITY_MAP`, e.g. `[value]`), which find/sort/filter reads instead of `params`. Two facts made this more than a one-liner:

1. **`mapped_params` coupling** — `getModifiedValue(…)` returns `[expr]`, so a non-canonical `'High'` currently projects to `[expr]`. Normalizing `params.severity` without refreshing the projection would leave the rule unfindable/unsortable by severity — not "functioning normally." The write path that keeps them in sync doesn't run during migration.
2. **Encrypted Saved Object** — `params` *and* `mapped_params` are both in the rule's encryption AAD (`RuleAttributesIncludedInAAD`), and `apiKey`/`uiamApiKey` are encrypted against it. Mutating an AAD value requires re-encryption or `getDecryptedAsInternalUser` (the rule task runner) fails. That mandates the ESO `createModelVersion` wrapper.

## Changed behavior & residual risk

**Behavior:** On upgrade, migrating an `alert` to model version 14 lowercases `params.severity` (`High`→`high`, `MEDIUM`→`medium`, `Critical`→`critical`) and refreshes the coupled `mapped_params.severity` sort/filter projection. `createModelVersion` decrypts with the current registration, applies the transform, and re-encrypts `apiKey`/`uiamApiKey` against the normalized document, so rules stay decryptable and runnable. Rules already lowercase or without a `severity` param are logically unchanged.

**Residual risk:**
- Every `alert` doc is rewritten/re-encrypted (inherent to any data-transform model version) — a one-time migration cost on large deployments; already-lowercase rules' plaintext/behavior is unchanged.
- Rules that were *already* undecryptable pre-migration have encrypted attrs stripped (`shouldTransformIfDecryptionFails: true`, matching the connector_token precedent): unblocks the upgrade but they need re-auth — they were already non-functional.
- Anomalous rules with a `severity` param but no `mapped_params` object are normalized in `params` only (no fabricated projection, honoring "no storage-shape change"); the 8.2 migration guarantees such rules don't exist in practice.
- **Not compiler-verified:** the workspace has no `node_modules` (not bootstrapped), so `type_check`/`eslint` couldn't run. I verified by reading and by matching established in-repo precedents (ESO `createModelVersion`, `unsafe_transform` typing, import resolutions, the write-path spread idiom). The `check_registered_types` `alert` hash regeneration is the one expected test follow-up.
