## Summary

Kibana alerting rules (`alert` saved object, `x-pack/platform/plugins/shared/alerting`) get a new **model version 14** that lowercases each rule's `params.severity`. Rules already lowercase, or with no `severity` param, are untouched.

### Where I localized it & files changed

The `severity` param, its canonical values, and the `mapped_params` projection all live in the **`alerting`** plugin (not `alerting_v2`). The migration belongs in the append-only rule model-version registry.

| File | Change |
|---|---|
| `server/saved_objects/model_versions/rule_model_versions.ts` | Converted `ruleModelVersions` from a const to `[expr]`; added the `normalizeRuleSeverityCase` transform and **version 14**, wrapped in `encryptedSavedObjects.createModelVersion(…)`. |
| `server/saved_objects/schemas/raw_rule/v14.ts` (new) | Re-exports the v13 schema (no attribute-shape change), matching the v13 convention. |
| `server/saved_objects/schemas/raw_rule/index.ts` | Exports `rawRuleSchemaV14`. |
| `server/saved_objects/index.ts` | Call site now `ruleModelVersions(…)`. |

**Two things drove the design** (both surfaced from graph annotations/registration, not the prose):
1. `severity` is a *mapped param* — its sortable form is also stored in `mapped_params.severity` (via `SEVERITY_MAP`), which find/sort/filter reads instead of `params`. The transform recomputes `mapped_params` with `getMappedParams(…)`, mirroring `transformRuleDomainToRuleAttributes` and the existing 8.2 `addMappedParams` migration.
2. The `alert` SO is **Encrypted** and `params`/`mapped_params` are in AAD (`saved_objects/index.ts:58-77`). Changing a severity value changes the AAD for `apiKey`/`uiamApiKey`. A plain model-version transform would make every API-keyed rule undecryptable, so the change is wrapped in `createModelVersion` (decrypt→transform→re-encrypt), with frozen `inputType`/`outputType` snapshots — the pattern established by `actions`' `connector_token_model_versions.ts`.

### Related paths deliberately left unchanged

| Path | Proof it's out of scope |
|---|---|
| **`alerting_v2` plugin** (`.../alerting_v2/server/saved_objects/...`) | Its rule schema `ruleSavedObjectAttributesSchema` (`schemas/rule_saved_object_attributes/v1.ts`) has **no `severity` and no `mapped_params`** — a different rule model (`kind`/`metadata`/`query`/`state_transition`). The task's `severity` param doesn't exist there. |
| **Released model versions 1–13** | Boundary annotation + model-version semantics: "Released versions are frozen — new behavior is appended as a new version." I appended v14. |
| **Write paths** (`transformRuleDomainToRuleAttributes`, `update_rule.ts`, `getMappedParams`/`SEVERITY_MAP`) | `SEVERITY_MAP` keys are already lowercase (`mapped_params_utils.ts:19-24`); writers already emit canonical values. The defect is historical stored data, so it's a migration, not a write-path fix. |
| **Rule ESO registration** (`saved_objects/index.ts:306-315`, `RuleAttributesToEncrypt`/`RuleAttributesIncludedInAAD`) | v14 changes only AAD *values*, not the encrypt/AAD attribute *set*; the ESO skill requires `createModelVersion` only, so the registration is unchanged (I froze a matching snapshot in the migration). |
| **find/sort/filter read path** (`getModifiedField`/`getModifiedFilter`, `find_rules.ts`) | Reads `[expr]`, which the migration keeps consistent — no read-path change needed. |

### Changed behavior

Rules with miscased severity (`High`, `MEDIUM`, `Critical`, …) migrate to lowercase, and their `mapped_params.severity` sortable projection is corrected (e.g. `''` → `[value]`), so severity sort/filter works. API keys stay decryptable across the upgrade. Already-lowercase and severity-less rules are functionally unchanged.

### Residual risk

- **Test data to regenerate (not edited, per "don't modify tests"):** the `alert` migration hash in `x-pack/platform/plugins/shared/encrypted_saved_objects/integration_tests/ci_checks/check_registered_types.test.ts:70` changes when a model version is added — the standard mechanical update for any new model version.
- **Full re-encryption:** `createModelVersion` decrypts+re-encrypts *every* rule at 13→14 (new IVs on `apiKey`/`uiamApiKey`); decrypted values are identical. Inherent to ESO migrations (the connector-token migration does the same), unavoidable since AAD attributes change.
- **Undecryptable rules:** `shouldTransformIfDecryptionFails: true` strips encrypted attrs and logs a warning for rules whose key can't be decrypted (already broken), rather than aborting the upgrade — matches the connector-token precedent.
- **Could not run `type_check`/`eslint`/jest:** the worktree has no `node_modules` (un-bootstrapped). I verified types against source definitions (`EncryptedSavedObjectTypeRegistration`, `SavedObjectModelUnsafeTransformFn`, `RuleTypeParams`/`MappedParams`, `[expr]`) and matched the 8.2-migration and connector-token patterns.
