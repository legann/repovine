## Summary

I added **model version `14`** to the `alert` (rule) saved-object type in the mainline **`alerting`** plugin, normalizing each rule's `params.severity` to lowercase.

### Where the migration lives

The `severity` label the task describes is `params.severity` on rule saved objects — confirmed by `rules_client/common/mapped_params_utils.ts:19-24`, whose `SEVERITY_MAP` enumerates exactly `low`/`medium`/`high`/`critical` and returns `''` for any non-canonical (e.g. mis-cased) value. Rule model versions are registered on the `alert` type at `saved_objects/index.ts:147`, sourced from `saved_objects/model_versions/rule_model_versions.ts` — that is where I localized the change.

### The decisive constraint: `params` is AAD

The `alert` type is an Encrypted Saved Object (`saved_objects/index.ts:306-315`), and **`params` is part of its AAD** (`RuleAttributesIncludedInAAD`, `saved_objects/index.ts:67`; the comment at lines 53-55 warns these fields "are used to construct decryption AAD and must remain in this array to prevent decryption failures during migration"). Mutating `params.severity` changes the AAD bound to the encrypted `apiKey`/`uiamApiKey`. A plain transform would leave the stored ciphertext bound to the old AAD → decryption fails → the rule stops loading.

So the transform is wrapped with `encryptedSavedObjects.createModelVersion` (`[expr]`), which decrypts with the pre-migration AAD, applies the transform, then re-encrypts with the post-migration AAD — the same mechanism the connector-token ESO migration uses (`actions/.../connector_token_model_versions.ts:56-73`). I used `unsafe_transform` (correct for mutating existing data; `data_backfill` is documented as new-fields-only in `model_change.ts:107-109`) and `shouldTransformIfDecryptionFails: true`, matching the established rule-migration behavior (`migrations/utils.ts:31`).

### Residual risk

- **Every rule is decrypted and re-encrypted** during the upgrade (inherent to any ESO model version — the same happens in the connector-token migration), even lowercase/no-severity rules. Plaintext, storage shape, and AAD set are unchanged; only ciphertext bytes differ, so no observable behavior change. Cost is one crypto pass per rule at upgrade time.
- **Pre-broken rules**: if a rule's `apiKey` was already undecryptable (e.g. rotated key), `shouldTransformIfDecryptionFails: true` strips the encrypted attribute and continues rather than blocking the whole migration — matching existing rule-migration behavior, but such an already-broken rule would need its API key regenerated (it was non-functional before the upgrade regardless).
- The registered-types hash snapshot test above will fail until its `alert` hash is regenerated.
