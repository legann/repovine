## Summary

I localized and implemented the migration in Kibana's classic **`alerting`** plugin, on the **`alert`** (rule) saved-object type, as **model version 14**.

### The critical constraint that shaped the design
The rule SO is an **Encrypted Saved Object**: it encrypts `apiKey`/`uiamApiKey`, and its **`params` attribute is part of the AAD** (`RuleAttributesIncludedInAAD` in `saved_objects/index.ts:58`). The AAD is built from attribute **values** (`encrypted_saved_objects_service.ts:642` `getAAD` — "both keys and values"). So changing `params.severity` from `High`→`high` changes the AAD, and the previously-encrypted `apiKey` would fail to decrypt on the next read — breaking the rule.

The fix must therefore **decrypt → transform → re-encrypt**. I wrapped the new model version with `encryptedSavedObjects.createModelVersion(…)`, following the canonical pattern in `actions/.../connector_token_model_versions.ts` and `examples/eso_model_version_example`.

The transform returns the doc untouched when `severity` is absent or non-string, or already equal to its lowercase form — satisfying "already-lowercase / no-severity rules are unchanged." Input and output ESO registrations are identical (v14 changes no encrypted/AAD attribute *set*, only a value inside `params`); `shouldTransformIfDecryptionFails: true` matches the plugin's own convention (`migrations/utils.ts:31`).

Normalizing `params.severity` actually lets the next rule write produce a *correct* `mapped_params.severity` (previously `[expr]` → `''`).
