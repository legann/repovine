### Two couplings the naive "just lowercase `params.severity`" misses

1. **`mapped_params.severity` projection.** `find` rewrites sort/search/filter on `params.severity` to the stored `mapped_params.severity` (`SEVERITY_MAP`, e.g. `[value]`), and the create/update write paths that recompute it don't run during migration. A mis-cased `'High'` currently projects to `''`; lowercasing only `params` would leave it stale. The transform recomputes `mapped_params.severity` in lockstep (mirroring `getModifiedValue`: `[expr]`).
2. **Encryption AAD.** `RuleAttributesIncludedInAAD` contains **`params`** and **`mapped_params`** (`index.ts:58-77`), and `apiKey`/`uiamApiKey` are encrypted against that AAD. A plain `unsafe_transform` mutating `params` would make every migrated rule's API key **permanently undecryptable**. Version 14 is wrapped in `createModelVersion` (decrypt → transform → re-encrypt with the new AAD), with `shouldTransformIfDecryptionFails: true` matching the plugin's own encrypted-migration convention (`migrations/utils.ts:31`).

Already-lowercase / absent / non-string severities return the document unchanged (idempotent, no re-projection).

### Changed behavior & residual risk

- **Behavior:** on upgrade, rules with a non-lowercase `severity` get `params.severity` lowercased and `mapped_params.severity` re-projected; their API key is re-encrypted to the new AAD. Already-lowercase/severity-less rules are logically unchanged.
- **`check_registered_types.test.ts:70`** — the `alert` migration hash (`[expr]`) will change. I left it unmodified per "do not modify tests"; regenerating this hash is the standard follow-up for any new model version.
- **One-time re-encryption of all rules** — `createModelVersion` decrypts + re-encrypts every rule's API key (new IV, identical plaintext) regardless of whether severity changed. Behavior is unchanged; this is the same pattern as `connector_token` v2. It is one-time write amplification on upgrade.
- **Legacy rules with `params.severity` but no `mapped_params` object** — severity is lowercased, `mapped_params` left absent (shape preserved); such a rule stays unsortable-by-severity until its next write — identical to its pre-migration state (no regression).
- **Validation** — this worktree is intentionally not bootstrapped (the `tsc`/`eslint` shims block installs, type-checks, and tests). I verified statically against the actual model-version/ESO type definitions and three precedents (`fleet` `synthetics_disable_browser_input`, `synthetics` `model_version_1`, `actions` `connector_token_model_versions`); `no-unnecessary-condition`/`prefer-nullish-coalescing` are not enabled, and `[expr]` matches the existing `mapped_params_utils.ts` style.
