## Summary

I localized the migration to the **`alert` saved-object type in the `alerting` plugin** (`x-pack/platform/plugins/shared/alerting`), where the `severity` rule param lives under the flattened `params` attribute (`params.severity`). I added **model version 14**, which lowercases `params.severity`.

The load-bearing discovery: **`params` is part of the rule's encryption AAD** (`RuleAttributesIncludedInAAD` at `saved_objects/index.ts:67`). The `alert` type is an Encrypted Saved Object (encrypts `apiKey`/`uiamApiKey`). Mutating an AAD attribute with a plain transform would leave the encrypted `apiKey` bound to the old AAD and make it **permanently undecryptable**. So the transform is wrapped with `encryptedSavedObjects.createModelVersion(…)`, which does decrypt‑(old AAD)→transform→re‑encrypt‑(new AAD). Because the encrypt/AAD attribute *sets* are unchanged, `[expr]`, making this a clean single‑release change (`[expr]`, `encrypted_saved_objects_service.ts:661` — so rebuilding the `params` object is safe).

## Residual risk

- **Registry hash snapshot (requires follow‑up, not modified per "do not modify tests").** Adding model version 14 changes the `alert` type's migration hash. Exactly one fixture asserts it: `x-pack/platform/plugins/shared/encrypted_saved_objects/integration_tests/ci_checks/check_registered_types.test.ts:70` (`[expr]`) plus the `[expr]` entry. Its own header (lines 58‑61) prescribes regenerating via `jest_integration -u`, which intentionally triggers a Kibana Security team review of the ESO change. I left it untouched.
- **All rules are re‑encrypted, not just changed ones.** `createModelVersion` decrypts/re‑encrypts every rule (fresh IV). Decrypted values, AAD, and behavior are identical for already‑lowercase/no‑severity rules — only ciphertext bytes differ — but it is O(rules) work during upgrade, inherent to any AAD‑affecting ESO migration (same as `connector_token` v2).
- **`shouldTransformIfDecryptionFails: true`** means a rule whose `apiKey` is already undecryptable has its encrypted attrs stripped rather than blocking the whole migration. This prioritizes "every rule continues to load" (upgrade can't be blocked by one corrupt doc); such a rule was already non‑functional.
- **Verification was static only.** This worktree is intentionally not bootstrapped (`node_modules` absent; tooling shimmed to exit 127), so I could not run `type_check`/`eslint`/`jest`. Correctness rests on faithful reuse of established precedents (`connector_token_model_versions.ts` for the ESO wiring, the synthetics `unsafe_transform` shape, and the v13 schema re‑export).
