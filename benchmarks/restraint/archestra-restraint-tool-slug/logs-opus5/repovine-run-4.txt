## Where tool names become identifiers

`ToolModel.slugifyName(…)` (`platform/backend/src/models/tool.ts:80`) is the only transform: it lowercases, folds whitespace to `_`, then drops every character outside `[expr]`. It is a per-tool-pair function, so it cannot see that two raw names collapse to one slug — `Get_User`/`get user`, or any two names built purely of stripped characters, which both reduce to the bare `[expr]` prefix. Rows are keyed by that name under a unique `[expr]` constraint with `onConflictDoNothing` (`tool.ts:768`), so the losers silently vanish.

It is called from six sites; five are discovery batches that hold a server's whole tool list:

| Site | Path |
|---|---|
| `[expr]` | local + remote install |
| `[expr]` | local + remote deploy |
| `services/mcp-reinstall.ts:405` | reinstall sync |

## Files changed

- **`services/mcp-tool-naming.ts`** (new) — `slugifyToolNamesForServer(…)`. Slugs unique in the batch are returned byte-identical to what `slugifyName` produces today. In a colliding group the first tool keeps the shared slug (it is the one whose row wins the insert today), and each later one gets `[expr]`. The digest keys off the raw name only, so a tool's identifier is independent of its position in the list and of the server/catalog prefix.
- **`routes/mcp-server.ts`, `archestra-mcp-server/mcp-servers.ts`, `services/mcp-reinstall.ts`** — the five batch sites now name the list as a set.
- **`models/tool.ts`** — `syncToolsForCatalog` only. Its fallback match key is the lowercased raw name, which is lossy in exactly the way that creates collisions, so two now-distinct tools could claim one row (renaming it twice and orphan-deleting the other). It now tries the exact stored name first and refuses to match a row already claimed in the batch. `slugifyName`/`unslugifyName` are untouched.

## Residual risk

- **Not compiled or tested.** This worktree has no `node_modules`; type-check and vitest are blocked, so the change is verified by reading only. The `[expr]` inference and the `import ToolModel from "@/models/tool"` default import both match existing lines in the same files.
- Which tool of a colliding group keeps the base slug follows the server's `tools/list` order. If a server reorders its colliding tools between discoveries, the base slug moves between them and the pair is renamed.
- A disambiguated slug does not `unslugify` back to a raw upstream name, so such a tool is addressable and policy-governable but is not routed upstream by the gateway/proxy. Those tools are unreachable today too; extending the wire is a separate change.
- The suffix adds 9 characters. `slugifyName` never enforced the documented 128-char provider limit, and adding truncation would rename working tools, so long names get slightly longer.
