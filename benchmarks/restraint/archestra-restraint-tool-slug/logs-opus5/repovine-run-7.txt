## Where tool names become identifiers

`ToolModel.slugifyName(…)` (`platform/backend/src/models/tool.ts:80`) builds the string stored in `tools.name` — that string is the identifier the gateway serves and the LLM addresses. It drops every character LLM providers disallow, so distinct upstream names can produce one slug (`"get user"` / `"get_user"`, or any two names made only of dropped characters, which both yield the bare `[expr]`). It sees one name at a time and cannot detect this. Five call sites turn a server's `tools/list` into stored identifiers, all feeding `bulkCreateToolsIfNotExists` / `syncToolsForCatalog`.

## Changed

| File | Change |
|---|---|
| `models/tool.ts` | New `ToolModel.slugifyNamesForServer(…)`: slugs the server's tool list as a set — first tool to claim a slug keeps it, later collisions take the lowest free `[expr]`. Also `syncToolsForCatalog` now prefers the row already stored under the exact incoming name before raw-name matching. |
| `routes/mcp-server.ts` | Local + remote install discovery use the set-level naming (2 sites). |

`slugifyName` itself is untouched, so every non-colliding tool gets byte-identical names, and a lone tool whose name strips to empty keeps its bare `[expr]`.

## Residual risk

- Suffixes follow the upstream `tools/list` order. If a server reorders colliding tools between discoveries, which sibling holds the bare slug can flip, and assignments/policies follow the name.
- If a server later exposes a literal `[expr]`, a previously suffixed sibling shifts to `_3`.
- Reinstall/sync still matches upstream raw names against stored slug tails (`tool.ts:2186-2196`), so tools whose raw names differ only by case still resolve to one row on that path; I left that matching contract alone.
- Disambiguated names do not round-trip to an upstream raw name through `unslugifyName` — colliding tools were already unresolvable there, and the wire was not extended to route them.
