## What changed

**Where tool names become identifiers:** one choke point — `ToolModel.slugifyName(…)` at `platform/backend/src/models/tool.ts:85`. Every discovery/persistence path routes through it: `routes/mcp-server.ts:762` and `:924` (install), `archestra-mcp-server/mcp-servers.ts:1451`/`:1506`, `services/mcp-reinstall.ts:406`, `services/apps/app-mcp-backing.ts:73`, `models/tool.ts:864` (catalog clone). The stored `name` is what the gateway hands the LLM (`routes/mcp-gateway.utils.ts:1654`), and `dedupeToolsByName` at `:1668` is where a shared identifier becomes one visible tool.

**The collision:** the old code stripped every character outside `[expr]`, so any name with nothing else left — a name written in a non-Latin script, in emoji, or in punctuation — produced the same tool half. `検索`, `取得`, `日本語` all yielded `catalog__`; `получить_данные` and `создать_данные` both yielded `catalog___`. Rows collapse in `bulkCreateToolsIfNotExists` (matched by name) and again in the gateway dedupe, so only one of them can be assigned, policed, or called. The `[expr]` unique constraint is NULLS-DISTINCT for MCP tools (`database/schemas/tool.ts:83`), so nothing errors — it silently dedupes.

**Files touched (implementation only, no tests):**

| File | Change |
|---|---|
| `backend/src/models/tool.ts` | `slugifyName` now sanitizes each half and joins; new `slugifyRawToolName` returns a `[expr]` token when sanitizing leaves nothing identifying. Private `sanitizeNamePart` holds the original character rules. |
| `backend/src/clients/mcp-client.ts` | `resolveActualToolName` adds the slugified form of each remote tool name as a second key onto the same tool, so a derived token resolves back to the server's native name. Exact case-insensitive matches are filled first and win. |

A name keeps its exact current identifier whenever the sanitized form retains an alphanumeric, or when sanitizing changed nothing at all (`""`, `"-"`, `"_"`). I fuzzed 200,000 random server/tool pairs against the pre-change implementation: every difference is a derived-token case, and all 14 inputs pinned by `tool.test.ts` are byte-identical. Splitting the sanitize per half is safe because the only non-per-character rule collapses a whitespace run, and no run can span the `__` separator.

I could not run the repo's suites — this worktree has no `node_modules` and installs/tests are blocked, so verification is the fuzz comparison plus static reading. No existing test passes a non-ASCII tool name (grepped), so the new branch is uncovered by the current suite.

## Residual risk

- **MCP Apps path still forwards the token.** `mcp-server-gateway.utils.ts:60` lists `unslugifyName(…)` and `callToolForServer` (`mcp-client.ts:2999`) passes it upstream verbatim with no resolution step, so a derived-token tool reaches the server under its token. No regression (its raw half is empty today), but not fixed. A real fix needs the native name persisted on the row.
- **Reinstall recreates these rows.** Incoming key is the native name, DB key is the token, so they don't match; the orphan-transfer block (`tool.ts:2244-2277`) matches on the raw half — identical on both sides — so policies and assignments move and the identifier is stable, but the row id changes.
- **No backfill.** Catalogs installed before this change keep their old `catalog__` row until a reinstall sync prunes it; plain rediscovery adds the new rows without deleting the stale one.
- **Prefix collision** requires a server exposing a tool literally named `[expr]` *and* a degenerate-named sibling hashing to that digest; the direct name match wins in resolution.
- Names not fully degenerate still collide (`toolname` vs `tool.name`, `日本語_2` vs `中文_2` → `_2`). Separating them means changing an identifier that works today, which the constraints forbid.
