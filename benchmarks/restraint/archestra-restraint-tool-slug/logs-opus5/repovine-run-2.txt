## Where tool names become identifiers

`ToolModel.slugifyName(…)` — `platform/backend/src/models/tool.ts:80-85` — builds the identifier stored in `tools.name`. It lowercases, maps whitespace to `_`, and **drops every character outside `[expr]`**. That's the collision source: `"list repos"` and `"list_repos"` both give `srv__list_repos`, `"Foo"`/`"foo"` both give `srv__foo`, and any name that strips to empty (`"日本語"`, `[expr]`) gives the bare `srv__` prefix. Colliding tools then collapse onto one row under the `[expr]` unique constraint (`database/schemas/tool.ts:83-88`), so only one stays addressable.

It's a **per-pair** transform — it never sees sibling tools — so distinctness can only be decided by the layer holding a server's whole listing. Five such discovery write sites existed, all shaped `tools.map(…)`.

A slug produced by exactly one tool is returned byte-identical and is also seeded as reserved, so no disambiguated name can steal it. Only tools that actually share a slug get a discriminator, derived from the raw name (FNV-1a, base36) so re-discovery reproduces the same identifier regardless of listing order — discovery matches stored rows by name, so order-stability is what keeps a re-sync from churning rows and their policies. `slugifyName` is injected rather than imported, keeping the helper a pure function.

Verified by running the real codec against ported logic: non-colliding listings byte-identical to today; a *lone* empty-stripping tool keeps `srv__`; colliding ones each get a distinct id while non-colliding siblings are untouched; stable across shuffled listings; and when a disambiguated candidate would hit a sibling's real name, the sibling keeps it and the colliding tool backs off.

## Residual risk

Disambiguated names don't round-trip through `unslugifyName` (`srv___nbamha` parses back as server `srv_`, tool `nbamha`), so such a tool is stored and policy-governable but still not callable upstream — the annotation scopes this out explicitly ("the wire is not extended to route it"), and those tools were unaddressable before. Collision membership is listing-scoped: if a server later drops one of two colliding tools, the survivor takes the plain slug on the next sync — a rename affecting only already-broken tools. `slugifyName` never truncated to the 128-char LLM limit and I kept that; a discriminator adds ~8 chars, making that pre-existing ceiling marginally more reachable. Per the constraint I added no tests, and I confirmed no existing test asserts on names from the changed paths — including `mcp-reinstall.test.ts`, whose `ToolModel` mock exposes only `slugifyName` (which is why the helper takes it as a parameter).
