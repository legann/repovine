## Summary

**Where tool names become identifiers.** `ToolModel.slugifyName(…)` (`platform/backend/src/models/tool.ts:81`) is the single conversion: it concatenates `server__tool`, lowercases, collapses whitespace to `_`, and drops every character outside `[expr]`. It is not injective — `getUser` and `get.user` both yield `srv__getuser`, and a name made only of dropped characters yields the bare `srv__`. Because `tools` rows and every lookup are keyed by name, and the `[expr]` unique constraint is NULLS-DISTINCT for MCP tools (`database/schemas/tool.ts:83-88`), colliding tools land as **separate rows sharing one name** and only one is ever reachable.

Six call sites feed that conversion; the five discovery/sync writes reach it through two sinks — `bulkCreateToolsIfNotExists` (4 callers) and `syncToolsForCatalog` (1 caller).

**Changed** (3 files, implementation only):
- `models/tool.ts` — added `slugifyNamesForServer` plus three private helpers (`resolveDistinctToolNames`, `findToolNameOwner`, `disambiguateToolName`). A name no other raw name contests passes through byte-identically. Where several contest one name, the raw name that name **already serves upstream** keeps it, and the rest get `[expr]`. `slugifyName`/`unslugifyName` bodies are untouched.
- `archestra-mcp-server/mcp-servers.ts`, `routes/mcp-server.ts` — the four discovery sites now resolve the server's whole raw list at once instead of one pair at a time.
- `syncToolsForCatalog` resolves internally from the `rawToolName` it already receives, so `services/mcp-reinstall.ts` is unchanged.

The disambiguator joins with `-`, so names keep the same `__` count and `parseFullToolName` still splits off the same server prefix. Suffixes derive from the raw name, so they don't move when a server reorders `tools/list`.

**Deliberately unchanged, with the source that puts each out of scope:**
- **Wire consumers** — `routes/mcp-server-gateway.utils.ts:60`, `routes/mcp-server-proxy.ts:168`, `clients/mcp-client.ts:2120`: the module annotation marks these frozen ("Editing the wire consumers … changes the external serving/matching contract; these consumers are frozen alongside the codec"). I read them only to derive the ownership rule — `resolveActualToolName` (`mcp-client.ts:2134-2156`) matches upstream **case-insensitively**, which is why a lone case-insensitive match keeps its name rather than being renamed.
- **Clone reconciliation** (`models/tool.ts:870`) — its own comment states the precondition: "the source's tool names are unique within its catalog, and re-slugifying the un-prefixed name is idempotent." Distinct stored names therefore yield distinct clone names; this path re-derives from names already made distinct rather than converting an MCP-exposed name.
- **App launch tool** (`services/apps/app-mcp-backing.ts:73`) — a single `ToolModel.create`, no sibling set, and the comment above it documents its own uniqueness mechanism: the name "is suffixed with the app id so two apps that legitimately share a name across scopes don't produce the same `[expr]`."

Two tools whose raw names differ only by case remain mutually unresolvable upstream — the disambiguated names are distinct and addressable in the platform, but `resolveActualToolName`'s lowercased map cannot route them individually, and per the annotation the wire was not extended to do so.
