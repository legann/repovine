## Where tool names become identifiers

`ToolModel.slugifyName(…)` — `platform/backend/src/models/tool.ts:81`. It lowercases, maps whitespace runs to `_`, and drops everything outside `[expr]`, joined by `__`. Its output is written to `tools.name`, which the unique constraint on `[expr]` (`platform/backend/src/database/schemas/tool.ts:83`) makes the addressable identifier. Because it transforms one server/tool pair at a time, distinct raw names that differ only in case or stripped characters — `"Create Issue"`/`"create_issue"`, or two names stripped to empty — produce one identifier and collapse to a single row; the second tool never gets a row.

It is called from five MCP-discovery batch sites and two non-discovery sites.

## Changed behavior

A slug only one tool in the list holds is returned untouched, including the bare `server__`. Within a colliding group, the tool whose raw name already equals its own slugified form keeps the plain slug; the others take `[expr]`. The assignment follows from the names, not from `tools/list` order, so rediscovery and reinstall reproduce it. On an existing install, the collapsed row stays with the canonical tool — keeping its policies and assignments — and the previously-dropped sibling appears as a new row.

## Residual risk

1. A disambiguated name does not round-trip upstream: `resolveActualToolName` won't find `foo_1a2b3c4d` in the server's live list and passes it through, so calling such a tool fails at the upstream server. These tools had no row at all before, so nothing regresses — but they are now visible and assignable while not yet callable. Closing that means rekeying the frozen name-resolution map.
2. For a fully-stripped raw name the result is `[expr]`, and `parseFullToolName` splits it as server `srv_`. Cosmetic, affecting display/attribution (`search-tools.ts:421`, `observability/tracing/mcp.ts:155`) for these new tools only.
3. Disambiguated names run 9 characters longer against the 128-char provider limit. Nothing truncates today either, so this is a widening of an existing gap, not a new one.
4. Static verification only — no compile or test run was possible in this worktree.
