## Where tool names become identifiers

`ToolModel.slugifyName(…)` (`platform/backend/src/models/tool.ts:80`) builds the full identifier stored in `tools.name`. It lowercases, maps whitespace to `_`, then **strips every remaining disallowed character** — so distinct raw names can collapse to one identifier. The clearest case: a name made entirely of stripped characters (e.g. CJK) yields the bare `server__` prefix, and several such tools all land on it. Colliding rows share one `tools.name` and cannot be addressed individually.

It's called from five discovery/write sites, all shaped `tools.map(…)` → a bulk write.

## What I changed

`slugifyName` is a per-pair transform with no visibility into sibling tools, and its output for a lone empty-stripping tool (`server__`) is a working identifier that must not move. So distinctness went into the layer that holds a server's tools as a set, leaving the codec untouched.

| File | Change |
|---|---|
| `models/tool.ts` | New `ToolModel.slugifyNamesForServer(…)`; `syncToolsForCatalog` normalizes its incoming batch; internal `distinctToolNames` / `disambiguateSlug` helpers at file bottom |
| `archestra-mcp-server/mcp-servers.ts` | Local + remote discovery use the set-level helper |
| `routes/mcp-server.ts` | Local + remote install discovery use the set-level helper |

The first tool to claim a slug keeps it **verbatim**; only the second and later of each colliding group get a `_2`, `_3`, … suffix. Disambiguators also dodge the set of all base slugs, so a tool whose raw name genuinely produces `foo_2` keeps it rather than losing it to a `foo` sibling — I found and fixed that by tracing an adversarial case.

## Residual risk

- **Verification was static only.** This worktree has no `node_modules` and the sandbox blocks install/type-check/test, so I confirmed correctness by reading: `strict` is on without `noUncheckedIndexedAccess` (so the `[expr]` accesses type as `string`, matching the existing `[expr]`), the renamed `syncToolsForCatalog` param has no surviving references, and all ~16 real `syncToolsForCatalog` tests plus the sync-path reinstall tests pass collision-free input, where the new code is a pass-through.
- **Disambiguated names don't round-trip upstream** — `srv___2` parses back as server `srv_`, tool `2`. Such a tool is now stored and listed distinctly but still isn't callable upstream; that's the sanctioned boundary, not a regression.
- **Order dependence** — which colliding tool keeps the bare slug follows the server's `tools/list` order, so a server that reorders colliding tools between installs can swap which row is which. Non-colliding tools are unaffected.
- **Pre-existing reinstall gap** — `syncToolsForCatalog` matches existing rows by comparing the stored slugified suffix against the raw name, so it already misses any name slugification alters (spaces, stripped characters). Colliding tools may be re-inserted and orphaned across reinstalls rather than matched in place. Untouched here; fixing it means changing the frozen stored↔raw matching contract.
- No tests added per the constraint, so the new behavior isn't pinned by CI.
