## Where tool names become identifiers

`ToolModel.slugifyName(…)` (`platform/backend/src/models/tool.ts:80`) builds the full slug stored in `tools.name` — lowercase, whitespace→`_`, then everything outside `[expr]` deleted. It is a **per-pair** transform, so any two raw names that differ only in stripped characters produce one slug: `get.user`/`getuser`, `GetUser`/`getuser`, and every name that strips away entirely (`検索`, `[expr]`) collapsing onto the bare `server__`. The losing row is dropped by `onConflictDoNothing`, so those tools were never individually addressable.

It is called from six sites; five are per-server discovery batches, which is where the fix went.

## What changed

**`models/tool.ts`** — added `slugifyToolNames(…)`, a batch sibling that slugifies a whole server's tool list. First claimant of a slug keeps it byte-for-byte; later claimants take the smallest free `[expr]`, skipping every base slug in the batch so a suffix never steals the identifier of a tool whose own name yields it. Identical raw names still collapse. `slugifyName`/`unslugifyName` are untouched.

The suffix uses `-`, not `_`, so it stays clear of the `__` server separator: `server__-2` still parses as server `server`, where `server___2` would misparse as `server_`. That is what keeps clone re-slugification (`slugifyName(…)`) reproducing exactly what clone discovery computes.

**`routes/mcp-server.ts` (2), `archestra-mcp-server/mcp-servers.ts` (2), `services/mcp-reinstall.ts` (1)** — discovery batches now call the batch slugifier instead of mapping `slugifyName` per tool.

**`models/tool.ts` — `syncToolsForCatalog` row matching.** This one is load-bearing, not cosmetic. The reinstall path matched existing rows by the raw name extracted from the *stored* slug; `server__getuser-2` reduces to `getuser-2`, which no upstream tool answers to, so the raw-name map would have handed that incoming tool the row belonging to the sibling it collided with — renaming a working tool. Matching now runs two passes: exact stored name claims rows first, then the raw-name map (which exists to re-find a tool after a catalog rename) fills the rest, skipping claimed rows.

## Residual risk

- **Order dependence.** Which collider keeps the bare slug follows upstream `tools/list` order. That matches which row exists today, but a server that reorders its colliding tools between discoveries would swap the two identifiers. Non-colliding tools are unaffected.
- **Not runtime-verified.** No test run was possible here; the model layer and both route paths are exercised only by the simulations above.
- **Disambiguated tools still do not resolve upstream** — by design per the annotation. They become addressable *within* the platform (policies, assignments, guardrails UI); a `tools/call` against `server__getuser-2` reaches the wire's case-insensitive lookup and finds nothing, same as before the change.
- **Migration is one reinstall behind.** Existing collapsed rows only split once discovery re-runs; until then the deployment keeps its single row.
