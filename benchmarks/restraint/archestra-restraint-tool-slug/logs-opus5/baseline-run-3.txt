## Where tool names become identifiers

`ToolModel.slugifyName(…)` — `platform/backend/src/models/tool.ts:81` — is the only place an MCP-exposed tool name is turned into the platform identifier (`tools.name`). Callers:

| Site | Path |
|---|---|
| `routes/mcp-server.ts:762`, `:924` | install-time discovery (local / remote) |
| `archestra-mcp-server/mcp-servers.ts:1451`, `:1506` | deploy-time discovery |
| `services/mcp-reinstall.ts:406` | reinstall sync |
| `models/tool.ts:840` | catalog clone (provisional tools) |
| `services/apps/app-mcp-backing.ts:73` | app launch tool (constant short name) |
| `clients/mcp-client.ts:2120` | `stripServerPrefix`, reverse direction |

The defect: the tool segment drops every character outside `[expr]`, so any name written entirely in such characters (CJK/Cyrillic/emoji/punctuation) collapses to the empty segment. Every one of them lands on `[expr]`, and the `unique(…)` constraint (`database/schemas/tool.ts:83`) keeps exactly one row — the rest are dropped by `onConflictDoNothing`.

## Files changed

**`platform/backend/src/models/tool.ts`**
- `slugifyName` now composes a server segment and a tool segment (identical output for every input whose tool segment was already usable).
- New `ToolModel.slugifyRawToolName`: a name that loses characters to slugification *and* retains no alphanumeric gets `[expr]` instead. Deterministic, distinct per name, itself a valid slug (re-slugifying is a no-op, which the clone path at `:840` depends on).
- `syncToolsForCatalog`: falls back to matching existing rows by the stored slug segment when the upstream raw name doesn't match; extracted the four inline copies of "part after the last `__`" into `extractRawToolName`.

**`platform/backend/src/clients/mcp-client.ts`**
- `resolveActualToolName` now also indexes upstream names by their slug segment, so a call arriving under the stored identifier reaches the upstream tool. Slug keys are added only where unambiguous and never shadow a real tool name — exact matches still win, so every name that resolves today resolves identically.

## Deliberately left unchanged

| Path | Why it's out of scope |
|---|---|
| Server/catalog-name segment (a catalog named `天気` yields `__list`) | The tool's own name still yields a usable, distinct segment; constraint 1 protects it. `stripServerPrefix` (`mcp-client.ts:2118-2126`) recovers `list` correctly, since `[expr]`. |
| Partial-loss collisions (`tool@name` vs `toolname`) | Each already yields a usable identifier. `models/tool.test.ts:54-59` and `:78-83` pin lossy-but-usable slugs (`list all repos` → `list_all_repos`) as the contract. |
| Case-fold collisions (`Weather` / `weather`) | Pinned by `models/tool.test.ts:49-52`, and relied on by the case-insensitive raw-name matching documented at `models/tool.ts:2086-2087`. |

| Delegation tool names (`models/tool.ts:2462`, `:2603`) and A2A skill ids (`routes/a2a.ts:144`, `a2a-v2.ts:130`) | Derived from **agent** names via the shared `slugify`, not from MCP tool names. |

## Residual risk

- Derived names are opaque in the tools UI, logs, and traces; the raw name is recoverable only from the upstream server's list.
- No backfill: an existing collapsed `[expr]` row keeps its name. The next discovery inserts the distinct rows alongside it; the reinstall path deletes it as orphaned, the install path leaves it in place.
- Tools reached by raw name from MCP Apps still can't invoke a derived-name tool — unchanged from today, since that path has no route back from identifier to raw name.
- 48 bits of digest: collision odds within one server's tool list are negligible but not zero.
