## 2. What I changed

**`platform/backend/src/models/tool.ts`** (only file, +38/−4):
- `slugifyName` now slugifies the server and tool parts independently (extracted helper `slugifyToolNamePart`), then rejoins. When the tool part is empty **but the raw name was non-empty**, it falls back to `encodeUnsluggableToolName` — a hex encoding of the raw name's UTF-8 bytes (stays in `[expr]`, bijective, so distinct names → distinct identifiers).
- Splitting into parts is behavior-identical to the old combined transform, because the `__` separator is underscores (never whitespace) so `[expr]`/strip/lowercase never cross the boundary. I verified byte-for-byte equality against every pinned test case and both `search.web`→`searchweb` and `""`→`server__` are unchanged.

Newly-distinct tools were never storable before, so never invocable — no regression, and every working tool's slug is unchanged so its resolution is unchanged. |
| Archestra built-in tools | Fixed-constant `[expr]` names, never slugified from remote input. |

## Summary

**Behavior change**: MCP tools whose names slugify to an empty identifier (non-Latin scripts, all-punctuation) now each receive a distinct, deterministic identifier (`[expr]`) instead of all collapsing onto `server__`, so they can be stored and addressed individually. Every tool whose name already produced a non-empty identifier keeps that exact identifier.

**Files touched**: one — `platform/backend/src/models/tool.ts` (the `slugifyName` transform plus two private module-level helpers). No tests added or modified.

**Residual risk**:
- A previously-broken tool now has a *distinct* identifier but still isn't *remote-callable*, because `resolveActualToolName` can't map the hex back to the raw name — invocation was already impossible for these, so this is strictly an improvement, not a regression. Full round-trip invocation would require a separate change to the resolver.
- Theoretical collision if a tool were literally named to match another's UTF-hash-derived (astronomically unlikely, and strictly rarer than today's guaranteed collision).
- Very long all-non-Latin names produce longer hex ids; the old code never truncated to 128 either, so this matches existing behavior.
- Not machine-verified: the worktree is intentionally un-bootstrapped, so I confirmed equivalence via a standalone Node reproduction of the exact old/new logic rather than the repo's vitest/type-check.
