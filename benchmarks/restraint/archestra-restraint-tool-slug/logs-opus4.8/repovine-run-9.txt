## Summary

MCP tool names become identifiers through **`ToolModel.slugifyName(…)`** (`backend/src/models/tool.ts`), which builds `[expr]`, lowercases, maps whitespace→`_`, and strips characters outside `[expr]`. When a raw name strips to empty, every such tool yields the bare `[expr]`. For a regular MCP catalog the tools-table unique index `[expr]` is NULLS-DISTINCT (schema comment, `database/schemas/tool.ts:78-97`), so those colliding rows coexist under one `name` and cannot be addressed individually.

`slugifyName` is a per-tool-pair transform with no view of sibling tools; per the module's boundary annotation, distinctness "is a property of the layer that holds them together, not of this transform." So the codec is untouched and a set-level pass is added at the write/discovery layer.

## What changed

New in `models/tool.ts`: `ToolModel.slugifyDistinctNames(…)` + private `disambiguateSlugs`. It groups a server's tools by slug, returns any **unique** slug exactly as `slugifyName` produced it, and appends a stable `[expr]` suffix to the members of any colliding group (a `used`-set + counter guarantees final distinctness). Suffix derives from the raw name, not batch order, so a tool re-resolves to the same identifier across runs.

| File | Path where name→identifier is formed | Change |
|---|---|---|
| `models/tool.ts` | `slugifyName` (codec) | **unchanged** — frozen; added `slugifyDistinctNames`/`disambiguateSlugs` beside it |
| `routes/mcp-server.ts` | local + remote install (×2) → `bulkCreateToolsIfNotExists` | use `slugifyDistinctNames` |
| `archestra-mcp-server/mcp-servers.ts` | local + remote discovery (×2) → `bulkCreateToolsIfNotExists` | use `slugifyDistinctNames` |
| `models/tool.ts` → `syncToolsForCatalog` | reinstall write path | disambiguates internally (keyed by `rawToolName`); for a disambiguated tool it clears `rawToolName` so its stored suffix is the match key — the same key existing rows resolve to |

`bulkCreateToolsIfNotExists` matches by full name, so the disambiguated names flow straight through. All four install call sites and the reinstall path produce **identical** disambiguated names for the same catalog (same slug + same raw-name hash), so re-discovery, reinstall, and catalog rename match existing rows without churn.

## Residual risk

- **Disambiguated slugs don't round-trip upstream.** `unslugifyName`/`parseFullToolName` recover the hash suffix, not the real raw name — accepted per the annotation (those tools were already unresolvable; the wire isn't extended to route them). The fix makes them distinct *rows/policies/assignments*, not upstream-callable.
- **Migration of pre-fix collisions.** A catalog that collided under an older install carries legacy duplicate `[expr]` rows; the first reinstall migrates them to distinct names and drops the legacy rows. Their old (ambiguous) assignments aren't transferred, since orphan-transfer keys by raw name — acceptable, as those tools weren't individually addressable before.
- **Suffix is 32-bit** (`[expr]`); within-set re-collision or identical raw names are handled by the `used`-set counter fallback.
- **Not executed.** This worktree isn't bootstrapped, so type-check/tests couldn't run. Verified by static review: `noUncheckedIndexedAccess` is off (so `[expr]` is `string`), no parameter reassignment (param renamed to `inputTools`), the `slugifyName`/`unslugifyName` codec and its tests are byte-unchanged, and every non-colliding path is a strict no-op.

Every already-working tool keeps its exact identifier; only tools that previously shared one now get distinct identifiers.
