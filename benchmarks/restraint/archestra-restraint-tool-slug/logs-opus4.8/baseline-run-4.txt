## 1. What changed

**File:** `platform/backend/src/models/tool.ts` — `ToolModel.slugifyName()` (the single place a tool's raw name is turned into the identifier the platform stores and addresses it by).

The old code slugified `server__tool` as one string and **deleted** every character outside `[expr]`. A raw tool name made entirely of disallowed characters (non-Latin scripts, emoji, all-punctuation) was deleted to nothing, so **every such tool on a server collapsed to the identical `[expr]` identifier** and none could be addressed individually.

The fix slugifies the server and tool halves independently, then, **only when a non-empty raw tool name slugifies to an empty part**, substitutes a deterministic token (`x` + 16 hex chars of `sha256(…)`). Independent-then-rejoin is exactly equivalent to the old joint slug for every non-empty result (the `__` separator is an allowed, non-whitespace boundary that no regex run crosses), so all currently-usable identifiers are byte-for-byte unchanged.

## 2. Where names become identifiers, and what I left unchanged

`slugifyName` is the sole char-sanitizing chokepoint. Every producer calls it — `mcp-server.ts`, `mcp-server-proxy.ts`, `mcp-reinstall.ts`, `apps/app-mcp-backing.ts`, `archestra-mcp-server/mcp-servers.ts`, and `tool.ts`'s own clone/reconcile — and consumers (`stripServerPrefix`, `parseFullToolName`, `unslugifyName`) re-derive from the same slug. Fixing the one function covers discovery, storage, lookup, and clone/reconcile.

Deliberately left unchanged, with proof of scope:
- **`stripServerPrefix` + `resolveActualToolName` (`mcp-client.ts:2118`, `:2134`)** — the call-time round-trip to the upstream. It matches the stripped identifier against the upstream tool list **case-insensitively only** (`nameMap.set(…)`), so it never recovers *any* stripped character for *any* tool. The degenerate names were un-callable before my change (stripped to `""`) and remain so; making them callable would require a stored raw-name column and a call-path change — outside "turn the name into an identifier." No regression.
- **`archestraMcpBranding.getToolName` (`branding.ts:68`)** — derives from a fixed `ArchestraToolShortName` enum (controlled ASCII), not an MCP-exposed name.
- **`buildAgentDelegationToolName` / `slugify` / `urlSlugify` (`shared/agents.ts:36`, `[expr]`)** — derive identifiers from **agent/prompt names and URL slugs**, not from "a tool an MCP server exposes." The task's subject is the MCP tool name.
- **Case-only or partial collisions** (e.g. `getUser` vs `GetUser` → `getuser`) — unfixable by a pure per-tool function without changing a working identifier, and the DB's `[expr]` unique constraint makes that a dropped-row case, not a shared-identifier one.

## 3. Summary

**Behavior:** Tool names whose characters are all outside `[expr]` (previously all collapsing to `[expr]`) now get distinct, deterministic, charset-valid identifiers. Every name that already produced a non-empty slug — and the empty-input case `[expr]` → `server__` — is unchanged.

**Files touched:** one — `platform/backend/src/models/tool.ts` (+30/−4): a `node:crypto` import and a rewrite of `slugifyName`.

**Verification (static, worktree isn't bootstrapped):** a standalone Node reproduction confirmed all 10 pinned exact-value cases pass, all pattern cases stay in-charset, 6 formerly-colliding degenerate names become 6 distinct identifiers, output is stable across calls, and the clone→rediscover reconciliation still matches (`[expr]` on both sides).

**Residual risk:** (a) Degenerate-named tools are now addressable/assignable but still not callable upstream — a pre-existing round-trip limitation, unchanged. (b) The 64-bit token could in theory collide with a real tool literally named `[expr]` on the same server, or two degenerate names could hash-collide — both ~2⁻⁶⁴, negligible for per-server tool counts. (c) I could not run the suite or type-check here; behavior was validated by mirrored standalone execution and line-by-line comparison against the unmodifiable tests.
