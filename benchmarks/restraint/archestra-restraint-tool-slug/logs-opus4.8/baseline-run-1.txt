## 2. Where tool names become identifiers

**The single conversion point is `ToolModel.slugifyName(…)`.** It builds the DB `tools.name` — the identifier the LLM addresses and the `[expr]` unique key. Call sites (all now route through the fix):

- `[expr]`, `[expr]`, `services/mcp-reinstall.ts:406` — remote/local tool discovery
- `services/apps/app-mcp-backing.ts:73` — MCP Apps backing tools
- `models/tool.ts:839` — catalog clone (re-slug of an already-slug name; idempotent)
- `clients/mcp-client.ts:2120` — `stripServerPrefix` derives the prefix via `slugifyName(…)`

**The bug:** the old code did `[expr]` over the whole string — it *deleted* disallowed characters. Two tools on one server whose names differ only in deleted characters (dots, punctuation, any non-ASCII) collapsed to the same identifier; entirely non-ASCII names both collapsed to the empty tool portion (`server__`). The `[expr]` unique index then deduped them to one row (`bulkCreateToolsIfNotExists` uses `onConflictDoNothing`), so the second tool became unaddressable.

**The fix:** `slugifyToolName` keeps a name unchanged when nothing is dropped (identity path → every already-usable identifier is byte-for-byte preserved), and appends a 12-hex-char SHA-256 digest of the raw name only when characters *were* dropped — so distinct raw names keep distinct identifiers. It is idempotent (its output re-slugifies to itself), so `resolveActualToolName` now keys remote names by the same slug and recovers the exact raw name for execution. For clean names the slug equals the lowercased name, so resolution of already-working tools is unchanged.

**Related paths deliberately left unchanged, with proof of scope:**

| Path | Why out of scope (source) |
|---|---|
| Server-prefix slugification (still drops disallowed chars) | Exact-value tests pin the deletion: `tool.test.ts:61-83` (`[expr]`→`[expr]`, `[expr]`→`[value]`, `[expr]`→`[value]`). Prefixes are catalog-scoped, so their collisions never make two tools of one server indistinguishable. |
| Whitespace→`_` and lowercase normalization | Pinned as *collapsing* behavior: `[expr]`. `list all repos`/`list_all_repos` are meant to share an id; changing this would modify tests. This is exactly the "already-working identifier" to preserve. |

| `mcp-server-proxy.ts:168` + `mcp-server-gateway.utils.ts:60` (`unslugifyName`) | The Apps proxy lists and matches with the same `unslugifyName(…)` (self-consistent row selection); upstream execution delegates to the fixed `mcp-client` path (`mcp-server-proxy.ts:22`). |

## 3. Summary

**Changed behavior:** MCP tools whose names contain characters outside `[expr]` (dots, punctuation, non-ASCII) now receive distinct identifiers instead of colliding into one deduped row, and resolve back to their exact remote name at call time. Any tool whose name already produced a usable identifier is byte-for-byte unchanged in both how it is identified and how it is addressed.

**Files touched:** `models/tool.ts` (identifier generation — split into injective tool slug + lossy prefix slug, `node:crypto` digest for disambiguation); `clients/mcp-client.ts` (reverse resolution keyed by the same tool slug).

**Residual risk:**
- **Digest collision** — two disambiguated names on one server colliding needs a 48-bit SHA-256 clash (~1 in 2⁴⁸); negligible for realistic tool counts.
- **Length** — a pathologically long non-ASCII name plus the 13-char suffix could exceed the providers' 128-char cap; such names were fully broken before, and clean names (which have no suffix) are unaffected, so this is not a regression.
- **Idempotency dependency** — resolution assumes the remote server reports the same raw tool name at call time as at install; if a server renames a tool between discovery and call, resolution falls back to the stripped name (same as the prior behavior).
