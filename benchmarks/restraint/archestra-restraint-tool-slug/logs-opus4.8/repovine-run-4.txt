## Summary

An MCP server's tool names become platform identifiers through one codec, `ToolModel.slugifyName(…)` (`backend/src/models/tool.ts`), which builds `[expr]`, lowercased with disallowed characters stripped. Because it strips/lowercases, two distinct tool names on one server can produce the same slug (e.g. `a.b` and `ab` → `s__ab`; any two all-symbol names → the bare `s__`). The `[expr]` unique index is NULLS-DISTINCT for MCP-catalog tools, so colliding names don't conflict on insert — `bulkCreateToolsIfNotExists` then keys results by name and collapses them to one row, so both tools resolve to a single identifier and cannot be addressed individually.

## Fix

`slugifyName` is a per-tool-pair transform with no view of sibling tools, and it's a frozen boundary (stored + wire identity). Distinctness is a property of the layer that holds a server's tools together, so I added a set-aware method beside the codec and left the codec untouched:

- **`ToolModel.slugifyNames(…)`** (`backend/src/models/tool.ts`): slugifies each name via the unchanged codec, reserves every base slug, then disambiguates only names that collide *within the batch* — the first occurrence keeps its base slug byte-for-byte, later collisions get a `-N` suffix chosen to skip every other base slug. Unique slugs pass through unchanged, and the lone empty-strip tool stays `s__` because the batch can see it's the only one.

**Where tool names → identifiers, and what changed** — the five live-discovery sites that `[expr]` a server's tool list, now routed through `slugifyNames`:

| File | Site |
|---|---|
| `backend/src/routes/mcp-server.ts` | local install + remote install discovery |
| `backend/src/services/mcp-reinstall.ts` | reinstall / sync discovery |
| `backend/src/archestra-mcp-server/mcp-servers.ts` | post-deploy local + remote discovery |

All five funnel into `bulkCreateToolsIfNotExists` / `syncToolsForCatalog`, whose internals (keyed by name) stay correct now that names arrive distinct. Reinstall is included so a re-discovery can't undo the disambiguation.

## Residual risk

- **Ordering:** disambiguation is stable per discovery but depends on the server returning tools in a consistent order; if a server reorders *colliding* tools between installs, their `-N` suffixes may swap. Non-colliding tools are order-independent (always their unique base). Per invariant 7 colliding tools are already unresolvable upstream, so this only reshuffles already-broken identities.
- **Reinstall reconcile:** `syncToolsForCatalog` matches existing rows by the raw part of the stored slug; a disambiguated tool's raw part (`x-1`) differs from its original upstream name, so a colliding tool may be treated as new on reinstall (churn within the colliding set). Pre-existing for colliding tools; non-colliding tools reconcile exactly as before.
- **Length:** neither method enforces the documented 128-char cap (the codec never did); a suffix on a near-limit name could exceed it. No truncation added, to avoid altering existing identifiers.
