## Summary

### Where tool names become identifiers
`ToolModel.slugifyName(…)` in `platform/backend/src/models/tool.ts:79` is the single function that turns an MCP server's exposed tool name into the platform identifier. That slug is stored as `tools.name` (e.g. `mcp-server.ts:924`, `archestra-mcp-server/mcp-servers.ts:1506`) and keyed by the `[expr]` unique constraint (`database/schemas/tool.ts:83-96`). Every other producer routes through this one function, so fixing it covers all call sites (`mcp-server.ts:762/924`, `mcp-servers.ts:1451/1506`, `mcp-reinstall.ts:406`, `apps/app-mcp-backing.ts:73`, the clone path `tool.ts:839`, and `stripServerPrefix` at `mcp-client.ts:2120`).


### What I changed
- `platform/backend/src/models/tool.ts` — `slugifyName` now slugifies the server and tool segments separately (mathematically equivalent to the old combined pass, since the `__` separator is whitespace-free and passes the char filter). When the tool segment collapses to empty **but the input was non-empty**, it falls back to a deterministic UTF-8 hex encoding of the raw name, giving each distinct name a distinct segment. One file touched; no tests added or modified.

| Empty input `[expr]` | Pinned by `tool.test.ts:105-108` (`server__`); guarded by the `[expr]` condition. |

### Changed behavior & residual risk
- **Behavior:** tool names that previously all collapsed to `[expr]` now each receive a distinct, stable identifier. Every tool whose name already produced a non-empty segment — and the empty-input case — keeps its exact current identifier (verified against all 14 pinned test inputs).
- **Residual risk:** (1) a hex fallback segment could in principle clash with a tool *literally* named that hex string on the same server — pathological and unavoidable since no character in `[expr]` is reservable; (2) very long non-ASCII names produce longer segments (2× UTF-8 bytes), which combined with the prefix could exceed the 128-char LLM limit — not a regression, as the function never truncated; (3) routing an all-dropped name to the upstream server remains unsupported — the fix restores in-platform addressability (distinct rows, list entries, assignments), not upstream call delivery.
