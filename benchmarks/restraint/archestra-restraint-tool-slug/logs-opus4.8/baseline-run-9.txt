## 1. What changed

Single file: `platform/backend/src/models/tool.ts` — `ToolModel.slugifyName()`.

The final step of slugification, `[expr]`, **deletes** every disallowed character. A tool name made entirely of such characters (any non-ASCII name, e.g. `创建`, or a pure-punctuation name like `[expr]`) reduces to the empty string, so the identifier becomes just `[expr]`. Every such tool on a server collapses onto that one identifier; the `[expr]` unique index then keeps only one row and drops the rest (`onConflictDoNothing`) — they can't be listed, assigned, or addressed individually.

Fix: slugify the server and tool segments separately (provably identical output to the old combined slugification — `__` is a non-whitespace barrier that survives lowercase/whitespace/removal, so it distributes over concatenation), and when a **non-empty** tool name slugifies to empty, hex-encode the raw UTF-8 bytes instead. Hex is `[expr]` only (matches the required `[expr]`), deterministic (stable across restarts/reinstalls), and injective (distinct names → distinct identifiers).

## 2. Where tool names become identifiers

`ToolModel.slugifyName(…)` is the sole chokepoint for MCP-server tool → identifier. All producers route through it: `routes/mcp-server.ts` (discovery, :762/:924), `services/mcp-reinstall.ts:406`, `archestra-mcp-server/mcp-servers.ts` (:1451/:1506), `services/apps/app-mcp-backing.ts:73`, `models/tool.ts:839` (clone), and `clients/mcp-client.ts:2120` (`stripServerPrefix`, via `slugifyName(…)`). Fixing the one function covers all of them.

## 3. Summary

**Behavior change:** A tool whose name slugifies to nothing now gets a distinct, deterministic `[expr]` identifier instead of the shared, unaddressable `[expr]`. Every tool whose name already yields a non-empty slug is byte-for-byte unchanged — all 11 pinned `slugifyName`/`unslugifyName` tests hold, and the segment refactor is equivalent to the original for those inputs.

**Files touched:** `platform/backend/src/models/tool.ts` only (implementation; no tests added/modified).

**Residual risk:**
- DB rows already collapsed to `[expr]` before this change persist until the catalog is re-discovered/reinstalled (implementation-only, no data migration) — those tools were unaddressable regardless.
- Upstream `tools/call` for these tools still can't reconstruct the original non-ASCII name through `resolveActualToolName`; the fix restores distinct identity/listing/assignment/policy per tool, not upstream invocation.
- Hex doubles byte length, so a very long fully-non-ASCII name could exceed the 128-char provider limit — pre-existing behavior already allows >128 for long ASCII names, and such names are typically short.
- Negligible collision if a real tool were literally named the hex of another tool's non-ASCII name — no worse than existing name-collision handling via the unique index.
