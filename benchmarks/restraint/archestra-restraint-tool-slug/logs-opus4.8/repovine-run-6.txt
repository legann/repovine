## Summary

### Where tool names become identifiers

`ToolModel.slugifyName(…)` (`platform/backend/src/models/tool.ts:80`) is the codec that folds an MCP server's raw tool name into `tools.name` — the identifier the platform stores, assigns policies to, and shows the LLM. It's a per-tool-pair transform: it lowercases, collapses whitespace, and strips any char outside `[expr]`. Distinct raw names therefore collapse onto one slug (case folding, punctuation stripping, or a name that strips to empty → bare `server__`), and the two tools then share one identifier.

The collision can only be resolved where a **server's whole tool set is visible at once** — the discovery/write sites that map a server's raw tool list into rows:

| Local install | `routes/mcp-server.ts:762` | `bulkCreateToolsIfNotExists` |
| Remote install | `routes/mcp-server.ts:924` | `bulkCreateToolsIfNotExists` |

### What I changed

- **`models/tool.ts`** — added `ToolModel.slugifyNamesDistinct(…)`, a set-level helper that runs the unchanged codec over the batch, keeps every slug that's unique in the set byte-for-byte, and disambiguates only colliding ones by appending `[expr]` derived from the raw name. Distinctness within the batch is guaranteed by a reserved-name set + extend loop. Added an internal `toolNameDisambiguator` (FNV-1a) and separator const at file bottom.
- **The 5 discovery sites** — swapped the per-tool `slugifyName` call for one `slugifyNamesDistinct` call over the set, indexing the result. The reinstall site additionally keys `rawToolName` off the disambiguated tail so `syncToolsForCatalog`'s raw-name reconciliation stays stable across reinstalls (only for disambiguated tools; non-colliding tools keep `[expr]` exactly).

The suffix depends only on the raw name — not on batch order or size — so re-discovery re-derives the same identifier and adding/removing a sibling never rewrites an untouched tool's name.

### Changed behavior & residual risk

- **Behavior**: when a server exposes tools whose names collide on one slug, each now gets a distinct, stable `tools.name` (`[expr]`); tools that already slugify uniquely — including a lone `server__` — are untouched, so existing rows, assignments, policies, and wire addressing are byte-identical.
- **Residual risk**:
  - Disambiguated slugs don't round-trip to a raw upstream tool name, so a colliding tool remains unresolvable at the gateway/proxy — unchanged from today (it was already unaddressable). By design per the annotation.
  - Rows written *before* this change with a shared `server__x` name are replaced on the first reinstall (raw-name reconciliation can't bridge the old shared tail to the new distinct one), dropping their prior assignments. One-time migration cost for already-broken tools only.
  - 32-bit fingerprint: within one server's colliding group the extend-loop still guarantees uniqueness; the hash only affects readability/stability, and it's stable per raw name.
  - Verification was static only (worktree not bootstrapped — `type-check`/tests unavailable here); per the task I added/modified no tests.
