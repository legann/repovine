## Summary

### The bug
`ToolModel.slugifyName(…)` (`platform/backend/src/models/tool.ts`) builds a tool's identifier by removing every character outside `[expr]`. A tool whose name is entirely non-Latin/punctuation (e.g. `搜索`, `列表`) normalizes to **nothing**, so every such tool on a server collapses to the bare `[expr]`. Since all lookup and assignment goes by `name` (`findByName`, the catalog-sync map, agent-tool links), those tools can't be addressed apart.

### The fix
When `toolName` is non-empty but normalizes to empty, append a deterministic 16-hex-char `sha256(…)` suffix. Everything else is byte-for-byte unchanged.

| Input | Before | After |
|---|---|---|
| `[expr]` | `github__list_repos` | `github__list_repos` (unchanged) |
| `[expr]` prefix-builder | `server__` | `server__` (unchanged) |
| `[expr]` | `srv__` (collides) | `srv__44ce7ae909bbb28b` |
| `[expr]` | `srv__` (collides) | `srv__aedd6814ff8c516c` |

The suffix is deterministic (stable across re-discovery, so no identifier churn and clone-reconciliation still matches), hex-only (matches the `[expr]` provider pattern), and follows the repo's existing `createHash(…)` convention.

### Where tool names → identifiers, and files changed

**Changed** — `platform/backend/src/models/tool.ts`:
- `slugifyName` — the sole transform for external MCP-server tool identifiers. Called by the discovery/install/sync/reinstall/clone/apps paths (`routes/mcp-server.ts`, `archestra-mcp-server/mcp-servers.ts`, `services/apps/app-mcp-backing.ts`, `services/mcp-reinstall.ts`, `clients/mcp-client.ts`). All keep working: they either store the result or, for the `slugifyName(…)` prefix-builder in `clients/mcp-client.ts:2120`, pass an empty tool name (guarded by `[expr]`, so unchanged).
- Added module helper `normalizeMcpToolNameChars` (shared by the slug and the emptiness check) and the `node:crypto` import.

### Deliberately left unchanged (out of scope, with proof)
- **`slugify` / `urlSlugify`** (`[expr]`): agent/prompt/org and URL-gateway slugs, not MCP-tool exposure. `slugify`'s own docstring: *"Used for generating tool names from prompt/agent names"*; `urlSlugify`: *"URL identifiers (e.g., MCP gateway slugs)"*. They already replace disallowed runs with `_`/`-` (different behavior), not the path the task describes.
- **`buildAgentDelegationToolName`** (`platform/shared/agents.ts:37`): `[expr]` — the agent-delegation identifier space, with its own `[expr]` cap (`agents.ts:13`) and agent-name dedup. Not "an MCP server exposes a tool."
- **`archestraMcpBranding.getToolName(…)`**: built-in Archestra tool names built from curated short-name constants (`ARCHESTRA_TOOL_SHORT_NAMES`) that are already valid and unique — no collision to fix.
- **Upstream call-name resolution** (`clients/mcp-client.ts` `stripServerPrefix` → `resolveActualToolName`): resolves an identifier back to the upstream raw name. Untouched; the empty-toolName prefix guard keeps it unchanged.

### Residual risk
- **Symbol-only tools remain un-*callable*, though now distinctly *addressable*.** Executing a tool maps the identifier back to the upstream name via prefix-strip + case-insensitive match against the server's `tools/list` (`clients/mcp-client.ts:2156`, returns `[expr]`). A non-ASCII raw name has no ASCII to match, so this returned `""` before and returns the hash now — both fail upstream. The task scope is addressing ("cannot be addressed individually"); making the call round-trip would require storing the raw name and changing the call path, which is out of scope.
- **Hash collision**: 64-bit `sha256` prefix; collision among the few symbol-named tools on one server is negligible. Chosen over a fully-reversible hex encoding to keep the identifier within the 128-char provider limit.
- **Existing rows aren't migrated.** Any tool previously stored as bare `[expr]` keeps that name until the next discovery/reinstall re-creates it under the new distinct identifier; this change only affects identifier *generation*, adds/modifies no migration and no tests.
