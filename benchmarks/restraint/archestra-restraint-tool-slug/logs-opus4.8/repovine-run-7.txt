## Summary

MCP tool identifiers are the `tools.name` column, produced by `ToolModel.slugifyName(…)` (`platform/backend/src/models/tool.ts:80`). Because `slugifyName` lowercases, folds whitespace to `_`, and strips characters outside `[expr]`, two distinct raw tool names can collapse to one slug (e.g. `"get user"` and `"get_user"` → `server__get_user`; or several names that strip to empty → the bare `server__`). The DB unique index + `onConflictDoNothing` then keeps only the first row, so the others become unaddressable.

Per the module's own annotation, `slugifyName` is a **per-tool-pair transform with no visibility into sibling tools** — making identifiers distinct is a property of *the write layer that holds a server's tools as a set*, not the codec. So I added a set-level pass and applied it where a server's exposed tool set is turned into identifiers.

### 2. Files changed

- **`platform/backend/src/models/tool.ts`**
  - Added `[expr]` — pure set-level pass: the first occurrence of each slug keeps it exactly; each later collision takes the smallest free `[expr]` suffix (avoiding reserved and already-assigned names), staying within the `[expr]` grammar and a single `__` separator.
  - `syncToolsForCatalog` now disambiguates its incoming set first, and matches incoming tools to existing rows by the **(disambiguated) stored name's last segment** — the same derivation used for `existingToolsByRawName` — instead of the raw MCP name. Keying on the raw name (a different character space than the slug) would re-collapse colliding tools and delete them on reinstall.
- **`platform/backend/src/routes/mcp-server.ts`** — wrapped both install `toolsToCreate` maps. `discoveredToolNames` (clone reconciliation) derives from `toolsToCreate`, so it now sees the disambiguated names automatically.
- **`platform/backend/src/archestra-mcp-server/mcp-servers.ts`** — wrapped both discovery `toolsToCreate` maps.

The `mcp-reinstall.ts` call site is untouched (a test pins the exact args it passes to `syncToolsForCatalog`, which is mocked there), so disambiguation for that path lives *inside* `syncToolsForCatalog`.

### 3. Changed behavior & residual risk

**Behavior:** when two of a server's tools would share a slug, the first keeps its exact identifier and each later one gets `[expr]`, `[expr]`, … So they become distinct rows — individually addressable for assignments, policies, and gateway listings. Non-colliding tools and a lone `server__` tool are byte-for-byte unchanged. Reinstall now pairs disambiguated tools to their own rows (durable) rather than deleting them.

**Residual risk:**
- **Upstream call-through:** a disambiguated colliding tool's slug does not reverse to a live raw upstream name, so it's addressable *in the platform* but still not callable through to the origin server. The annotation states colliding/degenerate tools are already unresolvable upstream and the wire is intentionally not extended; already-working tools keep their working round-trip.
- **Ordering:** "first occurrence keeps the base slug" depends on the server's `tools/list` order; a reordering server could swap which colliding tool keeps the bare slug — same order-dependence as today's "first insert wins."
- **Length:** `[expr]` can push a name past the documented 128 chars; `slugifyName` already neither enforces nor truncates, so no newly-broken enforced invariant, and only suffixed (new) identifiers are affected.
- **`rawToolName`** is now unused by `syncToolsForCatalog` matching (retained because `mcp-reinstall` passes it and a test pins that; its value equals the stored last segment for every non-colliding tool).
- **Verification:** the worktree is intentionally not bootstrapped, so I could not run type-check/tests. Verified statically — traced every `syncToolsForCatalog` test (name-derived key equals the passed `rawToolName` for all clean-name cases → no-op), confirmed no discovery test returns colliding names within one batch (`disambiguateToolNames` is a no-op there), and left `bulkCreateToolsIfNotExists` and all wire consumers untouched.
