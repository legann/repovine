- New private `ToolModel.disambiguateSlugCollisions(…)` — renames within-batch duplicate slugs in place: the first tool to claim a slug keeps it; each later collider gets the lowest `[expr]` suffix not already used by any other tool in the batch.

## 2. Where names become identifiers, and scope

**The name→identifier pipeline:** `slugifyName(…)` (tool.ts:80) builds `[expr]`, lowercases, turns whitespace into `_`, and **strips every char outside `[expr]`**. Distinct raw names collapse to one slug — an all-stripped name → bare `server__`; `"list repos"` and `"list_repos"` → `server__list_repos`. The **write layer** `bulkCreateToolsIfNotExists` (tool.ts:678) persists that slug to `tools.name`; it's the single place that sees a server's tools as a set. Callers: `[expr]` (install) and `[expr]` (deploy discovery).

**Why the write layer, not the codec:** the schema's composite unique is NULLS-DISTINCT (agentId/delegateToAgentId NULL for MCP tools), so a normal catalog stored **several rows sharing one name**; the Archestra partial index instead **dropped** the extras via `ON CONFLICT DO NOTHING`. Both are fixed by making names distinct before the insert.

| Path | Proof it's out of scope |

## 3. Summary

**Changed behavior:** during MCP tool discovery, when two tools' names slugify to the same identifier, each now gets a distinct `tools.name` (first keeps the bare slug; the rest get `[expr]`, `[expr]`, …) so they're individually addressable. A tool whose slug is already unique — including a lone tool that strips to the bare `server__` — is byte-for-byte unchanged (the helper is a no-op unless a name repeats). The assignment is deterministic in tool-list order, so a stable server re-derives the same names on re-discovery and existing rows keep matching.

**Files touched:** `platform/backend/src/models/tool.ts` only — one new private helper plus one call in the discovery write layer. Codec and wire consumers untouched. Per the task constraint, no tests were added or modified.

**Residual risk:**
- **Reinstall (`syncToolsForCatalog`) is unchanged.** It can't re-match these edge tools (it derives raw names from the stored slug), so on reinstall they're re-created/churned as before — a pre-existing limitation of the frozen matching contract, deliberately not addressed here.
- **Suffix stability depends on server tool-list order.** If a server reorders colliding tools between discoveries, the disambiguated tools may swap suffixes; unique-slug tools are never affected. Acceptable because colliding tools had no stable identity before this change.
- **Disambiguated slugs don't round-trip to an upstream raw name** — per the module's invariant this is expected and not something the wire is extended to route; the fix only guarantees distinct, individually addressable stored identifiers.
