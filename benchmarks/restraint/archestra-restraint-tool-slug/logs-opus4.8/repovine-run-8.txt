## Summary

**What was broken.** An MCP tool's platform identifier is `tools.name`, produced by `ToolModel.slugifyName(…)` (`platform/backend/src/models/tool.ts:80`): it builds `[expr]`, lowercases, and strips everything outside `[expr]`. Two distinct raw names on one server can reduce to the same slug — names differing only in stripped characters (`[expr]` / `[expr]`), or non‑ASCII names that both collapse to the bare `server__` prefix. `slugifyName` sees one tool at a time and can't detect this. At the write layer the collision manifests as two rows keyed by the same name (the composite unique index is NULLS‑distinct for external catalogs, `database/schemas/tool.ts:83`) — indistinguishable, so they can't be assigned/policied/addressed individually.

**The fix.** Disambiguation is a property of the whole set, so I resolved it in the two write methods that receive a server's tool batch — the layer the module annotation names as *"the write layer any collision needs."* A new pure helper `disambiguateToolNames(…)` makes a batch distinct: names unique in the batch are returned **unchanged** (including a lone tool that reduces to bare `server__`); only colliders are disambiguated — first keeps the base slug, each later collision gets the next free `-N` suffix, guarding against stealing an already-distinct name. It runs at the top of `bulkCreateToolsIfNotExists` and `syncToolsForCatalog`.

**Residual risk**
1. **Reinstall of colliding tools churns the row ID / resets its policies.** `syncToolsForCatalog` matches existing rows by the raw name extracted from the stored slug (`:2074`), and a disambiguated slug (`srv__foo-2` → extracted `foo-2`) never equals the original raw (`[expr]`), so the collider is re-inserted and the old row orphaned. Assignments transfer by raw name (`:2253`); invocation/trusted-data policies don't, so they revert to defaults. Names stay distinct and no duplicate rows accumulate. This is a **pre-existing** trait of sync's raw-name matching (it already churns any single tool whose raw name has stripped characters), not introduced here; only pathological colliders hit it. A full-name fallback in `syncToolsForCatalog` would close it but touches test-covered matching logic — deferred.
2. **Clone first-install of a catalog with colliding source tools**: the route's `discoveredToolNames` set is built pre-disambiguation while `bulkCreateToolsIfNotExists` creates distinct rows; reconciliation of that pathological set is imperfect. Clone + within-catalog collision was already broken; common no-collision clones are unaffected.
3. Order-based (first-keeps-base): stable across rediscoveries since a server's `tools/list` order is stable; only matters for the already-unaddressable colliding set.
