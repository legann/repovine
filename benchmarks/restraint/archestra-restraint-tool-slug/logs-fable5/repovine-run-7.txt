## Summary

MCP tool names become platform identifiers via `ToolModel.slugifyName` (`platform/backend/src/models/tool.ts:80`): `server__` prefix + lowercase + whitespace→`_` + strip of anything outside `[expr]`. Distinct raw names (`get.issue`/`getissue`, `Foo`/`foo`) therefore collapse to one slug, and the DB doesn't catch it — the composite unique on `tools` (`database/schemas/tool.ts:83`) is NULLS-DISTINCT for MCP tools, so colliding tools end up as duplicate same-name rows or merged onto one row, unaddressable individually.

The fix makes identifiers distinct at the layer that sees a server's discovered tool list as a set — the batch write-mapping sites — leaving the per-pair codec untouched:

- **New** `platform/backend/src/utils/tool-name.ts` — `dedupeSlugifiedToolNames(…)`: a slug unique in the list is returned byte-for-byte (working identifiers, including a lone bare `server__`, never change); within a colliding group the first tool keeps the slug and later ones get the lowest `_N` suffix (N≥2) that is neither taken nor any tool's natural slug — so a suffix can never displace a tool literally named `foo_2`.
- **`routes/mcp-server.ts`** (2 install-discovery sites), **`archestra-mcp-server/mcp-servers.ts`** (2 deploy-discovery sites), **`services/mcp-reinstall.ts`** (reinstall sync) — each now passes its slug list through the helper before persisting. Clone-reconciliation name sets in the install route are built from the deduped names automatically.
- **`models/tool.ts` `syncToolsForCatalog`** — claim-once guard: an existing row backs at most one incoming tool per sync. Without it, two colliding entries (same raw-name key) would both match one row and race to rename it; now the first keeps the row and its name, the second is inserted under its deduped name. Inert when keys are unique, i.e. for every working tool.

## Deliberately unchanged, with the source proving scope

- **`slugifyName`/`unslugifyName` codec** (`tool.ts:80-93`): it's the stored-identity codec with no visibility into sibling tools; a codec-level fix would change the lone degenerate `server__` tool's working identifier, and `mcp-client.ts:2120` relies on the `slugifyName(…)` prefix form. The repovine boundary annotation on this module states distinctness "is a property of the layer that holds them together, not of this transform."
- **Wire consumers** — `clients/mcp-client.ts` name resolution (`:632`, `:2116-2130`), `routes/mcp-server-gateway.utils.ts:60`, `routes/mcp-server-proxy.ts:168`: they translate stored names back to raw upstream names for serving/matching; the annotation freezes them, and colliding tools were already unresolvable upstream, so the wire is not extended to route `_N` names.
- **Clone paths** (`tool.ts:840`, `:926`): they re-derive names from stored names, which the comment at `tool.ts:833-836` documents as unique per catalog; re-slugifying a stored slug is idempotent, so deduped names survive cloning distinctly.
- **`app-mcp-backing.ts:72`**: one launch tool per app server — no batch, no intra-server collision; cross-app naming is already suffixed by app id (comment at `:66-71`).
- **`bulkCreateProxyToolsIfNotExists`** (`tool.ts:2344`): proxy-sniffed tools store the observed call name verbatim — no name→identifier transformation happens there.
- **Delegation tools** (`tool.ts:2462`) and **Archestra built-ins** (fixed short-name constants, enforced by `tools_archestra_catalog_name_uidx`): not names exposed by an MCP server.
- **`bulkCreateToolsIfNotExists`**: matches by full name, so deduped inputs already key to their own rows — no change needed.

## Residual risk

- Suffix assignment within a colliding group follows the server's `tools/list` order; if a server reorders between discoveries, colliding tools may swap suffixes. Unique-slug tools are order-independent.
- A `_N` identifier doesn't round-trip to a raw upstream name, so gateway calls to it still can't reach the upstream tool — identical to today's behavior for colliding tools, and explicitly out of this task's scope per the module contract.
- On reinstall-sync, a disambiguated tool is re-created rather than updated in place (raw-name matching can't see it), resetting its policies while assignments transfer — the same churn that already affects any tool whose raw name differs from its slug (e.g. contains dots).
