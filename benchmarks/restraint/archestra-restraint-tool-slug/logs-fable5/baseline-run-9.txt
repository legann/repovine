## Summary

**The bug:** when an MCP server's tools are discovered, each raw tool name is turned into the platform identifier by `ToolModel.slugifyName()` (`platform/backend/src/models/tool.ts:79`): `[expr]`, lowercased, whitespace→`_`, all other disallowed characters stripped. The mapping is lossy, so distinct raw names on one server (e.g. `search.issues` / `searchissues`, `foo bar` / `foo_bar`, `getUser` / `GetUser`) collapse into one identifier — one `tools` row, one gateway listing, one policy target — and the tools can't be addressed individually.

**The fix:** discovery batches are now disambiguated in the model layer. Call sites pass each tool's original name (`rawToolName`); `bulkCreateToolsIfNotExists` and `syncToolsForCatalog` run the batch through a new `disambiguateDiscoveredToolNames()` helper:

- A tool whose slug is unique keeps its exact identifier — `slugifyName()` itself is untouched, so nothing already working is renamed.
- In a collision group, the bare slug stays with the tool whose raw name round-trips through it (exact match, then case-insensitive, then lexicographic tie-break) — that is the tool the shared identifier actually resolves to at call time today. Every other tool gets `[expr]` appended: deterministic, order-independent, stable across reinstalls.
- Any tool whose raw name can't be recovered from its final identifier (lossy slug or suffix) records it in `meta.rawToolName`. Execution (`mcp-client.ts`) resolves the upstream call from that stored name; re-sync matches rows by it (so suffixed identifiers survive catalog renames and repeated reinstalls); the server-scoped app gateway lists/gates by it.

### Related paths deliberately left unchanged, with proof

- **`slugifyName()` itself** — any change would rename working identifiers, violating the constraint.
- **`services/mcp-reinstall.ts`** — zero edits needed: it already passes `rawToolName` per tool (`mcp-reinstall.ts:411`); disambiguation happens inside `syncToolsForCatalog`. This also keeps `mcp-reinstall.test.ts:24-29` valid, which replaces `ToolModel` with a mock exposing only `slugifyName` and `syncToolsForCatalog`.
- **Catalog clone path** (`tool.ts` `cloneToolsAndPoliciesFromCatalog`) — derives clone names by prefix-swap of already-unique source identifiers and copies `meta` (`[expr]` in its insert), so a suffixed name and its `rawToolName` carry over; the suffix is a pure function of the raw name, so first-install discovery mints the same name and reconciliation matches.
- **App launch tools** (`services/apps/app-mcp-backing.ts:72-76`) — one synthetic tool per app, already made unique by the `[expr]` suffix (rationale in the comment directly above).
- **Archestra built-ins** (`seedArchestraTools`) — names come from the compile-time unique short-name registry (`ARCHESTRA_TOOL_SHORT_NAMES`), enforced by the `tools_archestra_catalog_name_uidx` partial unique index (`database/schemas/tool.ts:93-97`).
- **Agent delegation tool names** (`shared/agents.ts`, `[expr]`) — generated from agent names, not from tools an MCP server exposes; outside the task's scope statement.
- **Suffix-match fallbacks** (`getMcpToolsAssignedToAgentBySuffix`/`...AppBySuffix`, `[expr]`) — they match `[expr]`, and DB names contain only `[expr]`, so a raw name that slugification altered has never matched there; leaving them alone changes nothing that works.

### Residual risk

- **Verification:** this worktree is intentionally not bootstrapped (installs/type-check/tests blocked), so the change is verified by static tracing only — including through the sensitive existing tests (`tool.test.ts` sync/bulk cases, the `query-docs` rawToolName case, `mcp-client.test.ts` casing-resolution cases, and the reinstall mock). Run `pnpm type-check` and the backend suite in a bootstrapped checkout before merging.
- **Pre-existing duplicate rows:** the tools table's composite unique constraint is NULLS-DISTINCT, so past collisions could already have created two rows with one name. New duplicates can no longer be minted, and the sync path's existing duplicate handling cleans old ones up on the next reinstall, but no data migration is included.
- **Pure case-twins** (`getUser` vs `GetUser`): each now gets its own identifier and row, but the bare identifier keeps today's last-listed-wins upstream resolution (deliberately, per the don't-change-working-behavior constraint), so on such servers the bare identifier may still execute the other variant; the suffixed identifier is exact.
- **Length:** the suffix adds 9 characters; a base identifier over 119 chars could cross the 128-char LLM provider limit (`slugifyName` has never truncated — pre-existing exposure, unchanged).
- **One-time writes on next discovery:** lossy-named existing rows gain `meta.rawToolName` (meta-only update, identifier unchanged); a lone lossy-named row churns its row id once more on the next reinstall sync (today it churns every time) before the meta match stabilizes it.
