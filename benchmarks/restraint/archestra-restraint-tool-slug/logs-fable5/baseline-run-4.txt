## Summary

MCP tool identifiers are created by slugifying `[expr]` (lowercase, whitespace → `_`, strip everything outside `[expr]`). That transformation is lossy, so two different tool names on one server (e.g. `search` / `Search`, `get.user` / `getuser`, `my tool` / `my_tool`) collapsed into one identifier and one `tools` row — only one of them could ever be addressed. Discovery now assigns identifiers per batch: an uncontested name keeps its exact current slug; in a collision group, the name whose identifier already resolves at call time (slugification only lowercased it) keeps the plain slug, and every other name gets a deterministic suffix hashed from its raw name (`search_a591a6d4`). The assignment is a pure function of the server's tool-name set — independent of listing order — so identifiers stay stable across rediscoveries, reinstalls, and catalog clones, and call-time resolution can re-derive the exact same mapping from a live `tools/list`.

**Where names become identifiers, and what changed:**

- `platform/backend/src/models/tool.ts` — `slugifyName` (behavior byte-identical, now delegates to a shared helper); new `slugifyNames`/`slugifyShortNames` batch APIs implementing the disambiguation; `syncToolsForCatalog` now matches existing rows in two passes (identifier short-form first, raw spelling as a non-contesting fallback) so a suffixed tool can never claim — and rename — its canonical sibling's row on reinstall.
- Discovery/persist call sites switched to the batch API: `routes/mcp-server.ts` (local + remote install), `archestra-mcp-server/mcp-servers.ts` (deploy-tool local + remote), `services/mcp-reinstall.ts` (reinstall sync).
- `clients/mcp-client.ts` — `resolveActualToolName` now keys its name map by the same derived slugs instead of `rawName.toLowerCase()`, so a suffixed identifier executes the correct upstream tool; for every currently-working tool the two keys are provably identical.

**Deliberately unchanged, with the source that scopes them out:**

- `services/apps/app-mcp-backing.ts:73` — single synthetic launch tool whose prefix is already app-id-suffixed ("stable + globally unique", comment at `app-mcp-backing.ts:132-134`); no batch, no collision possible.
- Clone path `tool.ts` `cloneToolsAndPoliciesFromCatalog` — copies already-unique short names verbatim (`slugifyName(…)`); suffixes ride along, and reconciliation matches because the hash depends only on the raw name.
- Apps run path `mcp-server-gateway.utils.ts:60` + `callToolForServer` (`mcp-client.ts:2999-3014`) — lists `unslugifyName(…)` and forwards the name verbatim upstream with no raw-name resolution at all today, so it already fails upstream for *any* name slugification altered; nothing that works there today changes.
- `buildAgentDelegationToolName` (`shared/agents.ts:36`) — slugifies *agent* names, not MCP-server tool names; delegation tools are keyed by `delegateToAgentId` (unique constraint in `database/schemas/tool.ts:82`).
- Archestra built-ins and proxy-sniffed tools — fixed constant names / client-supplied identifiers; no name transformation occurs.

**Verification:** the repo's toolchain is intentionally unavailable in this worktree (installs/type-checks/tests blocked), so I verified by static review plus a standalone port of the exact algorithm (19 assertions: uniqueness, charset validity, keeper selection, order-independence, base-slug reservation, no `__` introduction, and byte-parity of `slugifyNames` with `slugifyName` for all non-suffixed results — all pass). Existing `slugifyName` unit tests pin single-name behavior, which is unchanged.

**Residual risk:** (1) A previously shared row with no resolvable member (all-lossy collision group) is orphan-deleted on the next reinstall and its agent assignments are not carried to the new suffixed rows — that identifier never executed, but assignments need re-creating. (2) If a collision later disappears upstream (the sibling is removed), the suffixed identifier stops resolving until the next reinstall renames the row back to the base slug — a transient, self-healing window. (3) When two names differ only by case and neither is exactly lowercase, today's per-connection winner was list-order-dependent; it is now deterministic (lexicographic), which can differ from what a given cached connection happened to pick. (4) Suffixes add ~9 characters; neither old nor new code enforces the documented 128-character provider cap (pre-existing).
