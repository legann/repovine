## Where tool names become identifiers

`ToolModel.slugifyName` (`platform/backend/src/models/tool.ts:80`) is the single codec that turns `[expr]` into the stored identifier (`tools.name`): it lowercases, converts whitespace to `_`, and strips everything outside `[expr]`. Because it is lossy, distinct raw names (`Search`/`search`, `get.user`/`getuser`, non-ASCII names) collapse onto one slug. The `tools` table's composite unique constraint is NULLS-DISTINCT for regular MCP tools (`database/schemas/tool.ts:83`), so colliding tools became duplicate-name rows (or piled onto one row during re-sync) — addressable only ambiguously.

Five batch write sites feed that codec with a full server listing: `routes/mcp-server.ts:762` and `:924` (install discovery → `bulkCreateToolsIfNotExists`), `services/mcp-reinstall.ts:406` (reinstall → `syncToolsForCatalog`), and `archestra-mcp-server/mcp-servers.ts:1451`/`:1506` (`deploy_mcp_server` tool → `bulkCreateToolsIfNotExists`).

## The fix (3 files)

- **`models/tool.ts`** — new `ToolModel.slugifyNames(…)` batch API plus a private `disambiguateToolSlugs` core: a slug unique within the listing is returned byte-for-byte; within a colliding group, the one tool whose raw name the slug already spells verbatim (at most one can exist) keeps the bare slug, and every other tool gets `[expr]` — deterministic and independent of listing order, so rediscovery, reinstall, and clone reconciliation all re-derive the same name. The suffix never introduces a new `__` (which would shift `parseFullToolName`). Identical raw names fall back to ordinals. `syncToolsForCatalog` now disambiguates internally (it already receives `rawToolName`) and matches existing rows in two passes — exact stored name first, then the pre-existing raw-name fallback over unclaimed rows, each row claimable once — so colliding tools reconcile against their own rows instead of issuing conflicting updates to one row.
- **`routes/mcp-server.ts`**, **`archestra-mcp-server/mcp-servers.ts`** — the four discovery sites now call `slugifyNames` over the listing; the reconciliation `discoveredToolNames` sets automatically pick up the final names.

## Deliberately unchanged, with proof

- `slugifyName`/`unslugifyName` and `parseFullToolName` — frozen stored-identity codec per the module's boundary annotation ("slugifyName is a per-tool-pair transform… making identifiers distinct across a server's tools is a property of the layer that holds them together").
- Wire consumers (`clients/mcp-client.ts` prefix stripping/name resolution, `routes/mcp-server-gateway.utils.ts:60`, `routes/mcp-server-proxy.ts:168`) — frozen per the same annotation; a suffixed slug isn't routed upstream ("the wire is not extended to route it" — colliding tools were already unresolvable upstream).
- `services/mcp-reinstall.ts` — its test replaces `ToolModel` with a mock exposing only `slugifyName` + `syncToolsForCatalog` (`mcp-reinstall.test.ts:24-29`); the fix lives inside `syncToolsForCatalog` so the file and its mock contract stay intact.
- `services/apps/app-mcp-backing.ts:73` — single synthesized launch tool, already uniquified with the app id; no listing to collide.
- `routes/proxy/utils/tools.ts:99` + `bulkCreateProxyToolsIfNotExists` — proxy-sniffed names are stored verbatim from client requests (already identifiers) and deduped in-batch.
- Delegation (`models/tool.ts:2462`, agent-name derived) and built-in Archestra/skill tools (fixed vocabulary guarded by the partial unique index) — not MCP-server-exposed names.
- `cloneToolsAndPoliciesFromCatalog` (`tool.ts:840`) — re-derives from stored (now distinct) names; because the suffix is a pure function of the raw name, clone-derived and discovery-derived names agree without changes there.

## Behavior change & residual risk

Non-colliding tools — every tool that works today — keep byte-identical identifiers and identical matching/addressing (each existing sync test scenario traces to the same outcome). Colliding tools now each get a distinct, stable identifier: distinct rows, own policies/assignments, both visible in gateway listings. Residual risk: a suffixed identifier is platform-addressable but doesn't round-trip to a raw upstream name, so calling it still fails at the upstream server — explicitly out of this task's scope per the codebase's boundary annotations; and upgrades of pre-existing collapsed rows re-key the non-canonical sibling to a new name on first re-sync (its old shared name was never individually addressable). I could not run `pnpm type-check`/tests here (worktree is intentionally not bootstrapped), so the change is verified by static reading only — worth a CI pass before merging.
