## The problem, located

`ToolModel.slugifyName` (`platform/backend/src/models/tool.ts:82`) builds the platform identifier as `[expr]` lowercased, whitespace→`_`, all other disallowed characters *deleted*. That is lossy: `search.issues` vs `searchissues`, `Get User` vs `get_user`, `getUser` vs `GetUser` all collapse to one string. The `tools` table has no raw-name column and the composite unique constraint is NULLS-DISTINCT for MCP tools (`database/schemas/tool.ts`, see its own comment), so colliding discoveries produced same-named rows that couldn't be addressed individually.

## Where names become identifiers, and what changed

Identifiers are minted in five batch discovery paths, all now passed through a new collision-aware step:

| Site | Path |
|---|---|
| `routes/mcp-server.ts:762` | local install, async tool discovery |
| `routes/mcp-server.ts:933` | remote install |
| `services/mcp-reinstall.ts:406` | reinstall / re-sync |
| `archestra-mcp-server/mcp-servers.ts:1451` | `deploy_mcp_server` tool, local |
| `archestra-mcp-server/mcp-servers.ts:1512` | `deploy_mcp_server` tool, remote |

New module **`backend/src/utils/tool-name-disambiguation.ts`**:
- `disambiguateSlugifiedToolNames`: names unique within the batch pass through untouched. In a colliding group, the tool the shared slug *already resolves to at call time* keeps the bare slug (mirrors `resolveActualToolName`'s last-write-wins, case-insensitive match), and every other tool gets `[expr]` — deterministic, stable across re-syncs and list reorderings, still matching the LLM-provider pattern `[expr]`. Residual collisions (e.g. a raw name that itself looks like a suffixed slug) lengthen the hash 8→16→32→64.
- `disambiguatedToolNameAliases`: the call-time inverse.

Routing and persistence, made suffix-aware:
- `clients/mcp-client.ts` `resolveActualToolName` registers each upstream tool's suffixed aliases before the raw lowercase names, so a genuine raw name always wins a contested key — existing lookups resolve exactly as before, and suffixed slugs now resolve to the exact raw upstream name.
- `models/tool.ts` `syncToolsForCatalog` gained a fallback row-match on the new name's own raw part, which only fires where the current lookup is a guaranteed miss (mangled/suffixed names); it stops those rows churning (delete+recreate, policy reset) on every reinstall.

It couldn't live on `ToolModel` because `mcp-reinstall.test.ts` mocks `ToolModel` down to `[expr]`; a standalone util keeps that test intact.

## Deliberately unchanged, with sources

- **`ToolModel.slugifyName` itself** — exact per-name outputs are pinned by `[expr]`; changing them would rename tools that already work.
- **App launch tool naming** (`services/apps/app-mcp-backing.ts:73`) — one tool per backing catalog, already app-id-suffixed per its comment ("so two apps that legitimately share a name … don't produce the same `[expr]`"); no batch, no collision.
- **Clone path** (`models/tool.ts:842`) — derives names from source rows that are unique per catalog (comment at `[expr]`); hash suffixes survive re-slugification verbatim and reconciliation (`[expr]`) still matches because the hash depends only on the raw name — verified in my harness.
- **Delegation tools** (`[expr]`) — identifiers derive from *agent* names, not MCP-server tool names; outside "when an MCP server exposes a tool".
- **Built-in Archestra tools** — code-defined constant names with their own unique index (`database/schemas/tool.ts`, `ARCHESTRA_TOOL_NAME_UNIQUE_INDEX`); no user-controlled input.
- **Apps run path** (`[expr]`, `[expr]`, `mcp-client.ts:2999` `callToolForServer`) — its contract is raw-name passthrough and it is already lossy for *any* mangled name, collision or not; colliding tools now at least list as distinct entries there, and I didn't extend upstream-call resolution into that pre-existing limitation.
- **`unslugifyName`/`parseFullToolName`** (`[expr]`) — suffixed fragments flow through as opaque strings; behavior pinned by `[expr]`.

This bench worktree blocks installs/type-check/tests, so verification was static reading plus an executable harness (system node, scratchpad only — no test files added) containing a byte-identical transliteration of the new module plus the frozen `slugifyName` and the patched resolution logic. Residual risks: `pnpm lint`/`type-check`/tests couldn't be executed here (I'd run backend checks once bootstrapped); a suffix adds ~9 chars, so a raw name already near the 128-char provider limit could exceed it (slugification never truncated before either); byte-identical duplicate listings from a non-compliant server still share one suffixed name — indistinguishable upstream too; and pre-existing shared rows for tools that never worked (no exact-match owner) are replaced, not renamed, on the next re-sync, so any policies configured on those dead rows are recreated as defaults.
