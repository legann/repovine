# Summary

**Changed behavior.** When an MCP server's discovered tool list is persisted, each tool's name is slugified into the stored identifier `tools.name` via `ToolModel.slugifyName(…)` — a lossy transform (lowercase, whitespace→`_`, strip other chars), so two different tool names (e.g. `foo.bar` and `foo:bar`, or `Foo` and `foo`) could yield one identifier and become individually unaddressable (one row shared, or duplicate rows under one name — the table's composite unique constraint is NULLS-DISTINCT and never fires for catalog tools). Now every tool in a discovery batch gets a distinct identifier: a tool whose slug is unique keeps **exactly** the slug it gets today; within a colliding group the first (batch order) keeps the plain slug and later ones get `-2`, `-3`, … suffixes that never take over a name another tool carries outright (a literal `foo-2` keeps `foo-2`).

**Where names become identifiers, and what I changed:**

| Path | Site | Change |
|---|---|---|
| Install (local async + remote sync) | `[expr]` | batch-dedup via new `ToolModel.slugifyNames` |
| Deploy tool (local + remote discovery) | `[expr]` | same |
| Reinstall/resync | `ToolModel.syncToolsForCatalog` (`[expr]`) | dedups in-model via private `assignDistinctNames`; call site `services/mcp-reinstall.ts` deliberately untouched — its test mocks `ToolModel` with only `slugifyName`/`syncToolsForCatalog` (`mcp-reinstall.test.ts:24-29`) and asserts exact call args |
| — | `platform/backend/src/models/tool.ts` | new `slugifyNames` (public, next to the codec) + `assignDistinctNames` (private); `syncToolsForCatalog` additionally claims each existing row for at most one incoming tool, with an exact-name fallback, so a colliding pair can't both match-and-rename one row on reinstall (only reachable when incoming raw names collide; singleton matching is byte-identical) |

Both layers use one algorithm, so install and reinstall agree on names. Clone reconciliation keeps matching because the routes build `discoveredToolNames` from the now-deduped batch, and suffixes survive the `[expr]` round-trip (set-based matching, `tool.ts:917-925`).

**Deliberately unchanged, with proof:**
- `slugifyName`/`unslugifyName` codec and `parseFullToolName` — frozen stored-identity boundary; per-tool transform can't see siblings (repovine boundary annotation on `mod:@backend/src/models/tool`; a lone degenerate `server__` tool keeps its working identifier only if the codec stays pairwise).
- Wire consumers — `clients/mcp-client.ts` (`stripServerPrefix`:2118, `resolveActualToolName`:2133), `routes/mcp-server-gateway.utils.ts:60`, `routes/mcp-server-proxy.ts:168` — frozen serving/matching contract per the same annotation ("the wire is not extended to route" disambiguated names).
- Proxy-sniffed tools (`routes/proxy/utils/tools.ts:96`) — client-sent names stored verbatim, no transformation to collide.
- App launch tool (`services/apps/app-mcp-backing.ts:72-76`) — single tool, app-id-suffixed, unique by construction.
- Clone provisioning (`tool.ts:837-858`) — inputs are already-unique stored names; a residual `__`-in-raw-name edge fails loudly on insert, never yields shared identifiers.
- Delegation tools (`tool.ts:2462`) and Archestra built-ins (`seedArchestraTools`) — not MCP-server-exposed; addressed by `delegateToAgentId` / fixed constants.
- `mcp-server.ts:1176` — discovery for credential validation only, result discarded.

**Residual risk.** A suffixed identifier doesn't round-trip to a raw upstream name, so calling such a tool upstream still fails — explicitly out of scope (those tools were unaddressable before; the wire contract is frozen). Which colliding tool gets the plain slug follows the server's list order, so a reorder can swap metadata between the pair's rows on resync; punctuation-collided pairs recycle row ids on reinstall (same pre-existing pattern as punctuation-named singletons).
