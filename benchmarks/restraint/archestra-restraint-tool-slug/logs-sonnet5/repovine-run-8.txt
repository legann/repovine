## Summary

**Where names become identifiers:** `ToolModel.slugifyName(…)` in `platform/backend/src/models/tool.ts:80` — it lowercases, turns whitespace into `_`, and strips any character outside `[expr]`. It's a pure per-pair transform: it only ever sees one tool name at a time, so two genuinely different raw names that differ only in stripped/normalized characters (`"Get.User"` vs `"GetUser"`, `"Get User"` vs `"Get_User"`, or names that fully strip to `""`) collapse onto the same string. That string is `tools.name` — the row the platform, gateway, and proxy all address the tool by — so colliding tools become indistinguishable (DB unique constraints don't catch it either, since the composite unique index is NULL-distinct for ordinary catalog tools).

**Fix:** added `ToolModel.slugifyToolNames(…)` (`platform/backend/src/models/tool.ts:105`), which slugifies a whole server's tool list together. A name that comes out unique is returned byte-for-byte as `slugifyName` would produce it — untouched. Only names that collide with another tool in the same batch get a numeric suffix, on every occurrence after the first. Wired it into the four places that build a tool-creation batch for one server, replacing their per-tool `ToolModel.slugifyName(…)` call:

- `platform/backend/src/routes/mcp-server.ts` (local-server async discovery, and remote-server sync install)
- `platform/backend/src/archestra-mcp-server/mcp-servers.ts` (`discoverLocalMcpServerTools`, `discoverRemoteMcpServerTools`)
- `platform/backend/src/services/mcp-reinstall.ts` (`syncToolsForServer`)

**Left unchanged, with evidence:**
- `slugifyName`/`unslugifyName` themselves — the repovine annotation on this module flags them as the frozen stored-identity codec; adding disambiguation there would couple new policy into every consumer that depends on that exact codec.
- Wire consumers `mcp-client.ts`, `mcp-server-gateway.utils.ts`, `mcp-server-proxy.ts:168` (`rejectDisallowedToolCall`'s `[expr]`) — explicitly called out as frozen alongside the codec; they resolve stored names against the live upstream list, an external contract this task doesn't extend.
- `bulkCreateToolsIfNotExists`, `syncToolsForCatalog`, `cloneToolsAndPoliciesFromCatalog`, `reconcileClonedCatalogTools` in `tool.ts` — all receive `name` already disambiguated from the call site, so they need no changes; `cloneToolsAndPoliciesFromCatalog`'s own comment ("source's tool names are unique within its catalog") documents exactly the invariant this fix now upholds.
- `bulkCreateProxyToolsIfNotExists` / `routes/proxy/utils/tools.ts` — no `slugifyName` call anywhere in that file (verified by grep); proxy-sniffed names come verbatim from LLM tool-call sniffing and are already deduped by an exact-string `seenToolNames` Set.
- `services/apps/app-mcp-backing.ts:72` — creates exactly one tool per call, so no batch collision is possible there; it already has its own documented anti-collision suffix (app id) for a different collision case (two apps sharing a name).
- `ToolModel.findOrCreateDelegationTool` / agent-rename tool naming — uses the unrelated `slugify()` helper on agent names, not an MCP server's tool name; outside "when an MCP server exposes a tool."

**Residual risk:** disambiguation is order-dependent (first tool in the discovered list keeps the bare slug, later collisions get `_2`, `_3`, …) with no persisted raw-name mapping, so if an upstream server's `tools/list` order ever changes between syncs, a previously-suffixed tool could swap identity with the bare one. This mirrors the order-sensitivity already inherent in the existing raw-name-matching sync logic and wasn't something a stateless per-pair-preserving fix could close without much larger surgery. Also, `slugifyName` has never actually enforced its documented 128-char cap — appending a suffix can't newly break that, but doesn't fix the pre-existing gap either.
