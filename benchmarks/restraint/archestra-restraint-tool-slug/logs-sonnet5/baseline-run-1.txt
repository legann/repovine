The `syncToolsForCatalog` fix was necessary, not optional: without it, the first reinstall after two colliding tools got distinct rows would re-derive both new tools' lookup key from their true (colliding) raw names, match both to the *same* pre-existing row, and delete the other as "orphaned" — silently undoing the fix on every pod restart.

## Residual risk

The primary agent/LLM dispatch path (`ToolModel.getMcpToolsAssignedToAgent`, exact `IN` match on `toolCall.name`) now resolves each disambiguated tool to its own row, so both are independently selectable, policy-scoped, and assignable — the core bug. However, the final "what literal name do we send to the upstream MCP server" hop (`resolveActualToolName`) still re-derives that name via a live case-insensitive lookup; for a tool whose collision was case/whitespace-only, its suffixed identifier (`..._2`) won't match anything in that lookup, so the wire-level call could still fail post-disambiguation rather than silently invoking the wrong tool. Fixing that would mean rewriting sensitive OAuth/connection-caching dispatch code across three more files — a materially larger change than tool-name→identifier minting, so I left it as a known gap rather than attempting it.
