## Fix

Added `dedupeSlugs(…)` to `platform/shared/utils.ts`, next to the existing `slugify`/`parseFullToolName` helpers. It reserves every input slug up front, then walks the list: a slug's first occurrence is returned untouched; any later duplicate gets `-2`, `-3`, … appended, skipping any suffix that would collide with another entry's own natural slug (so a collision can never steal an unrelated tool's identifier, regardless of list order).

Wired it into every place that turns one MCP server's full tool list into stored identifiers in a batch:

| File | Call site |
|---|---|
| `platform/backend/src/routes/mcp-server.ts` | local-server install, remote-server install |

## Residual risk

- **No DB-level backstop for external catalogs.** The unique index gap above (`tool.ts:89-92`) means this patch stops *new* collisions but doesn't retroactively clean up any duplicate-named rows already sitting in a database from before the fix (mirrors the exact scenario the `0285_dedup_archestra_builtin_tools_by_short_name` migration fixed for the built-in catalog, but for user-installed servers). A cleanup pass would need its own migration.
- **Dispatch for punctuation/whitespace collisions.** `resolveActualToolName` resolves the real remote tool name via a live, case-insensitive-only lookup. For two tools that collide by more than casing, the disambiguated (`-2`) identifier is now individually addressable at the platform layer (listing, policies, assignment), but actually invoking it may still hit this pre-existing, separate resolution gap. Closing that fully would need the true raw name persisted in the schema — a bigger change than tool-name handling.
- Disambiguation order depends on the order the MCP server reports its tools, assumed stable across calls (same assumption the existing reinstall/raw-name-matching code already relies on).
