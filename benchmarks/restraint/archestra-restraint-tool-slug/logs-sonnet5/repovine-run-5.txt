## The fix

New file **`platform/backend/src/utils/slugify-tool-names.ts`** exports `slugifyToolNames(…)`. It calls the unmodified `ToolModel.slugifyName` per name and only appends a numeric suffix (`-2`, `-3`, …) to a name that collides with an earlier one *in the same discovery batch* — mirroring the existing `buildSkillCommands` convention in `platform/frontend/src/app/chat/skill-commands.ts`, which solves the identical problem for skill slash-commands. A name with no collision is returned byte-for-byte identical to today's `slugifyName` output.

Updated the five places that turn one MCP server's discovered tool list into DB rows, replacing their inline `tools.map(…)` with a batch call to the new helper:

| File | Call site |
|---|---|
| `routes/mcp-server.ts:762` | local/K8s async install |
| `routes/mcp-server.ts:928` | remote sync install |
| `services/mcp-reinstall.ts:406` | reinstall/resync |
| `archestra-mcp-server/mcp-servers.ts:1451` | `discoverLocalMcpServerTools` (Archestra-tool-driven install) |
| `archestra-mcp-server/mcp-servers.ts:1507` | `discoverRemoteMcpServerTools` |

`models/tool.ts` itself is untouched — repovine flagged it as a frozen identity-codec boundary shared by persisted rows, clone reconciliation, and prefix-stripping. The uniqueness policy is a write-path/batch concern the codec can't provide on its own (it slugifies one name at a time), so it lives next to the callers instead.

One deliberate detail: the helper imports `ToolModel` via the barrel (`@/models`), not the direct `@/models/tool` path. `services/mcp-reinstall.test.ts:12-31` mocks `@/models` and stubs `slugifyName` with a simplified fake; importing the direct path would have silently bypassed that mock with the real implementation and broken two existing exact-name assertions (`mcp-reinstall.test.ts:1384`, `:1424`). Importing the barrel keeps the helper going through the same mock the test already relies on.

## Left unchanged, and why

- **`ToolModel.cloneToolsAndPoliciesFromCatalog`** (`models/tool.ts:840-843`) — re-slugifies one already-unique source name at a time when cloning a catalog. `slugifyName`'s stripping is a pure per-character filter over the whole string, so a tool-name's contribution to the slug never depends on the prefix — re-slugifying a unique name under a new prefix can't create a fresh collision. The method's own comment (`tool.ts:833-836`) already asserts this idempotence.
- **`services/apps/app-mcp-backing.ts:72-76`** — slugifies one fixed tool name (`APP_LAUNCH_TOOL_NAME`) per app; no sibling list to collide against.
- **`clients/mcp-client.ts:2118-2157`** (`stripServerPrefix` / `resolveActualToolName`) — the runtime invocation path, explicitly frozen by the same repovine boundary annotation. Its own docstring (`:2129-2132`) says it resolves only *casing* differences between the stored slug and the live server's raw name, not punctuation/whitespace that `slugifyName` strips — so exact upstream-call round-tripping for names with such characters is a pre-existing gap, unrelated to this fix.
- **`syncToolsForCatalog`'s raw-name reconciliation map** (`[expr]`) — its own comments already document and accept duplicate-raw-name handling as a known edge case "from previous buggy reinstalls." It's a rename-matching mechanism, not identifier generation, and now always receives already-unique names from the fixed call site.
- **Suffix-match lookups and classification** — `getMcpToolsAssignedToAgentBySuffix`/`...AppBySuffix` (`tool.ts:1583-1592`, `:1787-1793`) and `parseArchestraBuiltInName` (`tool.ts:3032-3045`) are read-only, not naming sites.
- **Agent-delegation tool names** (`[expr]`, `[expr]`, `delegation.ts`) and **skill slash-commands** (`skill-commands.ts`) — a different feature ("agent" or "skill" names, not "an MCP server exposes a tool"); skill-commands already has its own collision handling.

## Residual risk

- A disambiguated (suffixed) tool becomes listed/assignable, but whether the live upstream call actually resolves depends on the pre-existing `resolveActualToolName` case-only matching — same limitation that already exists today for any raw name containing more than a casing difference.
- In the reinstall/resync path, `syncToolsForCatalog` recomputes and overwrites `name` every sync; if two colliding tools' relative order in the server's `tools/list` response ever changes between reinstalls, which one keeps the bare slug could flip. This mirrors that function's existing by-design rename-on-mismatch behavior for catalog renames.
- Type-check/tests could not be run in this sandboxed environment (no `node_modules`); verification was done by static reading of call sites, types, and existing test mocks.
