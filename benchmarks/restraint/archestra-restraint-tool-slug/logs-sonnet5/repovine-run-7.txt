## Files changed

- **`models/tool.ts`**: added `ToolModel.slugifyToolNames(…)` — a new batch method next to `slugifyName`. It computes the naive slug per name, and only for names that collide with a sibling, picks one deterministic "primary" (the raw name already byte-identical to the shared slug, i.e. needed no normalization; otherwise lexicographically first) to keep the bare slug, and appends a `[expr]` suffix to the rest. Non-colliding names are returned byte-identical to today's `slugifyName` output. Also hardened `syncToolsForCatalog`'s existing-row matching to check an exact-name map before its fuzzy lowercased-raw-name map, so two newly-distinct names don't get merged back onto one row on a second reinstall/sync.
- **`archestra-mcp-server/mcp-servers.ts`**, **`routes/mcp-server.ts`**, **`services/mcp-reinstall.ts`**: the 5 real write-path call sites (local async discovery, remote discovery, remote sync-install, remote async-install, reinstall sync) now call `slugifyToolNames` over the whole discovered batch instead of `slugifyName` per tool.

## Deliberately left unchanged (with proof)

- **`slugifyName` / `unslugifyName` (the codec itself)** — untouched signature and behavior. Proven by the existing pinned unit tests (`tool.test.ts:44-153`) that assert exact 2-arg output, and by this repo's own repovine boundary annotation on the module, which calls these two out as the frozen "stored-identity codec" and says collision-handling belongs to "the layer that holds tools together," not this transform.
- **Wire/invocation path** (`clients/mcp-client.ts` `stripServerPrefix`/`resolveActualToolName`, `mcp-server-gateway.utils.ts`, `mcp-server-proxy.ts`) — untouched. `mcp-client.ts:2134-2156` resolves a stored name to the live upstream tool via a case-insensitive map built from `client.listTools()`, which by construction can only resolve one name per collision bucket. The repovine annotation explicitly states these are "frozen alongside the codec" and that a disambiguated slug not round-tripping to a raw upstream name "is not a defect this task repairs."
- **`cloneToolsAndPoliciesFromCatalog`** (`[expr]`) — untouched. Its own comment (`tool.ts:833-836`) states source tool names are already unique within their catalog and share one prefix, so re-slugifying under a new catalog name preserves uniqueness by construction.
- **`app-mcp-backing.ts:73`** — untouched. One synthetic launch tool per app, and the "server name" passed in is already suffixed with the app's own id (`[expr]`, per the comment at line 68-71), so it's a batch of size 1 — never collides.
- **Proxy-sniffed tools** (`routes/proxy/utils/tools.ts` → `bulkCreateProxyToolsIfNotExists`) — untouched. `toolName` is taken verbatim from an already-executed tool call, not generated via `slugifyName` at all.
- **Delegation tool names** (`[expr]`) — untouched. Scoped by `delegateToAgentId` uniqueness, not `name` (`tool.ts:2441-2498`), and not "an MCP server exposing a tool" per the task's own framing.

## Residual risk

If a collision group grows later (a third, alphabetically-earlier raw name joins two already-colliding tools, neither of which is byte-identical to the shared slug), the tie-break for "primary" can shift, renaming a previously-suffixed tool back toward the bare slug. This is a narrow edge case (requires an ongoing multi-way collision that then changes shape), and `syncToolsForCatalog` already treats such renames as a first-class, ID/policy-preserving operation (same mechanism it uses for catalog renames), so it degrades to a rename, not data loss.
