## Changes

- **`platform/backend/src/models/tool.ts`** — added `ToolModel.slugifyToolNames(…)`. It computes each name's base slug via the untouched `slugifyName`, groups by result, and for any group with more than one member keeps the lexicographically-first raw name's slug bare and appends the next free `-2`, `-3`, ... suffix to the rest (skipping any suffix already taken by an unrelated tool). Non-colliding names are returned unchanged. Grouping/tie-breaking is by raw name, not array position, so re-discovering the same server is idempotent regardless of `tools/list` ordering.
- **`platform/backend/src/routes/mcp-server.ts`**, **`archestra-mcp-server/mcp-servers.ts`** (2 sites each), **`services/mcp-reinstall.ts`** — the five places that build a `toolsToCreate`/`toolsToSync` array from one server's discovered tool list now call `slugifyToolNames` once over the whole batch instead of `slugifyName` per tool, then zip results back by index.

I verified the algorithm by extracting it into a standalone script and running it against the existing pinned `slugifyName` unit-test cases (all still match byte-for-byte) plus collision scenarios (case-collision, three-way collision, order-independence, and suffix-clash avoidance) — all passed. `tsc`/`pnpm test` aren't runnable in this worktree (no `node_modules`), so this static/extracted-script check is the verification available here.

## Left unchanged, with reasons

- **`slugifyName`/`unslugifyName` themselves** (`tool.ts:80-93`) — a repovine boundary annotation on this file calls these out as the "stored-identity codec" that persisted rows, clone reconciliation, and prefix-stripping all depend on; I only added a new method alongside them.
- **`mcp-client.ts` (`resolveActualToolName`/`stripServerPrefix`)** — same boundary advisory names these as frozen wire consumers. They already only special-case *case* differences when mapping a stored name back to the live server's raw name (comment at `mcp-client.ts:2130-2133`); they don't undo whitespace/punctuation stripping either, so a disambiguated tool with a stripped-character collision could still fail at actual invocation. That's a pre-existing gap in this fuzzy matcher, not something this fix worsens for any previously-working tool — flagging as residual risk below rather than touching frozen consumers.
- **`services/apps/app-mcp-backing.ts:73`** — single-tool-per-catalog insert (one launch tool per app); no sibling tool list to collide with.
- **`archestra-mcp-server`'s own built-in tool names** and **agent delegation tool names** (`[expr]`) — not "an MCP server[[']s] tool name," per the task framing; built-ins are a hardcoded, type-checked list, and delegation names use a separate `slugify()` helper unrelated to `ToolModel.slugifyName`.
- **`tool.ts`'s `cloneToolsAndPoliciesFromCatalog`** (~line 897) — relies on "source tool names are unique within its catalog," an invariant this fix now upholds upstream; no change needed there.

## Residual risk

- Pre-existing DB rows created before this fix (already-collided/duplicated tool names) aren't retroactively repaired — this is a forward-looking code fix, not a data migration; they'll only get distinct names on their next discovery/reinstall pass.
- For a newly-disambiguated tool (the `-2`, `-3` one), actual invocation success depends on `mcp-client.ts`'s existing case-insensitive-only raw-name resolution being able to find the live tool; if the two raw names differ by more than case, that resolver's pre-existing fallback (`[expr]`) may still mis-resolve — the tool is now individually listed/addressable/policy-configurable, but end-to-end call correctness for that edge case inherits a limitation that already existed for non-colliding tools with punctuation in their names.
