## Fix

Added `ToolModel.resolveToolNamePrefix(…)`: returns `catalogName` unchanged unless another catalog already has tools under that exact prefix, in which case it appends an 8-char id fragment (mirroring the existing precedent in `services/apps/app-mcp-backing.ts`'s `createAppBacking`). Only the *prefix* is ever changed — never the part after the last separator — so call-time dispatch (which recovers the real upstream tool name via `lastIndexOf` on the separator) keeps working unmodified.

**Files touched:**
- `platform/backend/src/models/tool.ts` — added `resolveToolNamePrefix`; wired it into `cloneToolsAndPoliciesFromCatalog`; added an internal, no-op-by-default preprocessing step in `syncToolsForCatalog`.
- `platform/backend/src/routes/mcp-server.ts` — both install paths (local + remote) resolve the prefix before slugifying.
- `platform/backend/src/archestra-mcp-server/mcp-servers.ts` — both `deploy_mcp_server` discovery paths (local + remote), same change.

`services/mcp-reinstall.ts` needed the identical fix but its test file (`mcp-reinstall.test.ts`) mocks `ToolModel` wholesale with only `slugifyName`/`syncToolsForCatalog`; calling a new method from that file's production code would throw under that mock. So the fix for that path lives inside `syncToolsForCatalog` itself instead — invisible to that mock (which replaces the whole function) but active for the real caller.

## Deliberately unchanged, with proof

- **`slugifyName`/`unslugifyName` themselves** — untouched; a repovine boundary annotation flags them as the stored-identity codec that `mcp-client.ts`, `mcp-server-proxy.ts`, and `mcp-server-gateway.utils.ts` all depend on.
- **Call-time dispatch** (`mcp-client.ts:2118-2157` `stripServerPrefix`/`resolveActualToolName`, `mcp-server-proxy.ts:163-170`, `mcp-server-gateway.utils.ts:49-68`) — all resolve the real upstream tool name via `parseFullToolName`'s last-separator split, which doesn't care what the prefix contains. Verified by tracing that a disambiguated prefix still round-trips correctly with zero changes there.
- **Within-server raw-name collisions** (two tools on the *same* server whose names differ only by case/whitespace/symbols and collapse to the same slug) — left unfixed. `resolveActualToolName`'s upstream nameMap is keyed by `tool.name.toLowerCase()` from the *real* server's tools/list; any synthetic disambiguator on our side would never match it. Fixing this would require storing the true raw name out-of-band and having those consumers prefer it — exactly what the boundary annotation says not to do.
- **`app-mcp-backing.ts`'s `createAppBacking`** — untouched; it creates one fixed-name tool per app catalog and already suffixes its prefix with the app id, so it was never exposed to this bug.
- **`bulkCreateToolsIfNotExists`** internals — untouched; once callers hand it collision-free names, its existing by-name matching is already correct.

## Residual risk

- Two catalogs with the same name discovered for the very first time *concurrently* could both see "no collision yet" and both claim the plain prefix — a narrow TOCTOU window; no DB constraint closes it.
- The new collision check (`[expr]`) is a function-based predicate, so it can't use a plain index on `name` — a sequential scan per discovery/sync/clone call, same cost profile as the existing `[expr]` check already in this file.
- Not scoped to `organizationId`, so it can disambiguate across orgs that could never actually share an agent — safe (still correct, still addressable) but slightly more conservative than strictly necessary.
