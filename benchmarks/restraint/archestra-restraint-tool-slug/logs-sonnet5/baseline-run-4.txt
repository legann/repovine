## Summary

**Root cause**: `ToolModel.slugifyName(…)` (`platform/backend/src/models/tool.ts:80`) is the single place an MCP server's tool name becomes Archestra's internal identifier — it lowercases, folds whitespace to `_`, and **drops** every other disallowed character. It's a pure per-tool function with no visibility into sibling tools, so two distinct raw names that differ only in case or in characters that get stripped (`"GetUser"` / `"get.user"` / `"GET_USER"` → all `"getuser"`) collapse to one string. Whichever DB row shares that name last in various downstream `Map`-based lookups wins; the other becomes silently uncallable.

## What changed

| File | Change |
|---|---|
| `platform/shared/utils.ts` | Added `disambiguateSlugs(…)` — given a batch of already-computed slugs, gives every colliding one a stable `_2`, `_3`, ... suffix (ordered by original name, not array position, so it's order-independent across repeated discovery runs); non-colliding slugs pass through untouched. |
| `platform/backend/src/models/tool.ts` | Added `ToolModel.slugifyToolNames(…)` (per-item `slugifyName` + `disambiguateSlugs`) and `ToolModel.slugifyToolNamePart(…)` (the same transform, no server prefix — used to reverse it later). `slugifyName` and `unslugifyName` themselves are untouched. Also hardened `syncToolsForCatalog`'s tool-matching to try an exact full-name match before its raw-name heuristic (see "risk" below). |
| `platform/backend/src/routes/mcp-server.ts` (×2), `platform/backend/src/archestra-mcp-server/mcp-servers.ts` (×2) | The four tool-discovery/install call sites now batch-slugify via `ToolModel.slugifyToolNames` instead of mapping `slugifyName` per tool. |
| `platform/backend/src/services/mcp-reinstall.ts` | Same fix, but inlined (`slugifyName` + `disambiguateSlugs` directly) instead of calling `ToolModel.slugifyToolNames` — its test fully replaces `ToolModel` with a 2-method stub, so a new `ToolModel` method would throw there. |
| `platform/backend/src/clients/mcp-client.ts` | `resolveActualToolName` (used when actually invoking a tool) now builds its live-server name map with the same disambiguation, so a suffixed identifier resolves to the correct underlying live tool instead of 404ing or hitting whichever tool a `[expr]`-collision happened to keep. |

Tools with a unique slug get byte-identical output to today (`disambiguateSlugs` is a no-op for single-member groups) — verified against every existing fixture in `tool.test.ts`, `mcp-server.test.ts`, `mcp-servers.test.ts`, `mcp-reinstall.test.ts`, and `mcp-client.test.ts`'s casing-resolution suite by tracing each through the new code by hand (this sandbox has no `node_modules`, so I couldn't run them). ## Residual risk

While tracing the resync path I found `syncToolsForCatalog`'s rename-detection (matches by "part after the last `__`", pre-existing) can't recover a suffixed tool's true raw name, so on a later resync it would treat a disambiguated tool as new, delete the old row, and reset its policies to defaults — a real, if narrow, data-loss risk that would have made the fix fragile for exactly the tools it targets. I closed it with a small additive fast-path (try an exact full-name match first, fall back to the existing heuristic otherwise), verified safe against all 8 existing `syncToolsForCatalog` tests by hand-tracing each.

The one edge case still open: if a catalog is renamed *and* one of its tools needed a disambiguation suffix *in the same resync*, the exact-name fast path misses (name changed) and falls through to the pre-existing raw-name heuristic, which is no better or worse than it is today for any tool whose raw name contains stripped characters. Fixing that fully would need persisting the true raw name in the schema, which is beyond this task's scope.
