## Changes

- **`platform/shared/utils.ts`** — new `disambiguateSlugs(…)`: a raw name that's the first (in array order) to produce a given slug keeps it verbatim; a later, *distinct* raw name sharing that slug gets a deterministic `-2`, `-3`, ... suffix (skipping any suffix already legitimately used elsewhere in the batch). Exact repeats of the same raw name aren't a collision and keep the same slug.
- **`platform/backend/src/models/tool.ts`** — new `ToolModel.slugifyNames(…)`, computing base slugs via the untouched `slugifyName` and running them through `disambiguateSlugs`. `slugifyName`/`unslugifyName` themselves are byte-for-byte unchanged (verified via `git diff` — pure additions, no `-` lines in that region).
- **`platform/backend/src/routes/mcp-server.ts`** (2 sites) and **`platform/backend/src/archestra-mcp-server/mcp-servers.ts`** (2 sites) — swapped the per-tool `[expr]` for a `slugifyNames` batch call, indexing back into the original array. These files' tests use the real `ToolModel` against a PGlite DB, so this was a direct swap.
- **`platform/backend/src/services/mcp-reinstall.ts`** — same fix, but *not* via `ToolModel.slugifyNames`: `mcp-reinstall.test.ts` replaces `ToolModel` wholesale with a hand-rolled mock exposing only `slugifyName`/`syncToolsForCatalog`. Calling a new `ToolModel` method there would throw `undefined is not a function` in that suite. Instead it calls the (mocked) `ToolModel.slugifyName` per name and imports `disambiguateSlugs` directly from `@archestra/shared`, which the test doesn't mock — same fix, without depending on anything the test's `@/models` stub doesn't provide.

Since every non-colliding raw name is provably returned unchanged by `disambiguateSlugs` (first-occurrence-wins, verified by tracing the logic and cross-checked against `tool.test.ts`'s pinned `slugifyName` assertions and `mcp-reinstall.test.ts`'s `toHaveBeenCalledWith(…)` fixtures), no currently-working identifier changes.

## Left unchanged, deliberately

- **`slugifyName`/`unslugifyName` codec** (`tool.ts:80-93`) — untouched; every consumer (clone reconciliation, prefix stripping, `parseFullToolName`) depends on the exact same codec. Confirmed both by my own dependency trace and by repovine's boundary annotation on this module, which independently flagged it as a frozen surface.
- **`resolveActualToolName`/`stripServerPrefix`** (`clients/mcp-client.ts:2118-2157`) — invocation-time dispatch re-fetches the remote server's live `tools/list` and matches case-insensitively at call time; it's independent of the persisted slug. Repovine's boundary hint explicitly calls out these as frozen wire consumers. It also already has a pre-existing, unrelated gap: a raw name like `"Get.User"` (punctuation stripped by `slugifyName` but preserved in the live listing) already fails this exact-match-after-lowercase lookup today, with zero collisions involved — proving invocation fidelity for slug-altered names was never guaranteed, so leaving it alone doesn't regress anything.
- **`app-mcp-backing.ts:72-76`** — creates exactly one tool (`APP_LAUNCH_TOOL_NAME`) per app catalog, already disambiguated by an app-id suffix in the prefix (see the comment there); there's no sibling in that batch to collide with.
- **`ToolModel.cloneToolsAndPoliciesFromCatalog`** (`tool.ts`, clone path) — reslugifies each source tool's already-unique suffix under a new prefix. Since all tools in one catalog share an identical prefix, full-name uniqueness there is equivalent to suffix uniqueness, so an already-deduped source catalog stays deduped after cloning; no changes needed.
- **`seedArchestraTools`/`getArchestraMcpTools`** — built-in Archestra tools use a fixed, compile-time `ArchestraToolShortName` union (checked exhaustively against `TOOL_PERMISSIONS`), not names from an external "MCP server exposes a tool" event — out of scope by construction.
- **`syncToolsForCatalog`'s raw-name-from-slug reconstruction** (`tool.ts`, matching existing rows by stripping the last `__`) — a pre-existing heuristic that already mismatches for any raw name whose characters get altered by `slugifyName` (proven independent of collisions). A disambiguated tool may occasionally miss a description/parameter update on resync via this path; it degrades to "skip," never duplication or data loss — strictly better than the status quo's silent loss of one tool entirely.

## Residual risk

Tie-breaking within a colliding group uses first-occurrence-in-array-order, which assumes the remote server returns a stable/append-only tool list — true in practice, not a protocol guarantee. If a server ever reorders its list, which of two colliding tools keeps the bare identifier could theoretically flip. Also flagged: while exploring I hit an unrelated tooling glitch (a stray NUL byte got embedded during one `Edit` call, which silently broke `ugrep`'s text detection and masked subsequent edits) — caught and fixed via direct byte inspection; all touched files are now confirmed NUL-free.
