## Fix

Added `dedupeBySuffix` to `platform/shared/utils.ts` — a pure function that walks a list of strings and appends `_2`, `_3`, … to any repeat of an already-seen value, leaving the first occurrence and all non-repeated values untouched. This mirrors the exact pattern already established in this codebase for the identical class of problem (`platform/frontend/src/app/chat/skill-commands.ts`'s `buildSkillCommands`, which disambiguates colliding skill-slash-commands the same way).

Wired it into the 5 places that turn a whole MCP server's tool list into slugified names for persistence, applying it to the batch of `slugifyName(…)` outputs before they're written:
- `platform/backend/src/routes/mcp-server.ts` (local-server async discovery, remote-server sync discovery)
- `platform/backend/src/archestra-mcp-server/mcp-servers.ts` (the `deploy_mcp_server` agent tool's local/remote discovery — same feature, second entry point)
- `platform/backend/src/services/mcp-reinstall.ts` (reinstall/resync)

`ToolModel.slugifyName` itself is untouched, so any tool name that doesn't collide with a sibling produces byte-identical output to today — satisfying "keep the exact identifier it has today." I initially added a `ToolModel.slugifyNames` batch method instead, but `services/mcp-reinstall.test.ts` mocks `ToolModel` with only `[expr]` (not spread from the original), so any new `ToolModel` method would be `undefined` there and break every test in that file. Moving the dedup into a dependency-free shared utility sidesteps that mock entirely while leaving `ToolModel.slugifyName` called exactly as before.

## Left unchanged, with evidence

- **`ToolModel.unslugifyName`/`parseFullToolName`** — split on the *last* `__`; a `_2` suffix doesn't introduce a new `__`, so parsing is unaffected.
- **`cloneToolsAndPoliciesFromCatalog`** (`tool.ts:836`) — its own comment asserts "the source's tool names are unique within its catalog." That's exactly the invariant this patch restores at discovery time; the clone path is a consumer of already-turned identifiers, not a place identifiers are minted.
- **`mcp-client.ts:2120`** (`stripServerPrefix`) — calls `slugifyName(…)` once per server connection to compute a fixed prefix string to strip, not per-tool; no batch, no collision surface.
- **`app-mcp-backing.ts:73`** — one tool per app, prefixed with an 8-char slice of the app's UUID; not a batch of raw MCP tool names.
- **Built-in Archestra tools** (`seedArchestraTools`) — names come from a fixed, developer-authored `ARCHESTRA_TOOL_SHORT_NAMES` union, not arbitrary external strings, so this class of collision can't occur there.

## Residual risk

For the reinstall/resync path, `syncToolsForCatalog` matches existing rows by raw tool name extracted from the *previously persisted* slug. Disambiguation order is "first tool in the server's returned list keeps the bare slug." If a colliding MCP server ever changed the order it returns tools between syncs, which of the two colliding tools holds the bare vs. suffixed identifier could swap. This only affects the rare case of two names that already collide (never affects normal tools), and matches the same order-based convention already used elsewhere in this codebase for this problem class; a fully order-independent (content-hash-based) scheme would close it but wasn't justified given the scope of this fix. Pre-existing DB rows from installs that collided before this patch aren't migrated — this is a forward-fix, not a data backfill.
