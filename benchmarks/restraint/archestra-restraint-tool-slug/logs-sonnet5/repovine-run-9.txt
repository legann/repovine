## Summary

**Where names become identifiers:** `ToolModel.slugifyName(…)` in `platform/backend/src/models/tool.ts:80` — lowercases, replaces whitespace with `_`, and strips any character outside `[expr]`. This is a many-to-one mapping (e.g. `"GetStatus"` and `"getstatus"`, or `"foo Bar"` and `"foo_bar"`, all produce the same slug). Every call site fed a batch of raw tool names from one MCP server straight through this per-item function into `ToolModel.bulkCreateToolsIfNotExists`/`syncToolsForCatalog`, which insert by `name` with `onConflictDoNothing()` — so a colliding second tool silently failed to get its own row and became permanently unaddressable (not listed, not assignable, not callable).

**Fix:** added `[expr]` in `platform/shared/utils.ts` — a small, generic wrapper: run `slugify` per item as before, then for any output that repeats within the batch, append `-2`, `-3`, ... (in order of appearance, skipping any suffix that would collide with a genuinely different name) so every item gets a distinct string. An item whose slug is already unique in the batch passes through byte-identical to today. Wired it into the five places that build a tool-creation/sync list from a live MCP discovery:
- `platform/backend/src/routes/mcp-server.ts` (local-async and remote-sync install paths)
- `platform/backend/src/archestra-mcp-server/mcp-servers.ts` (`discoverLocalMcpServerTools`, `discoverRemoteMcpServerTools`)
- `platform/backend/src/services/mcp-reinstall.ts` (`syncToolsForServer`)

I initially implemented this as a new `ToolModel.slugifyNames` static method, but reverted it: `mcp-reinstall.test.ts` replaces `ToolModel` wholesale with a hand-built object exposing only `slugifyName`/`syncToolsForCatalog`, so any new `[expr]` method would throw at runtime there. The shared, dependency-injected helper avoids that — it only ever calls the already-mocked `slugifyName`, once per item, in the same order as before, so existing tests (including exact `toHaveBeenCalledWith` assertions on non-colliding names) are unaffected.

**Deliberately left unchanged**, each with the specific reason:
- `ToolModel.cloneToolsAndPoliciesFromCatalog` (`tool.ts:840`) — copies already-DB-unique rows into a clone catalog; not a fresh `tools/list` discovery, so it isn't the discovery-collision bug this task describes.
- App launch tool creation (`app-mcp-backing.ts:73`) — creates exactly one tool per app, never a batch, so there's no sibling to collide with.
- `mcp-client.ts:stripServerPrefix` (`slugifyName(…)`, line 2120) and `resolveActualToolName`'s live case-insensitive re-listing — these recover the upstream raw name at call time and are explicitly flagged by repovine's boundary annotation as a frozen wire-consumer/serving contract alongside the codec; they already have their own documented best-effort limitation for case-only-differing upstream names, independent of this fix.
- Agent delegation tool naming (`findOrCreateDelegationTool`/`syncDelegationToolNames`) — same shape of bug (two same-named agents produce identical delegation-tool names) but a different source (agent display names, not MCP tool names) and a different uniqueness key (`delegateToAgentId`); out of scope per the task's explicit "MCP server exposes a tool" framing.

**Residual risk:** which colliding tool keeps the bare slug vs. gets `-2` depends on order of appearance in the server's `tools/list` response; if a server ever reorders that list between syncs, the suffix assignment could shift. That's an existing implicit assumption elsewhere in this reconciliation code (not new here). Verified the logic standalone (case-only collisions, whitespace/underscore collisions, triple collisions, and a suffix-collides-with-a-real-name edge case) since `tsc`/`vitest` aren't runnable in this bootstrap-less worktree — recommend running `pnpm type-check` and the `mcp-reinstall.test.ts`/`tool.test.ts` suites before merging.
