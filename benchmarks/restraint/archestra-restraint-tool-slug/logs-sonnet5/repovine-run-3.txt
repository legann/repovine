## Summary

**Where names become identifiers:** `ToolModel.slugifyName` (`platform/backend/src/models/tool.ts:80-85`) — lowercases `[expr]`, turns whitespace into `_`, and strips everything else. It's a pure per-pair transform with no visibility into sibling tools, so two different raw names easily collapse onto the same string (`"Create Issue"` and `"create_issue"` both become `..._create_issue`). Whichever tool loses that race gets silently folded into the other's DB row by the `[expr]` unique index and the name-keyed `Map`s in `bulkCreateToolsIfNotExists`/`syncToolsForCatalog` — it never gets its own identifier.

**The fix** lives one layer up, where a server's whole tool batch is visible: a new `slugifyToolNames()` in `platform/backend/src/services/mcp-tool-naming.ts`, called at every write-path site that turns a discovery batch into DB rows, before any DB interaction. Non-colliding names get byte-identical output to today. Within a colliding group, the alphabetically-first raw name keeps the bare slug; every other member is re-derived from a numbered variant of its own raw name (`create_issue` → `create_issue_2`, bumped until unique) and re-run through the *unchanged* `slugifyName`, so it's still a well-formed slug.

| File | Change |
|---|---|
| `services/mcp-tool-naming.ts` | New: `slugifyToolNames(…)` → `[expr]` |
| `archestra-mcp-server/mcp-servers.ts` | 2 call sites (local + remote K8s tool discovery) switched to it |
| `routes/mcp-server.ts` | 2 call sites (local + remote install) switched to it |
| `services/mcp-reinstall.ts` | 1 call site (reinstall sync) switched to it; also threads the disambiguated raw name through as `rawToolName` so reinstall's own by-raw-name reconciliation keeps matching the same tool across syncs |

**Deliberately left unchanged, with proof:**
- `models/tool.ts`'s `slugifyName`/`unslugifyName` codec — untouched. repovine's own recorded annotation on this module states: *"slugifyName is a per-tool-pair transform... making identifiers distinct across a server's tools is therefore a property of the layer that holds them together, not of this transform."* (confirmed when a PreToolUse hook blocked my first attempt to add this logic there).
- `ToolModel.cloneToolsAndPoliciesFromCatalog` (tool.ts:820-900) — untouched. Its own existing comment proves source tool names are already pairwise-distinct (DB-unique) and re-slugifying them is idempotent, so cloning can't reintroduce a collision.
- `services/apps/app-mcp-backing.ts` — untouched. One tool per app catalog, not a batch; already disambiguated via an app-id suffix in the prefix.
- `clients/mcp-client.ts` (`resolveActualToolName`/`stripServerPrefix`), `routes/mcp-server-gateway.utils.ts`, `routes/mcp-server-proxy.ts` — untouched. Same repovine annotation: *"these consumers are frozen alongside the codec... a disambiguated slug that does not round-trip to a raw upstream name is not a defect this task repairs; the wire is not extended to route it."*
- A lone tool whose name strips to empty (`server__`) is left bare — only groups of size ≥2 get touched, matching the annotation's invariant that a solitary empty-slug tool already has a valid, unique identifier.

**Residual risk:** the `tools` table doesn't persist the original raw name, so if a collision appears *retroactively* (a new tool collides with an already-established one), the alphabetical tie-break can't consult history to know which raw name the existing row represents. If it guesses opposite to history, the existing row's id/policies/assignments are preserved, but its description/schema metadata could update to reflect the other sibling on next sync. Also, a disambiguated tool's slug isn't guaranteed to round-trip to a callable name via the existing live-listing invocation resolver — per repovine, that's a pre-existing gap for colliding/degenerate names, not something this task's scope repairs.
