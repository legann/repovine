## Where tool names become identifiers

The identifier *is* the `tools.name` column — there's no separate ID field. It's produced by `ToolModel.slugifyName(…)` in `platform/backend/src/models/tool.ts:79`, which lowercases, folds whitespace to `_`, and strips any character outside `[expr]`. That function had no collision handling: distinct raw names like `"Get User"` and `"get_user"`, or `"GetUser"`/`"getuser"`/`"GETUSER"`, all fold to the identical slug. Since the `tools` table has no uniqueness constraint on `[expr]` for ordinary MCP catalogs (only a partial index scoped to Archestra's own built-in catalog), colliding tools either landed as duplicate rows with the same name or silently shadowed each other in last-write-wins maps (`dedupeToolsByName`, etc.) — one tool became unaddressable.

## Fix

Added `ToolModel.slugifyNames(…)` (`tool.ts:94-136`) — a batch-aware wrapper around the untouched `slugifyName`. It computes the plain slug for every tool in a discovery batch; a slug that's unique in the batch is returned exactly as `slugifyName` would produce it, unchanged. For a colliding group, the first tool (in discovery order) keeps the bare slug and every later one gets a numeric `-2`, `-3`, … suffix, skipping any suffix that's already taken by another tool's natural name.

Updated the 5 call sites that build a batch of tools-to-create/sync from a raw discovery list to use `slugifyNames` instead of mapping `slugifyName` per item:

| File | Function |
|---|---|
| `platform/backend/src/models/tool.ts` | new `ToolModel.slugifyNames` |
| `platform/backend/src/routes/mcp-server.ts` | local-server install discovery, remote-server install discovery |
| `platform/backend/src/archestra-mcp-server/mcp-servers.ts` | `discoverLocalMcpServerTools`, `discoverRemoteMcpServerTools` |
| `platform/backend/src/services/mcp-reinstall.ts` | `syncToolsForServer` |

Changing its matching priority to fix a narrower residual case (below) risked destabilizing tested rename-cascade behavior for no requirement in the task. |

## Residual risks

- **Historical duplicates aren't backfilled.** Rows already created by the old buggy behavior (two DB rows sharing one `name`) aren't migrated; the fix only guarantees distinct identifiers for tools discovered/synced *after* this change. No data migration was in scope.
- **Order-dependence.** Which colliding tool keeps the bare slug depends on the order the MCP server returns tools in `tools/list`. This is deterministic for well-behaved servers but not contractually guaranteed by MCP.
- **Pure-case collisions surviving a later reinstall.** If two tools' raw names differ only by case, `syncToolsForCatalog`'s raw-name-based matching (left unchanged, see above) could still re-associate both to one existing row on a subsequent reinstall/resync, since that heuristic doesn't consider the disambiguating suffix. First-install and non-reinstall discovery paths (4 of the 5 fixed call sites, all using exact-name matching in `bulkCreateToolsIfNotExists`) aren't affected by this.

No tests were added or modified, per the task constraints; verification was by static review only — this sandboxed worktree has no `node_modules` and blocks type-check/test execution.
