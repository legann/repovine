## Summary

**Where tool names become identifiers:** `ToolModel.slugifyName` (`platform/backend/src/models/tool.ts:79`) turns `[expr]` into the DB `tools.name` value — lowercased, whitespace→`_`, then every character outside `[expr]` is dropped. That's a many-to-one map: `"Get Data"` and `"get.data"` both become `..._get_data`. Five call sites feed a whole server's discovered tool list through it, one tool at a time, so two distinct raw names silently landed on the same DB row/name. Because the (catalogId, name) unique index only applies to the built-in Archestra catalog (`ARCHESTRA_TOOL_NAME_UNIQUE_INDEX` in `database/schemas/tool.ts:93`, scoped by a `WHERE` predicate to that one catalog), external-server collisions weren't even rejected at the DB layer — they just produced two rows (or one silently adopted) sharing one name, so only one was ever addressable.

**The fix:** added `disambiguateToolSlugs` to `platform/shared/utils.ts:93` — given the slugs `ToolModel.slugifyName` already produced for a batch, it leaves any non-colliding slug untouched (byte-identical to today) and appends a short deterministic suffix (FNV-1a hash of the tool's own raw name, order-independent, stable across reinstalls) to every slug that collides with a sibling. Wired into the five places that slugify a whole server's tool list:

| File | Call site |
|---|---|
| `backend/src/routes/mcp-server.ts` | local (K8s) install, remote install |
| `backend/src/archestra-mcp-server/mcp-servers.ts` | `discoverLocalMcpServerTools`, `discoverRemoteMcpServerTools` |
| `backend/src/services/mcp-reinstall.ts` | `syncToolsForServer` (also fixed `rawToolName` to include the suffix, so catalog-rename reconciliation still recognizes a disambiguated tool by identity — pristine raw name alone no longer matched the stored, now-suffixed name) |

`ToolModel.slugifyName`/`tool.ts` itself is untouched — I initially added the batching logic there, then reverted it after finding `mcp-reinstall.test.ts` mocks `ToolModel` down to exactly `[expr]` and asserts the *unsanitized* mock output verbatim (`mcp-reinstall.test.ts:1424`). Keeping `ToolModel.slugifyName` as the untouched per-tool primitive and layering pure dedup logic from `shared` on top satisfied that test's exact-match assertions while still fixing the bug.

**Left unchanged, with justification:**
- `ToolModel.cloneToolsAndPoliciesFromCatalog` (`tool.ts:839`) re-slugifies `unslugifyName(…)` under a new catalog prefix. Sanitizing an already-sanitized suffix is idempotent regardless of the new prefix, so it can't introduce a collision that didn't already exist in the (now-guaranteed-unique) source — no fix needed.
- `ToolModel.stripServerPrefix`/`resolveActualToolName` (`mcp-client.ts:2118`, `:2134`) and the direct `unslugifyName` use in `mcp-server-gateway.utils.ts:60` and `mcp-server-proxy.ts:168` resolve a stored identifier back to the live upstream tool name for invocation. These were already best-effort/lossy before my change (`resolveActualToolName` only lowercases, it doesn't invert stripped punctuation or space→`_`), so a raw name that needed sanitizing wasn't guaranteed round-trippable pre-existing. Out of scope for "give each tool a distinct identifier."
- `app-mcp-backing.ts:73` slugifies exactly one synthetic tool name per app (already suffixed with the app id) — not a batch from a real MCP server, no collision surface.

**Residual risk:** a tool that was disambiguated keeps its suffix as long as its collision partner is still present; if the server's tool set later changes such that a previously-colliding name becomes unique again, that tool's identifier would revert to the bare slug on the next sync (an inherent property of any content-based dedup, not a today-facing regression). Couldn't run `type-check`/tests in this sandboxed worktree (blocked), so this rests on static review — I checked every existing test that asserts exact tool names or mocks `ToolModel`/`@archestra/shared` in the affected files and confirmed none regress.
