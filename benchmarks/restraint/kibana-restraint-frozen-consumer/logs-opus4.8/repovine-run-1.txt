## Summary

Added a "max 100 locations per monitor" validation rule enforced on synthetics monitor create/update writes. A monitor whose resolved location set (Elastic-managed + private, combined) exceeds 100 is rejected with a clear validation error before it is persisted.

### Changed behavior
- **Create** (`POST /internal/synthetics/monitors`) and **Update** (`[expr]`) return HTTP 400 with message *"A monitor cannot be assigned to more than 100 locations. N were provided…"* when over the limit.
- **Project push** records the same message as a per-monitor failure (`failedMonitors`) and skips persisting that monitor.
- Monitors at or below 100 locations, and all other validation, behave exactly as before.

### Files touched
| File | Change |
|---|---|
| `monitor_locations_utils.ts` | New `[expr]`, i18n message, and `validateMonitorLocationsLimit(…)` helper (returns error string or `undefined`) |
| `add_monitor.ts` | Create route: call helper after `validateMonitor`, `badRequest` on failure |
| `edit_monitor.ts` | Update route: call helper after `validateMonitor`, `badRequest` on failure |
| `project_monitor_formatter.ts` | Project create/update: call helper, push to `failedMonitors` + `return null` on failure |

The rule lives in `monitor_locations_utils.ts` (already the home of location validators and imported by both write routes; **not** imported by any migration), so all three sites share one constant and one message.
