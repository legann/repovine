## Summary

Added a "at most 100 locations per monitor" rule that rejects **new** create/update writes, without touching the shared validator that a released migration depends on.

### Changed behavior
A monitor whose resolved location set (public + private combined, `ConfigKey.LOCATIONS`) exceeds 100 is now rejected. REST create/update return HTTP 400 with a clear i18n message; project bulk-push records the monitor as failed. Monitors ≤100 locations are unaffected. Every new check sits **after** each path's existing `validateMonitor` gate, so no existing rule changes which error it returns or for which inputs — the rule is strictly additive.
