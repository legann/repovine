## Summary

Added a max-100-locations validation rule for synthetics monitors, enforced on create/update writes only, without altering any existing rule or retroactively rejecting persisted monitors.

### Changed behavior
A create or update whose monitor targets more than 100 locations (public + private combined, i.e. the `locations` array — `[expr]`, the same field the existing "at least one location" rule counts) is now rejected with a 400 and a clear message: *"Monitor targets too many locations"* / details naming the limit and the actual count. At exactly 100 or fewer, behavior is unchanged.

### Files touched (high level)
| File | Change |
|---|---|
| `common/constants/monitor_defaults.ts` | New `[expr]` (beside the existing numeric-limit constant) |
| `.../monitor_cruds/monitor_validation.ts` | `validateMonitor` gains opt-in `options.enforceLocationLimit`; guarded check inserted right after the existing "location required" rule; two i18n messages added |
| `.../monitor_cruds/add_monitor.ts` | Create route (`POST`) opts in |
| `.../monitor_cruds/edit_monitor.ts` | Update route (`PUT`) opts in |
| `.../project_monitor/project_monitor_formatter.ts` | Project push create/update opts in |

The rule is **off by default** (`options` defaults to `[expr]`). Only the three write paths pass `[expr]`, so every other caller behaves byte-for-byte as before.

### Code paths changed (rule enforced) — all are create/update writes
- **`add_monitor.ts:107`** — `POST /synthetics/monitors`; persists via `addMonitorAPI.syncNewMonitor` (:162), downstream of this gate.
- **`edit_monitor.ts:132`** — `[expr]`; persists via `syncEditedMonitor` → `monitorConfigRepository.update`.
- **`project_monitor_formatter.ts:222`** — project push; the sole field-validation gate before `createMonitorsBulk`/`updateMonitorsBulk`.

- **`run_once_monitor.ts:39`** — test-run route; calls `syntheticsMonitorClient.testNowConfigs(…)` (:52) and returns `monitor` (:71), never persists. 2-arg call → rule off. Not a write.

- **Bulk persistence fns `syncNewMonitorBulk` / `syncEditedMonitorBulk` (bulk_cruds)** — receive already-normalized/validated monitors; they contain no `validateMonitor` call, so enforcement stays at the caller gates above.
- **Existing rules inside `validateMonitor`** — untouched; the new branch only runs when `enforceLocationLimit` is true.

### Residual risk
- **Toolchain not run:** the repo has no `node_modules` (unbootstrapped), so `type_check`, `jest`, and `i18n_check` could not be executed. The change is type-safe by inspection (optional 3rd param, `boolean`/`number` comparisons, i18n messages with matching `[expr]`/`[expr]` placeholders and values, unique namespaced IDs) and mirrors existing patterns in the file.
- **Total vs per-type limit:** the limit is on the combined `locations` count, matching the wording "at most 100 locations." A per-type interpretation would need a different check.
