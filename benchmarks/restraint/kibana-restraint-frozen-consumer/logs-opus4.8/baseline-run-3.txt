## Summary

Added a max-100-locations validation rule for synthetics monitors, enforced only on **create/update writes**, with a clear rejection error. `validateMonitor` (the shared codec/schema validator) was deliberately left untouched so already-persisted monitors are never retroactively rejected.

### Behavior change
A create or update whose resulting monitor targets **more than 100 locations** is rejected with HTTP 400 and message: *"A monitor can be assigned to at most 100 locations, but N were provided. Remove the extra locations and try again."* Monitors with ≤100 locations behave exactly as before.

### Files touched
| File | Change |
|---|---|
| `monitor_cruds/monitor_validation.ts` | New `[expr]`, `validateLocationsLimit()` helper, `TOO_MANY_LOCATIONS_ERROR` i18n message; enforcement added inside `validateProjectMonitor` (project bulk push). `validateMonitor` unchanged. |
| `monitor_cruds/add_monitor.ts` | Enforce limit after `validateMonitor` on the POST create route. |
| `monitor_cruds/edit_monitor.ts` | Enforce limit after `validateMonitor` on the PUT update route. |

- **Verification gate not run.** `type_check`/`jest`/`eslint`/`i18n_check` require `yarn kbn bootstrap` (empty `node_modules`). Changes are type-reviewed manually; the new i18n key reuses the existing `[expr]` namespace and provides both `[expr]`/`[expr]` placeholders, so `node scripts/i18n_check --fix` should be a no-op or clean pickup.
- **Update of a pre-existing over-limit monitor** is rejected until its locations are trimmed to ≤100. This is the intended reading of "updating a monitor with more than 100 locations must be rejected"; the no-retroactive-rejection guarantee is preserved for at-rest/migration/read paths, which stay untouched.
- **Project path counts the raw (pre-normalization) location list.** If a push contained duplicates that normalize to ≤100, a raw count >100 would still reject. Negligible at the 100 threshold and errs toward the stricter, documented limit.
