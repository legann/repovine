## Summary

Added a server-side rule: a synthetics monitor may target **at most 100 locations**. Creates/updates exceeding this are rejected with a clear validation error. Already-persisted monitors are never retroactively rejected.

### Design constraint that shaped the patch
`validateMonitor` (the shared accept/reject gate) is a **frozen boundary contract**: the released migration `saved_objects/migrations/monitors/8.8.0.ts:119` calls it and **throws** when it returns invalid (`8.8.0.ts:127-131`). Putting the rule inside `validateMonitor` would make that migration reject any already-persisted monitor with >100 locations on load — exactly the forbidden "retroactive rejection." So the rule is a **new sibling function** wired only into write paths; `validateMonitor` is byte-for-byte unchanged.

## 1. Code paths changed (create/update writes)

| File | Change |
|---|---|
| `server/routes/monitor_cruds/monitor_validation.ts` | New exports `[expr]` + `validateMonitorLocationsLimit()` + two i18n messages. `validateMonitor` untouched. |
| `server/routes/monitor_cruds/add_monitor.ts` | **Create** route: runs the new check on the decoded monitor after `validateMonitor` passes → `response.badRequest` on >100. |
| `server/routes/monitor_cruds/edit_monitor.ts` | **Update** route: same, after the existing `validateMonitor` guard. |
| `server/synthetics_service/project_monitor/project_monitor_formatter.ts` | **Project push** create/update: same, routed through the existing `failedMonitors` collector. |

The new check always runs **after** the existing `validateMonitor` succeeds, so previously-invalid monitors get the identical existing error and no existing rule's behavior changes; only a previously-valid monitor with >100 locations is newly rejected.
