## 1. Patch implemented

A monitor may now target **at most 100 locations**; create/update writes exceeding it are rejected with a 400 validation error. Enforcement lives in a new helper, deliberately kept out of the shared `validateMonitor` (which a released migration reuses).

## 2. Code paths changed vs. intentionally left unchanged

### Changed (the create/update write paths)

| File | Symbol | Change |
|---|---|---|
| `[expr]` | `MAX_MONITOR_LOCATIONS`, `validateMonitorLocationsLimit` | New constant (100) + helper returning an i18n error when `[expr]`. Mirrors sibling `validateMonitorPrivateLocationSpaces`. |
| `[expr]` | `addSyntheticsMonitorRoute` (POST) | Calls the helper on the normalized monitor; returns `response.badRequest` when over the limit. |
| `[expr]` | `editSyntheticsMonitorRoute` (PUT) | Same check on the edited monitor. |

Both checks are placed **immediately before** the existing `validateMonitorPrivateLocationSpaces` call, so every pre-existing check still runs first in its current order — no existing rule's behavior or error precedence changes.

### Left unchanged (with proof of why each is out of scope)

| Path | Proof it is out of scope |
|---|---|
| `validateMonitor` (`monitor_validation.ts`) | Reused by the released SO migration `migrations/monitors/8.8.0` → `omitZipUrlFields`: `[expr]`. Adding the cap here throws on **load** for already-persisted >100-location monitors → retroactive rejection (forbidden). Also is an existing rule I must not alter. |
| `migrations/monitors/8.8.0` | Same `throw` on `validateMonitor` invalid; its accept/reject behavior is frozen (annotated boundary). |
| `ProjectMonitorFormatter` + `syncNewMonitorBulk`/`syncEditedMonitorBulk` | `configureAllProjectMonitors` iterates **all** `this.monitors` in a push and re-validates + re-writes each (even unchanged) via `updateMonitorsBulk`. Enforcing here would reject already-persisted >100-location monitors on routine re-syncs → retroactive rejection. Distinct bulk subsystem (uses `validateProjectMonitor` + `failedMonitors`, not the add/edit routes). |
| `inspect_monitor.ts` | `grep` for `monitorConfigRepository.create/update`, `syncNew/EditedMonitor`, `savedObjectsClient.create/update` → **none**. Calls `validateMonitor` only to preview; never persists. |

| `[expr]` | Under `public/` (browser-side) — a UX affordance, not the authoritative write. Server route rejection is the enforcement point the task requires. |

## 3. Summary

**Behavior change:** `POST /internal/synthetics/monitors` and `[expr]` now return `400 badRequest` (`message`/`attributes.details` = i18n `xpack.synthetics.validation.maxLocations`) when the monitor's combined public+private location set exceeds 100. At-most-100 is unaffected. No existing validator was modified.

**Files touched:** the two REST write routes (`add_monitor.ts`, `edit_monitor.ts`) and one shared helper module (`monitor_locations_utils.ts`) — 43 insertions, 0 deletions.

**Residual risk:**
- **Project-monitor push is not capped**, by design (see table). A *new* project monitor with >100 locations is not rejected on that path. Capping it safely would require rejecting only monitors whose location set actually changed, to preserve "no retroactive rejection."
- **Pre-existing over-limit monitors** (created before this rule) can no longer be updated via PUT — including the enable/disable toggle, which routes through the edit endpoint — until their locations are reduced. This is inherent to the task's "updating … must be rejected" requirement.
- **Toolchain not run:** `type_check`/`eslint`/`i18n_check` require `yarn kbn bootstrap` (absent here).
