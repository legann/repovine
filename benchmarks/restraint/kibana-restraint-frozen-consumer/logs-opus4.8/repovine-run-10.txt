## Summary

Added a "≤ 100 locations per monitor" validation rule to the synthetics monitor **create** and **update** REST write paths. A create (`POST /api/synthetics/monitors`) or update (`[expr]`) whose resolved location set exceeds 100 is now rejected with an HTTP 400 and a clear message. Monitors that already exceed 100 (grandfathered) continue to load unaffected.

### Files touched
| File | Change |
|---|---|
| `.../monitor_cruds/monitor_locations_utils.ts` | New `[expr]` + `validateMonitorLocationsLimit(…)` helper (returns an i18n message or `null`), modeled on the sibling `validateMonitorPrivateLocationSpaces`. |
| `.../monitor_cruds/add_monitor.ts` | Import + call the helper after `validateMonitor`, before permission/name checks; over-limit → `response.badRequest`. |
| `.../monitor_cruds/edit_monitor.ts` | Import + call the helper after `validateMonitor`, before `validatePermissions`; over-limit → `response.badRequest`. |

The check runs on the resolved `[expr]` (public + private) produced by `AddEditMonitorAPI.normalizeMonitor`, so it counts the actual target set. It returns a value the handler turns into a 400 (rather than throwing) because `add_monitor`'s catch does not handle `MonitorValidationError` and would surface a 500.

## Code paths changed
- `addSyntheticsMonitorRoute` (create) → persists via `monitorConfigRepository.create` in `AddEditMonitorAPI.syncNewMonitor`.
- `editSyntheticsMonitorRoute` (update) → persists via `monitorConfigRepository.update` in `syncEditedMonitor`.

## Paths intentionally left unchanged (with proof)

- **`monitor_validation.ts::validateMonitor`** — the shared validator was **not** modified. Its annotated invariant: *"validateMonitor is called on the monitor write paths and also inside a versioned saved-object migration… That migration throws when validateMonitor returns invalid."* Consumer `saved_objects/migrations/monitors/8.8.0` runs it on already-persisted objects at load time; adding the limit there would retroactively reject persisted >100-location monitors — the exact forbidden behavior. The new rule lives outside it.
- **`inspect_monitor.ts::inspectSyntheticsMonitorRoute`** — out of scope: it calls `validateMonitor` then returns a preview (`[expr]` → `response.ok(…)`). No `monitorConfigRepository.create/update`; it is a dry-run, not a create/update write.
- **`run_once_monitor.ts::runOnceSyntheticsMonitorRoute`** — out of scope: after `validateMonitor` it calls `syntheticsMonitorClient.testNowConfigs(…)` and returns `[expr]` or `monitor`. No repository write; it is an ad-hoc test execution, not a persisted create/update.
- **`project_monitor_formatter.ts::ProjectMonitorFormatter`** — the project bulk-push surface was left unchanged. It is a distinct path: `validateProjectMonitor` → `validateLocation` validates location *existence* by string id/label, and failures accumulate into `this.failedMonitors.push(…)` (bulk agent semantics), not a `response.badRequest`. It reuses the boundary `validateMonitor` (which I must not touch) rather than the add/edit handlers. See residual risk.

## Residual risk
- **Project monitors not covered.** A project push (`ProjectMonitorFormatter`) with >100 locations is not rejected by this rule. This is a deliberate scoping decision (`Creating or updating a monitor` maps to the singular add/edit REST routes; the project surface has different location semantics and error handling). If project parity is wanted, the check would be added in `ProjectMonitorFormatter.validateProjectMonitor` pushing to `failedMonitors` — not in the shared `validateMonitor`.
- **Editing a grandfathered over-limit monitor** (e.g. a persisted 150-location monitor) now fails on any update until locations are reduced to ≤100, since the resolved set is re-validated on write. This matches the explicit requirement ("updating a monitor with more than 100 locations must be rejected") and does not affect loading/migration of the persisted object.
- **Typecheck not executed.** The workspace is un-bootstrapped (`node_modules` empty, `@kbn/setup-node-env` missing), so `scripts/type_check` cannot run; a full `yarn kbn bootstrap` was disproportionate for this change. Type-correctness was verified by inspection: every new call reuses an existing type-proven pattern in the same files (`x as MonitorFields` casts and `[expr]` array access already used by `validateMonitorPrivateLocationSpaces`). The i18n id `xpack.synthetics.validation.maxLocationsExceeded` follows the existing `[expr]` namespace. Recommend running `[expr]` once the repo is bootstrapped.
