## Summary

### Changed behavior
Synthetics monitors are now rejected at create/update when they target **more than 100 locations** (Elastic‑managed + private combined, counted on `ConfigKey.LOCATIONS`, which is the merged post‑normalization list). Rejection is a `400` with reason *"Monitor targets too many locations"* and details naming the limit and the actual count. Monitors with ≤100 locations, and all existing rules, are unaffected.

The rule is an **opt‑in** flag on `validateMonitor` (`enforceLocationsLimit`, default `false`). Only new create/update write paths pass it; every other caller keeps byte‑for‑byte current behavior.

### Residual risk
- **Editing a pre‑existing >100‑location monitor**: if such a monitor was persisted before this rule, any subsequent edit (even one not touching locations) now fails until locations are reduced, because the update path merges prior locations and re‑validates. This is consistent with constraint #2 as written ("the rule governs new **create/update** writes") — the persisted monitor is never rejected at load/migration/re‑sync, only when a new write is attempted. If product intent is to grandfather such monitors through edits, that would need an explicit previous‑vs‑new count comparison, which I did not add.
- **Tooling not executed**: `eslint`/`type_check`/`jest` could not run (no `node_modules`). The change is type‑safe and mirrors existing patterns in the same file, but it has not been machine‑verified in this environment.
