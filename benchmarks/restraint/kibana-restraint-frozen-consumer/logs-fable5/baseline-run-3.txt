## Summary

Synthetics monitors are now limited to **100 target locations per monitor**. Create and update writes exceeding the limit are rejected with HTTP 400: message `Monitor targets too many locations`, details `[expr]` The check counts the monitor's resolved, deduplicated location set (public + private combined), and runs after the existing "at least one location" rule so no existing rule's verdict changes for any payload with ≤ 100 locations.

## Files touched

- `common/constants/monitor_defaults.ts` — added `[expr]` beside `ALLOWED_SCHEDULES_IN_MINUTES`.
- `server/routes/monitor_cruds/monitor_validation.ts` — new early-return check in `validateMonitor` (`monitor_validation.ts:102`), gated by a new optional `enforceLocationsLimit` option (default `true`), plus the two i18n messages.
- `server/saved_objects/migrations/monitors/8.8.0.ts` — the migration's `validateMonitor` call passes `[expr]` so persisted docs keep byte-identical migration behavior.

## Code paths changed (all through the single choke point `validateMonitor`)

- **Create** — `POST /api/synthetics/monitors` validates the normalized monitor at `add_monitor.ts:107`; locations are resolved/merged/deduped beforehand (`add_monitor_api.ts:230`, `getMonitorLocations` dedupes via `uniqBy(…)` at `common_fields.ts:268`).
- **Update** — `[expr]` validates the merged result (previous + requested locations) at `edit_monitor.ts:132`, so the limit also catches merges that push the count over 100 (`parseMonitorLocations` merge branches, `add_monitor/utils.ts:44-76`).
- **Project push** — `ProjectMonitorFormatter` validates each normalized monitor at `project_monitor_formatter.ts:222`; over-limit monitors land in the response's `failedMonitors` with the same reason/details.
- **Inspect and run-once** (`inspect_monitor.ts:52`, `run_once_monitor.ts:39`) also inherit the check. Neither is a persisted-monitor path — both validate `request.body` only — and parity avoids "inspect passes but save fails".

## Paths intentionally left unchanged, with proof of scope

- **8.8.0 migration** (`8.8.0.ts:120`): operates on already-persisted docs, and a validation failure alters migration output — the throw at `8.8.0.ts:129` is swallowed at `8.8.0.ts:81-86`, silently skipping ZIP-URL field stripping. The explicit opt-out preserves exact pre-rule behavior, satisfying "persisted monitors must not be retroactively rejected".
- **Private-location label rename** (`settings/private_locations/helpers.ts:74-121`): rewrites persisted monitors via `syncEditedMonitorBulk` (`helpers.ts:112`) with no `validateMonitor` call (see imports, `helpers.ts:7-22`); its `locations.map(…)` at `helpers.ts:92-94` is 1:1 and cannot change the count. Legacy >100-location monitors still get label updates.
- **Test-now for saved monitors** (`test_now_monitor.ts:51-67`): reads the persisted doc via `monitorConfigRepository.getDecrypted` and forwards to the service without validation — persisted monitors remain test-runnable.
- **Reset monitor** (`reset_monitor.ts:31` → `ResetMonitorAPI`): re-provisions Fleet resources for persisted monitors; absent from the exact-match repo-wide list of `[expr]` callers.
- **`validateProjectMonitor`** (`monitor_validation.ts:397`): raw project payloads may contain duplicate/aliased location names (`LocationsMap` aliasing, `common_fields.ts:231`), so counting there would be wrong; the resolved set is counted at `project_monitor_formatter.ts:222` instead.
- **io-ts codecs / `getMonitorLocations`**: a max-length constraint in the shared `Locations` codec would fire wherever persisted attributes are re-decoded (e.g. the migration above, and edit-route decoding of merged persisted attributes at `edit_monitor.ts:107-132`), risking retroactive rejection; `getMonitorLocations` is skipped when an edit reuses `prevLocations` (`add_monitor_api.ts:196-211`), so neither is a complete or safe enforcement point.
- **All existing rules in `validateMonitor`** (empty locations `monitor_validation.ts:93`, type codec, alert config, schedule, exact codec decode, browser script/timeout, spaces): logic untouched; the new check is a separate disjoint early return.
