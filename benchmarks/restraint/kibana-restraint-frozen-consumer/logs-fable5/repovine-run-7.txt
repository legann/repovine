# Summary

Synthetics monitors are now capped at **100 locations per monitor** (public + private combined) on every create/update write. A new helper, `validateMonitorLocationsLimit`, counts the resolved, deduplicated `locations` array of the monitor about to be persisted and returns an i18n'd message: *"A monitor cannot target more than 100 locations. This monitor targets N locations. Remove some locations and try again."* At each write site the check runs **after** all existing validation succeeds, so any payload that previously failed still fails with exactly the same error — only previously-valid writes with >100 locations are newly rejected (HTTP 400 on the CRUD routes; a per-monitor `failedMonitors` entry on project push).

## Paths intentionally left unchanged, with proof

- **`monitor_cruds/monitor_validation.ts` (`validateMonitor`) — byte-identical.** The released 8.8.0 saved-object migration imports it (`8.8.0.ts:29`) and `omitZipUrlFields` **throws** when it returns invalid (`8.8.0.ts:127-131`). Putting the cap there would fail migration of already-persisted >100-location monitors — exactly the retroactive rejection the task forbids. The repovine boundary annotation on this module confirms it is a migration-stability contract. `validateProjectMonitor`/`validateLocation` are also untouched; the project cap lives in the formatter instead, on the resolved deduped locations (`getMonitorLocations` dedupes via `uniqBy(…)`, `common_fields.ts:268`), so duplicate raw entries don't overcount.
- **`saved_objects/migrations/monitors/8.8.0.ts`** — consumes only unchanged exports; `monitor_defaults.ts` gained a new export, and the ones the migration imports (`8.8.0.ts:18-24`) are untouched.
- **`inspect_monitor.ts`** — calls `validateMonitor` (line 52) but performs no repository write; it hydrates and formats the config for display. Non-persisting, so outside "create/update writes".
- **`run_once_monitor.ts`** — validates then calls `syntheticsMonitorClient.testNowConfigs` (line 52): an ephemeral test run, nothing persisted.
- **`settings/private_locations/helpers.ts:112`** — calls `syncEditedMonitorBulk` directly (no validation imports) to re-sync existing monitors when a private location is edited/deleted. Applying the cap here would block location maintenance on legacy >100-location monitors — a retroactive rejection.
- **`bulk_cruds/add_monitor_bulk.ts` / `edit_monitor_bulk.ts`** — persistence layer below validation; also used by the rollback path (`edit_monitor_bulk.ts:213` reverts `monitorsToRevert`) and the private-location re-sync above, both of which must accept persisted state as-is.
- **`services/reset_monitor_api.ts`** — re-syncs already-persisted attributes to Fleet/service (`syntheticsMonitorClient.editMonitors`/`addMonitors`, lines 157/206); no user payload is written, so the rule must not apply.
- **UI form validation** (`public/.../monitor_add_edit/form/validation`) — untouched; the UI submits through the changed routes and will surface the server's 400 message, which is the authoritative gate.

This matches the task's "updating … must be rejected" and the codebase's established semantic (an edit of a monitor with a no-longer-allowed schedule is likewise rejected today), but it's the one user-visible edge worth knowing. Monitors at rest keep loading, running, migrating, and syncing.
