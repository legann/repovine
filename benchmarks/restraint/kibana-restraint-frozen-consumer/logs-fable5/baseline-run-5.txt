## Summary of changed behavior

A synthetics monitor may now target at most 100 locations. Any create or update write whose **resolved, deduplicated** location set (public + private, deduped by `uniqBy(…)` in `getMonitorLocations`, `server/synthetics_service/project_monitor/normalizers/common_fields.ts:268`) exceeds 100 is rejected with HTTP 400 / a per-monitor failure entry:

- reason: `Monitor has too many locations`
- details: `[expr]`

Exactly 100 locations is still accepted; the limit applies strictly above 100.

## Files touched

- `x-pack/solutions/observability/plugins/synthetics/common/constants/monitor_defaults.ts` — new exported constant `[expr]`, placed next to the analogous rule bound `ALLOWED_SCHEDULES_IN_MINUTES`.
- `x-pack/solutions/observability/plugins/synthetics/server/routes/monitor_cruds/monitor_validation.ts` — new check in `validateMonitor` immediately after the existing empty-locations rule, plus two i18n messages following the file's reason/details pattern.

## Code paths now governed by the rule

`validateMonitor` is the single choke point every create/update write flows through:

1. **Create via API/UI** — `POST /api/synthetics/monitors` calls it at `server/routes/monitor_cruds/add_monitor.ts:107` → 400.
2. **Update via API/UI** — `[expr]` calls it at `server/routes/monitor_cruds/edit_monitor.ts:132` → 400. If the request omits locations, previous locations are carried into the merged payload (`add_monitor_api.ts:196-197`), so an explicit update of a monitor exceeding the limit is rejected until locations are reduced — which is the requested "updating … must be rejected" behavior.
3. **Project push (create and update)** — `ProjectMonitorFormatter.validateProjectMonitor` calls it on every normalized monitor at `server/synthetics_service/project_monitor/project_monitor_formatter.ts:222`; failures become `failedMonitors` entries in the push response.
4. **Preview endpoints** (non-persisting) — `run_once_monitor.ts:39` and `inspect_monitor.ts:52` share `validateMonitor` and now reject the same payloads, consistent with every existing rule in that function.

## Residual risk

- **No dynamic verification**: this worktree is intentionally not bootstrapped (installs, typecheck, lint, and jest are blocked), so the change was finalized from static reading. It mirrors the adjacent schedule-rule pattern exactly (constant import, guard clause, i18n reason/details), so risk is low.
- **8.8.0 migration edge case**: a hypothetical pre-8.8 legacy *browser* doc with >100 locations would skip zip-URL field stripping with a logged warning instead of being re-encoded (doc preserved, never rejected) — the same degraded-but-safe mode that migration already exhibits for other post-8.8 validation rules.
- **Error precedence**: payloads with >100 locations that previously failed a later rule (schema, schedule) now fail with the locations error first — inherent to adding any early validation rule.
