## Changed behavior

A monitor create or update that targets more than 100 locations (public + private combined, counted after resolution and dedup) is now rejected: the REST API returns a 400 with message "Monitor targets too many locations" and details "`N` locations supplied to monitor configuration. A monitor may target at most 100 locations."; a project push records the same error per monitor in the response's `failedMonitors` and skips that monitor. Exactly 100 locations is still accepted.

## Files touched

- **`x-pack/.../server/routes/monitor_cruds/monitor_validation.ts`** — new exports `[expr]` and `validateMonitorLocationsCount()` (returns the module's standard `ValidationResult`), plus two i18n error strings. `validateMonitor` itself is byte-identical.
- **`.../monitor_cruds/add_monitor.ts`** — POST route: new gate right after the existing `validateMonitor` gate, same `badRequest` shape.
- **`.../monitor_cruds/edit_monitor.ts`** — PUT route: same gate on the merged edited monitor.
- **`.../synthetics_service/project_monitor/project_monitor_formatter.ts`** — project push: gate after the existing normalized-monitor validation, routed through the formatter's `validateMonitor` wrapper so failures land in `failedMonitors`; the monitor never reaches `syncNewMonitorBulk`/`syncEditedMonitorBulk`.

The new check runs *after* the pre-existing checks on every path, so which error a previously-invalid payload receives is unchanged.
