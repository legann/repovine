## Summary

**Changed behavior:** Synthetics monitor create/update writes are now rejected with a `400`-style validation error when the monitor's final resolved `locations` array (public + private combined) exceeds **100**. Enforcement lives in a new additive validator, `validateMonitorLocationsLimit`, called from the three persisting write paths after all existing validation. Error: reason "Monitor has too many locations", details "Monitor is configured with {count} locations. A monitor can target at most 100 locations, including private locations."

|---|---|
| `common/constants/monitor_defaults.ts` | New `[expr]` (next to the other validation-constraint constants). |
| `server/routes/monitor_cruds/monitor_validation.ts` | New exported `validateMonitorLocationsLimit()` + two i18n error messages. **Purely additive** — `validateMonitor` is byte-identical. |
| `server/routes/monitor_cruds/add_monitor.ts` | `POST /api/synthetics/monitors` (create): limit check after the existing `validateMonitor` block, same `badRequest` shape. |

The UI needs no separate change: the create/edit forms submit through the two changed routes (`public/apps/synthetics/state/monitor_management/api.ts:28` POSTs and `:73` PUTs `SYNTHETICS_MONITORS`).

### Related paths intentionally left unchanged (with citations)

The complete caller set of `validateMonitor` is six sites (verified by dependency-graph impact analysis + grep). The three non-write callers are untouched because `validateMonitor` itself is untouched:

- **`server/saved_objects/migrations/monitors/8.8.0.ts:119-131`** — the released migration calls `validateMonitor` and **throws** on invalid. This is why the limit was *not* added inside `validateMonitor`: it would make already-persisted >100-location monitors fail migration/load, violating the no-retroactive-rejection constraint.
- **`server/routes/monitor_cruds/inspect_monitor.ts:52`** — config preview; grep confirms the handler contains no `monitorConfigRepository.create/update`/`syncNewMonitor`/`syncEditedMonitor` call, so it persists nothing.
- **`server/routes/synthetics_service/run_once_monitor.ts:39-66`** — ad-hoc test run; after validation it only calls `syntheticsMonitorClient.testNowConfigs(…)`, no saved-object write.

Persistence/maintenance layers that rewrite **already-persisted** monitors — deliberately not gated so legacy >100-location monitors keep working:

- **`[expr]`** — private-location rename maps existing `locations` 1:1 (`.map`, count unchanged) and calls `syncEditedMonitorBulk` directly.
- **`server/routes/monitor_cruds/bulk_cruds/add_monitor_bulk.ts` / `edit_monitor_bulk.ts`** — shared persistence primitives; grep confirms they contain no `validateMonitor` call today, and they serve the maintenance flow above. All request-driven writes reaching them pass through one of the three gated paths first.
- **`server/routes/monitor_cruds/services/reset_monitor_api.ts:157-166`** — reset re-syncs the persisted monitor's own locations (filtering to still-valid private locations, only ever reducing count); no request-supplied locations.

Delete/read routes (`[expr]`, `[expr]`) take no location input.

### Residual risk

- **Grandfathered monitors on edit:** a legacy monitor persisted with >100 locations keeps loading, running, syncing, and migrating — but any subsequent UI/API edit (including the enable/disable toggle, which goes through the edit route) is rejected until locations are reduced. This matches the codebase's established edit semantics (the merged doc is fully re-validated, e.g. against `ALLOWED_SCHEDULES_IN_MINUTES`), but it is a judgment call on "update" scope worth flagging.
- **Error precedence:** a payload failing both an existing rule and the new one still reports the existing rule's error (new check runs last), so no existing rule's observable behavior changes; only previously-accepted >100-location payloads are newly rejected.
- Lint/type-check/tests could not be executed in this intentionally non-bootstrapped worktree; the change mirrors adjacent patterns exactly (same casts, destructuring, and response shapes as the neighboring validation blocks), and i18n IDs/constant names were verified unique repo-wide.
