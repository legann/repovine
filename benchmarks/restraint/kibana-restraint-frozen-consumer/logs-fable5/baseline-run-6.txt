## Summary

Synthetics monitors are now limited to **100 locations per monitor** on create and update. The rule lives in the shared `validateMonitor()` as an opt-in option (`checkMaxLocations`), enabled only by the three write paths. A monitor exceeding the limit is rejected with message *"Monitor cannot target more than 100 locations"* plus details stating the supplied count and that the limit spans elastic managed and private locations combined. The check runs on the fully normalized monitor, after location resolution, so it counts the real resolved location list (public + private expanded).

## Paths intentionally left unchanged (with citations)

- **8.8.0 saved-object migration** — `migrations/monitors/8.8.0.ts:119-131` calls `validateMonitor` on persisted docs and **throws** if invalid. The option defaults to off, so persisted monitors with >100 locations still migrate — this is precisely the "no retroactive rejection" constraint.
- **Inspect route** — `inspect_monitor.ts:52` validates, then only renders config via `syntheticsMonitorClient.inspectMonitor(…)` (line 85); it never writes a monitor, so it is not a create/update write.
- **Run-once route** — `[expr]`: validates a payload and pushes an ephemeral test via `testNowConfigs(…)`; nothing is persisted.
- **Private-location label resync** — `settings/private_locations/helpers.ts:87-120` (`updatePrivateLocationMonitors`) rewrites *already persisted* monitors via `syncEditedMonitorBulk` and never calls `validateMonitor`; a persisted 100+-location monitor must survive a location rename, which is why the rule was placed in route-level validation rather than the bulk sync helpers it flows through.
- **Bulk sync helpers / repository writes** — `bulk_cruds/add_monitor_bulk.ts:71` and `[expr]` receive pre-validated monitors from the routes/formatter and also serve the resync path above plus the revert logic (`edit_monitor_bulk.ts:213`), so enforcing there would hit persisted monitors.
- **Edit rollback** — `edit_monitor.ts` `rollbackUpdate` (lines 249-273) restores previous persisted attributes via `savedObjectsClient.update` on failure; it must never be blocked and doesn't pass through validation.
- **`validateProjectMonitor`** (`monitor_validation.ts`) — validates the raw project payload where locations are still string IDs/labels; the resolved count is only known post-normalization, which the `validateMonitor` call at `project_monitor_formatter.ts:222` covers. Its behavior is untouched.
- **Reset route & legacy uptime plugin** — `reset_monitor.ts` only rebuilds Fleet package policies for an existing monitor (`ResetMonitorAPI`), and `uptime/server/legacy_uptime/routes/synthetics/` contains only the read-only `last_successful_check.ts`; neither writes monitor configs.

## Residual risk

- I could not run lint/typecheck/jest (environment intentionally not bootstrapped, verified by the blocked bootstrap attempt), so there's a small chance of a formatting nit; the TypeScript change itself is additive and backward-compatible with all existing call sites.
- A pre-existing monitor with >100 locations keeps running untouched, but its next update — including an enable/disable toggle, which routes through the edit endpoint and merges previous fields (`edit_monitor.ts:96-107`) — will be rejected until locations are reduced. - Inspect and run-once still accept >100-location payloads by design (they aren't writes); if product intent later wants the limit there too, it's a one-line opt-in per route.
