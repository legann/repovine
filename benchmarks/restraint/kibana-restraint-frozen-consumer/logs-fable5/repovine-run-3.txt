## What changed

A synthetics monitor may now target at most **100 locations**. The cap is enforced in `getMonitorLocations` (`server/synthetics_service/project_monitor/normalizers/common_fields.ts:271-273`), the single function where every create/update write resolves its final, deduplicated public + private location set. When the resolved set exceeds 100, it throws `InvalidLocationError` with a new i18n message stating the limit, the offending count, and the fix.

**Files touched (2):**
- `x-pack/.../synthetics/common/constants/monitor_defaults.ts` — new `[expr]` constant, next to the existing validation limits (`ALLOWED_SCHEDULES_IN_MINUTES`).
- `x-pack/.../synthetics/server/synthetics_service/project_monitor/normalizers/common_fields.ts` — the check after `uniqBy` dedup, plus the `getTooManyLocationsError` i18n helper mirroring the adjacent `getInvalidLocationError`.

## Write paths covered by the one check

All three create/update surfaces flow through `getMonitorLocations`, and each already converts `InvalidLocationError` into a clear validation error:

| Path | Reaches the check via | Error surfaced at |
|---|---|---|
| `POST /api/synthetics/monitors` (UI + public API create) | `AddEditMonitorAPI.normalizeMonitor` → `getMonitorLocations` (`add_monitor_api.ts:230`) | 400 `badRequest` (`add_monitor.ts:180-182`) |
| `[expr]` (UI + public API update) | same, on the merged final set — `mergeSourceMonitor` carries previous locations into the payload (`saved_object_to_monitor.ts:90`), so the cap governs the monitor's resulting state | 400 `badRequest` (`edit_monitor.ts:229-231`) |
| Project push (`synthetics push`) | `getNormalizeCommonFields` → `getMonitorLocations` (`common_fields.ts:73`) | per-monitor `failedMonitors` entry with `INVALID_CONFIGURATION_ERROR` (`project_monitor_formatter.ts:234-242`); monitor not created/updated |

On updates the rule applies to the final merged set — the same semantics as existing write-time rules (e.g. the schedule rule at `monitor_validation.ts:135-142` also rejects any edit of a monitor whose resulting state is invalid, until fixed).

## Paths intentionally left unchanged (with proof of scope)

The released migration calls `validateMonitor` and **throws** on invalid (`saved_objects/migrations/monitors/8.8.0.ts:119-131`), so putting the cap there would fail migration of persisted >100-location monitors. `validateMonitor` (`monitor_validation.ts:78-207`) is untouched; `getMonitorLocations` has exactly two callers (`add_monitor_api.ts:230`, `common_fields.ts:73` — verified by grep), neither in a migration.
