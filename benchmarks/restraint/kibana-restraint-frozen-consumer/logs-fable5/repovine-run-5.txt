## Summary of changed behavior

A synthetics monitor may now target at most 100 locations. Any create or update write whose **resolved, deduplicated** location set (public + private combined) exceeds 100 is rejected: the UI/API create and edit routes return HTTP 400 with the message "Monitor targets N locations, but a monitor may target at most 100 locations, including private locations. Remove some locations and try again.", and a project push reports the same message as a per-monitor failure. Monitors at or under 100 locations behave byte-for-byte as before.

## Files changed

- `x-pack/solutions/observability/plugins/synthetics/common/constants/monitor_defaults.ts` — added `[expr]` alongside the existing validation constants (`ALLOWED_SCHEDULES_IN_MINUTES`, etc.).
- `x-pack/solutions/observability/plugins/synthetics/server/synthetics_service/project_monitor/normalizers/common_fields.ts` — in `getMonitorLocations`, after the existing invalid-location check and the `uniqBy` dedup, throw `InvalidLocationError` with a new i18n message (`xpack.synthetics.projectMonitorApi.validation.maxLocationsExceeded`) when the final set exceeds the cap.

`getMonitorLocations` is the single choke point where every user-facing create/update write resolves its final location set, so one check covers all three write paths:

| Write path | Reaches the check via | Error surfaced at |
|---|---|---|
| POST /api/synthetics/monitors (create) | `normalizeMonitor` → `getMonitorLocations` (`add_monitor_api.ts:230`) | `InvalidLocationError` handler → 400 (`add_monitor.ts:180`) |
| PUT /api/synthetics/monitors/{id} (edit) | same `normalizeMonitor` call | handler → 400 (`edit_monitor.ts:229`) |
| Project push (create + update) | normalizers → `getNormalizeCommonFields` → `getMonitorLocations` (`common_fields.ts:73`) | caught → per-monitor `INVALID_CONFIGURATION_ERROR` (`project_monitor_formatter.ts:231-243`) |

The check runs after the existing unknown-location check (`common_fields.ts:252-261`) and after dedup, so no input that previously produced a different validation error changes outcome, and the cap applies to the true effective set (edit-route merges of previous + new locations in `parseMonitorLocations`, `add_monitor/utils.ts:44-75`, are included).

## Paths intentionally left unchanged, with proof

- **`validateMonitor` and the whole `monitor_validation.ts`** — untouched. The frozen 8.8.0 saved-object migration calls it and **throws on invalid** (`server/saved_objects/migrations/monitors/8.8.0.ts:119-131`); putting the cap there would fail migration of persisted >100-location monitors. That migration calls only `validateMonitor`, never `getMonitorLocations` (grep of `8.8.0.ts` shows no other validation import), so it cannot hit the new rule.
- **Edit with no location fields in the payload** — `normalizeMonitor` short-circuits at `add_monitor_api.ts:196` (`[expr]`) without calling `getMonitorLocations`, so a legacy >100-location monitor can still be renamed/enabled/disabled. Grandfathering per the "not retroactively rejected" constraint.
- **Private-location rename re-sync** — `updatePrivateLocationMonitors` builds updates directly from persisted attributes (`m.attributes.locations.map(…)`, `settings/private_locations/helpers.ts:92`) and calls `syncEditedMonitorBulk` directly (`helpers.ts:112`); no `getMonitorLocations` on that path.
- **Reset** — `ResetMonitorAPI` reads persisted monitors via `monitorConfigRepository.getDecrypted` (`services/reset_monitor_api.ts:60`) and pushes them via `syntheticsMonitorClient.editMonitors`/`addMonitors` (`[expr]`); it never resolves locations through `getMonitorLocations`.
- **Dry-run paths** — `inspect_monitor.ts:52` and `run_once_monitor.ts:39` call `validateMonitor` directly on the raw payload and never call `getMonitorLocations`; they are not persisted writes and behave exactly as before.
- **Rollback writes** — `rollbackUpdate` (`edit_monitor.ts:260`) and the bulk revert (`bulk_cruds/edit_monitor_bulk.ts:213`) restore previous persisted attributes without normalization, so a failed edit can always be rolled back.
- **Write-path completeness**: all monitor saved-object writes go through `monitorConfigRepository.create/createBulk/update/bulkUpdate` (`add_monitor_api.ts:91`, `add_monitor_bulk.ts:71`, `edit_monitor.ts:319`, `[expr]`); the only direct `soClient.create` on the monitor type is the delete-and-recreate branch inside `MonitorConfigRepository.update` itself (`monitor_config_repository.ts:237`). ## Residual risk

- **Verification is static only.** This benchmark worktree deliberately blocks bootstrap, so `node scripts/type_check`, eslint, and Jest could not run (`yarn` shim exits with "intentionally NOT bootstrapped"). I verified by careful reading: the new code mirrors existing patterns in the same function (`InvalidLocationError` and `getInvalidLocationError` are likewise referenced before their declarations, resolved at call time), the i18n id is unique repo-wide, and placeholders match the values object.
- **Client-side UX**: the UI monitor form has no matching client-side cap; a >100-location save fails at the server with the 400 message rather than an inline form hint. In practice the form's location picker is bounded by available locations, and the server message is surfaced by the existing error handling.
