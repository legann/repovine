## Summary

Synthetics monitors are now limited to **100 locations** on create and update. The count is checked against the monitor's final, normalized `locations` array — which `getMonitorLocations` builds by merging public and private locations and de-duplicating by id (`common_fields.ts:263-268`) — so the limit covers public + private combined, after de-duplication. A violating write is rejected with HTTP 400, reason "Monitor has too many locations" and details "N locations supplied to monitor configuration. A monitor can target a maximum of 100 locations." (project pushes report the same error per-monitor in the push response's `failedMonitors`).

Mechanically: `validateMonitor` gained an optional `[expr]` parameter (default off), and only the three write paths opt in. This makes every other caller provably unchanged, including re-validation of already-persisted monitors.

## Paths intentionally left unchanged, with citations

- **8.8.0 saved-object migration** (`server/saved_objects/migrations/monitors/8.8.0.ts:119`) calls `validateMonitor` on every persisted browser monitor; a failure there throws (`8.8.0.ts:127-131`) and degrades the migration (caught at `8.8.0.ts:81-86`, skipping zip-URL cleanup and `formatSecrets`). Its two-argument call keeps enforcement off, so persisted monitors with >100 locations migrate exactly as before.
- **Inspect route** (`monitor_cruds/inspect_monitor.ts:52`) is a dry-run: its handler only calls `syntheticsMonitorClient.inspectMonitor` (`inspect_monitor.ts:85`), which formats and returns configs — no repository write. Not a create/update, so it keeps the default.
- **Run-once route** (`routes/synthetics_service/run_once_monitor.ts:39`) executes an ephemeral test via `syntheticsMonitorClient.testNowConfigs` (`run_once_monitor.ts:52-65`) and persists nothing. Same reasoning.
- **Private-location rename resync** (`routes/settings/private_locations/helpers.ts:74-121`) rewrites persisted monitors' location labels via `syncEditedMonitorBulk` (`helpers.ts:112`) with no `validateMonitor` call anywhere in the file; adding enforcement there would retroactively reject persisted >100-location monitors when someone renames a location.
- **Reset API** (`[expr]`) re-syncs persisted monitors to the service/package policies via `syntheticsMonitorClient.editMonitors`/`addMonitors` — service-side repair of stored monitors, no validation today.
- **Bulk CRUD helpers** (`bulk_cruds/add_monitor_bulk.ts`, `bulk_cruds/edit_monitor_bulk.ts`) are pure persistence; grep confirms their only callers are the project formatter (validated upstream at `project_monitor_formatter.ts:221-224`, now enforcing) and the private-location resync above.
- **Coverage completeness**: the repository exposes exactly four write methods (`[expr]`); every non-test caller is one of the paths above, so no write path was missed. Existing rules are untouched — with the flag off the function's statement sequence is identical, and with it on the new check only fires for >100 locations, so any previously-valid payload behaves byte-identically.
