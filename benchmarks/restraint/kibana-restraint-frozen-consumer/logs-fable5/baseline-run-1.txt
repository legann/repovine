## Summary

Synthetics monitors are now limited to **at most 100 locations** (public + private combined, counted after normalization). Create and update writes exceeding the limit are rejected with HTTP 400: reason `Monitor cannot target more than 100 locations`, details `[expr]`

### Files touched

| File | Change |
|---|---|
| `common/constants/monitor_defaults.ts` | New constant `[expr]` (monitor_defaults.ts:136) |
| `server/routes/monitor_cruds/monitor_validation.ts` | New rule in `validateMonitor` after the existing empty-locations rule (monitor_validation.ts:112-119), gated by a new optional `ValidateMonitorOptions.enforceMaxLocations` (default **on**); new i18n messages |
| `server/saved_objects/migrations/monitors/8.8.0.ts` | The one caller that validates already-persisted docs now passes `[expr]` (8.8.0.ts:124-127) so migration behavior is byte-identical to before |

### Code paths that now enforce the rule (all via the single check in `validateMonitor`)

- **Create** — `POST /api/synthetics/monitors`: `add_monitor.ts:107` validates the normalized monitor (merged public+private locations, built in `add_monitor_api.ts:230-242`) before the saved-object write at `add_monitor_api.ts:91`.
- **Update** — `[expr]`: `edit_monitor.ts:132` validates the merged result (previous + edits) before the write at `edit_monitor.ts:319`. Per the task, the rule governs the *write*: an update whose resulting monitor exceeds 100 locations is rejected, even if the excess predates the rule; the persisted monitor itself keeps running.
- **Project push (create and update)** — `project_monitor_formatter.ts:221-222` validates each normalized project monitor inside `configureAllProjectMonitors` (lines 133-171) before both `createMonitorsBulk` and `updateMonitorsBulk` (lines 173-176); failures are reported per-monitor with the new reason/details (`failedMonitors`, formatter lines 455-471).
- **Side effect, intentional** — `inspect_monitor.ts:52` and `run_once_monitor.ts:39` share `validateMonitor` but validate only `request.body` (inspect_monitor.ts:45, run_once_monitor.ts:33) — new user payloads, never persisted monitors. They now reject >100 locations too, which keeps dry-run/test-run consistent with what save would do; no persisted monitor is affected.

### Related paths intentionally left unchanged (with proof they're out of scope)

- **8.8.0 SO migration** — `omitZipUrlFields` calls `validateMonitor` on persisted legacy docs (8.8.0.ts:119); on failure it throws, and the catch at 8.8.0.ts:81-86 degrades the migration (skips zip-URL stripping). Enforcing there would retroactively change how persisted >100-location monitors migrate, so it opts out explicitly.
- **Test-now for saved monitors** — `test_now_monitor.ts:51-67` reads the persisted monitor via `monitorConfigRepository.getDecrypted` and pushes it straight to `testNowConfigs` with no `validateMonitor` call, so persisted >100-location monitors can still be test-run.
- **Reset** — `reset_monitor_api.ts:157-173` (default) and `:204-213` (force) re-push persisted attributes to the service without `validateMonitor`; persisted monitors keep resetting.
- **Private-location label rename propagation** — `settings/private_locations/helpers.ts:87-120` rewrites persisted monitors via `syncEditedMonitorBulk` with no validation call; renaming a location cannot brick an existing >100-location monitor.
- **Rollback writes** — `edit_monitor.ts:249-273` and `edit_monitor_bulk.ts:148-222` restore previous persisted attributes unvalidated; error recovery is unaffected.
- **Project-level `validateLocation`/`validateProjectMonitor`** (monitor_validation.ts:439+) — no count check added there; the authoritative count is the *resolved* combined `locations` array, which the same push flow validates at `project_monitor_formatter.ts:222`, so a second check would be redundant duplication.

- **Existing rules** — the new check sits between the empty-locations rule (monitor_validation.ts:103-110) and the type-codec rule (monitor_validation.ts:121); every payload with ≤100 locations flows through all existing rules with unchanged inputs and outcomes. ### Residual risk

- Tests, type check, and lint could not be executed here (worktree blocks bootstrap); the signature change is backward-compatible (optional third parameter) and all existing call sites pass two arguments, but this is statically verified only.
- Payloads with >100 locations that are *also* invalid for other reasons now report the locations error first (short-circuit before codec/schedule checks) — the rejection outcome is unchanged, only which error message such a payload receives.
- Saved-object import/export at the platform level bypasses all synthetics validation (it bypasses every existing rule the same way) and remains a path where an out-of-limit monitor could technically be written; that predates this rule and is outside the synthetics API surface.
- The UI monitor form performs no client-side count check; users with >100 selectable locations will see the server's 400 message on save rather than inline form feedback.
