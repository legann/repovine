## Summary

Synthetics monitors are now limited to **100 locations per monitor** on create and update. The rule is a new, opt-in check inside `validateMonitor` — enabled only at the three write gates — so every other consumer of that function behaves exactly as before. A violating write is rejected with reason `Monitor location limit exceeded` and details naming the actual count and the 100-location maximum (public + private combined). The count is taken from the normalized monitor's `locations` array, which `getMonitorLocations` builds by merging public and private locations and deduplicating by id, so it is the true total the monitor would target.

### Changed paths (rule enforced)

- `common/constants/monitor_defaults.ts` — new `[expr]` next to `ALLOWED_SCHEDULES_IN_MINUTES`.
- `server/routes/monitor_cruds/monitor_validation.ts` — `validateMonitor` gains an optional `ValidateMonitorOptions` third parameter (`enforceLocationsLimit`, default off). The check sits after the existing empty-locations rule; two new i18n messages follow the existing reason/details pattern.
- `server/routes/monitor_cruds/add_monitor.ts:107` — create route (`POST /api/synthetics/monitors`, used by UI and public API); failure returns the standard 400 via the existing invalid-result branch.
- `server/routes/monitor_cruds/edit_monitor.ts:132` — update route (`[expr]`); same 400 path. Because `normalizeMonitor` falls back to the previous locations when the payload omits them (`add_monitor_api.ts:196-197`), any update of a >100-location monitor is rejected, as the task specifies for update writes.
- `server/synthetics_service/project_monitor/project_monitor_formatter.ts:222` — project push, covering both bulk create (`syncNewMonitorBulk` → `createBulk`) and bulk update (`syncEditedMonitorBulk` → `bulkUpdate`); a violating monitor is added to `failedMonitors` with the reason/details and skipped, like other per-monitor validation failures.

These five call sites are exhaustive: every monitor saved-object write in the plugin (`monitorConfigRepository.create/createBulk/update/bulkUpdate`) is reached only through those gates, except the paths below.

### Paths intentionally left unchanged (with citations)

- **8.8.0 saved-object migration** — `migrations/monitors/8.8.0.ts:119-131` calls `validateMonitor` two-arg on persisted docs and `[expr]` on failure. Enforcing here would retroactively reject persisted monitors during upgrade; with the default-off flag its behavior is unchanged.
- **Run-once test route** — `run_once_monitor.ts:39` validates, then line 52 calls `syntheticsMonitorClient.testNowConfigs`; the file contains no `monitorConfigRepository` write, so it is not a create/update.
- **Inspect route** — `inspect_monitor.ts:52` validates, then line 85 calls `syntheticsMonitorClient.inspectMonitor` to return a rendered preview; no write, and enforcing would break inspect for a pre-existing >100-location monitor.
- **Private-location label rename** — `settings/private_locations/helpers.ts:74-121` rewrites persisted monitors' `locations` labels (line 92) and calls `syncEditedMonitorBulk` directly with no `validateMonitor` call; blocking it would strand pre-existing large monitors.
- **Test-now on existing monitor** — `[expr]` only reads (`getDecrypted`) and triggers a test; no validation or write.
- **Bulk-edit revert path** — `edit_monitor_bulk.ts:213` `bulkUpdate` restores previous persisted attributes after a failed sync; input is prior persisted state, not a new write.
- **Raw project payload check** (`validateProjectMonitor`, `monitor_validation.ts:381`) — unchanged; enforcement happens on the normalized, deduplicated monitor, which is what gets persisted.

Existing rules are untouched: the new branch is purely additive and gated, and all pre-existing callers pass two arguments, so their results are byte-identical.

### Residual risk

- This benchmark worktree blocks bootstrap, so type check, eslint, and jest could not be run; verification is static. - The limit counts unique resolved locations; a payload with duplicate location IDs that dedupes to ≤100 is accepted, which matches "targets at most 100 locations".
