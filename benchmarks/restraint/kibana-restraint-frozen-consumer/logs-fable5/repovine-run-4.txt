## Summary

A monitor may now target at most 100 locations. Creating or updating a monitor with more than 100 resolved locations is rejected with: *"Invalid locations specified. A monitor can target a maximum of 100 locations, but N locations were specified."*

The rule lives in **`getMonitorLocations`** (`server/synthetics_service/project_monitor/normalizers/common_fields.ts:271-273`) — the single choke point where every write that specifies locations resolves its final location set. It counts the deduplicated union of public + private locations (`uniqBy(…)`, so 100 passes, 101 fails) and throws the pre-existing `InvalidLocationError`, after the existing invalid-location-name check so existing error precedence is unchanged.

## Files touched

- `x-pack/.../synthetics/common/constants/monitor_defaults.ts` — added `[expr]` next to the other validation limits.
- `x-pack/.../synthetics/server/synthetics_service/project_monitor/normalizers/common_fields.ts` — the count check in `getMonitorLocations` plus an i18n'd `getMaxLocationsError` helper (mirrors the sibling `getInvalidLocationError`).

Adding the rule there would fail migration of already-persisted >100 monitors — exactly the retroactive rejection the task forbids. The repovine graph independently flags this node as a frozen `boundary` for the same reason.
- **Edit carry-forward branch (`add_monitor_api.ts:196-211`)** — `[expr]` skips `getMonitorLocations`. Updates that don't touch locations (rename, enable/disable) still succeed on a legacy >100 monitor — the grandfathering guarantee.

The change was verified statically: it copies the file's existing patterns (`i18n.translate` helper shape, throw-before-return, use-before-declaration of `InvalidLocationError` already present at `common_fields.ts:254`), and the new constant's import/export was re-read after editing.
