## Summary

A synthetics monitor may now target at most 100 locations. The check lives in a single choke point — `getMonitorLocations` in `server/synthetics_service/project_monitor/normalizers/common_fields.ts` — which computes the final resolved, deduplicated (public + private) location set for every monitor create/update write. When the unique set exceeds 100, it throws `InvalidLocationError` with the message "A monitor cannot use more than 100 locations, but {N} locations were specified.", which each write route already maps to a clear validation error.

**Files touched (2):**
- `x-pack/solutions/observability/plugins/synthetics/common/constants/monitor_defaults.ts` — added `[expr]` (alongside `ALLOWED_SCHEDULES_IN_MINUTES`, the file that owns validation-limit constants).
- `x-pack/solutions/observability/plugins/synthetics/server/synthetics_service/project_monitor/normalizers/common_fields.ts` — count check after `uniqBy` in `getMonitorLocations`, reusing the module's existing `InvalidLocationError` and i18n pattern.

## Code paths changed (all create/update writes, via the one check)

`getMonitorLocations` has exactly two callers repo-wide (verified by grep; the uptime plugin's same-named function at `uptime/server/legacy_uptime/lib/requests/get_monitor_locations.ts:28` is an unrelated ES query):

1. **Create** — `POST /api/synthetics/monitors` → `AddEditMonitorAPI.normalizeMonitor` (`add_monitor_api.ts:230`) → route catch `error instanceof InvalidLocationError` → HTTP 400 (`add_monitor.ts:180`).
2. **Update** — `[expr]` → same `normalizeMonitor` (`edit_monitor.ts:126`) → same catch → HTTP 400 (`[expr]`). Updates that omit locations carry the previous location IDs through `parseMonitorLocations` (`add_monitor/utils.ts:44-75`) into the same check, so any update write is validated against the effective target set.
3. **Project push** — `[expr]` → type normalizers → `getNormalizeCommonFields` (`common_fields.ts:74`) → caught in `ProjectMonitorFormatter.validateProjectMonitor` (`project_monitor_formatter.ts:234-243`), reported as a per-monitor `failedMonitors` entry with the message in `details`; the monitor is not created/updated — identical shape to existing invalid-location failures on that route.

Duplicates don't inflate the count (check runs after `uniqBy`), and public + private locations count toward the limit together.
