## Residual risk

- **Editing an existing >100-location monitor is blocked** until its locations are trimmed — including edits that only change the name or the enabled flag, because `edit_monitor.ts:107` merges via `mergeSourceMonitor(…)` and validates the merged result. This follows the literal requirement ("updating a monitor with more than 100 locations must be rejected"). Reads, runs, service sync, maintenance-window updates, and deletion are unaffected.
- **`elastic-synthetics push`** of such a monitor now lands in `failedMonitors` with the new message rather than updating.
- **Counting differs slightly by path.** The API path dedups first — `parseMonitorLocations` returns `Array.from(…)` — while the project path's `getMonitorLocations` is a plain `.map` with no dedup, so a project config repeating the same location counts it twice.
- **Unverified build.** No type check, lint, or test run was possible here. The riskiest spots if something is off would be the new third parameter (all other call sites are two-arg and unaffected) and the two new i18n ids, which I confirmed by grep are unique and under the registered `xpack.synthetics` namespace.
