## Summary

Added a max-100-locations rule to synthetics monitor create/update writes.

**Changed behavior:** a create or update whose resolved location list (public + private, merged) exceeds 100 is rejected with `400` and the message *"A monitor cannot run in more than 100 locations. This monitor is configured with N locations…"*. The check runs **after** every existing validator, so it only fires on payloads that previously passed — no existing rule's outcome or message changes.

| `monitor_cruds/monitor_locations_utils.ts` | New `[expr]` and `validateMaxMonitorLocations(…)` returning `[expr]` — the `[expr]` idiom already used by `validatePermissions` / `validateUniqueMonitorName` |
| `monitor_cruds/add_monitor.ts:119` | POST create route → `response.badRequest` |
| `monitor_cruds/edit_monitor.ts:140` | PUT update route → `response.badRequest` |
| `project_monitor/project_monitor_formatter.ts:231` | Project push (create + update) → `failedMonitors.push`, per that file's error idiom |

### The key design constraint

The obvious home, `validateMonitor`, is **deliberately untouched**. `migrations/monitors/8.8.0.ts:119-131` calls it and `[expr]` when invalid — a rule added there would make an already-persisted browser monitor with >100 locations fail to migrate. repovine flags this module as a frozen boundary contract, and the code confirms it. So the rule lives on the write paths instead.
