## What changed

A monitor may now target at most **100** locations. The rule is a new, opt-in check inside the shared server validator, enabled only on the paths that persist a monitor.

| File | Change |
|---|---|
| `common/constants/monitor_defaults.ts:302` | `[expr]`, next to the other write-rule constants (`ALLOWED_SCHEDULES_IN_MINUTES`, `HEARTBEAT_BROWSER_MONITOR_TIMEOUT_OVERHEAD_SECONDS`) |
| `server/routes/monitor_cruds/monitor_validation.ts` | `[expr]` third param on `validateMonitor` (defaults `false`); the check at `:216`; `TOO_MANY_LOCATIONS_ERROR` / `TOO_MANY_LOCATIONS_DETAILS(…)` i18n messages |
| `server/routes/monitor_cruds/add_monitor.ts:107` | create — opts in |
| `server/routes/monitor_cruds/edit_monitor.ts:132` | update — opts in |
| `server/synthetics_service/project_monitor/project_monitor_formatter.ts:222` | project push create/update — opts in |

Two design points:

- **The check runs last**, after every pre-existing rule returns. Any payload an existing rule rejected still gets that rule's exact `reason`/`details`; only previously-valid payloads can newly fail. That's why the constraint "do not change existing rule behavior" holds even for inputs that violate several rules at once.
- **Opt-in, not opt-out.** The default `false` is what keeps the rule off the migration path (below). All three call sites return the `ValidationResult` through plumbing that already exists — `response.badRequest` in the two routes, `failedMonitors.push` in the project formatter — so no error handling was added.

## Residual risk

1. **Editing an existing over-limit monitor is now blocked entirely.** A persisted 150-location monitor can't take *any* `PUT` — even `enabled: false` — until locations are trimmed, because `normalizeMonitor` carries `prevLocations` forward (`add_monitor_api.ts:196-197`) and the result still exceeds the cap. This follows the literal requirement ("updating a monitor with more than 100 locations must be rejected"), but if you meant to grandfather such monitors, the fix is to compare against the previous count in `edit_monitor.ts` rather than the absolute cap. Worth a decision.
2. **Fail-open for future write paths.** Opt-in means a new persistence path added later skips the rule unless its author passes the flag. The alternative — opt-out — would have pulled `inspect` and `run_once` in, degrading existing over-limit monitors. The JSDoc on `ValidateMonitorOptions` states the intent for whoever adds the next path.
3. **No backfill.** Monitors already over the limit keep running and syncing; nothing reports them. If you want visibility, a warning in `monitor_warnings.ts` (which already surfaces `warnings` from both routes) is the natural place.
4. **Unverified by tooling.** No typecheck/lint/test run was possible here. The change is small and mechanical, but the added third parameter and the two new i18n ids are exactly the kind of thing `type_check` and `i18n_check` would confirm.
