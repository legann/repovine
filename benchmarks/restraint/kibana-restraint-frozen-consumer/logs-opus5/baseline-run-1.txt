## Changed behavior

A monitor may target at most 100 locations (elastic-managed + private, after dedup by id). Create and update writes that exceed it are rejected with reason `Monitor has too many locations` and details naming the limit and the supplied count. The check runs on the normalized `locations` array, so `locations` and `private_locations` count together.

## Residual risk

- A monitor persisted before this change with more than 100 locations now fails **any** subsequent update, including unrelated edits such as the enable/disable toggle (`edit_monitor.ts:126-132` merges `previousMonitor.attributes.locations` when the payload omits locations). This follows from the stated rule that updates above the limit are rejected; such monitors must shed locations to be editable. Elastic-managed locations number well under 100, so this only affects deployments with very large private-location fleets.
- Enforcement is opt-in per call site, so a future write path that calls `validateMonitor` with two arguments would silently skip the limit. The `ValidateMonitorOptions` doc comment states the contract.
- Existing tests call `validateMonitor(…)` (`monitor_validation.test.ts:209` and following) and there is no mock of the module anywhere, so the default-off third parameter leaves them on their current code path — asserted by reading, not by a test run.
