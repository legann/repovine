## The key constraint

repovine flagged `monitor_validation.ts` as a **boundary** surface, and reading the code confirmed why: the released 8.8.0 saved-object migration reuses the runtime validator and **throws** on rejection.

## Residual risk

- **Server-only enforcement.** A user assembling >100 locations in the UI sees the error on submit, not while selecting. Adding a client-side rule is a separate UX change; `MAX_MONITOR_LOCATIONS` is in `common/` so the UI can import it.
- **Pre-existing over-limit monitors stay editable only if the edit reduces the count.** An update that resubmits an already-persisted >100-location monitor unchanged is now rejected. That follows from "the rule governs new create/update writes" — reads, loads, migrations, and resets are untouched — but it is the one place a legacy monitor meets the new rule.
