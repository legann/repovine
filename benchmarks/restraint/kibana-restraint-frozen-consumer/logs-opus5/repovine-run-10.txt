## Summary

A monitor may now target at most **100 locations** (elastic-managed + private, counted after de-duplication). Create/update writes over the limit are rejected with a 400 and a message naming the limit, the configured count, and how many to remove.

### Files touched

| File | Change |
|---|---|
| `common/constants/monitor_defaults.ts` | New `[expr]` |
| `server/routes/monitor_cruds/monitor_locations_utils.ts` | New `validateMonitorMaxLocations()` + two i18n strings |
| `server/routes/monitor_cruds/add_monitor.ts` | Rule wired into POST create |
| `server/routes/monitor_cruds/edit_monitor.ts` | Rule wired into PUT update |
| `server/synthetics_service/project_monitor/project_monitor_formatter.ts` | Rule wired into project (push) create/update |

**A design note worth flagging:** my first attempt put the rule inside `validateMonitor` behind an opt-in flag. A repovine boundary annotation on `monitor_validation.ts` rejected that — `validateMonitor` is run unchanged by the released 8.8.0 saved-object migration (`saved_objects/migrations/monitors/8.8.0.ts:119`, which throws at line 128 on any invalid result), so *any* edit there couples the new rule to a frozen consumer. I reverted it; `git diff` on `monitor_validation.ts` is empty. The rule lives in `monitor_locations_utils.ts` instead, which already owns write-path location validation and which `monitor_validation.ts` imports from (so it can't import back — no cycle).

In all three sites the check runs **after every pre-existing validation** and immediately before the persist call. That's deliberate: any input an existing rule would reject still gets rejected with the identical reason and details. Only inputs that previously passed everything change outcome.

### Residual risk

1. **Grandfathered monitors become read-only past 100 locations.** Editing a pre-existing 150-location monitor — even a name-only PUT — is now rejected, because `normalizeMonitor` carries prior locations forward when the request omits them (`add_monitor_api.ts:196-199`). This follows from "updating a monitor with more than 100 locations must be rejected"; the persisted record still loads, migrates, runs, and can be deleted. If the intent was that grandfathered monitors stay editable, the fix is to skip the check in `edit_monitor.ts` when the previous monitor was already over the limit — say the word and I'll add it.
2. **No UI-side guard.** The form has no locations rule, so an over-limit selection fails only on save, at the server.
3. **Unverified by tooling.** This worktree has no `node_modules`, so `type_check`, `eslint`, `i18n_check`, and Jest could not run. I verified statically: every `as MonitorFields` cast I added duplicates one already present on the same variable in the same file (`add_monitor.ts:148`, `edit_monitor.ts:133`, `project_monitor_formatter.ts:167`); both i18n IDs are unique repo-wide and use the file's existing `[expr]` namespace; and no import cycle is introduced. Per the constraint, no tests were added or modified — all 21 existing `validateMonitor(…)` call sites in `monitor_validation.test.ts` are unaffected since that file is byte-identical.
