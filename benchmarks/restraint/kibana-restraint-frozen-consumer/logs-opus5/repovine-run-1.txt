## Changed behavior

A monitor may now target at most **100 locations**. Create and update writes that exceed it are rejected with `[expr]` The count is taken from the *normalized* `locations` array (public + private combined), which is what actually gets persisted.

## Files touched

| File | Change |
|---|---|
| `monitor_cruds/monitor_locations_utils.ts` | New `MAX_MONITOR_LOCATIONS`, `MAX_LOCATIONS_EXCEEDED_ERROR`, `validateMaxMonitorLocations` |
| `monitor_cruds/add_monitor.ts` | Rejects create with 400 |
| `monitor_cruds/edit_monitor.ts` | Rejects update with 400 |
| `project_monitor/project_monitor_formatter.ts` | Pushes to `failedMonitors`, monitor skipped |

**Key placement decision:** the rule is *not* in `validateMonitor`. `8.8.0.ts:119-131` calls `validateMonitor` inside a released saved-object migration and `throw`s when it returns invalid — a persisted browser monitor with >100 locations would fail to load. The graph flagged this module as a boundary surface for exactly this reason. In all three write paths the check runs *after* the existing `validateMonitor` block, so no existing rule's error can be preempted.

## Residual risk

- **Grandfathered monitors become harder to edit.** In `add_monitor_api.ts:196-197`, an update that omits `locations` inherits `prevLocations`. A monitor already stored with 150 locations will now fail a name-only PUT until the caller also sends a ≤100 location list. This follows directly from "updating a monitor with more than 100 locations must be rejected"; if grandfathering edits is wanted instead, the fix is to skip the check when the location count did not increase.
- **No client-side guard.** The UI surfaces the server's 400; a user can build a >100 location selection before learning it's rejected.
