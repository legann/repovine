## What changed

A monitor with more than 100 locations is now rejected at validation time with reason `Monitor has too many locations` and details naming the actual count and the limit. The check sits in `validateMonitor` immediately after the existing "at least one location" check, so it participates in every create/update flow that already used that validator.

## Residual risk

- The `skipWriteOnlyRules` opt-out is honored only where explicitly passed. Any future caller that re-validates persisted monitors gets the rule by default — that default is intentional (new write paths are covered automatically), but it makes the migration-style exception something a reviewer has to notice.
- Ordering: a payload that violates both this rule and a later one (invalid type, bad schedule, schema) now reports the location count first. Every such payload was already rejected; only the reported reason changes.
- Editing a pre-existing monitor over the limit is now blocked until locations are trimmed — including its "Run test" and "Inspect" buttons, which validate the same form payload. That follows from the rule governing updates; reads, listing, and reset of such monitors are unaffected.
