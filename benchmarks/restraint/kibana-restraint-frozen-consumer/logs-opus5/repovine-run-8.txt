## What changed

A monitor may now target at most **100** locations (public + private combined). Exceeding it returns `400` on create/update; project pushes report the monitor as failed and skip it.

| File | Change |
|---|---|
| `common/constants/monitor_defaults.ts` | New `[expr]`, beside the other validation limits |
| `server/routes/monitor_cruds/monitor_locations_utils.ts` | New `validateMonitorLocationsCount(…)` → error message or `undefined`, plus its i18n string `xpack.synthetics.validation.maxLocationsExceeded` |
| `server/routes/monitor_cruds/add_monitor.ts` | `POST /monitors` — checks the resolved `normalizedMonitor.locations` |
| `server/routes/monitor_cruds/edit_monitor.ts` | `[expr]` — checks the merged `editedMonitor.locations` |
| `server/synthetics_service/project_monitor/project_monitor_formatter.ts` | Project push — checks `[expr]`; failures land in `failedMonitors` |

The count is taken after location normalization, so it measures what would actually be persisted.

## Paths intentionally left unchanged

**`monitor_validation.ts` / `validateMonitor` — the obvious home, deliberately avoided.** `8.8.0.ts:119-131` (`omitZipUrlFields`) calls `validateMonitor(…)` and does `[expr]`, with `isMigrationNeededPredicate: return true`. A location-count rule there would make an already-persisted browser monitor with >100 locations throw during migration — exactly the retroactive rejection the constraints forbid. That is also why the constant lives in `monitor_defaults.ts` rather than the validator module.

**`inspect_monitor.ts`** — `syntheticsMonitorClient.inspectMonitor(…)` then `response.ok(…)`; no `monitorConfigRepository` write.

**`run_once_monitor.ts`** — `syntheticsMonitorClient.testNowConfigs(…)` then `[expr]`; no write.

**`test_now_monitor.ts:51`** — `monitorConfigRepository.getDecrypted(…)` feeding `testNowConfigs`; read-and-run on an existing monitor.

**`reset_monitor_api.ts:163-165`** — `[expr]`. A filter can only shrink the set, and it acts on persisted monitors.

**`private_locations/helpers.ts:92-94`** — `m.attributes.locations.map(…)`. A 1:1 `map`, so the count is preserved; gating a label rename would retroactively reject grandfathered monitors.

**`bulk_cruds/add_monitor_bulk.ts`, `bulk_cruds/edit_monitor_bulk.ts`** — sync helpers, not gates. `project_monitor_formatter.ts:139-171` only pushes into `normalizedNewMonitors` / `normalizedUpdateMonitors` when `this.validateProjectMonitor(…)` returns a monitor, and `add_monitor_api.ts:91` (`monitorConfigRepository.create`) is reached only from the `add_monitor.ts` route after its gate.

**`[expr]`** — grepping `locations` in that file returns nothing; the form has no location rule today, so location validation stays server-side as it already was.

## Residual risk

- **Grandfathered monitors on edit.** An existing monitor with >100 locations that is edited without touching locations inherits `prevLocations` (`add_monitor_api.ts:196-197`, `[expr]`) and will now be rejected. I read "already persisted must not be retroactively rejected" as covering read/migrate paths, and "updating … must be rejected" as governing writes — but this is the one interpretive call in the patch. Reverse it by comparing against the previous location count and only enforcing when the count increases.
- **Error precedence.** In `add_monitor.ts` the new check runs before `validateUniqueMonitorName` and `validatePermissions`, so a request that violates both now reports the location error. Every such request was already a 400; no existing rule's accept/reject set changed.
- **Unverified build.** This worktree has no `node_modules`, so `type_check`, `eslint`, and `i18n_check` could not run. Verification was static: `.locations` access is proven by the adjacent pre-existing `validatePermissions(…)` calls in both routes, `[expr]` in `monitor_types.ts:72` backs the project-path indexing, the i18n key is unique repo-wide, and `x-pack/.i18nrc.json:155` maps `xpack.synthetics` to this directory.
