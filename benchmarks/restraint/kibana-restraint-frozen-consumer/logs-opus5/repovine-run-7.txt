## Residual risk

- **Unverified by execution.** This worktree has no `node_modules`, so `type_check`, `eslint`, `jest`, and `i18n_check` could not run; correctness is from static reading. The three `as MonitorFields` casts each duplicate an assertion the same file already makes on the same value (`add_monitor.ts:156`, `edit_monitor.ts:169`, `project_monitor_formatter.ts:168`), and `[expr]` mirrors line 69 of the file it was added to. The two new i18n ids are unique repo-wide.
- **Existing over-limit monitors are frozen on edit.** A monitor persisted with 150 locations loads, runs and syncs, but any update — including an unrelated name change through the UI, or an unchanged project re-push — is now rejected until locations are trimmed. That follows from "the rule governs update writes"; there is no grandfathering that compares against the previous location count.
- **Ordering.** On a payload violating both, the limit error now surfaces where a permission (`add_monitor.ts`) or private-location-space error would have surfaced before. No existing rule's accept/reject set changes.
- **The rule lives on the write paths, not in the shared validator.** A future create/update path that skips `monitor_locations_utils` would not inherit it. The alternative — centralizing in `validateMonitor` — is what the frozen migration forecloses.
