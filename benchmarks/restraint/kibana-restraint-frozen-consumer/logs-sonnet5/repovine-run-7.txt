## Summary

Implemented a new validation rule: a monitor create/update write is rejected if the final `locations` array (public + private combined) exceeds 100 entries.

**Design decision:** `validateMonitor()` in `monitor_validation.ts` is annotated as a frozen contract — it's reused unchanged inside `saved_objects/migrations/monitors/8.8.0.ts`, which replays it against already-persisted documents during a Kibana upgrade and `throw`s on invalid. Editing that function (even behind a flag) would make the migration retroactively reject pre-existing monitors with >100 locations. So the new rule is a **separate function**, `validateMonitorLocationsCount()`, called explicitly only from the three actual persistence call sites, positioned as the last gate before each one's write call (after every pre-existing check), so no existing rule's outcome or error-message precedence changes.

- **`server/routes/synthetics_service/run_once_monitor.ts`** — calls `validateMonitor` then `syntheticsMonitorClient.testNowConfigs(…)` ("Test now"); no saved-object write.
- **`server/routes/monitor_cruds/bulk_cruds/add_monitor_bulk.ts` / `edit_monitor_bulk.ts`** — `syncNewMonitorBulk`/`syncEditedMonitorBulk` persist monitors, but only the arrays `configureAllProjectMonitors()` builds exclusively from `this.validateProjectMonitor(…)`'s return value — i.e., they only ever receive monitors that already passed the new check.
- **`server/routes/monitor_cruds/reset_monitor.ts`** — request body is `[expr]` only; delegates to `ResetMonitorAPI.execute` to re-provision Fleet resources for the monitor's existing locations, never sets/replaces `locations`.
- **`get_monitor.ts`, `get_monitors_list.ts`, `get_monitor_summary_stats.ts`, `delete_monitor.ts`, `delete_integration.ts`** — read/delete routes, don't call `validateMonitor` or `validateMonitorLocationsCount` at all.
