## Implementation

## Why not inside `validateMonitor` itself

`monitor_validation.ts`'s `validateMonitor` is annotated as a frozen contract: it's reused unchanged inside the versioned saved-object migration `saved_objects/migrations/monitors/8.8.0.ts`, which **throws** when validation fails (`[expr]`). Editing `validateMonitor`'s behavior would make that migration reject already-persisted monitors that happen to have >100 locations — directly violating "monitors already persisted must not be retroactively rejected." So the new rule lives outside that function and is invoked only from the write routes.

## Residual risk

- No client-side (UI form) mirror of this limit was added — the rule is enforced at the API/write boundary only, consistent with how other cross-cutting checks in these same files (name uniqueness, space permissions) already surface errors on submit rather than client-side.
- Could not run `type_check`/`eslint`/jest: this worktree is intentionally non-bootstrapped for this task (`yarn kbn bootstrap` is blocked with an explicit message to finalize from static reading). I verified correctness by matching each new call's casts (`as MonitorFields`) and destructuring shapes exactly against pre-existing, already-compiling calls in the same files, and manually checked all changed lines against the repo's 100-column line-length convention.
