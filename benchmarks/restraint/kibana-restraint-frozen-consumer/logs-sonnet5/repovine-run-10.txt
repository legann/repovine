## Summary

I added a 100-location cap enforced on monitor create/update, without touching the shared `validateMonitor` function that a frozen saved-object migration also calls.

### Changed code paths

| File | Change |
|---|---|
| `server/routes/monitor_cruds/monitor_validation.ts` | Added `[expr]`, `TOO_MANY_LOCATIONS_ERROR(…)`, and a new standalone `validateMaxMonitorLocations(…)` — added *after* `validateMonitor`'s closing brace, not inside it. Also added an unconditional count check (public `locations` + `privateLocations`) at the top of `validateLocation`. |
| `server/routes/monitor_cruds/add_monitor.ts` | POST create route: after existing `validateMonitor` check succeeds, calls `validateMaxMonitorLocations(…)` and returns `badRequest` if it fails. |
| `server/routes/monitor_cruds/edit_monitor.ts` | PUT update route: same pattern, checked against `validationResult.decodedMonitor.locations.length`. |

This covers both monitor shapes: single monitors (UI/API, unified `locations` array covering public+private) via the two route files, and project/CLI-push monitors (separate `locations`+`privateLocations` string-id arrays) via `validateLocation`, which `validateProjectMonitor` already calls before any bulk create/update persists.

### Why `validateMonitor` itself was left untouched

I initially added the check as an opt-in flag inside `validateMonitor`, but a repovine boundary annotation on that function stopped me: it's called by the released `8.8.0` saved-object migration (`omitZipUrlFields` in `saved_objects/migrations/monitors/8.8.0.ts`) to revalidate **already-persisted** monitors during upgrade, and the annotation explicitly records this as frozen — "an un-migrated monitor... must migrate the same way it always did." Even a default-off flag would have coupled a future change to that consumer. I reverted and moved the check entirely to the callers instead, verified via `git diff` that `validateMonitor`'s body (lines 78–207) is byte-identical to HEAD.

### Paths verified as out of scope, with citation

- **`saved_objects/migrations/monitors/8.8.0.ts`** — calls `validateMonitor` only, never the new `validateMaxMonitorLocations`; unaffected by design (the reason above).
- **`inspect_monitor.ts`** (`inspectSyntheticsMonitorRoute`) — calls `validateMonitor` but its handler never calls `monitorConfigRepository.create`/`.update` or `savedObjectsClient.create`/`.update`; it only calls `syntheticsMonitorClient.inspectMonitor(…)`, a preview/dry-run. No persistence, so not a create/update write.
- **`run_once_monitor.ts`** (`runOnceSyntheticsMonitorRoute`) — calls `validateMonitor` but only invokes `syntheticsMonitorClient.testNowConfigs(…)`; no saved-object write call anywhere in the handler.
- **`services/reset_monitor_api.ts`** — mutates a persisted monitor's `locations` only via `[expr]` — a filter can only shrink the array, never grow it past a prior valid count, so it cannot introduce a new violation.
- **`bulk_cruds/add_monitor_bulk.ts` / `bulk_cruds/edit_monitor_bulk.ts`** — pure persistence helpers with no independent location validation; both are called from `project_monitor_formatter.ts` only after `validateProjectMonitor` (→ `validateLocation`) already passed, so the new check upstream already gates them.
- **`project_monitor_formatter.ts`'s second `validateMonitor` call** (line ~221, re-validating the normalized monitor) — unreachable when locations are invalid, since the first check (`validateProjectMonitor` → `validateLocation`, line ~204) already returns early via `this.failedMonitors.push` before this second call executes.

I verified types by reading the actual codec definitions (`[expr]` is a required, non-optional array field; `ProjectMonitor.locations`/`.privateLocations` are `[expr]`) and manually checked `sort-imports` ordering and Prettier line-length against existing file conventions. Recommend running `node scripts/type_check --project x-pack/solutions/observability/plugins/synthetics/tsconfig.json`, `node scripts/eslint --fix`, and `node scripts/i18n_check --fix` once dependencies are available.
