## Summary

**Implementation**: added a `[expr]` check to the single validation function all monitor writes funnel through, `validateMonitor()` in `x-pack/solutions/observability/plugins/synthetics/server/routes/monitor_cruds/monitor_validation.ts`. It slots in right after the existing empty-locations check and returns the same `[expr]` shape as every other rule in that function, so it surfaces through the existing route error handling as an HTTP 400 with a clear message, exactly like the current "at least one location is required" error.

Because this function is also invoked by the `8.8.0` saved-object migration to re-validate **already-persisted** legacy monitors, the check is gated behind a new optional parameter (`enforceLocationsLimit`, default `true`) rather than being unconditional. The migration call site explicitly passes `[expr]`, so old monitors that predate this rule can never fail migration because of it.

### Code paths changed

| File | Change |
|---|---|
| `server/routes/monitor_cruds/monitor_validation.ts` | Added `MAX_MONITOR_LOCATIONS`, the `enforceLocationsLimit` option, the count check, and `TOO_MANY_LOCATIONS_ERROR`/`TOO_MANY_LOCATIONS_DETAILS` i18n messages |
| `server/saved_objects/migrations/monitors/8.8.0.ts` | Passes `[expr]` at its `validateMonitor` call so migration of historical data is unaffected |

Since `validateMonitor()` is the single gate every write path decodes through, this automatically covers all callers that pass no third argument (default `true`): `add_monitor.ts:107` (create), `edit_monitor.ts:132` (update), `inspect_monitor.ts:52` (dry-run/preview), `run_once_monitor.ts:39` (test-now from the add/edit draft form), and `project_monitor_formatter.ts:222` (CLI/project-monitor push, applied to the already-merged public+private `locations` array). No call site other than the migration needed edits.
