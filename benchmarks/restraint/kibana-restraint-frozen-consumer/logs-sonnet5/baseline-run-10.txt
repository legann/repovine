## Summary

**Implemented:** a new `[expr]` cap enforced by a new `validateMonitorLocationsCount()` function in `monitor_validation.ts`, called explicitly from the three places that actually create/update a monitor's persisted config.

### Code paths changed

| File | Change |
|---|---|
| `server/routes/monitor_cruds/monitor_validation.ts` | New exported `validateMonitorLocationsCount(…)` + `MAXIMUM_MONITOR_LOCATIONS` constant + two i18n error strings. Returns the same `ValidationResult` shape as `validateMonitor`. `validateMonitor` itself is untouched — the new function is a sibling, not an addition to its body. |
| `server/routes/monitor_cruds/add_monitor.ts` | POST create route: calls the new check right after `validateMonitor` succeeds, before permission/name checks. Rejects with `response.badRequest`. |
| `server/routes/monitor_cruds/edit_monitor.ts` | PUT update route: same insertion point, on the post-merge `decodedMonitor` (final location list after merging with the previous monitor). |
| `server/synthetics_service/project_monitor/project_monitor_formatter.ts` | CLI push create/update path (`ProjectMonitorFormatter.validateProjectMonitor`): calls the check via the existing `this.validateMonitor(…)` helper, so failures surface in `failedMonitors` exactly like other push validation errors. |

All three call sites check the location count on the **final, normalized** `locations` array (public + private combined), matching how `getMonitorLocations`/`mergeSourceMonitor` already produce a unified list before persisting.

### Paths left unchanged (with proof)

- **`saved_objects/migrations/monitors/8.8.0.ts`** — calls `validateMonitor` on legacy persisted docs during Kibana upgrade and `throw`s on invalid (`monitor_validation.ts`-adjacent code: `[expr]` in `omitZipUrlFields`, `8.8.0.ts:127-131`). Since `validateMonitor` itself was not modified, this migration path is untouched — a pre-existing monitor with >100 locations will still migrate successfully. This was the deciding constraint against putting the check inside `validateMonitor`.
- **`run_once_monitor.ts` / `inspect_monitor.ts`** — both call `validateMonitor` but never persist anything and are only ever invoked with an in-editor draft, never a saved monitor: `RunTestButton` reads `getValues()` from `useFormContext()` (`public/.../monitor_add_edit/form/run_test_btn.tsx:29-43`), and the inspect portal passes `format(…)` (`public/.../monitor_add_edit/steps/index.tsx`), both only reachable from the Add/Edit form routes. Left unchanged since `validateMonitor` wasn't touched; out of scope regardless since neither creates nor updates a monitor.
- **`test_now_monitor.ts`** ("Run test manually" on an already-saved monitor) — fetches the persisted monitor via `monitorConfigRepository.getDecrypted(…)` and never calls `validateMonitor` at all (`triggerTestNow`, `test_now_monitor.ts:51-67`). No code path through my change touches it.
- **`reset_monitor.ts` / `bulk_cruds/reset_monitor_bulk.ts`** — `ResetMonitorAPI` only reads `attrs.locations`/`monitor.locations` for permission checks and Fleet policy sync (`[expr]`); it never calls `validateMonitor` or writes a new `locations` array, so there is no location-count write vector here.
- **`bulk_cruds/add_monitor_bulk.ts` / `edit_monitor_bulk.ts`** — grepped for `validateMonitor`/`validateLocation`: no matches. They only sync already-validated monitors produced by `ProjectMonitorFormatter`, which is patched.
- **`MonitorLocationsCodec`/`LocationsCodec`** (io-ts, `common/runtime_types`) — deliberately left alone rather than adding a max-length refinement there, since that codec is reused for decode/encode on read paths too; a codec-level change would have non-additive blast radius on existing reads, unlike the imperative check added here.
- All read-only routes (`[expr]`, `get_monitor_project.ts`, health/stats routes) and delete routes — none call `validateMonitor`/`validateMonitorLocationsCount`, confirmed via `routes/index.ts` route inventory.
