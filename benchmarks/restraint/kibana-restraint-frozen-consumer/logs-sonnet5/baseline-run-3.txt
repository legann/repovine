## Implementation

Added a shared, opt-in check in `validateMonitor()` (`monitor_validation.ts`) that rejects a monitor whose resolved `locations` array exceeds 100 entries, and wired it into the three request handlers that actually persist a monitor create/update.

### Changed paths

| File | Change |
|---|---|
| `server/routes/monitor_cruds/monitor_validation.ts` | `validateMonitor()` gets a 3rd optional param `[expr]`. When `true`, and only then, adds: `[expr]`, placed right after the existing empty-locations check, using the same `ValidationResult` shape. Added `[expr]` and an i18n `TOO_MANY_LOCATIONS_ERROR` message, styled like the sibling `LOCATION_REQUIRED_ERROR`. |
| `server/routes/monitor_cruds/add_monitor.ts:107` | `POST /api/synthetics/monitors` (create) now calls `validateMonitor(…)`. |
| `server/routes/monitor_cruds/edit_monitor.ts:132` | `[expr]` (edit) now calls `validateMonitor(…)`. This checks the fully merged/resolved location set (previous + new, deduped) that would actually be persisted. |
| `server/synthetics_service/project_monitor/project_monitor_formatter.ts:222` | Project-monitor bulk push (`[expr]`, used by the `@elastic/synthetics` CLI) now opts in too. Per-monitor: an over-limit monitor is added to `failedMonitors` (the existing partial-failure mechanism), the rest of the batch still succeeds — same as today's handling of any other per-monitor validation error. |

Because the flag defaults to `false`, every pre-existing call passing only 2 arguments is untouched, and any payload with ≤100 locations skips the new branch entirely and follows the exact prior code path.

### Left unchanged, with proof

- **`server/routes/synthetics_service/run_once_monitor.ts:39`** — calls `validateMonitor(…)` (still 2 args). This handler takes `request.body` as an ephemeral "test now" config and passes it to `syntheticsMonitorClient.testNowConfigs(…)`; it contains no `monitorConfigRepository.create/update/bulkUpdate` call anywhere in the file — nothing is persisted, so it isn't a create/update write.
- **`server/routes/monitor_cruds/inspect_monitor.ts:52`** — same signature, unchanged. It builds a preview via `syntheticsMonitorClient.inspectMonitor(…)`; its only saved-objects call is a read (`monitorConfigRepository.get`, line 160, for existing Fleet package-policy reference links). No persistence call exists in the file.
- **`server/saved_objects/migrations/monitors/8.8.0.ts:119`** — same signature, unchanged, and this one had to stay excluded: `isMigrationNeededPredicate` returns `true` unconditionally (line 42-46), so `migration880` reprocesses *every* already-persisted legacy browser-type monitor on upgrade, and `omitZipUrlFields` (line 119-131) `throw`s if `validateMonitor` reports invalid. Gating the new check here would have made the migration itself reject grandfathered monitors with >100 locations — exactly the retroactive rejection the task prohibits.
- **`server/routes/monitor_cruds/bulk_cruds/add_monitor_bulk.ts` / `edit_monitor_bulk.ts`** — verified by direct read: neither file references `validateMonitor` at all. They only persist already-normalized `[expr]` objects that `ProjectMonitorFormatter` validated earlier in the pipeline.
- **`bulk_cruds/reset_monitor_bulk.ts` / `delete_monitor_bulk.ts`** — take `[expr]` only; no `locations` field exists on these payloads.
- **Every other existing check in `validateMonitor`/`validateLocation`/`validateProjectMonitor`/`monitor_locations_utils.ts`** (empty-locations, invalid-location-id, private-location space coverage, schedule/type/timeout checks) — none of their lines were touched; the new branch is a pure addition gated off by default.
- **Location dedup** (`uniqBy` in `common_fields.ts`, `Set`-based dedup in `add_monitor/utils.ts`) — left as-is; the cap counts the same resolved/deduped array the pre-existing empty check already uses, so "100 locations" means 100 distinct resolved locations, consistent with existing semantics.
