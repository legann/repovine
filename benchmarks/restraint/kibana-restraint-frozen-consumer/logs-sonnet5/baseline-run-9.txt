## Implementation complete

**The rule:** a monitor may target at most 100 locations (public + private combined). Enforced at the exact point each write path has already normalized/decoded the monitor's final `locations` array, so the count reflects what would actually be persisted.

### Files changed

| File | Change |
|---|---|
| `common/constants/monitor_defaults.ts` | Added `[expr]`. |
| `server/routes/monitor_cruds/monitor_validation.ts` | Added standalone `validateMonitorLocationsLimit(…)` (returns `null` or a `ValidationResult`), plus `TOO_MANY_LOCATIONS_ERROR`/`TOO_MANY_LOCATIONS_DETAILS` i18n messages, modeled on the existing `LOCATION_REQUIRED_ERROR` pair. |
| `server/routes/monitor_cruds/add_monitor.ts` (create) | Calls the new check right after `validationResult.decodedMonitor` is obtained; returns `response.badRequest` on violation. |

| `server/synthetics_service/project_monitor/project_monitor_formatter.ts` | Calls the check on the normalized `decodedMonitor` inside `validateProjectMonitor()` (the project-monitors/CLI-push bulk create+update path), routing failures through the existing `this.validateMonitor()` → `failedMonitors` mechanism. |

I initially added the check directly inside the shared `validateMonitor()` function (next to the existing empty-locations check), but reverted that: `validateMonitor()` is also called from a saved-object migration and two non-persisting endpoints (below), and one of those **throws** on invalid results. Extracting a standalone function let me wire it into only the three genuine write paths.

### Paths intentionally left unchanged (with citations)

- **`server/saved_objects/migrations/monitors/8.8.0.ts:119-131`** — calls the shared `validateMonitor()` and `throw`s if invalid (`[expr]`). This runs during Kibana upgrades over already-persisted legacy browser monitors. Since the new rule lives only in `validateMonitorLocationsLimit()`, which this file never calls, already-persisted over-limit monitors keep migrating. This is the concrete reason the check isn't inside `validateMonitor()` itself.
- **`server/routes/monitor_cruds/inspect_monitor.ts:52`** — calls `validateMonitor()` but never calls `monitorConfigRepository.create`/`.update`; the only repository access is `.get`, guarded by `[expr]` (lines 160-164). It's a dry-run config preview, not a create/update write, so it's outside "creating or updating."
- **`server/routes/synthetics_service/run_once_monitor.ts:39`** — calls `validateMonitor()` but has no `monitorConfigRepository` usage anywhere in the file; it only triggers `syntheticsMonitorClient.testNowConfigs(…)`, an ad hoc test run. Leaving it unchanged means manually re-running an already-saved, grandfathered over-limit monitor still works.
- **`monitor_validation.ts`'s `validateLocation()`/`validateProjectMonitor()`** (raw project-monitor pre-normalization check, e.g. `[expr]`) — operates on the raw pre-merge `locations`/`privateLocations` string arrays. `ProjectMonitorFormatter.validateProjectMonitor()` calls this first (`project_monitor_formatter.ts:204-212`) and separately calls `validateMonitor()` on the final normalized monitor afterward (`:221-224`) — my new check sits right after that second call, so it measures the true combined count rather than duplicating against incomplete pre-merge data.
- **`server/routes/settings/private_locations/helpers.ts:92-94`** (`updatePrivateLocationMonitors`) — bypasses `validateMonitor()` entirely, calling `syncEditedMonitorBulk()` directly. The only mutation is `m.attributes.locations.map(…)` — a `[expr]`, which is length-preserving by construction. It cascades a private-location rename and can never change a monitor's location count, so it cannot create or resolve a violation.
- **`bulk_cruds/add_monitor_bulk.ts` / `edit_monitor_bulk.ts`** — persist monitors that `ProjectMonitorFormatter.configureAllProjectMonitors()` has already routed through `validateProjectMonitor()` before adding them to `normalizedNewMonitors`/`normalizedUpdateMonitors`; they contain no independent business-rule validation of their own to extend.
- **Client-side location picker (`public/apps/synthetics/...`)** — not touched. The task's "rejected with a clear validation error" describes API-level enforcement; no existing UI-side count limit exists to preserve, and adding one would be a new feature beyond fixing the validation gap.

### Residual risk

Update semantics for monitors already persisted over the new limit: `edit_monitor.ts` builds the edited monitor via `mergeSourceMonitor()` (`formatters/saved_object_to_monitor.ts:86-101`), whose customizer returns `srcValue` for the `locations` key — so a normal UI save (which resends the full `locations` array) fully replaces rather than merges it. If a monitor was saved before this rule with, say, 150 locations, the *next* edit to it — even to an unrelated field — will now be rejected unless locations are trimmed to ≤100 first. This matches the literal requirement ("updating a monitor with more than 100 locations must be rejected") and never affects the monitor at rest (migrations/run-once/inspect are untouched), but it does mean touching any field on a grandfathered monitor now also requires fixing its location count.
