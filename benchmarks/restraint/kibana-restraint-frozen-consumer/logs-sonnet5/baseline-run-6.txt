**Change:** Added a rule that a monitor's combined `locations` array (public + private) may contain at most 100 entries, enforced with a new `TOO_MANY_LOCATIONS_ERROR` validation error.

**Implementation:**
- `common/constants/monitor_defaults.ts` — added `[expr]`, alongside the existing sibling validation constants (`ALLOWED_SCHEDULES_IN_MINUTES`, etc.).
- `server/routes/monitor_cruds/monitor_validation.ts` — `validateMonitor()` gained an opt-in third parameter, `[expr]` (default `false`). When true, it checks `[expr]` immediately after the existing "at least one location" check and returns the new i18n'd error, mirroring that check's shape exactly.
- Three call sites opted in by passing `[expr]`: `add_monitor.ts` (POST create), `edit_monitor.ts` (PUT update), and `project_monitor_formatter.ts` (project-monitor/CLI push create+update). All three already funnel `validationResult.valid`/`reason`/`details` into their existing 400/failed-monitor response plumbing, so no other code in those files needed to change.

**Why opt-in, not a blanket check:** `validateMonitor` is also called from three places that are not "new create/update writes": `inspect_monitor.ts` (preview, no persistence), `run_once_monitor.ts` (test-now, no persistence), and — critically — `saved_objects/migrations/monitors/8.8.0.ts:119`, which calls `validateMonitor` while migrating already-persisted legacy browser monitors and **throws** if the result is invalid (`omitZipUrlFields`, line 127-131). Making the new check unconditional would have risked breaking that migration for any historical document with >100 locations, directly violating "monitors already persisted must not be retroactively rejected." Making it opt-in means those three call sites need zero changes and are provably unaffected — the default parameter value preserves their exact prior behavior.

**Left unchanged, with citation:**
| Path | Citation proving it's out of scope |

| `inspect_monitor.ts:52` | Handler only returns a computed preview (`response.ok(…)`); no `savedObjectsClient`/`monitorConfigRepository` write call in the file. |

| `private_locations/helpers.ts:112` (`updatePrivateLocationMonitors`) | Resyncs monitors on private-location rename via `syncEditedMonitorBulk` directly; never calls `validateMonitor` at all, so it's unaffected regardless of where the check lives. |
| `bulk_cruds/add_monitor_bulk.ts` / `edit_monitor_bulk.ts` | Pure persistence helpers (`monitorConfigRepository.createBulk`/`bulkUpdate`); no validation call — validation happens upstream in `project_monitor_formatter.ts`, which I did change. |
| `server/schemas/common_schemas.ts` `monitorFiltersSchema.locations` | Only imported by `synthetics_stats_overview_embeddable_schema.ts` / `synthetics_monitors_embeddable_schema.ts` — a dashboard-embeddable filter schema, unrelated to monitor persistence. |

**Residual risk:** the OpenAPI doc (`docs/openapi/synthetic_apis.yaml`) still documents `locations` with no `maxItems`; I left it alone since it's documentation, not enforced at runtime, and the task scoped this to implementation. Also, there's no client-side (UI form) pre-check, so a user adding >100 locations in the UI will only find out at save time via the server's 400 — acceptable given the task's scope is the server-side rejection rule, but worth flagging if a smoother UX is later desired.
