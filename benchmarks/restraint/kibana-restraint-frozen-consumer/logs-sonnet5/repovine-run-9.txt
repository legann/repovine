## Implementation complete

**Constant:** `[expr]` in `monitor_locations_utils.ts`, enforced via a new `validateMonitorLocationsCount(…)` helper returning an i18n error message (or `undefined`) when a monitor's final location count exceeds it.

### Why not edit `validateMonitor` directly

`monitor_validation.ts`'s `validateMonitor` looked like the obvious place (it already has the sibling "zero locations" check), but the repovine annotation flagged it as a frozen contract: `saved_objects/migrations/monitors/8.8.0.ts`'s `omitZipUrlFields` calls `validateMonitor(…)` and `throw`s when invalid — and that migration replays over **every already-persisted monitor** on upgrade/restore. Adding the count check there would make old monitors with >100 locations fail to load, directly violating "monitors already persisted must not be retroactively rejected." So the new rule lives in a sibling file (`monitor_locations_utils.ts`, already imported by both write routes) and is called explicitly from the three write paths only.

### Code paths changed

| File | Route/flow | What changed |
|---|---|---|
| `server/routes/monitor_cruds/monitor_locations_utils.ts` | — | Added `MAXIMUM_MONITOR_LOCATIONS` + `validateMonitorLocationsCount` |
| `server/routes/monitor_cruds/add_monitor.ts` | `POST /monitors` (create) | Check added right after `validateMonitor` succeeds → 400 on failure |
| `server/routes/monitor_cruds/edit_monitor.ts` | `[expr]` (update) | Same pattern |
| `server/synthetics_service/project_monitor/project_monitor_formatter.ts` | `ProjectMonitorFormatter.validateProjectMonitor` (CLI push, create+update) | Same check, failure recorded into the existing `failedMonitors` per-item list |

### Paths intentionally left unchanged (with citation)

- **`monitor_validation.ts` (`validateMonitor` body)** — untouched; `migrations/monitors/8.8.0.ts` imports and calls it, throwing on invalid — see above.
- **`inspect_monitor.ts`, `run_once_monitor.ts`** — call `validateMonitor` but never call `monitorConfigRepository.create/update/createBulk/bulkUpdate`; they only preview (`syntheticsMonitorClient.inspectMonitor`) or test-run (`testNowConfigs`) a config. Not a persisted create/update.
- **`reset_monitor.ts` / `services/reset_monitor_api.ts`** — only re-syncs Fleet policies for a monitor's existing locations; no code path adds/removes locations, so count can't change here.
- **`bulk_cruds/add_monitor_bulk.ts` / `bulk_cruds/edit_monitor_bulk.ts`** — grep confirms `[expr]` has exactly one caller (`project_monitor_formatter.ts:274`) and `[expr]` has two (`project_monitor_formatter.ts:400`, `helpers.ts:112`); neither helper calls `validateMonitor`/`validateProjectMonitor` itself (confirmed via dependency-impact query), so gating once upstream in the formatter covers both.
- **`settings/private_locations/helpers.ts` (`updatePrivateLocationMonitors`)** — triggered when a private location is renamed; does `m.attributes.locations.map(…)`, a 1:1 map that never changes array length, then calls `syncEditedMonitorBulk` directly, bypassing all monitor validation exactly as it did before. A legacy monitor with >100 locations keeps working through this path.
- **Rollback helpers** (`rollbackUpdate`, `rollbackCompletely`, `rollbackFailedUpdates`, `rollBackNewMonitorBulk`) — write back the prior persisted attributes verbatim or delete; never introduce a larger location set.
- **UI location picker (`public/apps/synthetics/...`)** — no existing count guard found to mirror (`locations.length` usages there are display-only); adding one would be scope beyond "must be rejected with a clear validation error," which the server enforces.

### Residual risk

`edit_monitor.ts`'s `normalizeMonitor` carries over the **previous** location list unchanged when a PUT body omits `locations`/`private_locations` (`[expr]`). So a legacy monitor already at, say, 150 locations will now have *any* future edit rejected (even one that doesn't touch locations), not just edits that push it over 100. I read "must not be retroactively rejected" as scoped to the automatic migration replay (the one concrete mechanism that touches persisted monitors without user action), not as a guarantee that grandfathered monitors stay freely editable forever — but if you intended the narrower reading, it needs an explicit carve-out in `edit_monitor.ts` to skip the check when the request doesn't touch locations.
