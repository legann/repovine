### Key decision: kept `validateMonitor` itself untouched

repovine's annotation on `monitor_validation.ts` flagged that `validateMonitor` is reused, unchanged, inside a released saved-object migration (`server/saved_objects/migrations/monitors/8.8.0.ts`), which **throws** when validation fails. Adding the location-count rule there would have retroactively rejected already-persisted monitors during migration — exactly what the task prohibits. So the new rule was added at a different layer (route handlers + `validateLocation`, a sibling function not touched by the migration) instead of inside `validateMonitor`.

### Left unchanged, with citations

- **`validateMonitor` (monitor_validation.ts:78-207)** — not modified. It's called from `add_monitor.ts`, `edit_monitor.ts`, `inspect_monitor.ts`, `run_once_monitor.ts`, **and** `saved_objects/migrations/monitors/8.8.0.ts`'s `omitZipUrlFields`, which does `[expr]`. Changing this function would change migration behavior for pre-existing monitors.
- **`inspect_monitor.ts`** — calls `validateMonitor(…)` (line ~63) but never persists; no `syncNewMonitor`/`update` call follows. Since `validateMonitor` itself is untouched, this dry-run/preview endpoint's behavior is unaffected.
- **`run_once_monitor.ts`** — calls `validateMonitor(…)` then only `syntheticsMonitorClient.testNowConfigs(…)`; no saved-object write. Unaffected for the same reason.
- **`bulk_cruds/add_monitor_bulk.ts` (`syncNewMonitorBulk`) and `bulk_cruds/edit_monitor_bulk.ts` (`syncEditedMonitorBulk`)** — their call lists (`monitorConfigRepository.createBulk`/`bulkUpdate`, `syntheticsMonitorClient.addMonitors`, telemetry, rollback helpers) contain no validation calls; they only persist monitors that `ProjectMonitorFormatter.validateProjectMonitor` already validated upstream. The new check is enforced before these run, not duplicated here.
- **`migrations/monitors/8.8.0.ts`** — imports only `validateMonitor` (line 27 of that file: `[expr]`), not `validateLocation`/`validateProjectMonitor`. Since neither touched function is used there, and `validateMonitor`'s body is unchanged, already-persisted monitors with any location count continue to migrate exactly as before.
- **Existing rules in `validateMonitor`, `validateLocation`, and `validateMonitorPrivateLocationSpaces`** — no existing check's logic, order, or return shape was altered; the new checks are additive `if` blocks appended after existing logic, each returning early with its own message.
