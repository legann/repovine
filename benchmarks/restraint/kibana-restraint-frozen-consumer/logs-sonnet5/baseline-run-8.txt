## Why grandfathered monitors aren't retroactively rejected

`AddEditMonitorAPI.normalizeMonitor()` has a carry-forward branch (`add_monitor_api.ts:196-211`): `[expr]`. This branch never calls `getMonitorLocations()`. So a PUT that doesn't touch `locations`/`private_locations` (e.g. toggling `enabled`) on an already-persisted >100-location monitor keeps working unchanged. The cap only fires on the "recompute" branch — i.e., when the write actually supplies new location data. Reads (`get_monitor.ts`, `get_monitors_list.ts`) never call this function at all, and the 8.8.0 saved-object migration calls `validateMonitor()` directly (never `getMonitorLocations()`), so upgrading Kibana with legacy >100-location monitors still succeeds.

## Residual risk

- **Interpretation choice**: the cap gates on whether the write actually recomputes locations (per the existing carry-forward/recompute branch), not on whether the new count is *larger* than the previous persisted count. So an edit that explicitly resubmits `locations`/`private_locations` on a grandfathered >100 monitor is rejected even if the new count is lower than before (e.g. 150 → 120) — only an edit that omits both fields entirely is exempt. If the intended behavior was "only block increases," that needs an extra comparison against `previousMonitor.attributes.locations.length`, which isn't implemented.
- **No dynamic verification**: this worktree has no `node_modules` (bootstrap/type-check/lint/tests are blocked here by design), so this was verified by static reading only, including a manual scan confirming no existing test builds a >100-location monitor. Recommend running `node scripts/type_check --project x-pack/solutions/observability/plugins/synthetics/tsconfig.json` and the plugin's Jest suite in a bootstrapped environment before merging.
- **i18n**: the new key `xpack.synthetics.projectMonitorApi.validation.tooManyLocations` only has an English `defaultMessage`; non-English catalogs aren't touched, consistent with how this codebase back-fills translations.
