The value checked (`[expr]`) is the fully-normalized, deduped set of public+private locations (confirmed via `getMonitorLocations()` in `common_fields.ts:263-268`, which merges and `uniqBy(…)`s both lists) — i.e. exactly the count of distinct locations the monitor targets, not raw/duplicated input.

### Paths left unchanged, with citations

- **`monitor_validation.ts` → `validateMonitor()`** — not touched. It's called directly on already-persisted data by the saved-object migration `server/saved_objects/migrations/monitors/8.8.0.ts:119-131` (`[expr]`, runs on every legacy browser monitor during upgrade). Adding the rule there would retroactively reject old monitors that already exceed 100 locations — the exact failure mode the task prohibits. Putting the check in the route handlers instead keeps this migration provably unaffected.
- **`inspect_monitor.ts:52`** (dry-run "test config") and **`run_once_monitor.ts:39`** ("test now") — both call `validateMonitor()` but neither persists a create/update write (they call `inspectMonitor`/`testNowConfigs`, not a saved-objects write). Since `validateMonitor()` itself is untouched, these are provably unaffected by the same citation as above.
- **Project-monitors push API** (`add_monitor_project.ts`, `project_monitor_formatter.ts:204-228`) — intentionally left uncapped. This is a real create/update path, but I scoped the new rule to match the codebase's own precedent: the closest analogous business rule, `validateMonitorPrivateLocationSpaces`, is wired into exactly `add_monitor.ts:146` and `edit_monitor.ts:161` and nowhere else (confirmed by grep — no references in `project_monitor_formatter.ts`). This is a **residual gap**, not a proven non-issue: a monitor pushed via the project/CLI API can still exceed 100 locations today. Closing it would mean calling `validateMonitorMaxLocations` from `ProjectMonitorFormatter.validateProjectMonitor()` right after its own `validateMonitor(…)` call (`project_monitor_formatter.ts:222`) — flagging for your call rather than silently expanding scope.
- **io-ts codecs** (`MonitorLocationsCodec`, `NonEmptyArray` in `@kbn/securitysolution-io-ts-types`) — untouched; `NonEmptyArray` only enforces `[expr]` and is a shared package well beyond this plugin, so folding a plugin-specific business rule into it would be a much larger blast radius for no benefit.
- **Saved-object type/mappings** (`synthetics_monitor_config.ts`, `monitor_mappings.ts`) — untouched; `[expr]` is empty (no schema validation on read), and reads (`get_monitor.ts`) spread `attributes` directly without decoding, so there's nothing there to change and no read-time risk.
