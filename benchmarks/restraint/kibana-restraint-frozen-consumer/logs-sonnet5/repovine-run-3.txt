## Summary

Implemented the 100-location cap as two small, independent checks placed only at genuine create/update write validators — deliberately **not** inside the shared `validateMonitor()` function, which a released saved-object migration (8.8.0) calls directly and unconditionally on every existing monitor.

### Changed paths

| File | Change |
|---|---|
| `common/constants/monitor_defaults.ts` | Added `[expr]`. |
| `server/routes/monitor_cruds/monitor_locations_utils.ts` | Added `validateMonitorLocationsCount(…)`, returning a structured error when `[expr]`. Mirrors the existing `validateMonitorPrivateLocationSpaces` pattern in the same file. |
| `server/routes/monitor_cruds/add_monitor.ts` | POST `/monitors` (create): calls the new check right after schema validation, before permission/name checks. |

### Paths intentionally left unchanged (with proof)

- **`validateMonitor()` in `monitor_validation.ts:78-207`** — not touched. `server/saved_objects/migrations/monitors/8.8.0.ts:119-131` (`omitZipUrlFields`) calls this function on every legacy browser-type monitor during the upgrade migration and `throw`s on `[expr]`. Adding the cap here would fail the migration for any already-persisted monitor that happens to exceed 100 locations — exactly the "retroactive rejection" the task forbids. repovine's boundary annotation on this module independently flagged the same function as a frozen migration contract.
- **`inspect_monitor.ts:52`** — preview-only; calls `syntheticsMonitorClient.inspectMonitor(…)`, never `monitorConfigRepository.create/update`. No write occurs.
- **`run_once_monitor.ts:39`** and **`test_now_monitor.ts` (`triggerTestNow`)** — trigger an ephemeral test run via `testNowConfigs`, not a saved-object write; `test_now_monitor.ts:51` loads the monitor by id from the repository, i.e. it operates on an already-persisted config, so gating here would block use of a pre-existing over-limit monitor.
- **`bulk_cruds/add_monitor_bulk.ts` / `edit_monitor_bulk.ts`** — internal SO-sync helpers, not validators. Dependency analysis shows `edit_monitor_bulk.ts`'s sync is also reached from `private_locations/add_private_location.ts` and `edit_private_location.ts` when a private location's config changes; those resync monitors' *existing* location lists and never change their count.
- **`reset_monitor.ts` / `reset_monitor_bulk.ts`** — request schema is `[expr]` only; no `locations`/`private_locations` field; only resets Fleet package-policy resources for an existing monitor.
- **`edit_private_location.ts`** — request schema (`EditPrivateLocationSchema`, lines 26-33) is `[expr]`; its only monitor-side effect (`updatePrivateLocationMonitors`) renames a location label inside monitors that already reference it.
- **Client-side form validation** — left unchanged; enforcement is a server concern and the task scoped this to implementation, not new UI.

### Residual risk

- Two call sites implement the same rule (`validateMonitorLocationsCount` for UI/API monitors, an inline check in `validateLocation` for project/push monitors) sharing the `MAX_MONITOR_LOCATIONS` constant but not a single function, since their input shapes differ (`MonitorFields` location objects vs. `ProjectMonitor` string-id arrays). A future change to the rule must be applied in both places.
- The project-monitor check counts raw `locations`/`privateLocations` array lengths from the push payload (consistent with how the rest of `validateLocation` already treats these arrays, e.g. the existing empty-location check), so a payload listing the same location ID twice would count it twice — unlike the UI/API path, which de-dupes via `parseMonitorLocations`'s `Set` before counting. This only makes the project-monitor check slightly more conservative, never less safe.
- Could not run `type_check`/`eslint`/tests — this worktree is intentionally not bootstrapped for this benchmark. I verified types and prettier width manually against existing precedent in the same files (identical casts and i18n patterns already present) and confirmed no line exceeds the repo's 100-char `printWidth`.
