## Implementation summary

**New rule:** `validateMonitorLocationsLimit()` in `monitor_locations_utils.ts` (`[expr]`) checks the monitor's combined public+private `locations` array and returns a `[expr]` error when count > 100, else `null`. Wired into the three places a monitor is actually created or updated:

| File | Route/consumer | Where the check runs |
|---|---|---|
| `monitor_locations_utils.ts` | — | New function + constant (no existing code touched) |
| `add_monitor.ts` | `POST` create route | Right after `validateMonitor` succeeds, before permission/name checks → `response.badRequest` |
| `edit_monitor.ts` | `PUT` update route | Right after `validateMonitor` succeeds, before permission checks → `response.badRequest` |
| `project_monitor_formatter.ts` | Project-monitors "push" API (CLI create/update) | Right after the second `validateMonitor` call succeeds → pushed into `failedMonitors` (matching that file's existing per-monitor bulk-failure convention) |

## Why `validateMonitor` itself was not touched

`monitor_validation.ts`'s `validateMonitor` is annotated as a shared contract also consumed unchanged by saved-object migration `saved_objects/migrations/monitors/8.8.0.ts`, which calls it inside `omitZipUrlFields` and does `[expr]`. `analyze_dependencies` impact analysis confirmed this migration as a real caller. Adding the location-count check inside `validateMonitor` would make that migration throw on any already-persisted monitor that happens to exceed 100 locations — a direct violation of "monitors already persisted must not be retroactively rejected." The new check is therefore a sibling function, called explicitly only from write routes, never from the migration.

## Paths left unchanged, with citations

- **`inspect_monitor.ts`** — calls `validateMonitor` but its handler only calls `syntheticsMonitorClient.inspectMonitor(…)`; no `monitorConfigRepository.create/update` call anywhere in the file. It's a dry-run config inspector, not a persisted write.
- **`run_once_monitor.ts`** — calls `validateMonitor` but its handler only calls `syntheticsMonitorClient.testNowConfigs(…)`; the file has no `monitorConfigRepository` import at all. It triggers a one-off test run, not a persisted write.
- **`bulk_cruds/add_monitor_bulk.ts` / `edit_monitor_bulk.ts`** — pure persistence helpers (`syncNewMonitorBulk`, `syncEditedMonitorBulk`) invoked by `project_monitor_formatter.ts` only *after* `validateProjectMonitor` has already filtered monitors into `normalizedNewMonitors`/`normalizedUpdateMonitors`; neither imports `monitor_validation.ts` or has an independent validation entry point.
- **`add_monitor_project.ts`** (outer PUT route) — only enforces aggregate request-size limits (`[expr]`, `[expr]`) before delegating to `ProjectMonitorFormatter`; the per-monitor location-count gate correctly lives one layer down where individual payloads are validated.
- **`validateLocation`/`validateProjectMonitor`** in `monitor_validation.ts` — only check that named locations exist and private-location space coverage is adequate; no count concept, and no need to touch this file since the new gate runs as an independent, additional step right after its result is consumed.
- **8.8.0 is the only monitor migration** — `analyze_dependencies` on `validateMonitor` showed no other migration module as a caller.
- **Public/UI code** — impact analysis for both `validateMonitor` and the new `validateMonitorLocationsLimit` shows only server-side modules as consumers; no `public/apps/synthetics` code calls either, and the task specifies server-side write rejection, not client UX.

## Residual risk

- **No compiler/lint run**: this worktree has no `node_modules` (intentionally, per an explicit block message from a background bootstrap attempt), so `type_check`/`eslint` couldn't execute. I verified type-correctness statically instead — `MonitorFields` and `SyntheticsMonitor` both derive `[expr]` from the same non-optional `CommonFieldsCodec` field, and every cast I added (`as MonitorFields`) mirrors a cast already present on the same line/file for the sibling `validateMonitorPrivateLocationSpaces` call. This is a substitute for, not equivalent to, a real compile.
- **Interpretation**: "100 locations" is enforced as public+private combined (the same merged array `validateMonitor` already checks for non-emptiness), not as two separate 100-limits. That reading matches the task's literal wording ("target at most 100 locations").
- **Expected edge case**: a pre-existing monitor with >100 locations (if any exist) will pass silently until its next full edit or project-push, at which point that specific write is rejected — this is the intended "governs new writes" behavior, not a gap.
