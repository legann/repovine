## Summary

Added a hard cap of 100 locations per synthetics monitor, enforced only at the three points where a monitor is actually written (created or updated), not in the shared validators that migrations/test-runs/previews also call.

### Changed

| File | Change |
|---|---|
| `common/constants/monitor_defaults.ts` | Added `[expr]` |
| `server/routes/monitor_cruds/monitor_locations_utils.ts` | Added `validateMonitorLocationsCount(…)`, returns an i18n error string if `[expr]`, else `undefined` |
| `server/routes/monitor_cruds/add_monitor.ts` | Calls the check right after `validateMonitor()` succeeds, in the single-monitor `POST` (create) route |
| `server/routes/monitor_cruds/edit_monitor.ts` | Calls the check right after `validateMonitor()` succeeds, in the single-monitor `PUT` (update) route |
| `server/synthetics_service/project_monitor/project_monitor_formatter.ts` | Calls the check on the final decoded monitor, after the second `validateMonitor()` call inside `ProjectMonitorFormatter.validateProjectMonitor` (the project/CLI-push bulk create+update path) |

All three call sites check the location count on the **final, deduplicated, decoded monitor** (the object that is actually about to be persisted), so it counts real target locations, not raw/duplicate request entries.

### Intentionally left unchanged (with proof)

| Path | Why out of scope |
|---|---|
| `monitor_validation.ts`'s `validateMonitor()` itself | Shared by `server/saved_objects/migrations/monitors/8.8.0.ts` (`omitZipUrlFields` calls it and throws on failure). Its repovine annotation states the invariant explicitly: *"A released migration's output and accept/reject behavior are frozen: an un-migrated monitor... must migrate the same way it always did."* Adding the rule here would retroactively reject already-persisted monitors during upgrade — exactly what the task forbids. |
| Same function, `run_once_monitor.ts:38` call | This route only calls `syntheticsMonitorClient.testNowConfigs(…)`; it never calls `monitorConfigRepository.create`/`.update`. It's a test-run, not a create/update write. |
| Same function, `inspect_monitor.ts:57` call | Only calls `syntheticsMonitorClient.inspectMonitor(…)` to preview compiled config; no `monitorConfigRepository` write call anywhere in that file. |
| `validateProjectMonitor()` / `validateLocation()` in `monitor_validation.ts` | Confirmed (via `analyze_dependencies impact`) their only caller is `project_monitor_formatter.ts`, so they are on the write path — but they see the **raw, pre-dedup** `ProjectMonitor.locations`/`privateLocations` string arrays (`monitor_types_project.ts:45-46`), before the `uniqBy(…)` dedup in `normalizers/common_fields.ts:268`. Checking there could over-reject a payload with duplicate entries that resolves to ≤100 unique locations, so the check was placed after normalization instead. |
| `edit_monitor.ts`'s `rollbackUpdate()` (writes via `savedObjectsClient.update` at line 260) | Writes back the pre-edit `decryptedPreviousMonitor.attributes` — already-validated prior state — to undo a failed policy sync. Not a new write of new content. |
| Private-location definition routes (`add_private_location.ts`, etc.) | Those manage the pool of available location *definitions*, not how many a given monitor targets — different resource entirely. |
| Client-side/UI form code | The task requires server-side rejection with a clear error; the UI surfaces whatever the API returns, so no UI change is required for the rule to take effect. |
