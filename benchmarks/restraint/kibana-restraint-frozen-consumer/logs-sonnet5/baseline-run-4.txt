## What changed

The rule lives in one place: `validateMonitor()` in `monitor_validation.ts`, right next to the existing "at least one location" check:

[code excerpt removed — 6 line(s)]

`validateMonitor()` is called from **6 places** in the plugin, and it's called with fully-resolved `locations` (public+private merged), so this one check is sufficient everywhere — but only 2 of the 6 are genuine create/update writes. The new third parameter (`previousLocationsCount`) is what lets the same function serve both without a blanket rule:

| Caller | Nature | What's passed | Effect |
|---|---|---|---|
| `add_monitor.ts` (create) | new write | *(omitted → 0)* | any create >100 locations rejected |
| `edit_monitor.ts` (update) | new write | previously-persisted count | only rejects if the edit **increases** locations past 100 |
| `project_monitor_formatter.ts` (project push, create/update) | new write | previously-persisted count (fetched), or `undefined` for a genuine create | same growth-only rule for pushed monitors |
| `migrations/monitors/8.8.0.ts` | SO migration over old data | the document's own current count | never rejects — new === previous, by construction |
| `run_once_monitor.ts` ("run once") | not a write | the monitor's own current count | never rejects — it's a test-execution, not a save |
| `inspect_monitor.ts` (preview) | not a write | the monitor's own current count | never rejects — preview-only, nothing persisted |

For project monitors, I extended `ExistingMonitor`/`getProjectMonitorsForProject()` to also fetch `ConfigKey.LOCATIONS` (confirmed non-encrypted, plain mapped field) so the previous count is available when comparing.

## Why "increase past previous count," not a blanket >100 check

A blanket check inside `validateMonitor()` would have hit all 6 callers, including the 4 that aren't create/update writes. Concretely, it would have:
- **Broken the 8.8.0 migration** for any legacy monitor that already has >100 locations — that migration runs `validateMonitor()` over already-persisted docs and throws on invalid (`monitor_validation.ts` line ~127 in the migration file), which would corrupt/block upgrades for that data.
- **Permanently blocked all future edits** to a legacy monitor already over 100 locations, since `edit_monitor.ts`'s partial-update flow carries forward the previous `locations` unchanged whenever a request doesn't touch that field (`normalizeMonitor` in `add_monitor_api.ts`, lines 196–211) — any unrelated field edit (toggle enabled, change schedule) would then fail forever.
- **Blocked "run once"/"inspect"** on any already-saved over-limit monitor, since those pass the monitor's existing config straight through without ever persisting.

Comparing against the previous count sidesteps all of this: it's the mechanism that keeps "monitors already persisted must not be retroactively rejected" true, without needing to special-case each read-only caller differently.

## Left unchanged, with citations

- **`validateProjectMonitor()`/`validateLocation()` in `monitor_validation.ts`** — these validate that referenced location IDs exist (`monitor_validation.ts:413-487`), a distinct rule from the count cap; they don't touch `locations.length` limits, and the normalized monitor they help produce still passes through `validateMonitor()` afterward (`project_monitor_formatter.ts:225-232`), where the new cap applies.
- **The `NonEmptyArray` codec / `MonitorLocationsCodec`** (`monitor_types.ts:56-72`, `kbn-securitysolution-io-ts-types/.../non_empty_array/index.ts:13-31`) — untouched; it only enforces non-empty, and schema-level codecs aren't the validation layer this plugin uses for business rules (confirmed: the monitor SO type has `[expr]` with no `schemas`, in `synthetics_monitor_config.ts:13-31` — all validation is in route-handler code, not SO schemas).
- **`add_monitor.ts`** — no edit needed; omitting the third argument correctly defaults to `[expr]`, giving strict enforcement for genuine creates, which is what's wanted.
- **All existing checks inside `validateMonitor()`** (empty-locations, schedule, timeout, schema decode, space membership) — untouched, still run in their original order with unchanged logic.

- The rule is enforced on the fully-normalized/merged location list, so a create or update that supplies locations by a mix of public+private references is capped on the combined total, not each side separately — matches "a monitor may target at most 100 locations" read as a single combined limit.
