## Summary

Added a 100-location cap for synthetics monitors, enforced at both real write paths, without touching the shared low-level validator that a frozen saved-object migration depends on.

**Files changed:**
- `server/routes/monitor_cruds/monitor_validation.ts` — added `[expr]` and `TOO_MANY_LOCATIONS_ERROR`; added a count check inside `validateLocation()` (public + private location count > 100 → reject).
- `server/routes/monitor_cruds/add_monitor.ts` — after the existing `validateMonitor()` success check, reject if `[expr]`.
- `server/routes/monitor_cruds/edit_monitor.ts` — same guard on `validationResult.decodedMonitor.locations.length`.

**Why not inside `validateMonitor()` itself:** that function is annotated as a frozen boundary — `server/saved_objects/migrations/monitors/8.8.0.ts` calls it (`omitZipUrlFields`) to re-validate **already-persisted** monitors during upgrade, and throws if invalid. Adding the cap there would let the migration retroactively reject old documents, violating the constraint directly. So the rule lives in `validateLocation()` (used only by the project-monitor write path) and as an explicit extra check in the two single-monitor route handlers — all real create/update entry points, none of them the migration.

**Code paths changed:**
| Path | Covers |
|---|---|
| `add_monitor.ts` | UI/REST create (`POST .../monitors`) |
| `edit_monitor.ts` | UI/REST update (`[expr]`) |
| `validateLocation()` → `validateProjectMonitor()` | CLI-pushed project monitors, both create and update — `project_monitor_formatter.ts`'s `configureAllProjectMonitors` calls `this.validateProjectMonitor` for every monitor before branching into new vs. update |

**Code paths intentionally left unchanged, with citations:**
- **`validateMonitor()` body** — untouched. Its own repovine annotation: *"validateMonitor is a shared validator a released saved-object migration runs unchanged... A released migration's output and accept/reject behavior are frozen."* Confirmed by reading `migrations/monitors/8.8.0.ts`, which imports and calls it on pre-existing documents and throws on invalid result.
- **`migrations/monitors/8.8.0.ts`** — not modified; it only consumes the (unchanged) `validateMonitor`, so it's unaffected.
- **`inspect_monitor.ts`** — not modified. Its handler calls `validateMonitor` then only `syntheticsMonitorClient.inspectMonitor(…)` (a dry-run config preview); no `monitorConfigRepository`/`savedObjectsClient` create/update call anywhere in the file — it doesn't persist a monitor.
- **`run_once_monitor.ts`** — not modified. Handler calls `validateMonitor` then `syntheticsMonitorClient.testNowConfigs(…)`; likewise no persistence call — it's a one-off test run, not a create/update.
- **`bulk_cruds/add_monitor_bulk.ts` / `edit_monitor_bulk.ts`** — not modified. They only run `monitorConfigRepository.createBulk`/`bulkUpdate` on monitors that `project_monitor_formatter.ts` already pushed into `normalizedNewMonitors`/`normalizedUpdateMonitors`, which only happens after `this.validateProjectMonitor(…)` (the now-updated gate) returned non-null — the new rule is already enforced upstream of these.
